# 人脸库扫描功能设计方案（素材 → 博主/模特 全库匹配）

> 状态：**已实施完成（v2.0）** · 版本 v2.0 · 2025-08
> 需求：对素材库批量扫描人脸，自动为素材关联穿搭博主 / 职业模特；性能高效。
> 流程定调：**AI 扫描匹配仅产出「候选」，人工在扫描页审核确认后，才最终建立人物关联。**
> 实施记录见 §12（含与设计的差异、验证结果、部署注意事项）。

---

## 1. 需求与目标

- 一键扫描全素材库（几万张图片）中的人脸
- AI 自动匹配已注册的穿搭博主（几百~上千）与职业模特（几百），产出**候选结果（含置信度）**
- 人工在扫描页**审核确认**后，才建立「素材 ↔ 人物」关联；未确认/未命中的人脸可手动指派或忽略
- 性能：全库首扫 ≤ 15 分钟（GPU），增量秒级，重匹配任务化后台执行

## 2. 现状盘点（代码事实，方案据此设计）

| 环节 | 现状实现 | 对方案的影响 |
|---|---|---|
| 人脸检测/特征提取 | 独立子服务 `face-service/`（onnxruntime 直载 buffalo_l：RetinaFace det_10g 检测 + ArcFace w600k_r50 提取 512 维），**GPU 优先自动回退 CPU**；`_get_embeddings` 目前逐张推理 | 重活所在；需批量端点榨取 GPU 吞吐 |
| 子服务接口 | `POST /api/face/embed`（单图，无脸 404）、`register`、`match`、`persons` | 批量场景需要新端点 |
| 主后端调用 | `face_client.embed(image_bytes)` 逐图 HTTP（timeout 30s） | 逐图往返是扫描性能瓶颈之一 |
| 博主特征库 | `blogger_face_embeddings`：每博主一条**平均池化** 512 维 float32（2048B BLOB），注册 = 1~5 张正脸平均 | 模特特征库照此对称扩展 |
| 检测结果 | `inspiration_face_detections`：每素材每张人脸一条记录（embedding + bbox + `matched_blogger_id` + confidence），**embedding 已落库** | 关键资产：重匹配复用，不重扫素材 |
| 匹配实现 | `detect_inspiration_faces`：Python 逐条循环点积（人脸 × 全部博主），阈值 `face_match_threshold=0.5` | 需替换为 numpy 矩阵匹配 |
| 任务队列 | `task_queue` 表（type/status/progress/total/done/result/重试/心跳租约）+ 独立 worker 串行执行，`TASK_HANDLERS` 注册 | 扫描/重匹配任务直接复用，新增 `face_scan`、`face_match` 类型 |
| 模特侧 | `models` 表 + `model_photo_sets` + `model_photos`（写真照片组，**不进入素材库**）；无特征表、无人脸能力 | 需新增特征表 + 「从照片组注册」流程 |
| 素材 | `inspirations`（media_type 区分图片/视频；有 thumbnail_path） | **第一版只扫图片**（media_type != video） |
| 人物关联 | `inspiration_bloggers` / `inspiration_models` 关联表（素材详情「关联人物」区块）；`face_detections.matched_*` 为人脸匹配结果（详情「人脸识别」区块）——**两套并存、互不同步** | 审核确认后的「最终添加」以**关联表**为落点 |
| 前端 | 人物管理 `PersonView`（page-header + 博主/模特双 Tab）；路由在 `router/index.ts` 注册；素材详情 `FaceDetectionSection` 仅展示博主匹配 | 入口放 PersonView；扫描页独立路由；详情页适配模特 |

## 3. 架构选型结论（多对多 vs 单对多）

**结论：不做「以人物为中心、每次全库重扫」的单对多；采用「多对多批量检测一次 + 已存 embedding 支撑随时单对多重匹配」。**

数学事实（设素材 M 张、人脸 F 张、人物 P 人）：

- **检测成本**是决定性的：单对多按人物全库重扫 = P×M 次检测（千级人物 × 几万素材 ≈ 千万级次，GPU 也要数十小时~数天）；多对多全库只扫一遍 = M 次检测（几万次，GPU 5~15 分钟）。**检测次数取决于素材被扫几遍，与比对模式无关。**
- **比对成本**：任何组织方式总点积数恒为 F×P（矩阵乘一次性完成，内存/秒级），不是瓶颈。

「检测一次、匹配多次」混合架构同时拿到：
1. 性能最优下界（检测总量恒为 M）
2. 灵活性：新人注册/阈值调整 = 纯内存重匹配任务，不碰 GPU、不重扫素材

## 4. 性能测算（GPU：onnxruntime CUDA）

| 场景 | 量级 | 预估耗时 |
|---|---|---|
| 全库首扫（5 万张原图，批量端点 + 2~4 路并发） | 5 万次检测 | **~10~20 分钟**（原图解码更重；可接受，后续可加缩略图优化） |
| 增量扫描（新素材入队） | 每批 64 张 | 每批秒级 |
| 全库重匹配任务（F≈6~8 万脸 × P≈1500） | 矩阵乘 6e10 FLOP | **1 分钟内**（numpy float32，分块控内存） |
| 单人新增后重匹配任务 | 一次矩阵乘 | 秒级~十秒级 |

内存：F×P 相似度矩阵 float32 = 8 万 × 1500 × 4B ≈ 480MB（分块按 1 万张人脸一批，峰值 < 100MB）。

## 5. 总体架构与流程

```
┌─────────────┐   HTTP    ┌──────────────────┐
│ 主后端 API   │ ────────▶ │ face-service     │
│ (FastAPI)    │  批量embed │ (GPU onnx 推理)  │
└──────┬──────┘           └──────────────────┘
       │ 任务队列 task_queue（worker 串行执行 face_scan / face_match）
       ▼
┌────────────────────────────────────────────────────────┐
│ 三段式流程：                                          │
│ ① 检测（重活，只做一次）                              │
│    增量扫无记录素材（原图）→ embed-batch → 落库        │
│ ② 匹配（轻活，任务化）                                │
│    矩阵乘产出候选 → 写 matched_* + match_status=pending│
│ ③ 审核确认（人工，扫描页）                            │
│    候选按人物/置信度审核 → 确认 = 写人物关联表         │
│    + matched_* 置 confirmed；驳回 = 清空候选           │
└────────────────────────────────────────────────────────┘
```

三层分工：
- **层 1｜批量检测流水线（重活，全库只跑一次）**：增量扫无记录素材，embedding 落库
- **层 2｜候选匹配（轻活，随时任务化重跑）**：人物特征载入内存，矩阵乘全库比对，产出**待审核候选**
- **层 3｜人工审核确认（唯一写关联的入口）**：确认后才建立素材↔人物关联

## 6. 后端设计

### 6.1 face-service：批量 embed 端点（第一步，可独立验收）

`POST /api/face/embed-batch`（multipart，多文件字段 `files`）

```json
// 请求：files = [img1, img2, ..., imgN]（建议每批 32~64 张）
// 响应：
{
  "items": [
    { "index": 0, "face_count": 2, "faces": [{ "bbox": [x1,y1,x2,y2], "det_score": 0.98, "embedding": [512 维] }] },
    { "index": 1, "face_count": 0, "faces": [] }   // 无脸：正常业务结果，不再 404
  ]
}
```

- 服务端循环 `face_engine.extract`（模型已共享加载；消除 N 次 HTTP 往返与解码开销是主要收益）
- 可选优化（实现时验证后启用）：det_10g 动态输入是否支持 batch>1；rec 模型尝试动态 batch——不支持则维持逐张（GPU 单张推理毫秒级，可接受）
- 单张失败不整体失败：item 级错误标记（如 `"error": "decode_failed"`），主后端按 item 计数
- 主后端封装：`face_client.embed_batch(images: list[bytes])`，worker 内 2~4 路 asyncio 并发

### 6.2 模特特征库（新增表 + 注册流程）

**表 `model_face_embeddings`**（与 `blogger_face_embeddings` 对称，无缩略图字段）：

| 列 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK autoincrement | |
| model_id | INTEGER FK→models.id ON DELETE CASCADE，**unique + index** | 一模特一条 |
| embedding | LargeBinary | 512 维 float32（2048B） |
| updated_at | DATETIME | |

**注册流程 `POST /api/models/{id}/face`**（从写真照片组注册）：
1. 读取该模特全部照片组照片（`model_photos.file_path`，按组内 sort_order）
2. 逐张 embed，每张取 **det_score 最高**的人脸
3. 按 det_score 降序取 **Top-5**（范围 1~9）张最高质量人脸 → 平均池化 → L2 归一化 → 入库（覆盖旧特征，即「重新注册」）
4. 响应：`{ registered: true, model_id, photos_used: K, total_photos: N, updated_at }`

**查询状态 `GET /api/models/{id}/face`**：`{ registered, model_id, updated_at }`（对齐博主端模式）

> 注：模特/博主特征都存主后端自管表（不依赖 face-service 的 register 持久化），face-service 只负责 embed。

### 6.3 检测结果表扩展（挂模特 + 审核状态）

`inspiration_face_detections` 新增两列：

| 列 | 类型 | 说明 |
|---|---|---|
| matched_model_id | INTEGER FK→models.id ON DELETE SET NULL，nullable，index | 命中模特时写入 |
| match_status | VARCHAR(16) nullable，index | **NULL=传统/手动结果（直接展示）**；`pending`=批量扫描候选（仅扫描页可见）；`confirmed`=人工审核确认 |

**状态语义与展示规则**：

| match_status | 含义 | 素材详情页「人脸识别」区块 | 扫描页 |
|---|---|---|---|
| NULL | 单素材「检测并匹配」/手动指派结果（现有行为不变） | 展示 | 不出现 |
| pending | 批量扫描 AI 候选，**未经审核** | **不展示**（避免「未确认却显示已关联」） | 候选区展示，可确认/驳回 |
| confirmed | 人工审核通过，已写人物关联 | 展示 | 已确认区展示 |

- 一张人脸至多命中一种人物；全库匹配时博主+模特特征**合并为一个矩阵**比对（ArcFace 特征同一空间，余弦可比），取全库最高分者
- 现有 `matched_blogger_id` 保留不动（历史数据兼容）

### 6.4 全库匹配服务（层 2，替换现逐条循环）

新服务函数 `match_all_faces(db, person_scope="all"|"bloggers"|"models"|specific_ids, threshold=None)`：

1. 载入全部检测人脸 embedding → 矩阵 F×512（float32）
2. 载入人物特征（博主 + 模特）→ 矩阵 512×P
3. `scores = faces @ persons`；每行 argmax → 候选人物 + 分数
4. 阈值过滤（默认 `settings.face_match_threshold=0.5`，可传参覆盖）
5. 按 detection id 批量 UPDATE：`matched_*` + `confidence` + **`match_status='pending'`**（只写有变化的行）
6. 分块执行（按 1 万张人脸一批），控制峰值内存
7. 返回统计：`{ total_faces, matched_bloggers, matched_models, unmatched, duration_ms }`

**注意**：批量匹配**只写候选（pending），不写关联表**——最终关联由审核确认（层 3）完成。

现 `detect_inspiration_faces`（单素材检测）的匹配段同步替换为矩阵版（小规模 = 同函数分块特例），且**保持现有行为不变**：单素材流程写 `matched_*`、`match_status` 保持 NULL（直接展示），不引入 pending。

### 6.5 扫描任务（层 1，复用 TaskQueue）

新增任务类型 `face_scan`，handler 注册进 `TASK_HANDLERS`（`task_runners/face_scan.py`）：

**任务载荷（result JSON 初始值）**：
```json
{ "scope": "incremental" | "all", "auto_match": true, "batch_size": 64 }
```

**执行流程**（worker 内，每批提交一次）：
1. 计算待扫素材：**无任何 detections 记录**的图片素材（media_type != video），分页游标遍历；`scope=all` 时先清空全部 detections（全量重扫语义）
2. 每批 64 张：**读原图**（`file_path`，已确认方案）→ `embed_batch` → 先清后写本批 detections（幂等）
3. 每批后更新 `task.done / total / progress` 并提交；每批后 `db.refresh(task)` 检查 status：被外部改为 `cancelled` 则停止（已写不回滚）
4. 全部扫完且 `auto_match=true` → 自动创建 `face_match` 任务（候选匹配），扫描任务 result 中记录其 task_id
5. 完成统计：`{ scanned, faces, matched_candidates, unmatched, failed_files }` 写入 result，status=success

**增量 = 断点续跑**：中断/取消后重跑只扫无记录素材，天然续跑；**不做暂停按钮**（已确认）。

### 6.6 主后端 API 清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/models/{id}/face` | 从照片组注册模特特征（Top-5 平均池化） |
| GET | `/api/models/{id}/face` | 模特特征注册状态 |
| POST | `/api/face-scan/start` | 创建扫描任务 `{ scope, auto_match }` → `{ task_id }` |
| POST | `/api/face-match/run` | 创建候选匹配任务 `{ person_type?, person_id? }` → `{ task_id }`（**任务化**，已确认） |
| GET | `/api/face-scan/task` | 最近扫描/匹配任务状态（含进度与统计；复用 task_queue 查询） |
| GET | `/api/face-scan/results` | 候选/已确认/未匹配明细：`?status=pending\|confirmed&person_type=&person_id=&page=&size=` |
| POST | `/api/face-scan/confirm` | **审核确认/驳回（层 3 核心）**：`{ action: "confirm"\|"reject", items: [{ detection_id, person_type, person_id }] }` → 统计 |
| PUT | `/api/inspirations/{id}/face-detections/{detection_id}` | 扩展支持 `person_type`（单素材手动指派，保持现有 NULL 语义） |

**审核确认（confirm）的事务逻辑**：
1. 校验 candidate 存在且 status=pending（或 NULL 手动指派场景）
2. **confirm**：幂等 upsert `inspiration_bloggers` / `inspiration_models` 关联表（复用现有 link 服务逻辑）→ 同时把 `matched_*` 置为该人物、`match_status='confirmed'`、`confidence` 保留 → 提交。素材详情页「关联人物」与「人脸识别」两区块同时反映
3. **reject**：清空 `matched_*` / `confidence` / `match_status=NULL` → 该人脸回到未匹配区（可再手动指派）
4. 重复 confirm 同一 detection：幂等（关联表 upsert 已存在则跳过，状态已 confirmed 则直接返回）

### 6.7 数据库变更汇总（Alembic 迁移）

1. 新建表 `model_face_embeddings`
2. `inspiration_face_detections` 加列：`matched_model_id`、`match_status`
（现有表/索引不动；`inspiration_bloggers` / `inspiration_models` 关联表已存在，直接复用）

## 7. 前端设计

### 7.1 入口：人物管理页（PersonView）

- `page-header` 右侧加「人脸库扫描」按钮 → `router.push('/face-scan')`
- 理由：扫描对象就是该页管理的两类人物；与页面语义一致（已确认）

### 7.2 扫描页：新路由 `/face-scan` → `FaceScanView.vue`（views/）

页面结构（自上而下）：

1. **任务卡片**（顶部）
   - 状态行：未开始 / 检测中（a-progress：已扫 X / 总数 Y）/ 候选匹配中 / 已完成 / 已取消 / 失败（错误原因）
   - 操作：开始扫描（范围：增量 / 全量重扫）+ 自动匹配开关 + 取消按钮
   - 预估耗时提示（增量秒级、全量 10~20 分钟）
   - 运行中每 3~5s 轮询 `/api/face-scan/task`；扫描完成后若有 `face_match` 子任务，继续轮询匹配进度
2. **待审核候选区**（核心，`status=pending`）
   - **博主 / 模特 双 Tab**（与人物管理一致）
   - 人物卡片：头像 + 名字 + 候选数 + 最高/平均置信度；点击展开候选素材缩略图列表（缩略图 + 置信度 + 来源素材，分页）
   - **快捷审核**：按置信度区间批量操作——「一键确认 ≥0.75 的全部候选」「一键驳回 <0.55 的全部候选」（区间可调），剩余中置信度人工逐条过目
   - 勾选多张（或整人物）→ **「确认添加」/「驳回」**按钮：确认 = 建立人物关联（最终落点），驳回 = 清除候选
3. **已确认区**（`status=confirmed`）：按人物聚合展示已确认关联数，可跳素材详情；支持「撤销确认」（= 解除关联 + 候选状态回退或清除，与详情页解除逻辑一致）
4. **未匹配区**（无候选或已驳回）：人脸缩略图（bbox 裁剪）+ 来源素材；支持勾选多张 → 选择人物（a-select，复用人物选择器 allow-search 模式）→ 批量指派（写 confirmed + 关联表）

### 7.3 人物详情页连带

- 模特详情页：新增「人脸特征注册」折叠面板（复用博主侧折叠样式，默认收起），内容 = 「从照片组注册」按钮 + 状态标签 + 选图说明（Top-5 策略）；照片组更新后提示「建议重新注册」
- 博主/模特详情页：操作区加「全库匹配 TA 的素材」→ `POST /api/face-match/run`（限定该人物）→ 产物进入扫描页候选区待审核

### 7.4 素材详情页连带（FaceDetectionSection）

- 展示规则：只显示 `match_status IS NULL OR confirmed` 的匹配（pending 候选不显示）
- 命中模特时显示模特徽标与名称（PersonTypeTag 复用）；手动指派选择器支持人物类型切换（博主/模特）

## 8. 边界情况与容错

| 场景 | 处理 |
|---|---|
| 素材文件缺失/损坏 | item 级错误计数（failed_files），跳过不阻塞整批 |
| face-service 不可用 | 任务失败 → 现有重试机制（max_retries + 指数退避） |
| 单图无脸 | 正常结果（face_count=0），仍写入「已扫」状态（有记录即跳过） |
| 阈值未命中 | 视为未知人脸，不产候选，进未匹配区人工处理 |
| 删除人物 | 特征 CASCADE 删除；detections 的 matched_* SET NULL；关联表按现有删除逻辑处理 |
| 任务中断 | 增量语义自动续跑；已扫素材跳过 |
| 重复审核 | confirm/reject 均幂等；确认后二次 confirm 直接返回 |
| 确认后人物被删除 | 关联表现有解除逻辑兜底，detections 回未匹配 |
| 视频素材 | **第一版不扫**（media_type=video 跳过；视频抽帧扫描列为后续迭代） |
| 同人脸命中多人 | 只产最高分者候选（跨类型可比）；不做多归属 |

## 9. 实施顺序与产出

| 步骤 | 内容 | 产出/验收 |

## 11. 性能风险清单与预案（v1.2 新增）

按全链路环节梳理风险点，每条给出**提前预案**；标注「实现时验证」项需在步骤 1 验收时确认。

### 11.1 素材读取与解码（读原图）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| 几万张原图（穿搭图 1~10MB）磁盘随机 I/O + cv2 解码 CPU 密集；HDD 下随机读是灾难 | 素材存本地 storage，无缓存层 | ① worker 内「解码线程池 + 推理批队列」流水线：预读下一批与推理当前批并行，隐藏 I/O 延迟 ② 有界并发读图（Semaphore 4~8 路）防内存峰值 ③ 按 storage 目录顺序扫描减少 HDD 寻道 ④ 损坏/缺失文件计数跳过不阻塞 ⑤ 兜底迭代：缩略图优先 |

### 11.2 主后端 → face-service 传输

| 风险 | 现状事实 | 预案 |
|---|---|---|
| 每批 64 张原图 multipart（≈150~200MB）内存/带宽压力；timeout 30s 对大批量临界 | `face_client` 每次请求新建 AsyncClient，无连接池 | ① 批大小双上限：≤64 张 **且** ≤150MB 总字节，超限自动拆批 ② 模块级复用 httpx client（keep-alive），2~4 路并发共享 ③ 超时按批动态放大（30s + 批预估耗时×3），防误判重试 ④ 失败仅重发失败批（item 级定位），不整任务重跑 |

### 11.3 GPU 推理吞吐（face-service 内部，最大杠杆）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| det 每图一次 640×640；rec **逐张**推理（`_get_embeddings` 循环，batch=1），kernel launch 开销大，GPU 利用率不足；解码与推理串行 | FaceEngine 懒加载 + 线程安全；GPU 优先 | ① **实现时验证**：det_10g 动态输入是否支持 batch>1 → 支持则 det 批量推理（主要收益）② **实现时验证**：rec w600k_r50 是否支持动态 batch → 支持则一次 rec 全批 ③ 均不支持则保持逐张（GPU 单张 10~30ms，5 万张 ≈ 10~25 分钟，可接受但需实测）④ 解码放线程池与推理并行，GPU 不空等 ⑤ onnxruntime 线程/arena 配置按 GPU 场景调优 ⑥ **验收基准：64 张/批吞吐 ≥ 20 张/秒**，不达标逐项排查 |

### 11.4 detections 落库（SQLite）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| 5~8 万条人脸记录；ORM 逐条 add + 频繁 commit 灾难；大表清旧 delete | **WAL 已开启**（读写不互斥）；先清后写；有 (inspiration_id, face_index) 索引 | ① 每批一个事务：批量 delete（WHERE inspiration_id IN 本批）+ `bulk_save_objects` 批量 insert ② commit 频率 = 批频率（64 张/次），进度 done 同批更新 ③ 避免逐条 ORM 与 selectinload ④ 预估单批事务 <50ms，写库占比小 |

### 11.5 矩阵匹配（match_all_faces，层 2）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| embedding 全表加载（8 万 × 2048B ≈ 160MB）+ 反序列化；F×P 结果矩阵 480MB；numpy 无 BLAS 则慢 10 倍 | `_bytes_to_embedding` 逐条 np.frombuffer（Python 循环 8 万次） | ① 批量反序列化：全部 BLOB 拼接 → 一次 `np.frombuffer` → reshape（消除循环）② 分块矩阵乘（每 1 万张人脸一批），峰值内存 <100MB ③ **实现时验证**：numpy 链接 BLAS（benchmark 简单矩阵乘），无则重装/降级分块 ④ 人物特征库（几 MB）**进程内缓存**，人物特征变更才失效 ⑤ 只写有变化的行（diff 后批量 UPDATE），避免全表写 |

### 11.6 任务执行环境（worker）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| face_scan 占 worker 10~20 分钟（排队已确认接受）；worker 内存峰值（并发 2~4 路 × 批 150MB）；worker 重启中断 | 心跳/租约 + stale 任务重置机制已存在 | ① 内存预算：并发路数 × 批字节上限 ≤ 1GB（配置化，默认 4 路 × 150MB）② 每批持久化进度 + 增量续扫（中断恢复成本 = 一批）③ 连续失败批次超阈值（如 10 批）→ 任务失败退出，防死循环 |

### 11.7 审核批量确认写库（层 3）

| 风险 | 现状事实 | 预案 |
|---|---|---|
| 一键确认 ≥0.75 可能几千~上万条；逐条接口/逐条事务灾难 | 关联表 link 逻辑为逐素材 API | ① confirm 接口**单事务批量**：批量 upsert 关联表 + 批量更新 detections（executemany）② 前端按「人物 × 置信度区间」粒度发起（一次几千条一个请求）③ 幂等（upsert + status 检查）④ 单请求 ≤ 5000 条上限，超出前端分批 |

### 11.8 结果查询与前端

| 风险 | 现状事实 | 预案 |
|---|---|---|
| pending 候选 6~8 万条；全量拉取卡死页面 | 无现成结果查询 | ① 统计接口 SQL GROUP BY person 聚合（每人物 count + 最高分）分页 ② 明细按人物 + 分页（50/页），缩略图 `loading=lazy` ③ 轮询 3~5s 只查轻量任务状态，结果任务完成后按需拉取 ④ 人脸小图首版用素材缩略图 + bbox CSS 定位（不新增裁剪接口） |

### 12.3 实施中与设计的差异（决策记录）

1. **无脸素材占位记录**：为维持「有记录即已扫」的增量语义，无脸素材写入一条 `embedding=b''` 的占位记录；`match_all_faces` 查询与素材详情列表均过滤空 embedding，占位记录不参与匹配、不展示（原设计未明确此细节）
2. **手动指定即确认**：素材详情页手动指定人物时 `match_status` 置 NULL（直接展示），与「批量候选 pending → 审核 confirmed」流程分离（原设计只提 pending 不展示）
3. **结果查询接口合并**：聚合（按人物）/ 明细（按人物）/ 未匹配三种模式合并为 `GET /api/face-scan/results`（`mode` 字段区分），按人物聚合支持博主/模特混合返回（原设计为多个端点）
4. **运行中取消**：扩展 `POST /api/tasks/{id}/cancel` 支持 `face_scan`/`face_match` 运行中取消（执行器每批检查状态自行停止），其他任务类型保持不可硬打断（原设计仅提「取消+增量续跑」，未明确运行中取消的实现方式）
5. **`_bytes_to_embedding` 迁移**：从 blogger_face 移至 face_match（消除模块循环导入）
6. **Alembic 迁移手工清理**：autogenerate 检测到 tags/ai_analysis_log 等历史库表与 ORM 的漂移（与本功能无关），两笔迁移均手工剔除漂移内容，仅保留本功能 DDL
7. **模特注册的质量过滤**：照片组注册按 det_score 过滤（≥0.65）并计算人脸宽度占比（≥5%），与博主一致；未保留逐张 photo_results 明细（照片组可达上百张，返回简化统计：photos_used/photos_total/qualified/warnings）
8. **扫描顺序稳定**：待扫素材按 `(created_at, id)` 排序（同秒创建时 id 兜底），保证行为可预测

### 12.4 部署注意事项（服务启停由用户手动执行）

1. **必须重启三个服务**：主后端（新路由/任务）、worker（新任务类型注册 `TASK_HANDLERS`）、**face-service（新增 `embed-batch` 端点，不重启无法调用）**
2. **使用前准备**：博主重新确认/注册人脸特征；模特补照片组并从详情页「从照片组注册」；然后人物管理页 →「人脸库扫描」→ 开始扫描（首扫全量 10~20 分钟 GPU，可取消续跑）→ 待审核候选确认/驳回 → 素材详情页可见关联
3. **可调参数**：批大小/字节上限/并发（`task_runners/face_scan.py`：SCAN_BATCH_SIZE=64、SCAN_BATCH_BYTES=150MB、EMBED_CONCURRENCY=4）、匹配阈值（`settings.face_match_threshold=0.5`）、快捷确认区间（前端 ≥0.75 / <0.55 文案）
4. **已知边界**：视频素材不扫描（第一版约定，后续迭代）；同一人脸只关联全库最高分者（不展示 top-N 候选）；face_scan 串行占用 worker（期间其他任务排队，已确认接受）
