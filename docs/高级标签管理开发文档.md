# 高级标签管理页面 — 开发文档

> 版本：v1.0（草案待评审）
> 关联页面：现有「标签管理」（`/tags`，`TagManageView.vue`）
> 技术栈：Vue 3 + TypeScript + Arco Design（前端）、FastAPI + SQLAlchemy async + SQLite（后端）

---

## 1. 文档概述

### 1.1 背景

现有「标签管理」页面已覆盖：分组浏览、搜索筛选、置顶与拖拽排序、别名归一化、批量改类别/重命名/合并/删除、重复扫描、标签备注、共现关系图与使用趋势、导入导出、素材关联预览。

本页面作为**独立路由页面**，与现有页面并存，专注**更深度的标签治理与分析**，不重复实现上述已有能力。

### 1.2 范围

| 模块 | 说明 |
| --- | --- |
| 标签健康度分析 | 扫描孤儿/低频/低质命名/疑似重复标签，输出健康评分与问题清单，联动一键修复 |
| 自动聚类分组 | 名称相似优先（含共现辅助），产出「候选合并组」，人工确认后批量合并/建别名 |
| 网络图增强 | 可调 Top-N 子图 + 社区发现 + 中心度 + 桥接节点高亮 |
| 批量高级编辑 | 正则查找替换 / 前后缀增删 / 格式归一化 / 正则批量合并，全部支持 dry-run 预览 |
| 操作历史与审计 | 新建 `tag_history` 快照表，单条操作级回滚 + 冲突检测；破坏性操作继续写现有 `audit_logs` |
| 标签层级结构 | `parent_id` 任意深度树，与 `category` 正交；树视图拖拽移动子树 |
| 使用效果分析 | 热度升降榜、标签组合排行、覆盖度统计、来源分布分析 |

### 1.3 需求决策记录（已与用户确认）

| 决策点 | 结论 |
| --- | --- |
| 功能方向 | 上述 7 大模块全部纳入 |
| AI 辅助 | 本期**仅统计与规则分析**，不调 Ollama；架构预留后续扩展点 |
| 页面定位 | 分析 + 操作并重（分析结果可直接转化为批量操作） |
| 层级结构 | `tags` 新增 `parent_id` 自引用，任意深度树；树与 `category` 正交 |
| 历史深度 | 历史 + 回滚都要；新建 `tag_history` 快照表；**单条操作级回滚**，冲突则拒绝并提示 |
| 聚类策略 | 名称相似优先、共现辅助；产出**合并建议**，不自动执行 |
| 网络图 | 图算法增强（社区发现 + 中心度 + 桥接高亮） |
| 健康度检查项 | 孤儿标签、低频标签（=1 次）、低质命名、疑似重复（**不含**缺备注） |
| 批量编辑规则 | 正则查找替换、前后缀增删、格式归一化、正则批量合并，全部支持 |
| 冲突策略 | 目标标签已存在时**自动合并**（与现有 merge 语义一致） |
| 效果分析指标 | 热度升降榜、标签组合排行、覆盖度统计、来源分布分析 |
| 图算法实现 | 社区发现/中心度**纯 Python 自实现**（标签传播 + 手算）；字符串相似度**复用现有 `tag_normalizer.string_similarity`（rapidfuzz）**，实施时把 `rapidfuzz` 补声明进 requirements.txt（修复既有未声明依赖问题） |
| 重计算执行 | 复用现有 `TaskQueue` **异步任务 + 进度轮询**（worker 执行、结果写任务行） |
| 页面布局 | 左侧 Tab 导航 + 右侧主工作区 |

### 1.4 非目标（本期不做）

- AI 语义聚类 / 同义词建议（Ollama 接口预留，后续迭代）
- 聚类建议自动执行（必须人工确认）
- 移动端（React Native）同步改造
- 标签使用效果回归模型 / 预测

## 2. 功能需求清单

### 2.1 标签健康度分析

**检查项与判定规则**（规则常量集中放 `backend/app/services/tag_health.py`）：

| 检查项 | 判定规则 | 一键操作 |
| --- | --- | --- |
| 孤儿标签（orphan） | 无任何素材关联（usage_count = 0） | 批量删除 / 批量移入某个父标签下归档 |
| 低频标签（low_frequency） | 恰好 1 次关联 | 查看素材 / 批量合并 / 保留 |
| 低质命名（low_quality_name） | **复用 `tag_normalizer.validate_tag_name()`**：纯英文（非白名单）、长度 > 8、含标点 `。！？…~`、描述句特征、hex 颜色、括号推测等；`reason` 取校验函数返回的原因文案 | 批量编辑（重命名 / 删） |
| 疑似重复（duplicate） | 复用 `find_duplicate_tag_pairs` 相似度扫描（阈值默认 0.75） | 批量合并 / 批量建别名 |

**健康评分**（0–100，默认规则可配置）：

- 基数 100 分，按问题占比扣分（每项有扣分上限，避免单项主导）：
  - 孤儿占比 × 0.5 分/百分点，上限扣 25 分
  - 低频占比 × 0.3 分/百分点，上限扣 15 分
  - 低质命名占比 × 0.4 分/百分点，上限扣 20 分
  - 疑似重复占比 × 0.4 分/百分点，上限扣 20 分
- 评分结果与各问题的标签 ID 列表写入异步任务 result；明细按问题类型分页查询。

### 2.2 自动聚类分组

- **相似度策略**（默认参数可调）：
  - 名称归一化：全角→半角、转小写、去首尾空白、去标点
  - **复用 `tag_normalizer.string_similarity()`（rapidfuzz `fuzz.ratio`）**，相似度 ≥ 0.75 为候选；实施时把 `rapidfuzz` 补声明进 requirements.txt（代码已在用、缺声明，见「待改进列表.txt」）
  - 包含/前缀匹配：短名被长名包含且长度差 ≤ 4
  - 共现辅助：候选对在同一素材共现 ≥ 2 次，相似度 + 0.1（可配置关闭）
- **聚类流程**：候选对按相似度降序，并查集合并成组 → 组内选「使用次数最高」为建议主标签，其余为建议合并源
- **产出形态**：候选合并组列表（每组含相似原因、成员、建议主标签），**人工勾选确认后**才执行
- **执行方式**：`/clusters/apply` 事务内完成合并（复用 `merge_tag_pair` 逻辑的批量版）或批量建别名，全部写 `tag_history`
- **性能**：长度桶 + 首字符索引预过滤，数千标签可控；走异步任务

### 2.3 网络图增强

- **子图范围**：可调 Top-N（20–500，默认 100）+ `min_count` + 可选按类别过滤
- **社区发现**：纯 Python 标签传播算法（Label Propagation，迭代上限 20 次），输出社区编号；前端按社区分配色板
- **中心度**：度中心度（degree/(n-1)）；介数中心度用 Brandes BFS + 随机采样近似（k = min(100, n)）
- **桥接节点**：跨社区边占比 ≥ 0.5 且度 ≥ 3 的节点高亮
- **交互**：点击节点 → 查看趋势（复用 `GET /tags/{id}/trend`）/ 素材预览；图例显示社区；支持导出 PNG（ECharts 自带）
- 结果缓存：任务 result + 内存缓存（key = 数据版本 + 参数）

### 2.4 批量高级编辑

规则类型（后端统一用 Python `re` 引擎，dry-run 预览同样由后端计算，避免 JS/Python 正则差异）：

| 规则类型 | 参数 | 说明 |
| --- | --- | --- |
| `regex_replace` | `pattern`、`replacement`（支持捕获组 `\1`）、`scope` | 正则查找替换 |
| `affix` | `mode`（add_prefix/remove_prefix/add_suffix/remove_suffix）、`text` | 前后缀增删 |
| `normalize` | `ops`（fullwidth_to_halfwidth / trim / dedup_chars） | 格式归一化 |
| `regex_merge` | `pattern`（捕获组）、`target_template` | 正则匹配后批量合并到目标 |

- **scope 选择范围**：指定 tag_ids / 按 category / 按 source / 按搜索结果
- **dry-run 模式**：返回逐条预览（原值 → 新值 / 动作类型 / 是否冲突转合并 / 目标标签），不落库
- **冲突策略**：目标标签已存在 → 自动合并（源删除、关联转移、按配置保留为别名），与现有 merge 语义一致
- **执行**：同批次规则共享一个 `batch_id`，写入 `tag_history`

### 2.5 操作历史与审计

- 所有标签写操作（create / rename / category_change / move / merge / alias_add / alias_remove / batch_edit / delete）写入 `tag_history` 快照表（before/after JSON）
- **回滚**：单条操作级；回滚前冲突检测——受影响标签的当前状态若与 `after_snapshot` 不一致（期间被其他操作改动），拒绝该条回滚并返回 409 与冲突详情
- merge 回滚：恢复源标签行 + 别名，并把合并进目标的关联移回源标签
- 破坏性批量操作（批量删除、清未使用、聚类 apply 中的删除）继续写现有 `audit_logs`（复用 `audit_service.record_audit_log`）
- 历史列表分页 + 按 operation / tag_id / batch_id 过滤

### 2.6 标签层级结构

- `tags.parent_id` 自引用外键，任意深度树；**与 `category` 正交**：树是整理视图，`category` 仍是标签属性
- 树视图：懒加载（顶层 + 按需展开子节点，每节点带 `has_children`）
- 拖拽移动子树 → `POST /tags/move` 批量提交；校验：不能移动到自己的后代（循环检测），可移回根（parent_id = null）
- 移动写 `tag_history`（operation = move）

### 2.7 使用效果分析

| 子指标 | 实现要点 |
| --- | --- |
| 热度升降榜 | 一次 SQL 按 `(tag_id, 窗口)` 聚合近 `2×days` 天内的关联数（素材 `created_at` 分桶），内存算 delta，取上升/下降 Top-N |
| 标签组合排行 | 在活跃标签子集（近 30 天有用例或使用次数 top 200）内两两共现计数，按次数降序 |
| 覆盖度统计 | 素材总量、带标签素材占比、单素材平均标签数、按类别覆盖率（SQL 聚合） |
| 来源分布 | 按 `tag.source` 分组：标签数、总使用次数、平均使用次数；Top AI 生成噪声标签（使用次数低但数量多） |

> 注：素材 `created_at` 为入库时间，趋势/升降榜以此为近似口径（与现有 trend 一致）。

## 4. 后端 API 设计

### 4.1 异步任务通用模式（复用现有 TaskQueue）

与现有「智能去重」完全一致的模式：

1. 前端 `POST` 创建任务 → 返回 `task_id`
2. worker（`app/worker.py` + `app/services/task_runners/`）串行执行，结果写入任务行 `result` JSON
3. 前端轮询现有 `GET /api/tasks/{task_id}`（`TaskOut`）直到 `success`，读取 `result`

新增任务类型（`task_runners/` 下各一模块）：

| type | 模块 | result 内容 |
| --- | --- | --- |
| `tag_health_scan` | `task_runners/tag_health.py` | 评分 + 各问题标签 ID 列表 |
| `tag_cluster_scan` | `task_runners/tag_cluster.py` | 候选合并组 |
| `tag_network_analyze` | `task_runners/tag_graph.py` | 节点（含社区/中心度/桥接标记）+ 边 + 社区摘要 |

> 注意：worker 串行执行，大计算任务会排队；本期可接受，后续如需可加优先级字段（不在本期范围）。

### 4.2 新增接口

#### (1) 健康度

`POST /api/tags/health/scan` — 创建健康度扫描任务

请求体：`{}`（可选 `{"duplicate_threshold": 0.75}`）

响应：
```json
{ "message": "已提交健康度扫描任务", "task_id": 42 }
```

`GET /api/tags/health/{issue_type}?page=1&size=50` — 明细（issue_type ∈ orphan | low_frequency | low_quality_name | duplicate）

响应（孤儿/低频/低质命名）：
```json
{
  "issue_type": "orphan",
  "total": 120,
  "items": [
    { "id": 101, "name": "宽松阔腿裤", "category": "item_type", "source": "ai_generated", "usage_count": 0, "parent_id": null,
      "reason": "低质命名：标签名过长 (15 字)" }
  ]
}
```
> 说明：`reason` 字段仅低质命名类型必填（复用 `validate_tag_name` 返回的原因）；其余类型可为 null。
响应（duplicate，复用重复对结构）：
```json
{
  "issue_type": "duplicate",
  "total": 12,
  "items": [
    { "tag_a": { "id": 1, "name": "白色", "category": "color" },
      "tag_b": { "id": 2, "name": "纯白", "category": "color" },
      "similarity": 0.92 }
  ]
}
```

#### (2) 聚类

`POST /api/tags/clusters/scan` — 创建聚类任务

请求体：
```json
{
  "threshold": 0.75,
  "use_cooccurrence_boost": true,
  "min_group_size": 2
}
```
响应：`{ "message": "已提交聚类任务", "task_id": 43 }`

任务 result（示例）：
```json
{
  "groups": [
    {
      "id": "g1",
      "reason": "名称相似 0.85（编辑距离）",
      "suggested_target": { "id": 5, "name": "毛衣", "usage_count": 120 },
      "members": [
        { "id": 12, "name": "白色毛衣", "usage_count": 3 },
        { "id": 33, "name": "黑毛衣", "usage_count": 2 }
      ]
    }
  ],
  "total": 18
}
```

`POST /api/tags/clusters/apply` — 应用选中的候选组（事务内，全部写历史）

请求体：
```json
{
  "batch_id": "cluster-20260824-001",
  "groups": [
    { "group_id": "g1", "keep_as_alias": true }
  ]
}
```
响应：
```json
{ "applied": 1, "merged": 2, "aliases_created": 2, "errors": [] }
```

#### (3) 网络图分析

`POST /api/tags/network/analyze` — 创建图分析任务

请求体：

## 5. 数据库变更

### 5.1 `tags` 表新增字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `parent_id` | `Integer` nullable，`ForeignKey("tags.id", ondelete="SET NULL")`，加索引 | 父标签 ID，null = 根节点 |
| `updated_at` | `DateTime`，`onupdate=func.now()` | 供回滚冲突检测；注意批量核心更新语句（`update()`）需显式赋值该列 |

### 5.2 新建 `tag_history` 表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | Integer PK autoincrement | 主键 |
| `batch_id` | String(64) nullable，加索引 | 同批次操作分组（批量编辑 / 聚类 apply / 一次 move） |
| `operation` | String(32)，加索引 | create / rename / category_change / move / merge / alias_add / alias_remove / batch_edit / delete |
| `tag_ids` | Text（JSON 数组） | 受影响标签 ID |
| `before_snapshot` | Text（JSON） | 操作前受影响标签完整状态（含 aliases、usage_count、关联数） |
| `after_snapshot` | Text（JSON） | 操作后状态（merge 记录源删除、目标合并详情） |
| `meta` | Text（JSON） nullable | 附加信息（正则规则、源/目标名等） |
| `created_at` | DateTime，加索引 | 记录时间 |

快照内容示例（每个受影响标签）：
```json
{ "id": 5, "name": "白色", "category": "color", "parent_id": null,
  "pinned": false, "sort_order": 0, "description": null,
  "aliases": ["纯白", "米白"], "usage_count": 120, "link_count": 120 }
```

### 5.3 回滚实现要点

- 普通操作回滚：用 `before_snapshot` 恢复 tags 行（name / category / parent_id / description / pinned / sort_order）与别名
- merge 回滚：恢复源标签行 + 别名，并把 `inspiration_tags` 中转移给目标的关联移回源标签
- 冲突检测：当前 tags 行状态与 `after_snapshot` 比对（逐字段 + `updated_at`），不一致 → 409 拒绝并返回冲突标签清单
- 回滚本身不写新快照（避免递归），但记录一条 meta 备注

### 5.4 迁移步骤

1. 修改 `backend/app/models/tag.py`（加 `parent_id`、`updated_at`）
2. 新建 `backend/app/models/tag_history.py`（`TagHistory` 模型）
3. `cd backend && alembic revision --autogenerate -m "标签层级 parent_id 与操作历史表" && alembic upgrade head`
4. 后端启动时会自动执行 `run_migrations`，无需手工干预（但部署需重启服务，见 §9）

## 9. 风险与注意事项

- **服务重启**：数据库迁移与后端新接口需要重启后端服务与 worker 才能生效，**由用户手动执行**（项目约定禁止自动执行 `scripts/restart.sh` 等脚本）
- **worker 串行执行**：重计算任务会与采集/去重任务排队；若任务积压成为问题，后续可增加优先级字段（本期不做）
- **历史表增长**：`tag_history` 会持续增长，预留清理策略（按时间/条数上限，配置项），本期仅做分页查询不做自动清理
- **时间口径**：趋势与升降榜基于素材 `created_at`（入库时间），非真实使用时间，属近似口径
- **Git 提交**：本功能为独立主题，功能完成（≥100 行）后按约定自动 commit + push；docs 类小改动攒批；**fix 提交不受行数限制**
- **既有问题顺带修复**：`rapidfuzz` 已在 `tag_normalizer.py` 中使用但未声明进 requirements.txt（待改进列表.txt 有测试失败记录），实施阶段一并补声明
- **TODO.md**：本期为新增功能，若 TODO.md 有对应条目按约定在完成后删除
- **移动端**：本期不改 `mobile/`，新接口不破坏现有移动端调用（全部为新增路由，不改动既有接口响应结构）
