# 日志系统整改说明（2026-11-02）

> **状态**：已实施（自动化测试通过；服务重启后生效，**重启由用户手动执行**）。
> **上游审计**：[日志系统全量扫描（2026-11-02）](日志系统全量扫描-2026-11-02.md)。
> **范围**：审计报告 §3 的 P0/P1/P2 全部发现（**不评估安全面**，与审计口径一致）。
> **不做的**：ELK/Loki/Prometheus/Sentry、远程日志上报、每请求写 DB 日志表——理由见审计 §4「明确不做」。

---

## 0. 一句话总结

API 进程接上了 root handler（`app.*` 业务日志不再丢），健康检查/2xx 访问行/httpx/ f2 子进程噪音被降掉；请求与任务有了 `request_id` / `task_id` / `run_id` 关联；except 统一带堆栈、静默 except 全部归类到 `logger.debug`；日志与台账有了保留期和清理入口；任务台账可从 API/前端查看；Web/移动端/插件有了本地诊断日志与「复制诊断信息」。**`LOG_LEVEL` / `LOG_FORMAT` 可切，默认行为与历史一致（只是不再丢日志）。**

## 2. 统一日志设计（`backend/app/logging_config.py`）

### 2.1 root handler 与 uvicorn

```python
logging.config.dictConfig({
    "version": 1,
    "disable_existing_loggers": False,   # 不能掐掉 alembic/sqlalchemy 的既有 logger
    "formatters": {"text": ContextFormatter, "json": JsonFormatter},
    "handlers": {"console": StreamHandler(sys.stdout)},
    "root": {"level": level, "handlers": ["console"]},
    "loggers": {
        "uvicorn": {...}, "uvicorn.error": {...}, "uvicorn.access": {...},
    },
})
```

- API 的 stdout 由 supervisor 捕获并做 10 MB × 5 轮转，**不再自己开文件**（避免两套轮转）；
- worker 在 root 上额外挂 `DailyFileHandler`（`logs/analyze-YYYY-MM-DD.log`），格式与主日志一致；
- `disable_existing_loggers=False` 与 `tests/test_logging_visibility.py` 守的是同一条回归（alembic `fileConfig` 默认会禁 logger）。

### 2.2 关联字段（request_id / task_id / run_id）

- `contextvars`：`request_id_var` / `task_id_var` / `run_id_var`；
- 通过 **LogRecord 工厂** 注入字段（不是 logger filter——filter 对子 logger 传播的记录不生效，会漏掉 handler）；
- API 中间件每请求生成 12 位 hex（尊重传入的 `X-Request-ID`），写 contextvar，响应头回传；
- worker 在 `_run_task_safe` 设置 `task=#id`，`_start_run_log` 拿到台账行后设置 `run=<id>`；
- 前端 API 拦截器读响应头 `X-Request-ID`，错误文案统一追加「（请求ID: xxx）」。

排查示例：

```bash
grep 'req=abc123def456' logs/backend.log
grep 'task=#739' logs/worker.log
```

### 2.3 访问日志降噪与慢请求

- 丢弃：`/api/health`（supervisor 每 5 秒探一次，占历史 55%）、WebSocket 连接/断开行、2xx/3xx 访问行；
- 保留：4xx/5xx 访问行、uvicorn 的真实错误日志；
- 慢请求：中间件对 > `SLOW_REQUEST_MS`（默认 1000ms）的请求记 WARNING（含方法/路径/状态/耗时）；
- 未处理异常：中间件先 `logger.exception` 记完整堆栈（带 request_id），再返回统一 500 `{"detail": "服务器内部错误"}`，避免 uvicorn 再打一遍重复 traceback。

### 2.4 开关

| 环境变量（`.env`） | 默认 | 作用 |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | `DEBUG` 时打印静默 except 分类日志、httpx 请求明细、SQL 日志 |
| `LOG_FORMAT` | `text` | `json` 时一行一条 JSON（本地排障用，不改变落盘位置） |
| `SLOW_REQUEST_MS` | `1000` | 慢请求阈值 |
| `LOG_RETENTION_DAYS` | `30` | `analyze-*.log` 保留天数 |
| `TASK_RUN_LOG_RETENTION_DAYS` | `90` | `task_run_logs` 保留天数 |

> 配置只在**进程启动**时读取：改完 `.env` 需要用户手动重启服务。

## 3. 子进程与第三方库

- **f2**：`_run_subprocess` 改为 `Popen(stdout=文件)`，输出写 `logs/f2-<时间戳>-<pid>.log`（沿用 `f2-*.log` 命名，清理脚本统一回收），worker.log 只留一行退出码 + 文件路径；失败附最后 20 行。测试里的 monkeypatch 点（`_run_subprocess` 两参数签名）未变。
- **httpx/httpcore**：默认 WARNING；`LOG_LEVEL=DEBUG` 临时打开。
- **face-service**：`RotatingFileHandler(10 MB × 3)` 直接写 `logs/face-service.log`；`restart.sh` 只把 uvicorn 启动/访问行重定向到 `logs/face-service-bootstrap.log`（不再与轮转文件争路径）。
- **前端 ANSI**：supervisor 给 vite 进程补 `NO_COLOR=1`、`CLICOLOR=0`（`FORCE_COLOR=0` 对部分输出无效）。

## 4. 异常与静默 except 规范

### 4.1 规则

1. `except` 中记录**非预期异常**统一 `logger.exception("...")`（或 `logger.error(..., exc_info=True)`）；
2. 预期内的降级（可重试、可选缓存、子进程清理、best-effort）用 `logger.warning` / `logger.debug`，不要用 ERROR；
3. 静默 `except: pass/continue/return` 必须至少有一条 `logger.debug` 说明「忽略异常（预期降级）」，或改用 `logger.exception`；
4. 只有**日志系统自身**（`logging_config.py` 的 filter、`daily_log.py` 的 handler emit、`config.py` 的 .env 兜底）允许保持静默（避免日志递归）。

### 4.2 落地

- 36 处 except 内 `logger.error` → `logger.exception`（正则/AST 精确改方法名，行为不变，只补堆栈）；
- 106 处静默处理器补 `logger.debug("函数名: 忽略异常（预期降级）：%s", exc)`（默认 INFO 级别不输出，`LOG_LEVEL=DEBUG` 可见；不再吞掉现场）；
- `backend/tests/test_logging_conventions.py` 两条 AST 断言：
  - except 内 `logger.error` 无堆栈 → 失败；
  - 静默 except（除 3 个日志系统自身文件）→ 失败。

> 为什么用 `logger.debug` 而不是全部 `warning`：历史 WARNING 已比 INFO 多（162 > 153），把 100+ 个 best-effort 路径升成 WARNING 只会让告警更失真；DEBUG 可随时打开且零日常噪音。

## 5. 级别与格式约定（P2-1 / P2-2 / P2-3）

| 级别 | 用途 |
| --- | --- |
| DEBUG | 逐条细节、静默降级路径（`LOG_LEVEL=DEBUG` 才输出） |
| INFO | 生命周期、每任务一条进度/结果 |
| WARNING | 可恢复但需关注（重试、降级、慢请求、外部服务异常） |
| ERROR | 操作失败需要处理（配合 `logger.exception` 留堆栈） |
| CRITICAL | 服务不可用（当前无使用场景） |

- 新增日志优先惰性格式化 `logger.info("... %s", value)`（f-string 仅纯静态短消息）；不要求批量改写历史 328 处，但代码评审按新约定执行；
- 每条日志都带 `时间 级别 logger:行号 [req= task=]`，JSON 模式字段为 `ts/level/logger/line/message/request_id/task_id/run_id`（异常另有 `exception`）。

## 6. 保留与清理（P1-4）

| 对象 | 策略 | 执行方 |
| --- | --- | --- |
| `backend.log` / `worker.log` / `frontend.log` | 10 MB × 5 大小轮转（保持原状；总量由轮转封顶） | supervisor |
| `supervisor.log` | 10 MB × 5 `RotatingFileHandler` | supervisor |
| `face-service.log` | 10 MB × 3，进程内轮转 | face-service |
| `analyze-YYYY-MM-DD.log` | 启动时删除超过 `LOG_RETENTION_DAYS`（30 天）的文件 | worker |
| `task_run_logs` | 启动时删除 `started_at` 超过 90 天的行 | worker |
| `f2-*.log` | 按次生成；0 字节空壳始终清，其余默认保留 | 清理脚本（手动） |
| `backend/logs/*`、`backend/*.out/.err` | 历史遗留，列入清理脚本 | 清理脚本（手动） |

清理入口（默认 **dry-run**，确认后加 `--apply`）：

```bash
python scripts/ops/cleanup_artifacts.py --target logs          # 预览
python scripts/ops/cleanup_artifacts.py --target logs --apply  # 删除
```

> 没有把清理脚本挂到 supervisor 自动执行：删除不可恢复（日志是事后证据），保持「人工确认」与本项目既有设计一致；`logs/` 总量已被各服务轮转上限约束（约 110 MB 稳态），不需要额外总预算熔断。

## 7. 任务台账可查（P1 路线图）

- 后端：`GET /api/tasks/{task_id}/runs?limit=50` → `TaskRunOut[]`（`started_at`/`finished_at` 带 `Z` 后缀，缺任务 404）；
- 前端：任务管理页每行（队列任务）「运行记录」按钮 → 弹窗展示：第几次执行（attempt）、状态、开始/结束（nowrap）、耗时、处理量/总数、GPU、错误摘要；无记录时提示「worker 重启后才有台账」；
- 台账仍由 worker 在任务开始/结束时写，**旧数据（worker 未重启前）为空**，见 §9 验证步骤。

## 8. 已知边界与未做项

| 项 | 说明 |
| --- | --- |
| 人脸子服务 404（worker WARNING 132 条） | 审计已判定是**接口路径/契约不匹配的业务问题**，不是日志问题；修复属业务改动，按审计「不评估业务逻辑修复」的范围未在本次处理，修好后 WARNING 自然消失 |

| 日志压缩（`.gz`）与 `logs/` 总预算 | 未做：各服务 10 MB × N 的轮转已把总量封顶（稳态约 110 MB），压缩收益小于「supervisor 与清理脚本两套策略打架」的复杂度；清理脚本保留人工 `--apply` |
| 诊断包 zip（路线图 §4 P2-2） | 未做：Web/Mobile 已有「复制诊断信息」，插件可查看/复制 session 日志；单机本地场景不需要再打 zip（按需再加） |
| 日志指标（路线图 §4 P2-3） | 未做：`task_run_logs` / `ai_analysis_log` 已有结构化字段（`GET /api/tasks/{id}/runs` 已露出台账），错误率/P95/GPU 统计可在 Insights 页按需做 |
| 未引入 OpenTelemetry / 远程日志 | 单机本地部署，contextvar + 文件 + SQLite 足够（审计 §4） |
| `LOG_FORMAT=json` 只覆盖 Python 进程 | 前端/子进程各有自己的日志形态（f2 输出单独文件、face-service 文本格式）；本地排障够用 |
| 前端诊断不新增后端接口 | 诊断文本在浏览器内拼装并复制/分享，不含远程上传 |
| 服务重启 | 按项目约定由用户手动执行；本说明不包含自动重启脚本调用 |

## 10. 回滚

- 日志格式/降噪出问题：`LOG_LEVEL=WARNING` 或临时移除 `logging_config.setup_logging` 调用即可回到 uvicorn 默认（不推荐，会再次丢 `app.*` 日志）；
- 前端/移动端诊断日志：`import.meta.env.DEV` / `__DEV__` 控制级别，生产只记 warn/error；
- 台账接口与前端入口互不影响任务执行，可不启用。
