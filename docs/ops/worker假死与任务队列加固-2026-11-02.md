# worker 假死与任务队列加固（2026-11-02）

> **状态**：事故复盘 + 加固已实施（自动化测试通过；**服务重启后生效，重启由用户手动执行**）。
> **关联**：[异步任务体系](../features/异步任务体系.md)、[日志系统整改说明](日志系统整改-2026-11-02.md)、[本地运行与排障](本地运行与排障.md)。
> **一句话**：worker 进程活着但事件循环卡死，心跳中断 → supervisor 只判进程存活、不重启 → 4 个云端出图任务永久排队。已补四道防线：supervisor 心跳监控、worker 任务看门狗、向量回填失败快路径 + Ollama 熔断、`/api/tasks` 列表瘦身。

## 1. 事故现象

- 用户报告「任务管理中卡住了」：任务一直 `pending`，状态不动。
- `GET /api/health/services` 返回 **worker: down**；但 `logs/service_status.json` 里 worker 进程「ok」（进程确实活着）。
- 数据库 4 条 `image_gen` 任务（#746~#749，云端 Seedream）从 23:43 起一直 `pending`，没有 worker 认领。

## 4. 判断

**直接原因**：worker 在执行遗留向量回填 #745 时卡死（文本嵌入全失败后进入 CLIP 图像编码，编码完成后事件循环停摆），心跳与任务进度都不再更新；单并发槽位被占死，后续任务永远排队。

**触发条件**：Ollama 未运行 + worker 启动时自动拉起遗留的向量回填（6 个素材）。

**为什么没自愈**：supervisor 只检查「worker 进程是否存在」，不检查心跳；worker 也没有任务级看门狗。

**未完全定位的部分**：事件循环内部为什么丢唤醒（py-spy 显示全线程 idle），从进程外部无法进一步取 asyncio 任务栈。本次按「限制爆炸半径」处理——即使根因未知，也不会再出现「无声停摆 20 分钟」；若以后复现，保留 `py-spy dump --native` 输出与 `service_status.json` 的 `heartbeat_age_seconds`。

## 5. 四道加固

### 5.1 supervisor 监控 worker 心跳（进程级兜底）

- 新增 `_read_worker_heartbeat(pid)`：只读打开任务库（`mode=ro`），读该 pid 最近心跳年龄，返回 `HeartbeatReading(age, error)`；
- worker 健康判定改为：**进程存活 + 心跳新鲜**。心跳超过 `WORKER_HEARTBEAT_STALE_SECONDS`（默认 90s）视为不健康，连续 3 次（≈15s）后走既有「强制重启」链路；
- 启动宽限：worker 启动后 `grace + 90s` 内**查询成功但还没有心跳行**时不误杀；
- **读失败不误杀（2026-11-03 修复 P1-1）**：库不存在/被锁/查询失败时 `error` 非空，健康判定直接返回健康且不累计 fail_streak；错误首次记 `supervisor.log` warning，并写入 `service_status.json` 的 `heartbeat_read_error`，不再把「读不到」当成「worker 死了」周期性重启；
- 状态文件 `logs/service_status.json` 的 worker 条目新增 `heartbeat_age_seconds` 与 `heartbeat_read_error`；强制重启原因写 `worker 心跳 Ns 未更新`，同时写 `supervisor.log` 与 `worker.log`（避免只在一处找不到）；
- 同一轮健康检查 + 状态文件只读一次心跳（短缓存），不会每轮读库两次。

> 时序：最多约 `90s（阈值）+ 15s（连续失败）+ 2s（重启延迟）` 后自动拉起，不再需要人工发现。

### 5.2 worker 任务看门狗（任务级兜底）

- 判定口径：本 worker 认领、`status=running`、`updated_at` 超过 `TASK_STALL_TIMEOUT_SECONDS`（默认 **1800s / 30 分钟**）没更新；
- **心跳不再刷新 `updated_at`（2026-11-03 修复 P0-1）**：`_write_heartbeat` 只写 `heartbeat_at`，并显式 `updated_at = TaskQueue.updated_at` 阻止 `onupdate` 生效。此前心跳每 10 秒刷新一次 `updated_at`，看门狗在正常路径下**永远不会触发**；
- 触发后：`asyncio.Task.cancel()` → `_run_task_safe` 捕获取消 → `_fail_stalled_task` 用新会话把任务标 `failed`（错误信息含「超过 N 分钟无进度更新…看门狗强制终止」）+ 补台账 `finished_at` + 广播失败事件；
- **收尾失败保留标记重试（2026-11-03 修复 P1-4）**：只有写库成功才清 `_WATCHDOG_CANCELLED`；写库失败时主循环每个看门狗周期重试，不会留下永久 `running` 僵尸；
- **槽位立即释放**，后续 pending 任务可被认领；重试不自动进行（卡死任务直接重跑很可能再次卡死），用户可以重新提交；
- 进程关闭时的取消（`asyncio.run` 收尾）**不写 failed**：保持 running，交给下次启动的 `_reset_stale_tasks` 按心跳重置（与历史语义一致）；
- 阈值可配（`.env` 的 `TASK_STALL_TIMEOUT_SECONDS`，`0` 关闭，负数/超过 7 天启动即报错）。

> 为什么不是「总运行时长」：f2 下载/全库批量分析可以合法跑几小时；看的是**进度是否还在动**（执行器写进度都会刷新 `updated_at`）。

### 5.3 向量回填失败快路径 + Ollama 熔断

- `_build_material_vectors`：本窗口**所有非空文本都嵌入失败**时，跳过 CLIP 图像编码（任务收尾必判失败，图像编码跑了也白跑；CLIP 首次加载/批量前向是分钟级重型操作）；日志区分「Ollama 连接不可达」与「文本内容/单条数据失败」（2026-11-03 P2-3）；
- `generate_text_embedding`：遇到 `ConnectError/ConnectTimeout`（Ollama 没启动/端口不通）**判一次即熔断**，期间后续文本直接返回 None，不再逐条等超时；`ReadTimeout/RemoteProtocolError` 也触发（用 1/3 时长）；拿到成功响应立即解除熔断；
- 熔断时长可配：`OLLAMA_EMBED_DOWN_COOLDOWN_SECONDS`（默认 30s，2026-11-03 P2-2 从写死 60s 调整）；
- 效果：Ollama 不可用时，一个窗口从「每条等 15s×2 次」缩短到「首条最多 15s，其余即时失败」，且不进入 CLIP 路径，几秒~几十秒内释放槽位。

### 5.4 `/api/tasks` 列表瘦身（页面卡顿）

- 现状：`task_queue.result` 合计 78.8 MB，最大单行 2.9 MB（`tag_health_scan`）；列表按 200 行返回曾是 **30.6 MB/次**响应，前端每 5 秒轮询，实测接口 1.3s；
- 改法（2026-11-03 修复 P1-2/P2-6）：写入任务时由 ORM 事件生成 `result_summary`（≤8KB 小 JSON，保留前端标题/摘要字段），列表**不再读 result 整列**，也跳过 `stage_state`；历史行由服务端启动时回填摘要；仅回填未完成的行才退回旧前缀策略；
- 详情接口 `GET /api/tasks/{id}` 仍返回完整 result（展开/排障用）；
- 实测（真实库 200 行）：响应体 **30.6 MB → 0.163 MB**，SQLite 侧查询 0.033s+0.264s 解析 → **0.048s**（轻列表 0.019s + 前缀 0.029s）。

### 5.5 孤儿台账收尾

- worker 启动时**只收尾「任务行不存在、或任务已不是 running」**的 `task_run_logs` 台账并补 `finished_at`（本次事故留下 id=5 的孤儿行即此类）；任务仍 running 的台账（无论跑多久）不动（2026-11-03 修复 P1-3：原按「开始超过 2 小时」会误标多 worker 下的长任务）。

### 7.2 重启后人工验收（用户手动重启）

1. 正常运行时 `logs/service_status.json` 的 worker 条目应带 `heartbeat_age_seconds` 与 `heartbeat_read_error`，且 `status=ok`；
2. 停掉 Ollama 后手动重启 worker（模拟事故触发条件）：向量回填任务应在**几十秒内**以失败收尾（错误含「文本向量全部生成失败」），任务队列继续认领后续任务——不会再出现长时间占死槽位；
3. 若真出现进程假死：`supervisor.log` 应出现 `[强制重启] worker worker 心跳 Ns 未更新`，`worker.log` 也有对应行，之后 worker 自动重启、`service_status.json` 的 `restarts` 加一；
4. 任务页「运行记录」不再长期显示 `进行中` 的孤儿行（下次 worker 启动按「任务已结束/不存在」规则收尾）。

## 8. 已知边界

| 边界 | 说明 |
| --- | --- |
| 看门狗也在事件循环内 | 若整个事件循环被同步阻塞/GIL 级死锁冻住，看门狗同样跑不了 → 由 supervisor 心跳监控兜底（进程级） |
| 取消不保证中断同步段 | 看门狗 `cancel()` 只能让协程在 `await` 处抛 `CancelledError`；若 handler 正卡在 `asyncio.to_thread` 里的同步代码（如 CLIP 编码），线程可能继续跑到自然结束，但其结果被丢弃、槽位已释放（本次事故的现场卡点也属于这一类，见向量回填快路径） |
| 重启会丢当前任务的内存进度 | 任务由 `_reset_stale_tasks` 重置回 pending，执行器按幂等语义重跑；已落库数据不丢 |
| 卡死任务不自动重试 | 看门狗直接标 failed，避免「卡死→重跑→再卡死」循环；需要时重新提交 |
| 列表 result 摘要 | 超长 result 在列表里是 ≤8KB 摘要（保留标题/摘要字段），完整内容走详情接口；极端情况下摘要只剩 `_truncated` 标记 |
| 根因未完全定位 | 事件循环内部丢唤醒的原因未能从进程外捕获；今后复现请保留 `py-spy dump --native <pid>` 与 `service_status.json` |
