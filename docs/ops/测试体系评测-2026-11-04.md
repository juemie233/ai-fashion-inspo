> 状态：评测报告 + 2026-11-04 P1 修复记录（P1 已全部修复；P2 仍待后续）
> 范围：后端 pytest、前端 vitest、移动端 jest、Playwright e2e、`scripts/ci` 门禁、CI 工作流，以及浏览器插件 / 人脸子服务等未纳入测试的子项目

> 结论：**7.0 / 10（B）**。后端测试体系是明显强项；主要风险不在「用例少」，而在**关键链路覆盖不均、E2E 已失效却不在门禁、前端/移动端没有覆盖率度量、文档与门禁口径漂移**。

## 1. 结论摘要

### 1.1 做得好的地方

1. **后端测试密度高、贴近真实链路**：2,734 个测试函数，实际收集 **2,983 条**用例；约 1,237 个测试直接走 `TestClient` 调 API，128 个测试文件直接读写数据库。不是「只测纯函数」的虚假繁荣。
2. **隔离设计认真**：临时数据库 + 临时存储、逐用例清表、清理生成目录/LanceDB/Cookie 缓存、重置 Ollama 熔断与 worker 全局状态，并用夹具阻止测试误扫真实下载目录（`backend/tests/conftest.py`）。
3. **事故驱动回归**：`test_worker_watchdog.py` 直接覆盖「心跳刷新 `updated_at` 导致看门狗永不触发」这类真实 P0；`test_eager_load_guard.py`、`test_api_serialization_matrix.py` 都是针对具体线上事故写的守卫，注释说明了「为什么这条用例必须存在」。
4. **契约与旅程测试**：`test_api_contract.py` 用 OpenAPI 快照锁字段；`test_journeys.py` 走完整业务链路（上传→打标→向量→垃圾桶→恢复→再删→清空），比单接口用例更能发现「环节衔接」问题。
5. **门禁种类齐全**：本地 `scripts/ci/test.sh` 有 13 项，覆盖 pytest + 覆盖率棘轮、ruff、vulture、mypy 棘轮、迁移链自检、ORM/库漂移、脚本规范、vue-tsc、vitest、eslint 告警棘轮、ts-prune、改动文件格式、移动端 tsc + jest。
6. **移动端有两条别人常漏的检查**：设计令牌/WCAG 对比度扫描，以及「非 `<Text>` 节点下不许有裸字符串」的渲染树断言，专门防真机白屏。

### 1.2 主要风险

| 级别 | 问题 | 直接证据 |
| --- | --- | --- |
| P1 | **E2E 当前是红的，且不在任何门禁里** | 本机实跑 20 条：**17 通过 / 3 失败**（3.0 分钟）；`test.sh` 与 `.github/workflows/ci.yml` 都没有 e2e 步骤 |
| P1 | **覆盖率只有全局阈值，关键模块低于均值也能过** | 总覆盖率 82.93%，但 `worker.py` 77.5%、`generation_service.py` 77.6%、`seedream_client.py` 76.6%、`search.py` 43.4%、`ai_settings.py` 45.5% |
| P1 | **前端/移动端完全没有覆盖率度量** | `web/package.json` 无 coverage 依赖/脚本；`mobile` 只有 jest 无 coverage 门槛 |
| P1 | **浏览器插件与人脸子服务零测试** | `browser-extension/` 9 个源文件、`face-service/app/` 5 个模块，均无测试文件，也不进 CI |
| P1 | **文档与门禁口径已经漂移** | README 写「12 项门禁 / 2299 用例 / 606 前端用例 / 243 移动端用例 / 覆盖率 81.73%」，实测分别是 13 项 / 2,983 / 921 / 246 / 82.93% |
| P1 | **一批写操作/破坏性接口没有直接用例** | 334 条路由中仅 262 条路径字面命中测试（78.4%）；`generate` 的 confirm/retry/regenerate/cancel/cleanup、`admin` 的去重/孤儿清理、`scraper` 的取消/重试/回滚等均未见直接调用 |
| P2 | **前端视图测试大量 mock 掉 composable** | 109 个测试文件里 64 个用 `vi.mock`、151 次 mock；视图测试验证编排，不验证 composable 与页面真实组合 |
| P2 | **E2E 依赖真实库、固定 sleep、CSS 类选择器** | `home.spec.ts` 里 `waitForTimeout(3000)`；断言 `.arco-table`、`.arco-popconfirm` 等 Arco 内部类；不造数、不清理 |
| P2 | **移动端测试进程强制退出** | jest 输出 `A worker process has failed to exit gracefully ... force exited`，说明有定时器/句柄泄漏 |
| P2 | **测试选择能力弱** | 没有 `slow`/`integration` 标记，没有 `--strict-markers`；`pytest.ini` 默认 `-n auto`，想跑快速子集只能手工指定文件 |

## 2. 评测范围与方法

### 2.1 本次实际执行的命令

```bash
# 后端：全量 + 覆盖率门槛 + 最慢用例
cd backend && python -m pytest -q -n auto --cov --cov-fail-under=82 \
  --cov-report=term:skip-covered --durations=15

# 前端：vitest
cd web && node node_modules/vitest/vitest.mjs run --reporter=dot

# 移动端：jest-expo
cd mobile && node node_modules/jest/bin/jest.js --ci --silent

# 端到端：Playwright（后端 18888、前端 17777 均在运行）
cd web && node node_modules/@playwright/test/cli.js test --reporter=list
```

### 2.2 统计口径

- 「测试函数」= 源码里 `def test_` 的数量；「收集用例」= pytest 参数化展开后的数量。
- 测试行数包含夹具、辅助函数与中文注释，不等于有效断言行数。
- 路由覆盖率用「路由路径字符串是否在测试文件中出现」做**粗口径**估算，参数化路径按通配处理；通过 helper/动态拼接调用的接口可能被低估，因此该数字只用于发现盲区，不作为精确覆盖率。
- E2E 使用本机真实数据库与真实服务，不造数；因此结果反映「当前本机数据下的可用性」，不等于 CI 可复现结果。

## 5. 分维度评估

### 5.1 分层结构：偏「集成奖杯」，不是经典金字塔

- 后端 1,237 个测试使用 `client` 夹具（`backend/tests/conftest.py` 的会话级 `TestClient`），占测试函数的 45%；另有 128 个文件直接访问数据库。真正的纯函数单测集中在 83 个 `test_unit_*.py`。
- 前端以 composable/store/组件测试为主，但视图测试大量替换 composable；只有 `generateApi.test.ts`、`poseGallery.test.ts` 两个 API 客户端测试（17 个 API 模块中 2 个）。
- E2E 只有读操作冒烟，没有上传、删除、出图提交这类写链路。

**判断**：对单体 FastAPI + SQLite 项目，集成偏重是合理的——接口层能同时验证路由、序列化、事务与软删除不变量。但代价是**定位成本高、运行时间长**，且纯逻辑（尤其前端）缺少细粒度保护。

### 5.2 覆盖率：总量达标，结构不均

`backend/.coveragerc` 设置了 `precision = 2`，避免了「78.65% 被四舍五入成 79% 却退出码为 0」的门禁漏洞；覆盖率棘轮从 81 提到 82，当前 82.93%。

但覆盖率是**全局单阈值**，关键模块可以低于均值而没人发现：

| 模块 | 覆盖率 | 风险 |
| --- | ---: | --- |
| `app/services/chrome_manager.py` | 22.3% | Chrome 启停/端口管理，E2E 也难覆盖 |
| `app/routers/ai_shared.py` | 28.8% | AI 共享状态/任务编排 |
| `app/scrapers/xiaohongshu.py` | 36.8% | 真实采集器，依赖浏览器 |
| `app/services/person/person_groups.py` | 37.8% | 人物分组 |
| `app/services/person/photo_sets.py` | 39.6% | 照片集 CRUD |
| `app/routers/search.py` | 43.4% | 搜索接口 |
| `app/routers/ai_settings.py` | 45.5% | Prompt / 模型配置 |
| `app/routers/ai_quality.py` | 52.6% | 质量审核接口 |
| `app/services/seedream_client.py` | 76.6% | 云端出图付费调用 |
| `app/worker.py` | 77.5% | 任务队列主循环/看门狗 |
| `app/services/generation_service.py` | 77.6% | 出图批次状态机 |

**尤其值得注意的是**：最近改动最频繁的出图链路（`generation_service` / `seedream_client` / `worker`）都在 77% 左右，低于总均值；而 `search`、`ai_settings`、`ai_quality` 这些用户直接触达的接口低于 55%。

覆盖率没有分支覆盖（branch coverage），因此「行覆盖了但分支没走到」的情况统计不到。

### 5.3 接口覆盖：78.4% 的路径有直接调用证据

用 334 条路由与测试文件中的路径字面量比对：

- **262 / 334 = 78.4%** 有直接调用证据；
- 缺口集中在写操作与运维接口：

| 路由文件 | 未见直接调用的例子 |
| --- | --- |
| `generate.py` | `POST /runs/{id}/confirm`、`/retry`、`/regenerate`、`/cancel`、`/runs/cleanup`、`/prompt/preview` |
| `scraper.py` | `POST /tasks/{id}/cancel`、`/retry`、`/tasks/retry-failed`、`f2-tasks/{id}/rollback`、`chrome/start`、`chrome/stop`、`chrome/status` |
| `admin.py` | `backup/status`、`largest-files`、`cleanup-orphans`、`find-duplicates`、`deduplicate`、`vector-backfill` |
| `bloggers.py` | `stats`、`batch/delete`、`face-candidates`、`works`、`insights`、`similar`、`bind-face` |
| `models.py` | `top`、`suggestions`、`photo-sets` 的增删改查 |
| `ai_models.py` | `models/pull`、`detail/update/copy`、`active`、`gpu-stats`、`unload-model` |

其中 `generate` 的 confirm/retry/regenerate/cancel/cleanup 是**付费出图链路的状态机入口**，`admin` 的去重/孤儿清理是**破坏性运维操作**，`bloggers/batch/delete` 是批量删除。它们没有直接用例，只有服务层或间接覆盖，属于「改坏了不一定有人喊」的区域。

**口径限制**：路径字面量匹配会低估通过 helper/变量拼接调用的接口；上表应理解为「没有直接调用证据」，不是「绝对零覆盖」。要精确结论需要 coverage.py 的 per-route 或 OpenAPI 驱动用例，本次不做。

### 5.4 隔离与确定性：后端优秀，E2E 不足

**后端（强）**：

- `conftest.py` 在导入 `app.*` 之前设置 `DATABASE_URL`、`STORAGE_ROOT`、`IMAGES_DIR`、`LANCEDB_DIR` 等，避免写入真实存储；
- 逐用例清空 30 张表，并递归清理 `images/thumbnails/videos/trash/person_photos/generated/lancedb/cookies` 等目录；
- 重置 Cookie 校验缓存、LanceDB 连接、Ollama 熔断、worker 看门狗/台账全局变量；
- `guard_f2_merge_off_real_roots` 夹具阻止「我的喜欢/收藏」合并误扫真实 `Download/douyin` 目录，越界直接失败；
- xdist 每个 worker 独立临时目录，测试之间不共享文件。

**后端（限制）**：

- 全局 mock 了 CLIP 图像编码（`_encode_image_sync` 返回固定向量），向量链路只验证「登记/落库/回填/搜索」的管道，不验证语义质量；
- CI 卸载 `hnswlib`，只走 O(n²) 降级路径；HNSW 主路径在 CI 中未被验证；
- `pytest.ini` 的 `filterwarnings` 忽略 `ResourceWarning`、`unclosed Transport` 等，可能掩盖异步资源泄漏；
- 后端测试没有钉时区（前端 vitest 钉了 `Asia/Shanghai`），少数用 `datetime.now()` 取本地日期的用例在 UTC CI 上存在跨日边界风险（如 `test_task_run_log.py`、`test_inspiration_service.py`）。

**E2E（弱）**：

- 使用本机真实后端与真实数据库，不造数、不清理；
- `home.spec.ts` 用 `waitForTimeout(3000)` 等固定时间，而不是等待具体网络/渲染条件；
- 断言依赖 Arco 内部 class（`.arco-table-th`、`.arco-popconfirm`）与中文文案，UI 一改就断；
- `workers: 1` 串行，20 条要 3 分钟；失败时 trace 保留，但没有任何「失败自动重跑/隔离」机制。

### 5.5 断言与用例质量

**优点**：

- 后端 8,112 个 `assert`、317 处 `pytest.raises`、67 个 `parametrize`；断言多为行为结果（状态码、字段、DB 行、文件是否存在），不是「调用过某个函数」。
- 关键用例写了「为什么需要这条」的长注释，例如 `test_api_serialization_matrix.py` 明确要求「返回素材里至少一条带人物关联，否则用例等于空跑」——这是很少见的、防止假通过的设计。
- 有专门的守卫测试：`lazy="raise_on_sql"` 漏预加载必须当场点名报错；看门狗心跳不得刷新 `updated_at`；垃圾桶三字段同真同假。

**不足**：

- 前端视图测试把 5 个 composable 全部 mock 掉（如 `ScraperView.test.ts`），只验证「页面调用顺序与渲染」，composable 与页面之间的真实组合没有覆盖；这类测试改 props/emit 就会碎，但抓不到 composable 内部回归。
- E2E 断言偏浅：「至少一行」「某个按钮可见」「没有渲染错误」；没有对数据正确性、状态迁移、写操作结果做断言。
- 没有快照测试（前后端都没有），没有 mutation testing，也没有针对 API 延迟/吞吐的性能回归；`test_performance.py` 测的是性能工具本身，不是系统 SLO。
- 测试文件偏大：`test_f2_import_execute.py` 1,462 行、`test_f2_import_status.py` 1,127 行、`test_task_runners.py` 1,069 行；单文件 40+ 用例，失败时定位与并行拆分都更困难。

### 5.6 门禁与 CI：本地强、CI 弱、口径漂移

**本地 `scripts/ci/test.sh`（13 项）**：

1. pytest + 覆盖率 ≥82%
2. ruff（app + scripts）
3. vulture（置信度 80，0 条）
4. mypy 棘轮（9 个已清零模块）
5. 迁移链空库自检
6. ORM ↔ 现有库漂移
7. 脚本规范（只读连接 / argparse）
8. vue-tsc
9. vitest
10. eslint `--max-warnings 34`
11. ts-prune 死代码基线
12. 改动文件格式
13. 移动端 tsc + jest

**CI（`.github/workflows/ci.yml`）**：

- web job：eslint、vitest、vue-tsc、ts-prune；
- mobile job：tsc、jest；
- backend job：ruff、vulture、mypy、迁移链自检、脚本规范、pytest + 覆盖率；
- **缺**：`check-web-format.mjs`（格式）、`check_alembic_drift.py`（真实库漂移）、**全部 e2e**。

**触发面**：

- CI 只在 GitHub 镜像触发（`on: push/pull_request`）；`origin` 主推是 Gitee，Gitee 没有 CI；
- GitHub 推送曾多次因本机代理失败，意味着「推 Gitee 成功」不等于「CI 跑过」；
- 因此**真正的门禁是本地 `bash scripts/ci/test.sh`**，而它不包含 e2e，也不包含「前端覆盖率」。

**提交钩子**：Husky `pre-commit` 只对暂存的前端文件跑 `lint-staged`（eslint --fix + prettier），不跑后端 lint/测试，也不跑类型检查。这符合「快速提交」的取舍，但意味着后端问题只能靠手动跑门禁或 CI 发现。

**文档漂移**（README `## 自动化测试`）：

| README 写法 | 实测 |
| --- | --- |
| 「一键运行全部门禁（12 项…）」 | `test.sh` 实为 **13 项** |
| 后端「2299 用例」 | 收集 **2,983 条**（2,734 个函数） |
| 前端「606 用例 / 75 个文件」 | **921 / 109** |
| 移动端「243 用例 / 24 个文件」 | **246 / 25** |
| 覆盖率「当前 81.73%；棘轮 81」 | **82.93%；棘轮 82** |
| `test.sh` 注释「当前 82.73%」 | 实测 **82.93%** |

这类漂移不会让测试失败，但会让新成员对「现在到底有多少保护」产生错误判断，也会让覆盖率棘轮的推进失去记录。

- **视图测试减少全量 mock**：至少保留 1–2 条「真实 composable + mock API」的集成测试，覆盖页面与状态层的组合。
