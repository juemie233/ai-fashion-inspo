# 运行产物与实验数据管理

> **状态**：现行｜编写日期 2026-11-01｜适用：Windows 单机本地部署
> **一句话**：项目产物分四类——**源码与结论入库，业务数据放外部盘并备份，实验证据放实验目录并留清单，日志/缓存定期清**。
> **目标**：换机器、删盘、半年后回看时，仍能回答「这是什么、用了什么参数、结论是什么、能不能重建」。

---

## 0. 速查

| 你要存的东西 | 放哪 | 入 git | 保留 |
| --- | --- | --- | --- |
| 代码、迁移、文档报告 | 仓库 `docs/` | ✅ | 永久 |
| SQLite 活库 | `DATABASE_URL` 指向的库（当前在外部盘） | ❌ | 随每日备份 |
| 素材原图 / 视频 / 向量 | `STORAGE_ROOT/` | ❌ | 随备份；源文件可再采集 |

| 实验对比图 / 中间产物 | `STORAGE_ROOT/poc/<日期>-<主题>/` | ❌ | 专题结项后归档或删 |
| 实验清单 | 实验目录 `manifest.json`（小体积可复制进 docs） | 视体积 | 永久 |
| 测试/实验结论 | `docs/<分类>/<主题>-<日期>.md` | ✅ | 永久 |

## 1. 四条管理原则

1. **可重建的进缓存区，不可重建的进备份**：缩略图、关键帧、出图候选能重算，不值得长期保存；DB、原图、向量、配置丢了就没了。
2. **单一落点**：同一种产物只允许一个权威位置。DB 路径统一走 `settings.db_file_path`，不要用 `storage_root.parent / "fashion_inspo.db"` 猜（`STORAGE_ROOT` 指到别的盘时，猜出来的是盘根的空库）。
3. **结论入库，证据出库**：报告（Markdown）进 git；对比图、中间产物、逐样本大文件放外部盘，报告里只写路径 + 清单。
4. **敏感数据不出内网、不进仓库**：`.env`、Cookie、Chrome profile、人脸特征、备份包都不入 git（备份含密钥，不要放公共网盘）。

## 3. 目录与命名

### 3.1 仓库内（入 git 的只有文档与代码）

```text

│  ├─ overview/ features/ mobile/ pose/ ops/ archive/
│  └─ 文档索引.md
├─ logs/                     # 只放服务日志（gitignore）
└─ backend/storage/          # 本地兜底；只放 _db_backups（gitignore）
```

### 3.2 外部存储根（`STORAGE_ROOT`，当前指向 G 盘）

```text
G:/fashion-inspo-storage/
├─ images/  videos/  trash/          # 原图、视频、垃圾桶
├─ thumbnails/  keyframes/  generated/  # 可再生物
├─ person_photos/  person_thumbnails/
├─ lancedb/                          # 向量库
├─ poc/                              # 实验证据根

│     ├─ logs/
│     └─ manifest.json
```

> `poc/` 位于 `STORAGE_ROOT` 下时，备份脚本的**全量镜像会把它一起带走**（只排除 `_crop_backup`、`logs`、`tmp`、`lancedb` 等）。若不想让实验图占备份空间，应把 `poc/` 移出 `STORAGE_ROOT`，或加入备份脚本的 `//XD` 排除清单。

### 3.3 备份目录（E 盘）

```text
E:/fashion-inspo-backups/
└─ 2026-11-01_030000/
   ├─ fashion_inspo.db           # 一致性快照
   ├─ fashion_inspo.sql          # 明文双保险
   ├─ storage/                   # 业务目录镜像
   ├─ backend/.env 等运行时配置
   ├─ git_head.txt  manifest.json  SUCCESS
   └─ backup.log
```

## 4. 数据库文件管理

### 4.1 唯一口径

- 活库位置由 `DATABASE_URL` 决定，代码统一用 `settings.db_file_path` 推导；**脚本禁止自行拼路径**；
- 库文件与 `storage/` 可以不在同一盘：`STORAGE_ROOT` 指到 G 盘时，`storage_root.parent` 是盘根，不能拿来推算 DB；
- 库文件、`-wal`、`-shm` 都不入 git（`.gitignore` 已覆盖 `*.db*`）。

### 4.2 改库前的快照

- 手工改数据 / 跑一次性回填前，先在 `backend/storage/_db_backups/` 放一份快照，文件名写清「为什么」；
- 快照是**本地临时保险**，不进正式备份、不属于 RPO 口径；
- 保留规则（2026-11-01 起由脚本执行）：**30 天 / 最多 20 份 / 总量 ≤ 512 MB**，三条任一命中即删，
  最新一份永不删。单份快照 400~500 MB，只靠份数/天数压不住磁盘；
  命令：`python scripts/ops/cleanup_artifacts.py --target snapshots --max-total-mb 512`（默认 dry-run，`--apply` 才删）。
- 2026-11-01 实测：已从 911 MB / 2 份降到 **482 MB / 1 份**（删掉 10-20 的 drift 快照，保留 10-24 的删空博主快照）。

### 4.3 正式备份

- 备份包含：DB 快照 + SQL 明文 + `storage/` 业务目录 + 运行时配置 + `git_head.txt` + `manifest.json`；
- 不包含：`logs/`、`tmp/`、`_crop_backup`、Cookie/Chrome profile、Ollama 模型、虚拟环境、代码；
- 保留：日备 7 份 + 周备 4 份 + 失败 3 份；RPO ≤ 1 天；
- 详细命令、校验三层、恢复 12 步见 [数据备份与恢复](数据备份与恢复.md)。

### 4.4 结构变更

- 结构变更只走 Alembic，见 [数据库迁移与回滚](数据库迁移与回滚.md)；
- 从旧备份恢复后**必须** `alembic upgrade head`，否则新代码查新列直接报错；
- worker 不跑迁移，由 API 进程统一执行。

## 5. 实验管理

### 5.1 生命周期

```text
立项 → 建实验目录 → 跑实验（产物落 outputs/） → 写 manifest.json
     → 写报告（docs/） → 判断结论 → 结项/归档 → 清理中间产物
```

**硬性要求**：只要跑了一次测试、对照、参数扫描或 PoC，就必须留下报告（CLAUDE 文档要求）；一次性诊断豁免（结论写提交信息）。

### 5.2 `manifest.json` 规范

每个实验目录放一份，字段如下（缺失可写 `null`，但键要稳定）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `date` | string | `YYYY-MM-DD` |
| `goal` | string | 这次验证什么 |
| `hypothesis` | string | 预期是什么 |
| `not_in_scope` | string | 明确不验证什么 |
| `git_head` | string | 代码提交号（`git rev-parse --short HEAD`） |
| `model` / `model_version` | string | 模型名与版本 |
| `params` | object | steps / cfg / 分辨率 / seed / 并发 / 阈值等 |
| `samples` | int | 样本数 |
| `inputs` | array | `[{id, sha256, source}]`；大文件只留 ID + 哈希 |
| `outputs` | object | `{dir, count, bytes}` |
| `metrics` | object | 量化指标（姿势分、身份相似、耗时、失败率） |
| `verdict` | string | 成功 / 失败 / 部分成功 |
| `next` | string | 下一步或停止理由 |
| `report` | string | 报告相对路径 |

示例：

```json
{
  "date": "2026-10-31",
  "goal": "验证 E3-Depth 路线能否保持本人与服装",
  "hypothesis": "Depth 约束能固定姿势，身份由换脸补",
  "git_head": "abc1234",
  "model": "sd_xl_base_1.0 + controlnet-union-sdxl-1.0-pro_max",
  "params": { "steps": 30, "cfg": 5.0, "size": "832x1216", "seed": 20261031 },
  "samples": 10,
  "inputs": [{ "id": "INSP-001", "sha256": "9f2c…" }],
  "outputs": { "dir": "G:/fashion-inspo-storage/poc/2026-10-31-e3-depth-10样本/outputs", "count": 10 },
  "metrics": { "pose": 3.7, "identity": 0.81, "seconds_per_image": 42 },
  "verdict": "部分成功：姿势可用，服装不保",
  "next": "停止该方向，结论进结项报告",
  "report": "docs/pose/换姿势实验报告-2026-10-31-E3-Depth路线10样本.md"
}
```

### 5.3 报告规范

报告放 `docs/<分类>/`，至少包含：

1. **目的与假设**：验证什么、不验证什么；
2. **生成流程**：模型/档位、关键参数、数据来源与样本量、随机种子；
3. **量化结果**：指标表 + 逐样本结果；
4. **图片对比**：写清 storage 路径（图不入库）；能用一张拼图说明的，不要让人开十个文件；
5. **判断与下一步**：成功/失败/部分成功，下一次改什么。

报告里**不要复制大段产物内容**，只放路径与摘要；`manifest.json` 承担参数与索引。

### 5.4 输入与产物留存

- **输入**：原素材本就在素材库，实验目录只记素材 ID + 哈希，不复制原图（避免双份占用）；
- **产物**：`outputs/`、`compare/` 保留到专题结项；结项后可整体归档到 `poc/_archive/`，或按结论删除；
- **可再生物**（中间 depth 图、临时裁剪）随时可删，报告结论不依赖它们；
- **对比图**：至少保留报告里引用的那几张，命名与报告章节对应（`fig1-overview.jpg`）。

### 5.5 结项与归档

- 报告状态改为「已结项」，在结项报告里列资产清单（目录、体积、是否保留）；
- 同一专题的多个实验目录可整体移动，不要逐个散落；
- 结项后不再向旧目录追加新文件（避免“已结项但还在长”）。

### 5.6 反例

- ❌ 把对比图直接提交到 `docs/`：仓库膨胀（`.gitignore` 现在已挡 `docs/**/*.{jpg,jpeg,png,webp,gif}`，靠 `-f` 强推才算违规）；
- ❌ 报告只写“效果不错”，没有参数、样本数、种子；
- ❌ 实验产物留在 `logs/` 或仓库根目录，成为无主文件；
- ❌ 用「已删除的目录」作为报告唯一证据。

## 6. 测试结果管理

### 6.1 三档，不要都写成文档

| 档位 | 场景 | 存放 | 保留 |
| --- | --- | --- | --- |
| **日常门禁** | `pytest`、`vitest`、`vue-tsc`、`ruff`、`alembic check` | 只跑不存；失败日志由 CI artifact 保留 | 7 天 |
| **功能验收** | 真机逐页、E2E、适配三查（小屏/字体/深色） | 并入功能文档的「实施 / 验证」节 | 永久 |
| **实验 / 基准** | 参数扫描、A/B、性能对比、模型对比 | 独立报告 + `manifest.json` | 永久 |

### 6.2 不提交的测试产物

- `.coverage`、`.coverage.*`、`htmlcov/`；
- `.pytest_cache/`、`__pycache__/`；
- `web/test-results/`、`web/playwright-report/`；
- 截图、录屏、trace、临时数据库、临时 storage。

> 测试必须使用临时数据库/临时存储，不能触碰真实数据；误写到真实存储时用 `python scripts/data/clean_test_files.py --delete` 清理。

### 6.3 失败日志与 CI

- CI 在失败时上传 `backend/pytest.log` 为 artifact，保留 7 天（`.github/workflows/ci.yml`）；
- 本地失败：贴关键堆栈到提交信息或修复提交，不要把整份日志入库；
- 覆盖率只作为门禁棘轮（CI 检查），不提交覆盖率报告。

### 6.4 功能验收记录模板

并入功能文档即可，至少写：

```text
设备/系统：nova 7 Pro / Android 12
版本：0.8.0（versionCode 33）
日期：2026-11-01
范围：素材库/搜索/详情/采集/设置 + 深色模式
结果：逐页通过；360×640、字体 1.3×、深色三查通过
遗留：无 / 或列出已知问题
```

### 6.5 一次性诊断

- 脚本用完即删（`git status` 自查不残留）；
- 结论写进提交信息或 TODO；
- 确需留档的，提炼成 `docs/ops` 的排障条目，而不是保留原脚本。

## 7. 日志与临时文件

### 7.1 服务日志

- 只允许 `backend.log`、`frontend.log`、`worker.log`、`supervisor.log`、`face-service.log` 及其轮转文件；
- supervisor 单文件 10 MB 轮转、保留 5 份（backend + worker 各约 55 MB，属正常占位，不要当垃圾删）；
- 日志不入备份、不入 git；排障手册见 [本地运行与排障](本地运行与排障.md)。

### 7.2 一次性日志

- f2 抓取、A/B 实验、脚本输出的临时日志**不要放 `logs/`**；
- 放实验目录的 `logs/`，结论落地后删除；
- 清理工具：`python scripts/ops/cleanup_artifacts.py`（默认只预览，规则见 §9）。
- 2026-11-01 清理结果：`logs/` 从 **152 个文件 / 114 MB** 降到 **74 个 / 107 MB**——删掉 78 个一次性日志
  （`ab-*.log`、`backfill_*.log`、`*_test.log` 等，合计 7 MB；`supervisor-bootstrap.log` 被 supervisor 占用未能删）。
  剩余 107 MB 基本是 5 份轮转 × 2 个服务，属策略内。58 个 `f2-*.log` 共 124 KB 默认保留
  （采集排障第一手材料）；要一起清加 `--include-f2`。

### 7.3 临时脚本与临时文件

- 优先放系统临时目录或已 gitignore 的位置；
- 不得在仓库根、`scripts/`、`storage/` 里留下“看起来像交付物”的临时文件；
- 提交前 `git status` 自查。

## 8. Git 边界

### 8.1 必入 / 必不入

| 必入 | 必不入 |
| --- | --- |
| 代码、迁移、测试 | DB 及 `-wal`/`-shm` |
| `docs/**/*.md` | `storage/`、`logs/` |
| 小体积清单（manifest、CSV 指标） | `.env`、Cookie、Chrome profile |
| `.env` 的脱敏示例（`backend/.env.example`，已补） | 模型权重、f2 下载、实验大图 |
| 设计令牌、配置默认值 | 运行时被后端重写的配置（见 §8.3） |

### 8.2 当前忽略规则（2026-11-01 已补齐）

已覆盖：`*.db`、`storage/`、`logs/`、`*.log`、`.coverage*`、`web/test-results/`、`web/playwright-report/`、`docs/decisions/`、`prompt_configs.json`、`face-service/models/`。

**文档图片（本轮已修）**：原来只写了 `docs/*.jpg`，只挡 docs 根目录，`docs/pose/*.jpg` 这类子目录的图会被误提交。现在改为逐条列扩展名（gitignore 不支持 `{a,b}` 花括号展开）：

```gitignore
docs/*.jpg
docs/**/*.jpg
docs/**/*.jpeg
docs/**/*.png
docs/**/*.webp
docs/**/*.gif
```

验证方式（改完规则跑一次）：

```bash
mkdir -p docs/pose/_tmp && echo x > docs/pose/_tmp/a.png
git check-ignore -v docs/pose/_tmp/a.png   # 应输出命中的规则行
rm -rf docs/pose/_tmp
```

**立场**：实验图一律放 `STORAGE_ROOT/poc/`，`docs/` 不存图（报告只写路径）。确实要入库的示意图（如架构图）用 `git add -f <文件>` 并在提交信息里说明理由。

**仍存在的边界**：`storage/` 在外部盘（`STORAGE_ROOT=G:`）时，仓库内的 `backend/storage/` 只剩 `_db_backups/`；该目录已由 `storage/` 规则覆盖，无需单独写。

### 8.3 运行时被重写的配置

- `backend/model_configs.json` 已入库，但运行时会被后端改写（界面改模型参数/超时会落盘）；
- 每次在界面改参数都会产生 git diff，存在误提交风险；
- **2026-11-01 决定：接受 diff + 提交前人工确认**（不改代码、不迁 `model_configs.local.json`）。
  理由：该文件只含模型参数与超时，无密钥；churn 是「偶发一行数字变化」，比动配置读写层的风险小；
- 执行方式（已写进 `CLAUDE.md` 的提交注意事项）：
  ```bash
  git diff backend/model_configs.json      # 提交前看一眼
  git checkout -- backend/model_configs.json   # 不是有意改默认值就丢掉
  ```
- **什么时候该改成迁出方案**：若出现「多台机器共用同一份配置」或「界面改参频繁到每次提交都要处理」，
  再改成「库内文件只存默认值 + gitignore 的 `model_configs.local.json` 存覆盖值」。

### 8.4 敏感信息

- `.env`、备份包含 API Key；不要放公共网盘、不要贴进 issue/聊天；
- 人脸特征属生物特征，只在本地库内使用，不随素材导出；
- 分享报告时先确认没有贴出本机绝对路径中的用户名/密钥。

## 9. 保留期与清理

| 对象 | 位置 | 建议保留 | 清理方式 |
| --- | --- | --- | --- |
| 服务日志 | `logs/*.log*` | 自动 5 份 | supervisor 轮转 |
| 一次性日志 | `logs/` 下非服务日志 | 结论落地即删 | `python scripts/ops/cleanup_artifacts.py [--apply] [--include-f2]` |
| DB 改前快照 | `backend/storage/_db_backups/` | 30 天 / 20 份 / 总量 512 MB | `python scripts/ops/cleanup_artifacts.py --target snapshots --max-total-mb 512` |
| 正式备份 | `E:/fashion-inspo-backups/` | 日 7 + 周 4 + 失败 3 | 备份脚本自动 rotation |
| f2 下载 | `F2_DOWNLOAD_ROOT` | 入库成功后按需 | `--prune-downloads` |
| 出图候选 | `STORAGE_ROOT/generated/` | 终态超期自动清 | 现有 30 秒调度循环 |
| 关键帧/缩略图 | `STORAGE_ROOT/{keyframes,thumbnails}` | 随素材 | 删素材时一并清理 |
| 实验产物 | `poc/<实验>/` | 专题结项 | 归档或删除 |
| 测试缓存 | `.pytest_cache/`、`test-results/` | 随时 | 直接删 |
| 一次性排查日志 | 仓库 `logs/`（历史遗留） | 结论落地即删 | 同上清理脚本（默认不删 f2 日志） |

### 9.1 每月巡检

```bash
# 服务与资源
bash scripts/ops/status.sh

# 体积 Top（外部盘按实际路径替换）
du -sh logs backend/storage/_db_backups backend/storage 2>/dev/null
du -sh "$STORAGE_ROOT"/{images,videos,thumbnails,generated,poc} 2>/dev/null

# 无主日志 / 过期快照（先预览，确认后加 --apply）
python scripts/ops/cleanup_artifacts.py
ls -lt logs/*.log | tail -20
ls -lt backend/storage/_db_backups

# 实验报告与产物的对应关系
grep -rho "G:/fashion-inspo-storage/poc/[^ )\`]*" docs | sort -u
```

### 9.2 删除前检查

1. 该产物是否被报告引用？先改报告再删；
2. 是否在备份里还有一份？`poc/` 在 `STORAGE_ROOT` 下会被备份带走；
3. 是否可重建？缩略图/关键帧可以，实验输出不一定；
4. 删除动作先 dry-run 列清单，确认后再执行（`scripts/ops/cleanup_artifacts.py` 默认就是 dry-run）。

## 10. 与备份 / 恢复的关系

- **备份覆盖**：DB、`storage/` 业务目录（含 `generated/`、`keyframes/`、若存在则 `poc/`）、运行时配置、`git_head.txt`；

- **实验结论不依赖备份**：报告 + manifest 必须能脱离图片独立阅读；图片删了，结论仍成立。
