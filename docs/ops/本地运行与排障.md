# 本地运行与排障手册

> **状态**：现行｜编写日期 2026-11-01｜依据 `scripts/ops/`、`backend/app/worker.py`、`backend/app/routers/health.py`
> **适用**：Windows 11 单机部署（后端 + 前端 + worker + 人脸识别 + Ollama 均在本机）。
> **原则**：服务启停由用户手动执行；本文只给命令与判断依据，不做自动重启。

---

## 1. 服务清单与端口

| 服务 | 端口 | 启动方式 | 由谁守护 | 健康判定 |
| --- | --- | --- | --- | --- |
| 后端 API | **18888** | `uvicorn app.main:app` | supervisor | `GET /api/health` |
| Web 前端 | **17777** | `vite` | supervisor | `GET /` |
| worker | 无端口 | `python -m app.worker` | supervisor | `service_heartbeats` 表心跳（supervisor 读心跳年龄，超 `WORKER_HEARTBEAT_STALE_SECONDS` 秒视为假死并重启） |
| 人脸识别子服务 | **18889** | `face-service/.venv` + uvicorn | **不由 supervisor 管**，restart.sh 单独拉起 | `GET /health` |
| Ollama | **11434** | 用户手动启动 | 无 | `GET /api/tags` |

> 端口以 `backend/.env` 的 `PORT` 为准（默认 18888）；前端端口固定 17777；人脸与 Ollama 端口见各自配置。改端口后 supervisor / restart.sh 会跟随 `.env`，但手工命令与前端代理需同步改。

## 2. 启停命令

在仓库根目录执行：

```bash
# 全量重启（先杀后启，含 worker 与 face-service）
bash scripts/ops/restart.sh

# 幂等确保服务在跑（只补缺失的，已在运行则跳过）
bash scripts/ops/ensure-services.sh

# 查看健康状态（优先走 API，失败回退 supervisor 状态文件）
bash scripts/ops/status.sh
```

手工启动（调试单服务时）：

```bash
# 后端（在 backend/ 下）
python -m uvicorn app.main:app --host 127.0.0.1 --port 18888

# worker（在 backend/ 下）
python -m app.worker

# 前端（在 web/ 下）
npm run dev        # 或 node node_modules/vite/bin/vite.js --port 17777

# 人脸服务（见 face-service/README.md）
cd face-service && .venv/Scripts/python -m uvicorn app.main:app --host 0.0.0.0 --port 18889
```

> **不要给后端加 `--reload`**。Windows 下 uvicorn reload 走 `multiprocessing.spawn`，文件变更时可能以 `OSError: [WinError 87]` 崩溃；强杀 reloader 还会留下孤儿 spawn worker 占着端口。restart.sh 用「先杀后启」拿最新代码，不需要 reload。

## 3. 健康检查

| 入口 | 返回 | 用途 |
| --- | --- | --- |
| `GET /api/health` | 基础存活 + schema 版本握手 | 前端启动比对、脚本探活 |
| `GET /api/health/services` | 后端 / 前端 / worker 状态、磁盘内存、日志大小、告警列表 | 管理页与 `status.sh` |
| `bash scripts/ops/status.sh` | 终端可读汇总（数据来源、服务、资源、告警） | 日常巡检 |

`/api/health/services` 的告警口径：前端无响应、worker 心跳超时、磁盘 ≥90%、内存 ≥90%。

> worker 进程级健康由 supervisor 判定：除进程存活外还读 `service_heartbeats` 心跳年龄
> （默认 90s 阈值，连续 3 次不健康后强制重启）。`service_status.json` 的 worker 条目带
> `heartbeat_age_seconds`，可直接看出「卡了多久」。任务级卡死由 worker 任务看门狗处理
> （`TASK_STALL_TIMEOUT_SECONDS`，默认 30 分钟无进度 → 取消并标 failed）。

## 4. 日志与状态文件

日志目录 `logs/`（当前固定为仓库根目录）：

| 文件 | 内容 |
| --- | --- |
| `backend.log` / `.1`…`.5` | 后端 stdout/stderr，10 MB 轮转 |
| `frontend.log` / `.1`… | Vite 输出 |
| `worker.log` / `.1`… | worker 轮询、任务执行、心跳、崩溃恢复 |
| `supervisor.log` | 守护进程的健康检查、重启、资源告警 |
| `supervisor-bootstrap.log` | supervisor 自身启动输出 |
| `face-service.log` / `.1`…`.3` | 人脸子服务（进程内 10 MB × 3 轮转）；启动行在 `face-service-bootstrap.log` |
| `analyze-YYYY-MM-DD.log` | worker 按天任务日志（保留 `LOG_RETENTION_DAYS`，默认 30 天） |
| `f2-<时间戳>-<pid>.log` | f2 子进程原始输出（不再直灌 worker.log；失败时 worker.log 会附最后 20 行） |
| `service_status.json` | 各服务 PID / 状态（restart.sh 兜底读取）；worker 另带 `heartbeat_age_seconds` |
| `supervisor.pid` | supervisor PID |

> 日志格式统一为 `时间 [级别] logger:行号 [req=<请求ID> task=<任务ID>] 消息`。
> API 每个响应都带 `X-Request-ID` 头，前端报错提示里也会显示请求 ID，可直接
> `grep 'req=<id>' logs/backend.log` 对齐一次请求。排障细节见
> [日志系统整改说明](日志系统整改-2026-11-02.md)。

常用排查：

```bash
tail -n 50 logs/backend.log
tail -n 50 logs/worker.log
grep -nE "ERROR|Traceback|locked" logs/backend.log | tail -20
grep 'req=abc123def456' logs/backend.log          # 按请求 ID 串起一次请求
grep 'task=#739' logs/worker.log                  # 按任务 ID 串起一次任务
curl -s http://127.0.0.1:18888/api/health
curl -s http://127.0.0.1:18888/api/health/services
```

需要 DEBUG 细节（静默降级路径/HTTP 请求/SQL）时，在 `backend/.env` 加
`LOG_LEVEL=DEBUG` 后**手动重启**后端/worker；结构化排障可加 `LOG_FORMAT=json`。
日志与台账清理：`python scripts/ops/cleanup_artifacts.py`（默认只预览，`--apply` 才删）。

## 5. 环境变量基线（`backend/.env`）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `HOST` | 127.0.0.1 | 手机连局域网时必须改 `0.0.0.0`，否则真机连不上 |
| `PORT` | 18888 | 后端端口 |
| `STORAGE_ROOT` | `backend/storage` | 素材/缩略图/视频/垃圾桶/LanceDB 根目录；迁移存储后子目录会跟随 |
| `DATABASE_URL` | SQLite 文件 | 默认 `backend/storage/...db`；必须保持文件型 SQLite |
| `API_KEY` | 空 | 为空只放行回环地址；破坏性接口需要 `X-API-Key` |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | 视觉/文本模型服务 |
| `FACE_SERVICE_URL` | `http://127.0.0.1:18889` | 人脸子服务 |
| `WORKER_CONCURRENCY` | 1 | 同时执行任务数；建议 1~2 |
| `ANALYZE_CONCURRENCY` | 见配置 | 批内分析并发；越大显存压力越大 |
| `F2_DOWNLOAD_ROOT` | f2 默认 Download | f2 产物盘符（实测 19 GB 级） |
| `F2_IMPORT_AUTO_ENABLED` | false | 是否每日自动回捞 |
| `LOG_LEVEL` | INFO | 日志级别；`DEBUG` 打开静默降级路径/HTTP 请求/SQL 明细 |
| `LOG_FORMAT` | text | `json` 时一行一条结构化日志（本地排障用） |
| `SLOW_REQUEST_MS` | 1000 | 慢请求阈值（毫秒），超过记 WARNING |
| `LOG_RETENTION_DAYS` | 30 | `analyze-*.log` 按天日志保留天数 |
| `TASK_RUN_LOG_RETENTION_DAYS` | 90 | `task_run_logs` 台账保留天数 |
| `TASK_STALL_TIMEOUT_SECONDS` | 1800 | 任务看门狗：无进度更新超过该秒数 → 取消并标 failed（0=关闭） |
| `WORKER_HEARTBEAT_STALE_SECONDS` | 90 | supervisor：worker 心跳超过该秒数视为假死，连续 3 次后强制重启 |

> `.env` 已 gitignore；脱敏示例值见 `backend/.env.example`（不含真实密钥），新增配置项时请同步更新示例。

## 6. 故障判断表

| 现象 | 先看 | 处理 |
| --- | --- | --- |
| 前端打不开 | `logs/frontend.log`；`web/node_modules` 是否存在 | `cd web && npm install`；再 `bash scripts/ops/ensure-services.sh` |
| 后端 502 / 连不上 | `logs/backend.log`；`netstat -ano \| grep 18888` | 看启动异常（迁移失败最常见）；端口被占则先停旧进程 |
| **改了代码但行为没变** | 是否有孤儿 uvicorn spawn worker / 旧 supervisor | `restart.sh` 会级联杀进程树；不要用 `--reload`；确认 `service_status.json` 里的 PID 已更新 |
| 页面能开但数据全空 | `curl /api/health`；手机端看设置里的后端地址 | 后端未启动 / 手机与电脑不同网段；后端绑了 127.0.0.1 时手机必须改 `HOST=0.0.0.0` |
| 任务一直排队 | worker 是否存活（`/api/health/services` 的 worker 心跳） | `logs/worker.log`；启动 `python -m app.worker` |
| **任务全部不动、worker 进程还在** | `service_status.json` 里 worker 的 `heartbeat_age_seconds`；`/api/health/services` 的 worker=down | 心跳年龄持续增大 = 事件循环假死，supervisor 应约 105s 内自动重启（`supervisor.log` 有「worker 心跳 Ns 未更新，强制重启」）；未重启则检查 supervisor 是否在跑、任务库是否可读。详见 [加固说明](worker假死与任务队列加固-2026-11-02.md) |
| 任务页很卡 / 加载慢 | 浏览器 Network 里 `GET /api/tasks?size=200` 的响应大小与耗时 | 列表已只回传 result 前缀（>8KB 置 null）；若仍慢，检查是否有新任务类型写了超大 result |
| 任务卡在 running | `task_queue.heartbeat_at` | 心跳超 90 秒会被自动重置；心跳正常但 handler 卡死时取消该任务（见 [异步任务体系](../features/异步任务体系.md)） |
| 任务反复失败 | `logs/worker.log` 的 `error`、`retry_count` | 可恢复错误重试 2 次（30s/120s）；永久错误直接 failed |
| 写库报 `database is locked` | 是否有长事务 / 备份正在跑 | WAL + 30s busy_timeout；避免长事务里再开独立会话写；备份与 worker 会互相等待 |
| 人脸功能全灰 | `curl 127.0.0.1:18889/health`；`logs/face-service.log` | 人脸服务未启动/模型缺失/CUDA 运行时未加载；启动后前端 15 秒内自动复检 |
| AI 打标全部失败 | `curl 127.0.0.1:11434/api/tags`；模型是否已拉取 | Ollama 未启动 / 模型名不匹配；任务会按可恢复错误重试 |
| 磁盘告警 / 备份失败 | `status.sh` 的资源区、`logs/` 体积 | 清理 f2 下载目录、旧日志、垃圾桶；备份策略见 [数据备份与恢复](数据备份与恢复.md) |
| npm 装包后缺依赖 | `npm i --legacy-peer-deps` 会删包 | 检查 `expo-linking` 等是否还在（移动端）；必要时重装 |
| GitHub / npm 网络失败 | 本机代理是否在跑 | Gradle 走 clash 7890；**npm 不要设代理**（走 npmmirror） |

## 7. 常用诊断命令

```bash
# 端口占用（PID 在最后一列）
netstat -ano | grep -E ":(18888|17777|18889|11434)" | grep LISTENING

# 按命令行找残留进程（Windows PowerShell）
powershell -Command "Get-CimInstance Win32_Process -Filter \"Name='python.exe'\" | Where-Object { \$_.CommandLine -like '*uvicorn app.main*' -or \$_.CommandLine -like '*app.worker*' } | Select-Object ProcessId,CommandLine"

# 级联杀进程树
taskkill //F //T //PID <pid>

# 数据库健康（只读）
sqlite3 backend/storage/fashion_inspo.db "PRAGMA integrity_check;"
```

> Git Bash 下 `taskkill` 的 `/F` 要写成 `//F`（MSYS 会转换单斜杠参数）；`robocopy` 同理需要 `MSYS_NO_PATHCONV=1`。
