## 1. worker 假死与任务队列加固

> 原文件：`ops/worker假死与任务队列加固-2026-11-02.md`｜原题：worker 假死与任务队列加固（2026-11-02）

> **状态**：事故复盘 + 加固已实施（自动化测试通过；**服务重启后生效，重启由用户手动执行**）。
> **关联**：[异步任务体系](../features/异步任务体系.md)、[日志系统扫描与整改 §2](日志系统扫描与整改-2026-11-02.md)、[本地运行与排障](本地运行与排障.md)。
> **一句话**：worker 进程活着但事件循环卡死，心跳中断 → supervisor 只判进程存活、不重启 → 4 个云端出图任务永久排队。已补四道防线：supervisor 心跳监控、worker 任务看门狗、向量回填失败快路径 + Ollama 熔断、`/api/tasks` 列表瘦身。

### 1. 事故现象

- 用户报告「任务管理中卡住了」：任务一直 `pending`，状态不动。
- `GET /api/health/services` 返回 **worker: down**；但 `logs/service_status.json` 里 worker 进程「ok」（进程确实活着）。
- 数据库 4 条 `image_gen` 任务（#746~#749，云端 Seedream）从 23:43 起一直 `pending`，没有 worker 认领。

### 2. 时间线（Asia/Shanghai）

| 时间 | 事件 |
| --- | --- |
| 23:41:05 | supervisor 重启三服务（加载当日新代码） |
| 23:41:14 | worker 启动；启动兜底把遗留待回填素材 flush 成任务 **#745（vector_backfill，6 个素材）** |
| 23:41:15 | worker 认领 #745 开始执行（台账 `task_run_logs` id=5 写入，`status=running`） |
| 23:41:18~23:42:26 | **Ollama 未启动**（11434 端口无监听）：6 条文本嵌入连续 `ConnectError / ConnectTimeout`，日志刷出大段 traceback |
| 23:41:34 | **最后一次服务心跳**（`service_heartbeats.last_heartbeat_at`），此后不再更新 |
| 23:42:57 | 转而加载 CLIP 图像模型，tqdm 显示首批 `Batches 100%|1/1` 编码完成——**worker 日志到此为止** |

| 23:49 | 用户报障；检查发现心跳已停 8 分钟、任务队列停摆 |

### 3. 现场证据（只读检查）

| 证据 | 结论 |
| --- | --- |
| `service_heartbeats` 最后心跳 23:41:34、`/api/health/services` worker=down | 心跳通道中断 |
| `worker.log` / `analyze-2026-11-02.log` 最后一行 23:42:57，之后无任何记录 | worker 不再写日志 |
| py-spy dump：主线程停在 asyncio `select`，其余线程（aiosqlite ×3、线程池、tqdm monitor）全部 idle，**没有任何线程在工作** | 不是「任务在跑」，而是事件循环/协程在等一个不会完成的 future |
| 10 秒 CPU 采样增量 **0.00s** | 进程空转，不是 CPU 型死循环 |
| 数据库写锁探测（`BEGIN IMMEDIATE`，2s）可立即获取 | 不是 SQLite 写锁互斥导致的死等 |
| `task_queue` 里 #745 行已不存在，但 `task_run_logs` id=5 仍 `running`、`finished_at=NULL` | 用户已在任务页删除僵尸任务；台账留下孤儿行 |
| `pending_vector_backfills` 为 0 行 | #745 flush 时清空，任务没走到失败收尾 → 6 个素材的待回填登记暂时丢失（重启后新任务会重新登记） |
| supervisor 对 worker 的配置 `health_url=None` → 只判进程存活 | **进程活着但事件循环卡死时不会自动重启**（本次未自动恢复的根因） |

### 4. 判断

**直接原因**：worker 在执行遗留向量回填 #745 时卡死（文本嵌入全失败后进入 CLIP 图像编码，编码完成后事件循环停摆），心跳与任务进度都不再更新；单并发槽位被占死，后续任务永远排队。

**触发条件**：Ollama 未运行 + worker 启动时自动拉起遗留的向量回填（6 个素材）。

**为什么没自愈**：supervisor 只检查「worker 进程是否存在」，不检查心跳；worker 也没有任务级看门狗。

**未完全定位的部分**：事件循环内部为什么丢唤醒（py-spy 显示全线程 idle），从进程外部无法进一步取 asyncio 任务栈。本次按「限制爆炸半径」处理——即使根因未知，也不会再出现「无声停摆 20 分钟」；若以后复现，保留 `py-spy dump --native` 输出与 `service_status.json` 的 `heartbeat_age_seconds`。

### 5. 四道加固

#### 5.1 supervisor 监控 worker 心跳（进程级兜底）

- 新增 `_read_worker_heartbeat(pid)`：只读打开任务库（`mode=ro`），读该 pid 最近心跳年龄，返回 `HeartbeatReading(age, error)`；
- worker 健康判定改为：**进程存活 + 心跳新鲜**。心跳超过 `WORKER_HEARTBEAT_STALE_SECONDS`（默认 90s）视为不健康，连续 3 次（≈15s）后走既有「强制重启」链路；
- 启动宽限：worker 启动后 `grace + 90s` 内**查询成功但还没有心跳行**时不误杀；
- **读失败不误杀（2026-11-03 修复 P1-1）**：库不存在/被锁/查询失败时 `error` 非空，健康判定直接返回健康且不累计 fail_streak；错误首次记 `supervisor.log` warning，并写入 `service_status.json` 的 `heartbeat_read_error`，不再把「读不到」当成「worker 死了」周期性重启；
- 状态文件 `logs/service_status.json` 的 worker 条目新增 `heartbeat_age_seconds` 与 `heartbeat_read_error`；强制重启原因写 `worker 心跳 Ns 未更新`，同时写 `supervisor.log` 与 `worker.log`（避免只在一处找不到）；
- 同一轮健康检查 + 状态文件只读一次心跳（短缓存），不会每轮读库两次。

> 时序：最多约 `90s（阈值）+ 15s（连续失败）+ 2s（重启延迟）` 后自动拉起，不再需要人工发现。

#### 5.2 worker 任务看门狗（任务级兜底）

- 判定口径：本 worker 认领、`status=running`、`updated_at` 超过 `TASK_STALL_TIMEOUT_SECONDS`（默认 **1800s / 30 分钟**）没更新；
- **心跳不再刷新 `updated_at`（2026-11-03 修复 P0-1）**：`_write_heartbeat` 只写 `heartbeat_at`，并显式 `updated_at = TaskQueue.updated_at` 阻止 `onupdate` 生效。此前心跳每 10 秒刷新一次 `updated_at`，看门狗在正常路径下**永远不会触发**；
- 触发后：`asyncio.Task.cancel()` → `_run_task_safe` 捕获取消 → `_fail_stalled_task` 用新会话把任务标 `failed`（错误信息含「超过 N 分钟无进度更新…看门狗强制终止」）+ 补台账 `finished_at` + 广播失败事件；
- **收尾失败保留标记重试（2026-11-03 修复 P1-4）**：只有写库成功才清 `_WATCHDOG_CANCELLED`；写库失败时主循环每个看门狗周期重试，不会留下永久 `running` 僵尸；
- **槽位立即释放**，后续 pending 任务可被认领；重试不自动进行（卡死任务直接重跑很可能再次卡死），用户可以重新提交；
- 进程关闭时的取消（`asyncio.run` 收尾）**不写 failed**：保持 running，交给下次启动的 `_reset_stale_tasks` 按心跳重置（与历史语义一致）；
- 阈值可配（`.env` 的 `TASK_STALL_TIMEOUT_SECONDS`，`0` 关闭，负数/超过 7 天启动即报错）。

> 为什么不是「总运行时长」：f2 下载/全库批量分析可以合法跑几小时；看的是**进度是否还在动**（执行器写进度都会刷新 `updated_at`）。

#### 5.3 向量回填失败快路径 + Ollama 熔断

- `_build_material_vectors`：本窗口**所有非空文本都嵌入失败**时，跳过 CLIP 图像编码（任务收尾必判失败，图像编码跑了也白跑；CLIP 首次加载/批量前向是分钟级重型操作）；日志区分「Ollama 连接不可达」与「文本内容/单条数据失败」（2026-11-03 P2-3）；
- `generate_text_embedding`：遇到 `ConnectError/ConnectTimeout`（Ollama 没启动/端口不通）**判一次即熔断**，期间后续文本直接返回 None，不再逐条等超时；`ReadTimeout/RemoteProtocolError` 也触发（用 1/3 时长）；拿到成功响应立即解除熔断；
- 熔断时长可配：`OLLAMA_EMBED_DOWN_COOLDOWN_SECONDS`（默认 30s，2026-11-03 P2-2 从写死 60s 调整）；
- 效果：Ollama 不可用时，一个窗口从「每条等 15s×2 次」缩短到「首条最多 15s，其余即时失败」，且不进入 CLIP 路径，几秒~几十秒内释放槽位。

#### 5.4 `/api/tasks` 列表瘦身（页面卡顿）

- 现状：`task_queue.result` 合计 78.8 MB，最大单行 2.9 MB（`tag_health_scan`）；列表按 200 行返回曾是 **30.6 MB/次**响应，前端每 5 秒轮询，实测接口 1.3s；
- 改法（2026-11-03 修复 P1-2/P2-6）：写入任务时由 ORM 事件生成 `result_summary`（≤8KB 小 JSON，保留前端标题/摘要字段），列表**不再读 result 整列**，也跳过 `stage_state`；历史行由服务端启动时回填摘要；仅回填未完成的行才退回旧前缀策略；
- 详情接口 `GET /api/tasks/{id}` 仍返回完整 result（展开/排障用）；
- 实测（真实库 200 行）：响应体 **30.6 MB → 0.163 MB**，SQLite 侧查询 0.033s+0.264s 解析 → **0.048s**（轻列表 0.019s + 前缀 0.029s）。

#### 5.5 孤儿台账收尾

- worker 启动时**只收尾「任务行不存在、或任务已不是 running」**的 `task_run_logs` 台账并补 `finished_at`（本次事故留下 id=5 的孤儿行即此类）；任务仍 running 的台账（无论跑多久）不动（2026-11-03 修复 P1-3：原按「开始超过 2 小时」会误标多 worker 下的长任务）。

#### 7.2 重启后人工验收（用户手动重启）

1. 正常运行时 `logs/service_status.json` 的 worker 条目应带 `heartbeat_age_seconds` 与 `heartbeat_read_error`，且 `status=ok`；
2. 停掉 Ollama 后手动重启 worker（模拟事故触发条件）：向量回填任务应在**几十秒内**以失败收尾（错误含「文本向量全部生成失败」），任务队列继续认领后续任务——不会再出现长时间占死槽位；
3. 若真出现进程假死：`supervisor.log` 应出现 `[强制重启] worker worker 心跳 Ns 未更新`，`worker.log` 也有对应行，之后 worker 自动重启、`service_status.json` 的 `restarts` 加一；
4. 任务页「运行记录」不再长期显示 `进行中` 的孤儿行（下次 worker 启动按「任务已结束/不存在」规则收尾）。

### 8. 已知边界

| 边界 | 说明 |
| --- | --- |
| 看门狗也在事件循环内 | 若整个事件循环被同步阻塞/GIL 级死锁冻住，看门狗同样跑不了 → 由 supervisor 心跳监控兜底（进程级） |
| 取消不保证中断同步段 | 看门狗 `cancel()` 只能让协程在 `await` 处抛 `CancelledError`；若 handler 正卡在 `asyncio.to_thread` 里的同步代码（如 CLIP 编码），线程可能继续跑到自然结束，但其结果被丢弃、槽位已释放（本次事故的现场卡点也属于这一类，见向量回填快路径） |
| 重启会丢当前任务的内存进度 | 任务由 `_reset_stale_tasks` 重置回 pending，执行器按幂等语义重跑；已落库数据不丢 |
| 卡死任务不自动重试 | 看门狗直接标 failed，避免「卡死→重跑→再卡死」循环；需要时重新提交 |
| 列表 result 摘要 | 超长 result 在列表里是 ≤8KB 摘要（保留标题/摘要字段），完整内容走详情接口；极端情况下摘要只剩 `_truncated` 标记 |
| 根因未完全定位 | 事件循环内部丢唤醒的原因未能从进程外捕获；今后复现请保留 `py-spy dump --native <pid>` 与 `service_status.json` |

### 2. 阻断级问题（P0）

#### P0-1 任务看门狗永远不会触发：`updated_at` 被心跳每 10 秒刷新

**位置**：

- 看门狗判定：`backend/app/worker.py:463 _stalled_task_ids()`，查询条件在 `:476-480`：
  ```python
  TaskQueue.status == "running",
  TaskQueue.claimed_by == worker_id,
  or_(TaskQueue.updated_at.is_(None), TaskQueue.updated_at < cutoff)
  ```
- 心跳写入：`backend/app/worker.py:594 _write_heartbeat()`，`:614`：
  ```python
  update(TaskQueue)
  .where(TaskQueue.status == "running", TaskQueue.claimed_by == worker_id)
  .values(heartbeat_at=now)
  ```
- 模型定义：`backend/app/models/task.py:66-68`
  ```python
  updated_at: Mapped[datetime] = mapped_column(
      DateTime, default=utcnow, onupdate=utcnow
  )
  ```
- 代码注释 `worker.py:466-467` 明确写着“心跳循环也会每 10 秒刷新被认领任务的心跳，但**不刷新 updated_at**”——这句是错的。

**实测**：用同一个 `TaskQueue` 模型做最小复现：

```python
# before: updated_at = now - 1h
db.execute(update(TaskQueue).where(...).values(heartbeat_at=utcnow()))
db.commit()
# after: updated_at = now（被 onupdate 刷新）
```

**结论**：只要心跳能正常写入（每 10 秒），所有 running 任务的 `updated_at` 就一直在当前时间附近，正常路径下不可能超过 30 分钟。看门狗 `_stalled_task_ids()` 每次都返回空，**`_fail_stalled_task` 基本不会被调用**。只有心跳写入本身失败（如数据库锁）时，`updated_at` 才会停止刷新；但那种情况下执行器的进度写入通常也失败，不能作为可靠的看门狗触发条件。

**为什么测试没发现**：`backend/tests/test_worker_watchdog.py` 的 `_add_task()` 直接把 `updated_at` 改成 1 小时前，然后查询；测试**没有启动/调用 `_write_heartbeat`**，所以没有暴露“心跳会刷新它”的事实。这是典型的“函数单测通过、真实交互不成立”。

**影响**：

- 本次提交宣称的“任务级卡死兜底”不生效；
- 如果 handler 卡在某个 `await`（事件循环仍然空闲、心跳继续写），supervisor 看到心跳新鲜不会重启，看门狗也不会取消 → 任务永久卡住；
- 只有整个事件循环被同步阻塞（心跳也停）时，supervisor 才会兜底；这只能覆盖事故中的一类卡死。

**修复建议（任选其一，推荐 1）**：

1. **新增 `progress_at` 列**（Alembic 迁移），只由执行器写进度时更新；看门狗用它判定；心跳只写 `heartbeat_at`，不碰 `progress_at`。
2. 改 `_write_heartbeat`，显式保留 `updated_at`：
   ```python
   .values(heartbeat_at=now, updated_at=TaskQueue.updated_at)
   ```
   但要确认 SQLAlchemy 不再应用 `onupdate`（显式给列值通常可以），并补测试证明“心跳不改变 updated_at”。
3. 用 `stage`/`progress` 的变更时间（需要额外字段）；不要复用 `updated_at`。

**测试要求**：新增一个用例：插入 running 任务 → 调用 `_write_heartbeat` → 断言 `updated_at` 不变（或 `progress_at` 不变）→ `_stalled_task_ids` 仍能返回它。再补一个 `_worker_loop` 集成用例：任务只 `await sleep`、心跳正常跑，超过短阈值后被取消并标 failed。

### 3. 高优先级问题（P1）

#### P1-1 supervisor 在“读不到心跳”时仍会重启，和文档“不误杀”不符

**位置**：`scripts/ops/supervisor.py:299 ManagedService.healthy()`：

```python
age = self.heartbeat_age()
if age is None:
    return self.age() < self.grace + WORKER_HEARTBEAT_STALE_SECONDS
return age <= WORKER_HEARTBEAT_STALE_SECONDS
```

`read_worker_heartbeat_age()`（`:397`）在库不存在、库被锁、查询失败、pid 为空时都返回 `None`。`healthy()` 把 `None` 当成“还没写出第一行心跳”，只在 `grace + 90s`（默认 105s）内视为健康；超过后返回 false，连续 3 次（15s）就强制重启。

**影响**：

- 如果 `DATABASE_URL` 解析错、supervisor 读不到库、库长时间被锁，worker 会在启动约 120 秒后被反复重启（restart loop），而不是“不误杀”；
- 本文 §1 写“库被锁/不存在时返回 None → 不误杀”，与代码不符；
- 单测 `test_worker_健康判定看心跳年龄` 甚至断言“已运行 200s + 读不到心跳 = 不健康”，等于把重启固化成了预期。

**修复建议**：

- 区分“读失败/库不可用”和“没有心跳行”：前者应记录告警并**不累计 fail_streak**（或使用更长的独立宽限），后者才按启动宽限处理；
- 在 `service_status.json` / supervisor.log 里记录 `read_error`，避免排障时只看到“没有心跳”；
- 至少把 `grace + stale` 的语义写清楚，不要声称“不误杀”。

#### P1-2 `/api/tasks` 列表瘦身让大量任务的摘要/标题变空

**位置**：`backend/app/routers/tasks.py:30 RESULT_PREVIEW_CHARS=8192`、`:33 _parse_result_preview()`、`:149 func.substr(...)`。

**机制**：列表只取 `substr(result, 1, 8192)`；`json.loads()` 对**被截断的 JSON 前缀必然失败**，于是返回 `None`。不是“只丢超大字段”，而是“result 超过 8KB 就整条摘要为 None”。

**实测数据**（`backend/fashion_inspo.db`，2026-11-03 只读统计）：

| 任务类型 | result > 8KB 的行数 | 最大值 |
| --- | ---: | ---: |
| `tag_health_scan` | 76 | 2.9 MB |
| `batch_analyze` | 20 | 280 KB |
| `face_cluster` | 11 | 49 KB |
| `enrich_blogger_profile` | 8 | 184 KB |
| `tag_network_analyze` | 8 | 238 KB |
| `tag_cluster_scan` | 7 | 1.5 MB |
| `vector_backfill` | 7 | 478 KB |
| `blogger_avatar_fill` | 4 | 130 KB |
| `batch_delete` | 3 | 294 KB |
| `f2_import` | 2 | 1.6 MB |
| `quality_check` | 1 | 20 KB |
| **合计** | **147** | — |

前端 `normalizeQueueTask`（`web/src/utils/taskPresentation.ts:511/528-529`）依赖 `result` 生成标题和完成摘要：

- `f2_import`：`result.fetch_mode` 决定“我的收藏/我的喜欢”标题；超过 8KB 时标题退化为通用名；
- `batch_analyze` / `vector_backfill` / `quality_check` / `enrich_blogger_profile`：`summarizeResult` 读 `done/text_done/approved/...`；超过 8KB 时完成摘要为空；
- `tag_health_scan` 本身没有摘要，但同理。

文档 `task队列加固` 写“前端摘要依赖的字段都很小，不受影响”，这句不成立——**摘要字段小，但整条 result 解析不了**。

**修复建议**：

1. 在任务完成时单独写一个 `result_summary` 小 JSON（或几个标量列），列表只取 summary；
2. 或用 SQLite JSON1 对已知字段做 `json_extract(result, '$.done')` 等投影，而不是截断原文；
3. 至少给 `f2_import`/`batch_analyze`/`vector_backfill` 等类型补一个“列表摘要仍正确”的前端/接口用例。

#### P1-3 孤儿台账收尾会误伤仍在跑的长任务

**位置**：`backend/app/worker.py:764 _finalize_orphan_run_logs()`：

```python
cutoff = utcnow() - timedelta(hours=2)
update(TaskRunLog)
.where(TaskRunLog.status == "running", TaskRunLog.started_at < cutoff)
.values(status="failed", ...)
```

**影响**：

- 多 worker 部署时，另一个实例正在跑的任务只要超过 2 小时，台账会被启动中的新 worker 标 failed；任务本身可能还在 running/success，台账与任务状态不一致；
- 单 worker 下，一个合法跑 >2 小时的任务若在此时重启（或另一个 worker 启动），也会被误标；
- 2 小时是硬编码，不随任务类型/配置变化；`task_run_logs` 没有 `updated_at` 参与判断。

**修复建议**：

- 只收尾“任务本身已不存在 / 已终态”的 ledger；或联合 `TaskQueue` 判断（status 不是 running 才收尾）；
- 多 worker 场景按 `worker_id` 判断，别收别的实例的；
- 把 2 小时做成配置或按任务类型给上限；
- 文档删掉“多 worker 下另一实例正在跑的任务不受影响”。

#### P1-4 看门狗收尾失败会吞掉标记，任务仍是 running

**位置**：`backend/app/worker.py:442-459 _run_task_safe()`：

```python
if task_id in _WATCHDOG_CANCELLED:
    _WATCHDOG_CANCELLED.discard(task_id)
    try:
        await _fail_stalled_task(task_id)
    except Exception:
        logger.exception("看门狗收尾失败: #%s", task_id)
raise
```

**影响**：

- 先 `discard` 再收尾；如果 `_fail_stalled_task` 因数据库锁/异常失败，标记已经没了，下一次看门狗扫描不会再处理这个 id；
- 执行协程已经取消，任务不会再跑，但 `TaskQueue.status` 仍是 `running`，直到进程重启后 `_reset_stale_tasks` 或人工处理；
- 与 P0-2（原提交的“预调用失败卡 running”）同类：状态机留下 running 僵尸。

**修复建议**：收尾成功后再 `discard`；失败时保留标记/重试；或直接在 `_fail_stalled_task` 内加一次重试并用独立连接；测试模拟 DB 异常。

#### P1-5 配置没有进 `.env.example`，文档与实现不一致

- `backend/app/config.py:178` 新增 `task_stall_timeout_seconds`，`scripts/ops/supervisor.py:101` 新增 `WORKER_HEARTBEAT_STALE_SECONDS`；
- `backend/.env.example` 没有这两项；文档 `docs/ops/本地运行与排障.md` 已列出，但示例文件没有，部署时容易漏；
- `WORKER_HEARTBEAT_STALE_SECONDS` 没有校验（可设 5s，低于心跳间隔 10s，导致持续重启）；`TASK_STALL_TIMEOUT_SECONDS` 没有上限/负数校验（负数=关闭，可能不是用户本意）。

**建议**：补 `.env.example`；在 supervisor/config 启动时打印生效值并校验 `stale > heartbeat_interval`、`timeout >= 0`。

### 5. 做得好的地方（应保留）

1. **supervisor 心跳监控设计正确**：只读 `mode=ro`、按 pid 过滤、启动宽限、连续 3 次失败、状态文件带 `heartbeat_age_seconds`；这能覆盖“事件循环卡死、心跳停”的真实事故。
2. **看门狗的执行语义考虑周全**：区分“看门狗取消”和“进程关闭取消”；先 cancel 再用新会话收尾，避免和卡死协程抢 SQLite 写锁；失败不自动重试，避免“卡死→重跑→再卡死”。
3. **向量快路径**：文本全失败时不再进入分钟级 CLIP，直接命中任务失败分支，事故爆炸半径明显缩小。
4. **Ollama 熔断**：把“每条文本 × 多档截断 × 2 次尝试”的分钟级等待压到首条一次，方向正确。
5. **列表瘦身**：响应体 30.6MB→0.163MB 是真实收益；详情接口保留完整 result，分层合理。
6. **测试方法正确**：supervisor 用临时 SQLite、vector 用 FakeOllama、tasks 用真实 TestClient；不依赖外网/GPU。
