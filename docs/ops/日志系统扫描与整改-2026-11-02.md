### 3. 主要发现（按优先级）

#### P0-1 API 进程业务日志被静默丢弃（最高优先级）

**证据**：

- `backend/app/main.py:49` 定义 `logger = logging.getLogger(__name__)`，启动时 `main.py:225` 有 `logger.info("... 启动于端口 ...")`；
- 但 `logs/backend.log*` 中 `app.*` 日志 **0 行**，启动/关闭/垃圾桶/定时采集等业务日志全部缺失；
- uvicorn 默认 `LOGGING_CONFIG` 只配置 `uvicorn` / `uvicorn.error` / `uvicorn.access`，**没有 root handler**（已用 `uvicorn.config.LOGGING_CONFIG` 核实）；
- `app.*` logger 向 root 传播，root 无 handler → INFO 记录被丢弃；WARNING+ 只能靠 Python `lastResort` 输出，格式与业务上下文都丢失；
- `backend/tests/test_logging_visibility.py` 只守住“迁移不禁用 logger”，**没有守住“root 有 handler / 日志真的落盘”**。

**影响**：接口 500、启动失败、定时任务异常、垃圾桶清理失败等关键信息无法从日志还原；现有 traceback 大多是 uvicorn/asyncio 噪音，真正的业务错误被淹没。

**建议**：新增统一的 `backend/app/logging_config.py`，在 `main.py` 与 `worker.py` 启动时调用；用 `dictConfig` 给 root 配 handler，`disable_existing_loggers=False`；格式统一带时间、级别、logger 名、`request_id`/`task_id`；加一条测试：启动后 root 必须有 handler，且 `logger.info` 能写进捕获的 stream。

#### P0-2 健康检查/访问日志刷屏

**证据**：`backend.log` 当前 54.7% 是 `/api/health`，29.6% 是其他 API 访问；全量历史 25 万行健康检查。supervisor 每 5 秒探一次健康，WebSocket 每次连接也打 `connection open`。

**影响**：10 MB × 5 的轮转很快被无价值行占满，日志保留期被压缩；真实 500/慢请求难以定位。

**建议**：

- 对 `uvicorn.access` 加 filter：`/api/health`、WebSocket open/close 不记；只保留 4xx/5xx 与慢请求（如 > 1s）。
- 或者关闭 uvicorn access log，用中间件只记录“非 2xx / 慢请求”，并带 `request_id`。
- 健康检查本身保留在 supervisor 的 `service_status.json`，不需要重复写 backend.log。

#### P0-3 worker 日志被 `httpx` 与子进程输出淹没

**证据**：`worker.log` 当前 50,186 行，`httpx` INFO 13,232 行（26.4%），f2 子进程原始 `INFO     ...` 13,024 行（26.0%）。`httpx` 每发一次 ComfyUI/Ollama/方舟请求都记一行。

**影响**：应用日志只占约一半；任务排障时要在大量 HTTP 请求行与无时间戳的子进程输出中翻找。

**建议**：

- worker 启动时 `logging.getLogger("httpx").setLevel(logging.WARNING)`、`httpcore` 同理；需要看请求时用 `LOG_LEVEL=DEBUG` 临时打开。
- 子进程（f2 等）stdout 不要直接继承到 worker.log：重定向到按任务/按次的文件，或在读取线程前加 `[f2 task#123]` 前缀与时间戳。
- 把 f2 的 `logs/f2-*.log` 纳入统一命名/清理策略。

#### P1-1 异常日志普遍没有堆栈

**证据**：`logger.exception` 只有 6 处；`logger.error(..., exc_info=True)` **0 处**；43 处 `logger.error` 绝大多数是 `f"...: {e}"`，只留一句字符串。

**影响**：同一个错误只能看到“失败: xxx”，看不到调用栈，无法定位到具体代码行；排查时只能复现。

**建议**：

- 约定：`except` 中记录“非预期异常”统一用 `logger.exception("...")`；需要自定义级别时用 `logger.error(..., exc_info=True)`。
- 预期内的降级（可重试、可选缓存、子进程清理）用 `logger.warning`/`logger.debug`，不要用 ERROR。
- 加一条轻量 AST 测试/评审清单：`except` 中 `logger.error(f"...{e}")` 且无 `exc_info` 的调用，应改为 `logger.exception`（允许白名单例外）。

#### P1-2 静默吞异常缺少分类

**证据**：462 个 `except` 中 107 个只有 `pass/continue/return`，73 个有其他语句但无日志；共约 180 个（39%）没有日志。

**影响**：部分“看起来正常”的降级实际上是 bug（例如向量/人脸/文件清理失败被吞），只能靠上层现象猜。

**建议**：

- 对 107 个静默点做一次分类：**预期降级** → 加 `logger.debug`（需要时开）；**非预期** → 加 `logger.exception` 并上报到任务 error。
- 优先处理核心链路：任务执行、入库、软删除/垃圾桶、AI 分析、向量写入。
- 在评审清单里加一条：“新增 `except: pass` 必须写注释说明为什么可以吞”。

#### P1-3 缺少请求/任务关联 ID

**证据**：没有 `request_id` / `trace_id` / `X-Request-ID` 中间件；只有 `seedream_client` 记录上游 `request_id`。worker 日志部分带 `#task_id`（如 `任务完成: #739`），任务 runner 内部日志大多不带。

**影响**：前端报错 → API 500 → worker 任务失败，三段日志无法串起来；只能靠时间窗口猜。

**建议**：

- API：中间件生成 `request_id`（如 `uuid4().hex[:12]`），写入 `contextvars`，日志 filter 自动注入；响应头返回 `X-Request-ID`。
- worker：任务开始时设置 `task_id`/`run_id`/`attempt` 的 contextvar，任务 runner 的日志自动带上。
- 前端：API 错误时读取响应头 `X-Request-ID`，在错误提示/“复制诊断信息”里展示，便于和 backend.log 对齐。
- 不需要引入 OpenTelemetry；一个 contextvar + filter 足够本地单机使用。

#### P1-4 轮转/保留/清理不完整

**证据**：

- supervisor 10 MB × 5，按大小轮转，无压缩、无按天保留；当前 `logs/` 109 MB，最早文件 10-01。
- `face-service.log` 由 `restart.sh` 直接 `>` 重定向，**不在 supervisor 内、无轮转**；face-service 也没有自动拉起。
- `logs/f2-*.log` 67 个（39 个 0 字节），无清理；`backend/logs/*` 16 KB 旧文件；`backend/api.out`/`api.err`/`worker.out`/`worker.err` 是 8 月手动启动遗留。
- `analyze-*.log` 按天生成，**没有保留期**；一旦 worker 重启，新的每日文件会持续累积。
- `task_run_logs` 每次任务尝试一行，无保留期/清理。

**建议**：

- 统一策略：按大小 + 按天，压缩（`.gz`），保留 14～30 天；`logs/` 总预算（如 200 MB）。
- `face-service` 纳入 supervisor（或单独给它加 `RotatingFileWriter`），并补健康检查/自动拉起。
- 增加 `scripts/ops/cleanup_logs.sh`：清理 `f2-*.log`（0 字节/超期）、`analyze-*.log`（超期）、旧 `backend/logs`、手动遗留 `.out/.err`；可挂到 supervisor 每日维护。
- `task_run_logs` 加保留期（如 90 天）或定期聚合；给出只读查询 API 后再考虑 UI。

#### P1-5 新任务台账/按天日志未生效（部署态）

**证据**：

- `task_run_logs` 表存在但 **0 行**；`logs/analyze-*.log` **0 个**；
- `task_run_log`/`DailyFileHandler` 提交时间 **2026-11-02 22:25:49**；supervisor 当前一轮启动记录在 **22:11:07**，`service_status.json` 的 worker 进程 `restarts: 0`；
- 在独立进程里调用 `_setup_logging()` 能正常生成 `analyze-2026-11-02.log`（已做一次诊断，随后删除）。

**结论**：**不是代码失效，而是运行中的 worker 早于该功能提交，尚未重启**。按项目约定，服务启停由用户手动执行；本次未自动重启。

**建议**：

1. 用户手动重启 worker（或整套服务）后，确认：
   - `logs/analyze-YYYY-MM-DD.log` 生成；
   - 执行任意任务后 `task_run_logs` 有行；
   - `logs/worker.log` 中 `任务开始/任务结束` 出现。
2. 在 worker 启动日志里加一行自检：`root handlers=[...]`、`analyze file=...`，避免下次再猜。
3. 补一条“日志落盘”集成测试（不是只测 handler 本身），启动 `_setup_logging` 后断言文件存在且包含启动日志。

#### P2-1 格式不统一

**证据**：`backend.log` 里 uvicorn 是 `INFO:     ...`；worker 应用日志是 `2026-... [INFO] app.xxx: ...`；f2 子进程是 `INFO     ...`；face-service 是 `2026-... INFO app.face: ...`；frontend.log 含 ANSI 颜色。

**影响**：无法用一套正则/SQL 解析；跨进程对比困难。

**建议**：统一为 `时间 级别 logger [request_id/task_id] 消息`；可选 `LOG_FORMAT=json`（本地默认 text，排障需要时 json）。子进程输出必须加前缀/时间戳，或单独文件。

#### P2-2 日志级别失真

**证据**：WARNING 162 > INFO 153；worker WARNING 238 条中 132 条是人脸 404、约 50 条是向量截断；ERROR 43 条多数是 `f"...{e}"`。

**影响**：WARNING 变成“所有非 200 都算”，失去“需要关注”的含义；真正的风险被稀释。

**建议**：

- 级别约定：DEBUG=逐条细节；INFO=生命周期/每任务一条；WARNING=可恢复但需关注；ERROR=操作失败需处理；CRITICAL=服务不可用。
- 对“每次都一样”的告警做聚合：同一任务/同一原因只记一次 + 计数；人脸 404 先修接口，不要降级日志掩盖。
- 修掉 `截断到 None 字符` 的文案 bug，向量截断只记一次最终维度。

#### P2-3 f-string 日志占 86.5%

**证据**：328/379 用 f-string；仅 25 处 `%s`。

**影响**：DEBUG 日志在关闭时也会做字符串拼接；格式不统一时更难做结构化字段。

**建议**：新代码统一 `logger.info("... %s", value)`；f-string 仅用于纯静态短消息。不是高优先级，但可在评审清单中约定。

#### P2-4 前端/移动端/插件只有 console

**证据**：Web 17 处、Mobile 3 处、Extension 13 处 `console.*`；无 logger 工具、无持久化、无诊断导出。

**影响**：用户看到“页面渲染出错/请求失败”时，开发者拿不到浏览器控制台；移动端 APK 更看不到；插件 service worker 关闭后日志消失。

**建议**：

- Web：新增 `web/src/utils/logger.ts`（级别、`import.meta.env.DEV` 开关、200 条环形缓冲）；全局错误/API 错误统一走它；ErrorBoundary 显示可复制的 `request_id` + 错误摘要；可选“复制诊断信息”（不新增后端接口）。
- Mobile：`mobile/utils/logger.ts`，用 `__DEV__` 控制；ErrorBoundary 提供“复制错误”按钮；不引入 Sentry 等外部依赖。
- Extension：加 `DEBUG` 开关；service worker 的关键失败（上传/查重/创建会话）写入 `chrome.storage.session` 环形缓冲，popup 可查看/复制；不默认上传。

#### P2-5 脚本与 face-service 的日志策略

- `backend/scripts`：41 次 logger + 777 次 print；CLI 输出用 print 合理，但长驻脚本 `fetch_xhs_following.py:250` 用无轮转的 `FileHandler`，应改为 `RotatingFileHandler` 或按天文件。
- `face-service`：`basicConfig` 可用，但进程不在 supervisor 内、日志无轮转；建议纳入 supervisor 或至少加 `RotatingFileHandler`。
- `frontend.log`：`FORCE_COLOR=0` 未去掉 ANSI；建议 `NO_COLOR=1`/`CLICOLOR=0`，或在读取时剥 ANSI。

```python
    "formatters": {"text": ContextFormatter, "json": JsonFormatter},
    "handlers": {"console": StreamHandler(sys.stdout)},
    "root": {"level": level, "handlers": ["console"]},
    "loggers": {
        "uvicorn": {...}, "uvicorn.error": {...}, "uvicorn.access": {...},
    },
})
```

- API 的 stdout 由 supervisor 捕获并做 10 MB × 5 轮转，**不再自己开文件**（避免两套轮转）；
- worker 在 root 上额外挂 `DailyFileHandler`（`logs/analyze-YYYY-MM-DD.log`），格式与主日志一致；
- `disable_existing_loggers=False` 与 `tests/test_logging_visibility.py` 守的是同一条回归（alembic `fileConfig` 默认会禁 logger）。

#### 2.2 关联字段（request_id / task_id / run_id）

- `contextvars`：`request_id_var` / `task_id_var` / `run_id_var`；
- 通过 **LogRecord 工厂** 注入字段（不是 logger filter——filter 对子 logger 传播的记录不生效，会漏掉 handler）；
- API 中间件每请求生成 12 位 hex（尊重传入的 `X-Request-ID`），写 contextvar，响应头回传；
- worker 在 `_run_task_safe` 设置 `task=#id`，`_start_run_log` 拿到台账行后设置 `run=<id>`；
- 前端 API 拦截器读响应头 `X-Request-ID`，错误文案统一追加「（请求ID: xxx）」。

排查示例：

```bash
grep 'req=abc123def456' logs/backend.log
grep 'task=#739' logs/worker.log
```

#### 2.3 访问日志降噪与慢请求

- 丢弃：`/api/health`（supervisor 每 5 秒探一次，占历史 55%）、WebSocket 连接/断开行、2xx/3xx 访问行；
- 保留：4xx/5xx 访问行、uvicorn 的真实错误日志；
- 慢请求：中间件对 > `SLOW_REQUEST_MS`（默认 1000ms）的请求记 WARNING（含方法/路径/状态/耗时）；
- 未处理异常：中间件先 `logger.exception` 记完整堆栈（带 request_id），再返回统一 500 `{"detail": "服务器内部错误"}`，避免 uvicorn 再打一遍重复 traceback。

#### 2.4 开关

| 环境变量（`.env`） | 默认 | 作用 |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | `DEBUG` 时打印静默 except 分类日志、httpx 请求明细、SQL 日志 |
| `LOG_FORMAT` | `text` | `json` 时一行一条 JSON（本地排障用，不改变落盘位置） |
| `SLOW_REQUEST_MS` | `1000` | 慢请求阈值 |
| `LOG_RETENTION_DAYS` | `30` | `analyze-*.log` 保留天数 |
| `TASK_RUN_LOG_RETENTION_DAYS` | `90` | `task_run_logs` 保留天数 |

> 配置只在**进程启动**时读取：改完 `.env` 需要用户手动重启服务。

### 3. 子进程与第三方库

- **f2**：`_run_subprocess` 改为 `Popen(stdout=文件)`，输出写 `logs/f2-<时间戳>-<pid>.log`（沿用 `f2-*.log` 命名，清理脚本统一回收），worker.log 只留一行退出码 + 文件路径；失败附最后 20 行。测试里的 monkeypatch 点（`_run_subprocess` 两参数签名）未变。

- **前端 ANSI**：supervisor 给 vite 进程补 `NO_COLOR=1`、`CLICOLOR=0`（`FORCE_COLOR=0` 对部分输出无效）。

### 4. 异常与静默 except 规范

#### 4.1 规则

1. `except` 中记录**非预期异常**统一 `logger.exception("...")`（或 `logger.error(..., exc_info=True)`）；
2. 预期内的降级（可重试、可选缓存、子进程清理、best-effort）用 `logger.warning` / `logger.debug`，不要用 ERROR；
3. 静默 `except: pass/continue/return` 必须至少有一条 `logger.debug` 说明「忽略异常（预期降级）」，或改用 `logger.exception`；
4. 只有**日志系统自身**（`logging_config.py` 的 filter、`daily_log.py` 的 handler emit、`config.py` 的 .env 兜底）允许保持静默（避免日志递归）。

#### 4.2 落地

- 36 处 except 内 `logger.error` → `logger.exception`（正则/AST 精确改方法名，行为不变，只补堆栈）；
- 106 处静默处理器补 `logger.debug("函数名: 忽略异常（预期降级）：%s", exc)`（默认 INFO 级别不输出，`LOG_LEVEL=DEBUG` 可见；不再吞掉现场）；
- `backend/tests/test_logging_conventions.py` 两条 AST 断言：
  - except 内 `logger.error` 无堆栈 → 失败；
  - 静默 except（除 3 个日志系统自身文件）→ 失败。

> 为什么用 `logger.debug` 而不是全部 `warning`：历史 WARNING 已比 INFO 多（162 > 153），把 100+ 个 best-effort 路径升成 WARNING 只会让告警更失真；DEBUG 可随时打开且零日常噪音。

### 5. 级别与格式约定（P2-1 / P2-2 / P2-3）

| 级别 | 用途 |
| --- | --- |
| DEBUG | 逐条细节、静默降级路径（`LOG_LEVEL=DEBUG` 才输出） |
| INFO | 生命周期、每任务一条进度/结果 |
| WARNING | 可恢复但需关注（重试、降级、慢请求、外部服务异常） |
| ERROR | 操作失败需要处理（配合 `logger.exception` 留堆栈） |
| CRITICAL | 服务不可用（当前无使用场景） |

- 新增日志优先惰性格式化 `logger.info("... %s", value)`（f-string 仅纯静态短消息）；不要求批量改写历史 328 处，但代码评审按新约定执行；
- 每条日志都带 `时间 级别 logger:行号 [req= task=]`，JSON 模式字段为 `ts/level/logger/line/message/request_id/task_id/run_id`（异常另有 `exception`）。

### 6. 保留与清理（P1-4）

| 对象 | 策略 | 执行方 |
| --- | --- | --- |
| `backend.log` / `worker.log` / `frontend.log` | 10 MB × 5 大小轮转（保持原状；总量由轮转封顶） | supervisor |
| `supervisor.log` | 10 MB × 5 `RotatingFileHandler` | supervisor |
| `face-service.log` | 10 MB × 3，进程内轮转 | face-service |
| `analyze-YYYY-MM-DD.log` | 启动时删除超过 `LOG_RETENTION_DAYS`（30 天）的文件 | worker |
| `task_run_logs` | 启动时删除 `started_at` 超过 90 天的行 | worker |
| `f2-*.log` | 按次生成；0 字节空壳始终清，其余默认保留 | 清理脚本（手动） |
| `backend/logs/*`、`backend/*.out/.err` | 历史遗留，列入清理脚本 | 清理脚本（手动） |

清理入口（默认 **dry-run**，确认后加 `--apply`）：

```bash
python scripts/ops/cleanup_artifacts.py --target logs          # 预览
python scripts/ops/cleanup_artifacts.py --target logs --apply  # 删除
```

> 没有把清理脚本挂到 supervisor 自动执行：删除不可恢复（日志是事后证据），保持「人工确认」与本项目既有设计一致；`logs/` 总量已被各服务轮转上限约束（约 110 MB 稳态），不需要额外总预算熔断。

### 8. 已知边界与未做项

| 项 | 说明 |
| --- | --- |
| 人脸子服务 404（worker WARNING 132 条） | 审计已判定是**接口路径/契约不匹配的业务问题**，不是日志问题；修复属业务改动，按审计「不评估业务逻辑修复」的范围未在本次处理，修好后 WARNING 自然消失 |

| 诊断包 zip（路线图 §4 P2-2） | 未做：Web/Mobile 已有「复制诊断信息」，插件可查看/复制 session 日志；单机本地场景不需要再打 zip（按需再加） |

| 未引入 OpenTelemetry / 远程日志 | 单机本地部署，contextvar + 文件 + SQLite 足够（审计 §4） |
| `LOG_FORMAT=json` 只覆盖 Python 进程 | 前端/子进程各有自己的日志形态（f2 输出单独文件、face-service 文本格式）；本地排障够用 |
| 前端诊断不新增后端接口 | 诊断文本在浏览器内拼装并复制/分享，不含远程上传 |
| 服务重启 | 按项目约定由用户手动执行；本说明不包含自动重启脚本调用 |

### 10. 回滚

- 日志格式/降噪出问题：`LOG_LEVEL=WARNING` 或临时移除 `logging_config.setup_logging` 调用即可回到 uvicorn 默认（不推荐，会再次丢 `app.*` 日志）；
- 前端/移动端诊断日志：`import.meta.env.DEV` / `__DEV__` 控制级别，生产只记 warn/error；
- 台账接口与前端入口互不影响任务执行，可不启用。
