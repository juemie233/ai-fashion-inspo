# 数据库审查（2026-11-06）

> 状态：审查报告（只读）
> 范围：主业务库 `backend/fashion_inspo.db`（SQLite）、`face-service/face_service.db`、`f2_hash_cache.db`、媒体存储 `G:/fashion-inspo-storage`、数据库备份 `E:/fashion-inspo-backups`
> 方法：只读连接（`mode=ro`）+ PRAGMA 检查 + 表/索引/列统计 + 外键与完整性检查 + 查询计划 + 文件与数据库对账
> 结论：**数据本身很干净，结构上有一个必须修的真实缺陷**——`inspirations.source_platform_id` 的唯一索引在库里仍是「全量唯一」，而代码与迁移都要求「仅未删除行唯一」。当前有 **1,706 条垃圾桶素材仍占用平台 ID**，会使「删除后通过上传/from-url 等非采集路径重新入库同一平台 ID」在查重通过后撞唯一索引，返回 500（采集路径另有 URL 墓碑拦截，不受此条直接影响）。除此之外，完整性、外键、时间、JSON、媒体文件对账均通过。

## 2. 审查范围与方法

### 2.1 实际检查内容

- 库文件、WAL、页数、freelist、journal/synchronous/auto_vacuum/cache/mmap 等 PRAGMA；
- 35 张表、103 个索引（含 8 个自动索引）的列、索引、外键、部分索引谓词；
- 全库 `integrity_check` / `quick_check` / `foreign_key_check`；
- 软删除不变量、时间倒挂、JSON 合法性、空值、重复、孤儿关联；
- 大字段体积（按 `LENGTH()` 汇总）；
- 关键查询的 `EXPLAIN QUERY PLAN` 与只读实测耗时；
- 素材路径逐条 `os.path.isfile` 对账，并反向检查磁盘孤儿文件；
- 备份目录、备份日志、磁盘余量。

### 2.2 口径与限制

- 所有数据库查询均使用 `file:...?mode=ro` 只读连接；**未执行 VACUUM、ANALYZE、DELETE、UPDATE 或迁移**。
- 本机 SQLite 未编译 `dbstat` 虚拟表，无法按表精确拆分页占用；第 5 节的「体积」是按列长度统计的业务载荷，不等于表+索引的磁盘占用。
- 查询耗时是单次只读实测（本机、缓存冷热混合），只用于判断量级，不是基准测试。
- 未做写入并发压测；WAL/锁行为只做配置与现场状态检查。
- 未审查 `f2_hash_cache.db` 的业务语义，只统计其规模；`face-service/face_service.db` 为空库。

## 5. Schema 与约束审查

### 5.1 核心发现：平台 ID 唯一索引与代码不一致

**现场 SQL（库中）：**

```sql
CREATE UNIQUE INDEX ix_inspirations_source_platform_id
ON inspirations (source_platform_id);
```

**ORM（`backend/app/models/inspiration.py:33-42`）：**

```python
Index(
    "ix_inspirations_source_platform_id",
    "source_platform_id",
    unique=True,
    sqlite_where=text("deleted_at IS NULL"),
)
```

**迁移（`backend/alembic/versions/02b765c8c4e5_平台id部分唯一索引_垃圾桶可重新采集.py`）：**

```python
op.drop_index('ix_inspirations_source_platform_id', table_name='inspirations')
op.create_index(
    'ix_inspirations_source_platform_id',
    'inspirations',
    ['source_platform_id'],
    unique=True,
    sqlite_where=sa.text('deleted_at IS NULL'),
)
```

**影响链：**

1. `check_platform_id_duplicate()` 只查 `deleted_at IS NULL`（`inspiration_dedupe.py:77-95`），所以垃圾桶里的同 ID 不算重复；
2. 调用方继续插入新行；
3. 全量唯一索引把垃圾桶行也算进去 → `UNIQUE constraint failed`；
4. 接口通常表现为 500，而不是预期的「允许非采集路径重新入库」或明确的 409。

**当前数据规模：**

- 垃圾桶素材 2,071 条；
- 其中 **1,706 条** `source_platform_id` 非空，仍占用唯一值；
- 365 条没有平台 ID，不受影响；
- 全库当前没有重复 `source_platform_id`，所以不是「已经重复」，而是「垃圾桶占位」。

**为什么门禁没拦住：**

- `python scripts/check_alembic_drift.py` 返回 `[ok] ORM 与数据库结构一致`；
- 该脚本底层是 `alembic check`；SQLite 方言下它没有把 `sqlite_where` 谓词差异判为漂移；
- `backend/scripts/check_fresh_migrations.py` 只验证「空库 upgrade head」，空库会建出正确的部分索引，所以也永远绿；
- `ensure_schema()` 的 `_SCHEMA_INDEXES` 只补 5 个列索引（`inspirations.is_ai_generated/content_hash/deleted_at`、`tags.pinned`、`task_queue.heartbeat_at`），不会修复这个索引。

**根因判断：**

`run_migrations()` 对「有业务表但没有 `alembic_version`」的历史库执行 `command.stamp(cfg, "head")`（`backend/app/database.py:116-120`），只写版本号、不执行任何迁移。如果库是在该迁移之前由 `create_all` 建的，就会被直接标记为 head，索引迁移被跳过。当前库满足「版本是 head、索引却是旧形态」的特征。最终需要在库上确认历史，但机制上这是最合理的解释。

### 5.2 索引与查询

**索引总量**：103 个（含 8 个自动索引）。ORM 元数据与库逐索引比对后，除上面的谓词差异外，其余索引名称/列/唯一性一致；列可空性也 0 差异。

**可优化的索引：**

| 表 | 现状 | 建议 |
| --- | --- | --- |
| `inspirations` | 只有单列 `deleted_at`、`created_at`、`quality_status`、`source_type` | 默认列表是 `deleted_at IS NULL ORDER BY created_at DESC`，建议复合 `(deleted_at, created_at DESC)`；常用筛选再加 `(deleted_at, quality_status, created_at)`、`(deleted_at, source_type, created_at)` |
| `task_queue` | 单列 `status`、`priority`、`next_retry_at` | 领取任务是 `status='pending'` + `ORDER BY priority DESC, id`，建议 `(status, priority, id)`；列表 `ORDER BY created_at DESC` 可加 `(created_at)` |
| `inspiration_tags` | 已有 `tag_id` 索引；PK 是 `(inspiration_id, tag_id)` | 按标签反查素材时，`tag_id` 索引回表取 `inspiration_id`；可考虑覆盖索引 `(tag_id, inspiration_id)` |
| `ai_extracted_tags` | 只有 `log_id`、`tag_id` 单列索引，无唯一约束 | 当前 0 重复，但建议加 `UNIQUE(log_id, tag_id)`，防止重复分析继续写入重复标签 |
| `task_run_logs` | 单列 `task_id`、`started_at` | 按任务查台账建议 `(task_id, started_at)`；当前 70 行，优先级低 |

**冗余索引：**

- `inspiration_face_detections.inspiration_id` 是 `(inspiration_id, face_index)` 的前缀，单列索引可删除（省写放大）。
- `collections` 的 `ix_collections_name` 与两个部分唯一索引不完全重复（根/子命名空间不同），保留。

**外键缺前导索引（低优先级，均是小表）：**

- `collection_items.inspiration_id`（2,245 行；删除素材时级联扫描）
- `collections.cover_inspiration_id`（21 行）
- `person_groups.primary_blogger_id`（2 行）

### 5.3 查询计划与统计信息

`sqlite_stat1` **不存在**，说明没有执行过 `ANALYZE`。当前关键计划：

```text
默认列表：
  SEARCH inspirations USING INDEX ix_inspirations_deleted_at (deleted_at=?)
  USE TEMP B-TREE FOR ORDER BY

按标签过滤：
  SEARCH it USING INDEX ix_inspiration_tags_tag_id (tag_id=?)
  SEARCH i USING INDEX sqlite_autoindex_inspirations_1 (id=?)
  USE TEMP B-TREE FOR ORDER BY

任务领取：
  SEARCH task_queue USING INDEX ix_task_queue_status (status=?)
  USE TEMP B-TREE FOR ORDER BY

任务列表：
  SCAN task_queue
  USE TEMP B-TREE FOR ORDER BY
```

只读实测（单次，非基准）：

| 查询 | 结果 | 耗时 |
| --- | ---: | ---: |
| 默认列表第 1 页（50 条） | 50 行 | 33.2 ms |
| 默认列表 OFFSET 10000 | 50 行 | 75.5 ms |
| 标签过滤（tag_id=18，18,419 条关联） | 50 行 | 127.0 ms |
| 标题 LIKE '%白色%' | 50 行 | 13.9 ms |
| 任务列表 50 条 | 50 行 | 47.4 ms |

当前规模下可以接受，但默认列表每次都排序 31,691 条 active 素材；数据量翻倍后，分页和轮询会先撞到这里。`caption LIKE '%...%'` 是全表扫描，目前 13.9ms 是因为 33k 行还小；如果搜索依赖它，后续应考虑 FTS5。

### 5.4 其他 Schema 观察

- `task_queue.stage_state`：709 行全 NULL，字段存在但未使用；
- `ai_quality_review.confidence`：14,697 行全 NULL，字段存在但未写入；

## 8. 性能与查询

### 8.1 连接与缓存配置

- `cache_size=-2000`（约 2MB）偏小。546MB 库、频繁扫描 31k 素材/795k 关联时，建议 API/worker 连接设 `PRAGMA cache_size=-65536`（64MB）或按内存调整。
- `mmap_size=0`；64 位环境可评估 `PRAGMA mmap_size=268435456`（256MB），减少读放大。
- `temp_store=0`（默认文件）；当前排序会产生临时 B-tree，若内存允许可设 `temp_store=MEMORY`，但要注意 worker 并发内存。
- `synchronous=2`（FULL）；WAL 下可评估 `NORMAL` 换取写入吞吐，但本项目是本地单机、写并发不高，FULL 的耐久性更稳妥，不建议轻易改。
- `auto_vacuum=0`：清理大字段后文件不会自动缩小；需要 `VACUUM`（要求约等于库大小的临时空间，C 盘 21GB 足够）。

### 8.2 关键查询

- 默认列表：`deleted_at` 索引 + 临时排序；数据量再增长会变慢；
- 标签过滤：先取 `tag_id` 关联（最多 1.8 万行），再回表 + 排序；127ms 已经接近可感知阈值；
- 任务领取：`status` 索引 + 排序；当前 pending 为空，量小；
- 任务列表：全表扫描 709 行 + 排序；47ms 主要来自页缓存冷；
- 标题 LIKE：全表扫描；当前 13.9ms，但属于 O(n)。

**建议**：先加 `(deleted_at, created_at)` 与 `(status, priority, id)` 两个复合索引，再跑 `ANALYZE`，用 `EXPLAIN QUERY PLAN` 验证不再出现 `TEMP B-TREE`；不要一次性加很多索引，写放大和迁移成本都要算。
