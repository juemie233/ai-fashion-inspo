# 数据库迁移与回滚手册

> **状态**：现行｜编写日期 2026-11-01｜依据 `backend/alembic/`、`app/database.py`、`backend/scripts/check_*.py`
> **一句话**：Alembic 是唯一的正式迁移工具；启动时自动 `upgrade head`，迁移失败会降级到 `ensure_schema` 兜底并记 ERROR。
> **前提**：SQLite 单文件库，WAL 模式；**worker 不跑迁移**，由 API 进程负责。

---

## 1. 什么时候需要迁移

| 改动 | 是否需要迁移 |
| --- | --- |
| 新增表 / 字段 / 索引 / 外键 | **必须** |
| 删除或重命名列、改约束、改 NOT NULL | **必须**（`create_all` 与手写 ALTER 做不到） |
| 纯数据回填（不改结构） | 可放迁移，也可单独写回填脚本；大数据量建议脚本 |
| 只改 ORM 默认值 / 校验逻辑 | 不需要 |

> 旧做法（往 `db_migrations.py` 的 `_SCHEMA_COLUMNS` 手写补列）**不再新增**；`ensure_schema` 只作兼容兜底。

---

## 2. 文件与真源

| 位置 | 作用 |
| --- | --- |
| `backend/app/models/**` | ORM 模型（结构真源） |
| `backend/alembic/versions/*.py` | 迁移脚本，当前 **46** 个，基线 `1aef95ac5977_baseline.py` |
| `backend/alembic/env.py` | 迁移环境：同步 SQLite 引擎；URL 取 `ALEMBIC_DB_URL` > `alembic.ini` > `settings` |
| `backend/app/database.py` | 启动时 `run_migrations()`；空库 upgrade、历史库 stamp、已管理库 upgrade |
| `backend/scripts/check_fresh_migrations.py` | 门禁：临时空库跑 `upgrade head` + `alembic check` |
| `backend/scripts/check_alembic_drift.py` | 门禁：现有库结构与 ORM 是否一致（`alembic check`） |

> `env.py` 的 `fileConfig(..., disable_existing_loggers=False)` **不要改回默认值**：否则服务进程执行迁移后，uvicorn 与 app 的 logger 会被整体禁用，接口 500 时日志里一行都没有。

---

## 3. 启动时的迁移逻辑

`app.main` 启动阶段调用 `database.run_migrations()`：

| 库状态 | 行为 |
| --- | --- |
| 空库（无业务表） | `alembic upgrade head`，由基线建出全部表 |
| 历史库（有业务表、无 `alembic_version`） | `stamp head`，只记录版本，不重建表 |
| 已管理库 | `alembic upgrade head` 应用增量 |
| 迁移抛错（锁竞争/脚本缺失） | 记 **ERROR**，降级到 `ensure_schema` 兜底，不阻断启动 |

- 同步引擎连接超时 10 秒：API 与 worker 并发启动时，worker 只 `create_all` + `ensure_schema`，不会抢迁移锁；
- 迁移文件位置用绝对路径，避免 CWD 不对导致找不到脚本。

## 4. 标准工作流

```bash
cd backend

# 1) 改 ORM 模型
# 2) 生成迁移（先确认本地库是最新的）
alembic upgrade head
alembic revision --autogenerate -m "新增收藏合集表_collections"

# 3) 人工审查生成的脚本（重点：有没有把无关漂移一起带进来）
# 4) 应用到本地库
alembic upgrade head

# 5) 门禁自检
python scripts/check_fresh_migrations.py   # 空库能否从零建出
python scripts/check_alembic_drift.py      # 现有库与 ORM 是否一致
```

**审查要点**：

- `--autogenerate` 会检测到**所有**历史漂移；只保留本次改动的语句，其余删掉；
- 索引/约束的创建改成「先 inspect 再建」，保证空库与老库都能跑（历史踩坑：链尾对齐迁移在空库上撞 `index already exists`，整条链断掉）；
- 迁移文件名格式：`<revision>_<中文描述>.py`；`down_revision` 必须指向当前 head，避免多 head。

## 5. 常用命令

| 命令 | 用途 |
| --- | --- |
| `alembic current` | 当前库版本 |
| `alembic history --verbose` | 迁移链历史 |
| `alembic heads` | 当前 head（应只有一个） |
| `alembic upgrade head` | 升级到最新 |
| `alembic downgrade -1` | 回退一步（仅开发环境） |
| `alembic merge -m "merge heads" <rev1> <rev2>` | 合并多 head |
| `ALEMBIC_DB_URL=sqlite:////tmp/test.db alembic upgrade head` | 对临时库执行，不碰真实库 |

> 项目测试与门禁统一用 `ALEMBIC_DB_URL` 指向临时库；不要在测试里跑真实库的迁移。

## 6. SQLite 特有限制

| 限制 | 做法 |
| --- | --- |
| 不支持直接 `ALTER COLUMN` / 改约束 | 用 `op.batch_alter_table(...)`（内部重建表） |
| 部分唯一索引 | `op.create_index(..., unique=True, sqlite_where=sa.text("deleted_at IS NULL"))` |
| 删除索引/约束前先判断存在 | `inspect(bind).get_indexes(...)`，避免空库/老库路径不一致 |
| `IN (...)` 变量上限 | 数据迁移分批，每批 ≤500（参考 `task_runners/common._chunked`） |
| 长事务阻塞写 | WAL 下读不阻塞写，但写与写仍串行；迁移尽量短，避免在事务里调外部服务 |

**必须遵守的模型约定**（迁移时不要破坏）：

- `inspirations` 主键是 UUID 字符串；其余业务表自增整数；
- 软删除表上的唯一约束必须用**部分唯一索引**（`deleted_at IS NULL`），否则素材进垃圾桶后平台 ID 被永久占死；
- 软删除三字段同真同假（`verify_trash_invariants`）；
- 时间列存 naive UTC，API 输出带 `Z` 后缀。

## 7. 数据迁移与回填

- 迁移里只做「结构 + 必要的轻量回填」；大数据量回填单独写脚本（放 `backend/scripts/`，argparse 入口、只读连接/分批提交）；
- 回填脚本必须**幂等**：重复执行不改变结果（按主键/条件过滤）；
- 破坏性回填（删列/改语义）前先备份，见 [数据备份与恢复](数据备份与恢复.md)；
- 回填完成后跑一次 `check_alembic_drift.py`，确认没有顺带改坏结构。

## 8. 回滚策略

| 场景 | 做法 |
| --- | --- |
| 开发环境刚加了迁移、还没写数据 | `alembic downgrade -1`，或删掉迁移文件后重新生成 |
| 迁移已应用到真实库 | **先停服务 + 备份**，再评估：能安全 `downgrade` 就降；涉及数据丢失时优先「恢复备份」而不是降级 |
| 迁移导致服务起不来 | 看 `logs/backend.log` 的 Alembic ERROR；必要时恢复备份后 `alembic upgrade head` |
| 从旧备份恢复 | **恢复后必须 `alembic upgrade head`**，否则新代码查新列会直接报错（恢复文档已强调） |
| 多 head | `alembic merge`，不要手工改 `down_revision` |

> `downgrade` 只保证结构回退，不保证数据回来；有 `DROP TABLE` / `DROP COLUMN` 的迁移，优先备份恢复。

## 9. CI 门禁

`bash scripts/ci/test.sh` 中的两项（与 GitHub Actions 对齐）：

1. **迁移链自检**（`check_fresh_migrations.py`）：临时目录建空库 → `upgrade head` → `alembic check` → 删库；全程不碰真实库。它断的是「换机器/恢复服务器后按迁移建库」这条路；
2. **ORM/库漂移**（`check_alembic_drift.py`）：`alembic check`，模型先改、迁移没跟上会显式失败。

> 历史教训：本地建库走 `create_all + stamp`，迁移链平时不执行，所以空库升级炸了也发现不了；这两项门禁就是补这个盲区。

## 10. 常见故障

| 现象 | 原因 / 处理 |
| --- | --- |
| 启动日志有「Alembic 迁移失败（降级到 ensure_schema 兜底）」 | 锁竞争 / 脚本缺失 / SQL 错误；先看完整异常，别依赖兜底继续跑 |
| 新列不存在（`no such column`） | 迁移没执行或执行失败；`alembic current` 看版本，`upgrade head` |
| `database is locked` | 迁移与备份/worker 抢写锁；停服务后单独执行迁移 |
| `Multiple head revisions` | 两条分支各自生成迁移；`alembic heads` 后用 `merge` |
| 空库升级失败 | 跑 `check_fresh_migrations.py` 复现；通常是索引已存在或约束假定老库 |
| `alembic check` 报一堆漂移 | 上次 autogenerate 没裁剪干净；对齐后再提交，避免债越滚越大 |
| 迁移后时间差 8 小时 | 时间格式口径被改；见 CLAUDE.md「API 设计约定」 |
