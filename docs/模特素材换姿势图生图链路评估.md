# 「模特素材 → 详情页按钮 → 图生图工作台换姿势」链路评估

> **状态**：已归档（2026-10-31）。路径一已按本评估落地（见 [实现说明](姿势图库换姿势（路径一）实现说明.md)）；
> 实际效果与最终结论见 [换姿势方向结项报告](换姿势方向结项报告-2026-10-31.md)。


> 评估对象：把姿势图库 **ai-pose-gallery-zh** 接入一条「选中模特素材 → 跳到图生图网页 → 选姿势图 → 改姿态 → 出图」的链路
> 评估时间：2026-10-30　评估范围：**仅方案与可行性，不写代码**
> 前置结论来自同目录两份评估：[合并版](AI姿势图库接入图生图可行性评估-合并版.md)（技术栈、生成能力缺口、合规风险）
> 本机环境事实：`fashion-inspo` 已有 i2i 链路（ComfyUI + Qwen-Image 2.1，参考图 1~10 张，最大 1024²；16 GB 显卡实测 1024² 文生图约 6.8 s、i2i 单图约 21 s；已有任务队列/生成历史/候选两段式入库）

## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 这个效果能不能做？ | **能，但不是"在当前项目里加一个按钮"就能闭环**。它实际是 **A（有模特素材的素材前端）→ B（图生图工作台）→ C（姿势图库 ai-pose-gallery-zh）** 三个角色的协同；ai-pose-gallery-zh 只能承担 **C**（姿势资产 + 选图 + 可选深链），**B 的生成能力与 A 的素材详情页都不在它内部**。 |
| 当前项目（ai-pose-gallery-zh）能否直接实现？ | **不能闭环**：它是纯静态站，没有模特素材、没有生成、没有存储/鉴权（详见先前评估）。在它内部能落地的是：姿势数据 CORS 化、按 id 的图片直链、可选的 `?pose=<id>` 深链、"在 i2i 中使用此姿势"按钮——**改动很小（1~2 人日级）**。 |
| 推荐路径 | **路径一（最省事）**：B 直接复用我们现有的 `fashion-inspo` 出图页（已有 i2i + 队列 + 候选入库），A 用素材库详情页加「换个姿势」按钮，C 以"构建期同步全年龄子集数据 + 缩略图"或"CORS 化只读接口"的方式接入。**PoC 3~5 天 → MVP 6~8 人日**，主要风险是"换姿势后身份/服装是否保得住"，而不是工程打通。 |
| 一句话 | **链路的"接线"很简单，难的是"换姿势后还像不像原来这个模特"**；建议先做 PoC 用样张验证质量，再决定是否投入产品化。 |

## 1. 需求拆解与角色澄清

用户描述的四个步骤，对应三个系统角色：

| 步骤 | 角色 | 现状归属 |
| --- | --- | --- |
| 1. 前端网页中已有模特的某个素材 | **A：素材前端**（素材库/详情页，持有模特照片、穿搭素材） | 不在 ai-pose-gallery-zh（该站只有 1439 张素体/姿势参考图，没有"模特照片素材"） |
| 2. 详情页按钮 → 跳转图生图网页 | **A → B 的衔接** | 按钮加在 A；ai-pose-gallery-zh 不承担 |
| 3. 在图生图网页中选择姿态图、改变模特姿态 | **B：图生图工作台 + C：姿势图库** | B 需要新建/复用；C = ai-pose-gallery-zh（姿势数据与图片） |
| 4. 最终生成图片 | **B + 生成后端** | B 及其后端；ai-pose-gallery-zh 无生成能力 |

> **需求角色说明（两种可能读法，结论一致）**
> - 读法一（推荐）：A = 我们自己的素材库（`fashion-inspo` 素材/模特详情页），B = 现有出图页升级为"带姿势库的工作台"，C = ai-pose-gallery-zh。此时 A/B 是现成或近现成的，C 作为姿势数据源接进来。
> - 读法二：A = ai-pose-gallery-zh 的前端灯箱（把"素体模特"当作"模特素材"）。那么按钮可直接加在灯箱里，但 B 依然必须是外部的生成服务；点进去后"选姿势"这一步会显得重复（因为起点本身就是姿势图），体验上不自然，不如让 C 直接提供 `?pose=<id>` 深链到 B。

## 2. 当前项目（ai-pose-gallery-zh）能做到什么，缺什么

### 2.1 现成可用的能力（已实测）

| 能力 | 事实 | 对本链路的价值 |
| --- | --- | --- |
| 姿势元数据 | `data/pose-zh.json` 1439 条，字段 `id / 体系 / 分类 / 姿势名称 / 角度 / 缩略图 / 原图 / 检索`；4 体系、26 分类、5 角度 | 可直接作为"姿势选择器"的数据源 |
| 图片直链 | 实测 URL 规律稳定：`https://ai-pose-gallery.anhao.app/thumbs/<id>.jpg`（约 12 KB，300×400）与 `/img/<id>.png`（900×1200，白底线稿）均 200 可访问、长缓存 | B 用 `<img>` 直接展示姿势缩略图/原图，**无需 CORS**；生成后端按 URL 服务端拉取也可行 |
| 静态托管与缓存 | Cloudflare Pages，`_headers` 对 `img/`、`thumbs/` 一年强缓存 | 姿势图分发成本低、延迟低 |
| 数据可复制 | 仓库可 clone，数据与图片可一次性同步 | B 也可离线镜像全年龄子集，不依赖在线站点 |

### 2.2 关键缺口（实测确认）

| 缺口 | 实测 | 影响 |
| --- | --- | --- |
| **无 CORS 头** | `curl -I https://ai-pose-gallery.anhao.app/data/pose-zh.json`：无 `access-control-allow-origin`；图片同样无 | B 的前端**不能跨域 `fetch` 姿势 JSON**（`<img>` 展示不受影响）；需给 C 加 CORS 或在 B 侧镜像数据 |
| 无生成/后端/存储/鉴权 | 全部不存在（见合并版评估 §1.3、§2） | B 的生成能力必须由外部提供（现有 `fashion-inspo` 或独立服务） |
| 无"模特素材"概念 | 数据里只有素体姿势图，无真人模特照片/穿搭素材 | "已有模特的某个素材"必须来自 A，而不是 C |
| 无深链参数 | 站点无路由参数处理 | 想"从 C 一键带姿势 id 跳到 B"需加一小段 JS 支持；从 A 跳到 B 则与 C 无关 |
| 内容属性 | 18+ 体系 674/1439（46.8%），全年龄子集 765 张 | 姿势选择器必须按 `age_rating` 过滤，只开放全年龄子集 |

### 2.3 C 侧最小改造清单（若让 gallery 作为在线姿势源）

1. `_headers` 增加 CORS（只放行 B 的正式域名与本地开发），或单独输出一个 `data/pose-api.json`（轻量：id/名称/角度/缩略图/原图/分级）；
2. 可选：灯箱加「在 i2i 中换这个姿势」按钮，生成 `https://<B>/i2i?pose=<id>` 深链；
3. 可选：构建期筛选出全年龄子集（765 条）单独输出 `pose-allages.json`；
4. **不新增生成能力**（延续合并版评估的结论：公开站在线生成不建议）。
5. 控制图（lineart/canny/openpose）**不建议塞进静态仓库**（100~300 MB），由 B 侧按需生成/缓存或放 R2。

## 3. 衔接方式：素材详情页按钮 ↔ 图生图网页

### 3.1 五种衔接方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **① URL 深链（推荐）** | 详情页按钮 `window.open(B + "?src=<素材引用>&from=<来源>")`；B 启动时解析参数并加载素材 | 无状态、可分享、可回退、实现最简；对新标签页/移动端友好 | 素材必须是 B 能访问的地址（公开 URL 或短时签名 URL）；大图/私有素材需签名 | A、B 不同产品/不同域时首选 |
| **② 同域路由跳转** | 若 A 与 B 在同一前端（如都在 `fashion-inspo`），直接 `router.push({name:'generate', query:{ref:<素材id>}})` + 前端状态 | 最省事：无跨域、无签名、可用前端 store 传大对象 | 仅限同域/同产品 | **路径一推荐**（B 复用现有出图页） |
| ③ iframe + postMessage | A 里嵌 B，或 B 里嵌 C；`postMessage` 传素材/姿势 | A 不离开页面、体验连贯 | 跨域 CSP/X-Frame、移动端 iframe 体验差、状态与鉴权复杂 | 仅做"姿势选择器"嵌入时可用 |
| ④ 剪贴板交接 | 按钮把图片 + JSON 复制到剪贴板，用户到 B 粘贴 | 零后端、零跨域 | 用户要多一步操作；浏览器剪贴板权限不稳定；大图/移动端差 | 兜底/低频 |
| ⑤ 服务端交接 token | A 后端把素材转存到临时存储，生成一次性 token URL，B 用 token 拉取 | 支持私有素材、可审计、可限时 | A/B 都需要后端与共享存储；成本最高 | 素材私有、合规要求高的生产环境 |

### 3.2 推荐衔接设计（路径一：B 复用现有出图页）

```text
[素材详情页] --点击「换个姿势」--> [出图页 /generate?ref=<素材id>&pose_lib=1]
                                      │
                                      ├─ 左侧：素材预览（已选为 i2i 参考图，恢复为现有 reference_ids）
                                      └─ 右侧：姿势选择器
                                             ├─ v1：弹窗内嵌「姿势库」（读镜像的全年龄子集数据）
                                             └─ v2：打开 C 的页面（?pose= 深链）或 iframe 选图

[选姿势] --> [参数面板：强度/尺寸/seed/模式] --> [生成任务] --> [候选区对比/下载/入库]
```

- **素材交接**：同一产品内用路由 + 素材 id（A 与 B 共享后端/素材库）即可；若 B 是独立产品，用 URL `?src=<签名URL>` 或 `?material_id=` + B 后端回调 A 的素材接口换取图片（需要 A 提供凭据/公开接口）。
- **姿势交接**：选姿势本质是"选中一条姿势记录"（`pose_id`），交接给 B 的生成参数（不是把姿势图当用户上传图）。`pose_id` 也可直接用于深链/日志/复现。
- **返回路径**：`?return=<A的地址>`（可选），生成成功后"回传"成 B 的素材（或 A 直接接收生成结果），避免用户手动搬运。
- **安全**：签名 URL 有有效期、只读、绑定 B 域名；CORS 白名单只放 B；C 侧不做鉴权（静态），敏感能力全部在 B 后端。

### 3.3 从 C 到 B 的另一条入口（可选，反向）

C 的姿势灯箱加「用这个姿势生成」→ `https://<B>/i2i?pose=<id>`。这样用户也可以"先在姿势库挑姿势、再去配模特"；与需求主链方向相反，但成本极低（一行深链），可作为补充入口。

## 4. 选姿态图 → 改变模特姿态 → 出图：链路可行性

把这条链路拆成 5 个环节，逐个判断：

| 环节 | 方案 | 可行性 | 主要风险/备注 |
| --- | --- | --- | --- |
| **① 姿势资产获取** | C 的 `pose_id` → `/img/<id>.png`（900×1200 白底线稿）；B 用 `<img>` 展示、后端按 URL 拉取 | **高** | 需要 CORS 仅在前端 fetch JSON 时需要；图片直链无需 CORS；18+ 需过滤 |
| **② 控制信号生成** | 路线 A：**lineart/canny**（线稿本身就是线稿，可直接当控制图，无需姿态估计）；路线 B：OpenPose/DWPose 骨架（需对素体线稿做姿态估计，跨域输入，双人/俯视/仰视不稳） | **A 高 / B 中** | 建议先做 A；B 只在对"关节级一致"有硬要求时再评估 |
| **③ 主体保持（像原模特）** | 路线 1：SDXL + ControlNet(lineart) + IP-Adapter/FaceID/InstantID 保身份与服装；路线 2：Qwen-Image-Edit / FLUX.2 multi-reference 双参考图指令编辑（源照片 + 姿势线稿） | **中~高** | 身份漂移、服装/肤色/发型变化是主要失败点；双人姿势、遮挡、手脚细节更差；不同路线需样张对比 |
| **④ 生成执行** | 本地 ComfyUI（已有：16 GB 卡，Qwen-Image 2.1 i2i 单图约 21 s、1024²；SDXL+ControlNet 预计 5~15 s/张）或云端 API | **高** | 显存 16 GB 下分辨率/步数受限（现有出图页已有尺寸与显存守门）；排队/超时/失败重试需沿用现有任务队列 |
| **⑤ 结果交付与迭代** | 候选区对比（原图/生成图）、多张候选、重跑、下载、入库（现有两段式）；带 `pose_id` 记入生成历史便于复现 | **高** | 生成历史/候选入库/失败文案都是现成能力，几乎零改造 |

### 4.1 三条推荐技术路线的对比（PoC 需要实测）

| 路线 | 输入 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- | --- |
| R1：Qwen-Image-Edit 双参考图 | 模特素材 + 姿势线稿 + 指令 | 复用现有 ComfyUI/模型；自然、链路最短 | 姿势保真不保证；双图关系靠提示词，可能"各画各的" | **PoC 首选**（成本最低） |
| R2：SDXL + ControlNet(lineart/canny) + IP-Adapter | 模特素材（身份/服装）+ 姿势线稿控制图 | 姿势/构图可控、可批量 | 需新增 SDXL+ControlNet+IP-Adapter 模型与工作流；显存/速度需实测；融合质量需调参 | **质量优先时的主路线** |
| R3：SDXL + ControlNet(OpenPose) + FaceID | 模特素材 + 骨架图 | 关节级姿势最准 | 骨架提取对素体线稿是跨域，双人/俯仰易失败；人脸模型许可与肖像合规风险 | 二期，仅在 R1/R2 不达标时评估 |

### 4.2 质量验收（PoC 建议）

- 样本：20~30 张，覆盖 4 体系 × 5 视角 × 单人/双人 × 全年龄子集，模特素材覆盖正/侧/半身；
- 指标：姿势保真（人工 1~5 分或骨架距离）、身份相似（人工/人脸相似度）、服装一致性、解剖错误（手/脚/多指）、背景与构图、耗时与显存、失败率；
- 通过线：姿势保真 ≥4 分占比 ≥70%、身份"能认出是同一人"≥80%、单张 ≤30 s（本地）、失败率 ≤10%；不达标则回退 R1 或只做"风格参考"不承诺姿势一致。

### 4.3 链路级风险（除质量外）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **内容合规** | C 的 18+ 占 46.8%；成人姿势用于换装生成在多数平台/法规下不可行 | 姿势选择器只开放全年龄子集（765 张）；B 侧审核与限额；不公开生成结果 |
| **版权** | C 的姿势图版权归原作者、MIT 不覆盖；生成图基于该姿势可能构成演绎 | 仅内部/自用；公开前取得许可或替换自有姿势资产；保留来源与删除通道 |
| **肖像/同意/深伪** | 若模特素材是真人（尤其他人照片），换姿势属于深度合成 | 默认只对自有/授权素材开放；明示同意、AIGC 标识、不留存原始/生成图可选 |
| **素材比例/构图** | 姿势图 900×1200（3:4），素材可能是任意比例/多人/特写 | 进入 B 时做裁剪对齐提示；单人全身优先；多人素材先裁剪 |
| **身份漂移** | 换姿势后脸/发型/身材变化 | PoC 选路线；必要时加 FaceID/IP-Adapter；结果给"身份保真度"提示与重试 |
| **性能与成本** | 本地 GPU 排队/显存；云端按张计费 | 沿用现有互斥/队列与显存守门；限额与预算告警 |
| **可复现性** | 同姿势/同素材结果不可控 | 生成历史记录 `pose_id + seed + 模型/工作流版本`（现有历史已能存参数） |

## 5. 推荐落地形态与工作量的分级

### 5.1 路径一（推荐）：A/B 复用 `fashion-inspo`，C 做姿势数据源

| 改动 | 说明 | 量级 |
| --- | --- | --- |
| A 素材详情页 | 加「换个姿势」按钮 → 跳转出图页并带素材 id（同域路由，最简） | 0.5 人日 |
| B 出图页 | 加"姿势选择器"（弹窗/侧栏）：列表 + 预览 + 搜索/体系/角度筛选（复用现有出图页样式）；选中写入生成参数 `pose_id`；调用现有生成接口 | 2~3 人日 |
| 姿势数据接入 | 构建期同步 C 的全年龄子集数据（765 条）+ 缩略图到本机/仓库静态目录（约 10 MB 数据 + 10 MB 缩略图）；或前端直连 C（需 C 加 CORS） | 1~2 人日 |
| 生成后端 | 新增 ComfyUI workflow：R1（Qwen-Image-Edit 双参考）或 R2（SDXL+ControlNet lineart）；接入现有任务队列/候选/历史；`pose_id` 与参考图一起落库 | 2~3 人日（复用现有链路） |
| 联调/验收 | 20~30 样本质量评估、失败文案、限额 | 1~2 人日 |
| **合计（MVP，内部可用）** | | **6~8 人日**（不含合规评审与生产化） |

### 5.2 路径二（独立 i2i 工作台）

若"图生图网页"要求是独立产品（不能复用 `fashion-inspo`）：B 需要新前端 + 新后端/存储 + 鉴权 + 计费，参考合并版评估的 P1 方案，约 **5~7 人日**起（仅受控内部用），公开化再 +2~4 周（合规/审核/限额）。

### 5.3 阶段建议

1. **Phase 0（3~5 天）PoC**：20~30 样本，对比 R1/R2（必要时 R3），只验证"选姿势 → 出图 → 像不像/姿势对不对"，不改产品；
2. **Phase 1（MVP，6~8 人日）**：路径一，内部可用；姿势选择器 + 现有出图页 + R1/R2 工作流；只开放全年龄子集；加 AIGC 标识与来源记录；
3. **Phase 2（产品化）**：若质量达标且确有需求，再讨论公开入口、审核、限额、授权与法务；C 侧仅做 CORS/深链/CORS 化数据等轻改造，**不在画廊内加生成**。

## 6. 最终结论

1. **可实现性**：目标效果整体**可实现**，但必须按 A（素材前端）→ B（图生图工作台）→ C（姿势库）三段式落地；**在当前项目 ai-pose-gallery-zh 内无法闭环**（它没有模特素材、没有生成/存储/鉴权），它只能做 C：提供姿势数据、图片直链、可选深链与 CORS 化——这部分改动很小（1~2 人日级）。
2. **衔接方式**：优先 **URL 深链**（跨产品）或**同域路由**（复用现有出图页）；素材用"公开 URL / 短时签名 URL / material_id + 后端换取"三种交接之一；姿势用 `pose_id` 交接而不是传图；可选 iframe 仅用于嵌入姿势选择器；剪贴板只作兜底。
3. **生成链路**：选姿态图 → 控制图（lineart/canny 优先，OpenPose 谨慎）→ 主体保持（Qwen-Image-Edit 双参考或 SDXL+ControlNet+IP-Adapter）→ 生成 → 候选/入库。**工程上每一环都可行**，最大不确定性是"换姿势后身份/服装是否保得住"——必须先用 20~30 个样本做 PoC，达标再产品化。
4. **推荐落地**：复用现有 `fashion-inspo` 出图页作为 B（它已有 i2i、任务队列、生成历史、候选入库），素材库详情页加按钮作为 A，ai-pose-gallery-zh 作为全年龄姿势数据源（构建期同步 765 条或 CORS 化只读接口）；MVP 约 6~8 人日，PoC 3~5 天。
5. **一句话**：**接线简单、质量是门槛；先 PoC 验证"像不像"，再投入产品化。**
