# 门禁增量执行方案（按改动范围裁剪）

> 状态：已实施（2026-11-26）
> 涉及文件：`scripts/ci/gate_scope.py`（新增）、`scripts/ci/test.sh`、`.github/workflows/ci.yml`、
> `backend/tests/test_unit_gate_scope.py`（新增）、`docs/overview/门禁增量执行方案.md`（本文）

## 1. 问题：全量门禁和改动范围无关

旧 `scripts/ci/test.sh` 无条件按顺序跑 15 项。典型场景：

| 改动 | 旧行为 | 与改动真正相关的项 |
| --- | --- | --- |
| 只改后端一个 service | 后端 7 项 + Vue 类型/单测/eslint/死代码/格式 + 移动端 tsc/jest + 子项目 | 后端 7 项 + 文档生成物 |
| 只改前端一个组件 | 同样跑满 15 项 | 前端 5 项 |
| 只改 `docs/` | 跑满 15 项（后端 pytest 就要 2~3 分钟） | 第 15 项（秒级） |

后果有两个：①本地每次提交前的等待成本高，开发者倾向于「先不跑门禁直接推」；
②门禁越慢越容易被跳过，质量反而下降。CI 侧同样为改 README 的 PR 装一遍
Python + Node + 移动端依赖，浪费 runner 时间。

## 2. 原则

1. **质量不降级**：只按「文件路径 → 影响面」裁剪，不做概率性跳过；后端 app 改动
   必然跑后端全套（含覆盖率棘轮、迁移链）。
2. **宁多勿漏**：无法识别的文件（仓库根新增文件、未知目录）一律**保守回退全量**。
3. **可全量**：`--all` 永远可强制跑满 15 项；CI 的 `workflow_dispatch` 也是全量。
4. **单一真源**：裁剪逻辑只写在 `scripts/ci/gate_scope.py`，本地 `test.sh` 与
   CI 共用同一份映射与自检，避免两边漂移。
5. **本地/CI 一致**：CI 的 job 开关同样由该脚本产出，且识别失败时回退全量。

## 3. 作用域 → 门禁步骤映射

### 3.1 路径归类（`gate_scope.classify`）

| 作用域标签 | 路径 | 说明 |
| --- | --- | --- |
| `backend_app` | `backend/app/**`（不含 models/database/迁移） | 后端业务代码 |
| `backend_db` | `backend/app/models/**`、`backend/app/database.py`、`backend/app/db_migrations.py`、`backend/alembic/**` | 会触发迁移链/库漂移检查 |
| `backend_tests` | `backend/tests/**` | 只跑 pytest，不跑 lint（门禁的 ruff 只扫 app + scripts） |
| `backend_req` | `backend/requirements*.txt` | 依赖可能影响测试/迁移，保守跑后端 1–6 |
| `backend_test_config` | `backend/pytest.ini`、`backend/.coveragerc` | 只跑 pytest |
| `backend_tooling` | `backend/pyproject.toml` | 只跑 ruff/vulture/mypy |
| `backend_scripts` | `backend/scripts/**` | ruff + 脚本规范 |
| `backend_misc` | 其余 `backend/**`（如 `.env.example`、`model_configs.json`） | 无自动门禁，给人工提示 |
| `rust` | `backend/rust/**` | Rust 试点不在 15 项门禁内，提示手动 cargo |
| `web` | `web/**` | 前端 5 项 |
| `mobile` | `mobile/**` | 移动端 tsc+jest |
| `shared` | `shared/types/**` | 同时影响 web 与 mobile |
| `browser_ext` / `face_service` | 对应目录 | 子项目测试 |
| `docs` | `docs/**` | 只跑文档生成物一致性 |
| `scripts` | `scripts/**` | ruff + 脚本规范 + 门禁自检 |
| `ci_config` | `.github/**`、`scripts/ci/**` | 脚本规范 + 门禁自检（不跑业务测试） |
| `root_docs` | `CLAUDE.md`、`README*.md`、`TODO.md`、`LICENSE` | 不触发自动门禁 |
| `tooling` | `.gitignore`、`.gitattributes`、`.claude/**` 等 | 不触发自动门禁 |
| `unknown` | 其余一切 | **保守回退全量** |

### 3.2 步骤触发（`TAG_STEPS`）

| 步骤 | 触发作用域 |
| --- | --- |
| 1 后端 pytest + 覆盖率 + 模块地板 | `backend_app`、`backend_db`、`backend_tests`、`backend_req`、`backend_test_config` |
| 2 后端 ruff | `backend_app`、`backend_db`、`backend_scripts`、`backend_tooling`、`backend_req`、`scripts` |
| 3 vulture | `backend_app`、`backend_db`、`backend_tooling`、`backend_req` |
| 4 mypy 棘轮 | `backend_app`、`backend_db`、`backend_tooling`、`backend_req` |
| 5 迁移链自检 | `backend_db`、`backend_req` |
| 6 库结构漂移 | `backend_db`、`backend_req` |
| 7 脚本规范 + 门禁自检 | `scripts`、`backend_scripts`、`ci_config` |
| 8–12 前端（vue-tsc/vitest/eslint/死代码/格式） | `web`、`shared`（`shared` 只跑 8–10 与 13） |
| 13 移动端 | `mobile`、`shared` |
| 14 子项目 | `browser_ext`、`face_service` |
| 15 文档生成物一致性 | `backend_app`、`backend_db`、`backend_req`、`docs` |

> 为什么 `backend_app` 要跑第 15 项：`docs/overview/API参考.md`、`数据模型.md`、
> `配置项参考.md` 由 router/model/config 生成，改后端不重跑生成器会让文档过期。
> 第 15 项是纯 AST 脚本，耗时约 1 秒。

## 4. 实现

### 4.1 `scripts/ci/gate_scope.py`（纯判断，不做执行）

- 只读脚本：用 `git diff --name-only --no-renames` 采集「基准 ref…HEAD」「未暂存」
  「未跟踪」三部分改动；默认基准 `origin/master → origin/main → 仅工作区`。
- 路径统一交给 `-c core.quotepath=false` 输出，并内置 C 风格转义解码：git 默认把
  `docs/文档索引.md` 转义成 `"docs/æ..."`，不还原会让整份计划误判 `unknown`
  而回退全量（2026-11-26 实测踩到，已加自检断言）。
- 输出四种格式：
  - `text`：人类可读计划（`--dry-run` 直接打印）；
  - `bash`：`GATE_STEP_n=0/1`、`GATE_NAME_n`、`GATE_SKIP_REASON_n`，供 `test.sh` `eval`；
  - `json`：排查用；
  - `github-output`：CI 的 job 开关（`backend/web/mobile/subprojects/browser_ext/face_service/scripts/docs/full`）。
- `--self-test`：内置 62 条分类/计划断言（以输出为准），门禁第 7 步在「只改 scripts」
  时也会跑，防止裁剪逻辑本身回归。
- 另有 `backend/tests/test_unit_gate_scope.py`（20 条用例）在完整后端 pytest 中覆盖。

### 4.2 `scripts/ci/test.sh`

- 默认改为「按改动裁剪」；新增参数：
  - `--all` 全量 15 项；
  - `--dry-run` 只打印计划；
  - `--no-cache` 忽略「同一状态已通过」缓存，强制重跑；
  - `--base=<ref>` / `--staged` / `--files=a,b` 控制改动来源；
  - 原有 `--cov/--slow/--e2e` 保留。
- 运行锁与同状态缓存（见 §6）：防止并发门禁互相擦除 coverage，并让「同一状态重复执行」秒过。
- 被跳过的步骤打印 `----- [n/15] 跳过：<名称>` 与**具体原因**（例如「本次改动不涉及 web/」），
  结束时汇总「执行 N/15 项，跳过 M 项」，不会让人误以为跑过全量。
- 识别失败 → 自动回退 `--all`（宁可贵一点，不漏门禁）。
- 无任何改动（工作区干净、相对基准也没有提交）→ 直接提示「无改动」并退出，
  同时提示可用 `--all` 强制全量。
- 改动落在「无自动门禁」范围（如只改 README / Rust 试点 / `backend_misc`）→ 0 项可跑时
  明确提示「本次改动无需执行自动门禁」，并提示 `--all` 兜底，不假装跑过。

### 4.3 `.github/workflows/ci.yml`

- 新增 `changes` job：`fetch-depth: 0` 取全历史，按 `pull_request.base.sha` /
  `push before` 作为基准跑 `gate_scope.py --format=github-output`，输出各 job 开关。
- 各 job 条件统一写 `always() && needs.changes.outputs.<x> != 'false'`：
  - 识别出「不需要」→ 跳过；
  - 识别失败 / changes job 出错（outputs 为空）→ **照常全跑**（安全兜底）；
- 按改动拆成 7 个 job：`changes / backend / web / mobile / subprojects / docs / scripts`：
  - `docs` job：只改 docs 时跑文档生成物检查（生成器纯 AST，**不装后端依赖**）；
  - `scripts` job：只改 scripts / CI 配置时只装 ruff，跑脚本规范 + 门禁自检 + ruff，
    不再为脚本改动安装整套后端依赖；
  - `subprojects` job：浏览器插件 / 人脸子服务按 `browser_ext` / `face_service` 分别决定
    是否安装与执行（人脸依赖安装很慢，不该被插件改动拖累）；
  - `backend` job 已包含第 15 项，因此后端改动不会再单独触发 `docs` job。
- `workflow_dispatch` 手动触发 = 全量（发版前想跑满时用）。

## 5. 实测（本机，2026-11-26）

| 场景 | 旧行为 | 新行为 | 实测耗时 |
| --- | --- | --- | --- |
| 只改 `docs/overview/API参考.md` | 15 项全跑（后端 pytest 约 2.5 分钟起） | 只跑第 15 项 | < 1 秒 |
| 只改 `scripts/ci/*.py` | 15 项全跑 | 第 2、7 项（ruff + 脚本规范 + 自检） | 约 2 秒 |
| 只改前端 | 15 项全跑 | 第 8–12 项 | 约 1 分钟（原 4~5 分钟） |
| 只改后端 app（不含 models） | 15 项全跑 | 第 1–4、15 项 | 约 3 分钟（原 4~5 分钟） |
| 后端 app + tests + scripts + docs 混合（本次门禁改造自身） | 15 项 | 第 1–4、7、15 项（6/15） | **174 秒**（全量 373 秒） |
| 同一状态重复执行（内容未变） | 再整跑一遍 | 命中缓存直接跳过 | 约 1 秒 |
| `--all` / 手动 CI / 未知文件 | 15 项 | 15 项（不变） | 4~5 分钟 |

> 具体耗时随机器与测试规模变化；后端的 pytest（含覆盖率）永远是最大头，所以对
> 后端改动只裁掉前端/移动端/子项目，不裁后端自己的质量项。

## 6. 重复执行抑制：运行锁 + 同状态缓存

**问题**：2026-11-26 观察到另一个会话在 40 分钟内调用了 11 次 `bash scripts/ci/test.sh`：
每改几行、或每修一次门禁失败就整跑一遍，且用后台任务启动、彼此重叠。后果：
1. 并发后端 `pytest --cov` 会互相 `coverage erase`，出现 54.48% vs 92.29% 的假红，进而触发更多重跑；
2. CPU/磁盘争抢让每次门禁更慢；
3. 同一状态被重复验证，纯浪费。

**运行锁**（`test.sh` 开头）：
- 锁目录 `.git/dsh-gate.lock`（原子 `mkdir`，落在 `.git` 内不入库），后来者打印等待信息并排队；
- 等待上限默认 900 秒（`GATE_LOCK_WAIT=<秒>` 可调）；`GATE_NO_WAIT=1` 立即 `exit 3`；
- 持有者 bash 退出后锁自动清理；异常残留（pid 已消失 / 锁超过 90 分钟）自动清理。

**同状态缓存**：
- 键 = `HEAD` + `git diff HEAD --binary`（已跟踪文件完整内容 diff）+ 未跟踪文件内容 sha256
  + 门禁实现指纹（`test.sh` / `gate_scope.py` 内容）+ 本次执行计划签名 + `--slow/--e2e` 标志；
- 只有**整轮全部通过**才写入 `.git/dsh-gate-cache.key`；失败退出不会留下「假通过」；
- 完全相同的状态再次执行 → 打印上次通过时间并秒过（约 1 秒）；`--no-cache` / `--all` 可强制重跑；
- 任一文件内容、执行计划、门禁实现变化都会换键，不会把旧结论误用于新状态。

**使用建议**：迭代过程中用定向测试（`pytest 单文件` / `vitest run 单文件`）快速验证，
一轮改动完成后在提交前跑**一次**门禁；想知道这次会跑哪几项时用 `--dry-run`。

## 7. 已知边界

1. **Rust 试点不在门禁内**：`backend/rust/**` 改动只提示手动 `cargo test` / `cargo clippy`。
2. **`backend_misc`（如 `.env.example`、`model_configs.json`）没有自动门禁**：只给人工提示，
   因为这类文件没有稳定的自动校验目标。
3. **分支保护与跳过 job**：GitHub 对被 `if` 跳过的 job 记为 skipped（对 required checks
   通常视为通过）。如果以后把 CI 改成「必须全绿才允许合并」的严格模式，建议保留本方案，
   因为裁剪的 job 本身与改动无关。
4. **CI 与本地仍有差异**：本地默认含未跟踪/未暂存改动，CI 只比较提交范围；
   覆盖率门槛本地 82.9 / CI 82（历史上 CI 未随本地同步上调，属既有差异，不在本方案范围）。
5. **`--e2e` 不受裁剪影响**：需要后端在跑，仍由显式参数触发。
6. **CI workflow YAML 本身没有本地门禁**：改 `.github/**` 只跑脚本规范 + 自检，
   workflow 语法由 GitHub 侧解析；建议改完在 Actions 页面确认一次。
7. **不要并发跑两个后端 pytest（尤其带 `--cov`）**：pytest-cov 启动时会
   `coverage erase` 并清理 `.coverage.*`，并发时会把对方的 worker 数据擦掉，表现为
   「测试全过、覆盖率却只有 50% 左右」的假红（2026-11-26 实测：54.48% vs 重跑 92.29%）。
   门禁已用运行锁把「经 test.sh 的并发调用」串行化；但手动/其他工具直接跑 `pytest --cov`
   仍可能冲突，同一时刻只保留一个后端测试进程。

## 8. 后续可优化（未做）
