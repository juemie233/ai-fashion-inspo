# ai-pose-gallery-zh 接入图生图能力可行性评估

> 评估对象：<https://github.com/anhao/ai-pose-gallery-zh>
> 评估日期：2026-10-30
> 评估范围：技术栈与现有图像处理实现、可行性判断、改造点、依赖、接口与风险；本阶段不含业务代码。

## 一、结论先说

- **技术上可行，但不能在该仓库内部独立完成**。它是纯静态站点，没有任何后端、账号、存储或推理能力；图生图必须新增一个独立的推理/后端服务。
- **个人/本地使用：可行性高**，可直接复用现有的 ComfyUI + Qwen-Image-Edit 后端，MVP 约 1–2 周。
- **公开/商用：当前条件下不建议直接上线**。图片与数据的授权（MIT 只覆盖代码）、成人向内容合规是 go/no-go 问题，不是技术问题。
- 真正的成本不在前端或接口，而在：GPU 推理、姿势控制图预生成、内容合规与资产授权。

## 二、项目现状（实测）

| 维度 | 事实 |
|---|---|
| 技术栈 | 纯静态：单个 `index.html`（约 59 KB）+ 内联 IIFE + CSS；无框架、无 `package.json`、无打包器 |
| 部署 | Cloudflare Pages；`scripts/build.sh` 只把 `index.html/_headers/data/thumbs/img` 拷到 `dist/`；`_headers` 做一年期图片缓存 |
| 数据 | `data/pose-zh.json`：1439 条记录 / 288 组姿势 / 4 个体系 / 26 个分类 / 5 个视角；字段只有 `id、体系、姿势编号、分类、姿势名称、角度、缩略图、原图、检索` |
| 图片 | 1439 张 900×1200 **RGB PNG（无 alpha）**，共 641 MB；缩略图 1439 张 300×400 JPG，26 MB；仓库约 1.3 GB |
| 内容 | 灰色、无五官的人体素体线稿（README 与页面指南明确说明），不含面部/服装/背景 |
| 现有图像处理 | **运行时为零**。`index.html` 只做筛选、灯箱、懒加载、原图下载；`scripts/download.py` 只做并发下载；`verify.py` 只校验文件头/大小；`i18n.py`、`apply_translation.py` 只处理文案；**没有上传、解码、缩放、缩略图生成**（缩略图是预生成后入库的） |
| 服务端能力 | 无 API、无账号、无数据库、无对象存储；唯一外部脚本是访问统计 |
| 授权 | `LICENSE` 是 MIT，但明确**只覆盖代码**；README 声明图片/数据著作权归原作者，镜像不构成商业授权；页面有成人向提示 |
| 数据缺口 | 没有 pose keypoints、骨架图或控制图；只有成品线稿图片 |

### 关键含义

这个项目目前是「姿势参考图库 + 静态画廊」，不是「生成应用」。接入图生图不是打开一个已有开关，而是**新增一条完整的生成链路**：上传/选图 → 控制条件提取 → 推理 → 存储 → 前端展示。

## 三、「图生图」在本项目里可能指什么

| 方案 | 输入 | 技术路线 | 价值与风险 |
|---|---|---|---|
| **A. 素体线稿 → 成图**（推荐 MVP） | 选中的姿势线稿 + 文字描述 | Qwen-Image-Edit（直接把线稿当参考）或 SDXL + ControlNet lineart/canny/openpose | 价值最高、风险最低；不涉及真人肖像，适合「把素体变成穿搭图」 |
| **B. 姿势迁移** | 用户照片/角色图 + 姿势线稿 | ControlNet OpenPose + IP-Adapter/InstantID | 功能最强，但涉及肖像/同意/深伪与模型许可（InsightFace 等） |
| **C. 普通 img2img 重绘** | 姿势线稿 + 去噪强度 | SDXL img2img / 云 API | 对灰色素体线稿价值低（只是上色/风格化），不建议作为主功能 |

从图库本身的内容看，**A 是最自然的切入点**；B 应作为第二阶段并配套合规措施。

## 四、能否接入：架构判断

1. **纯静态仓库无法承载推理**
   - Cloudflare Pages 只托管静态资源；Workers 适合做代理/鉴权，不适合跑 GPU。
   - Workers AI 有基础 img2img/t2i 模型，但**没有 ControlNet/OpenPose 姿态条件**，且内容策略与本站素材不匹配，不能作为主方案。

2. **必须新增一个推理服务**。推荐「静态画廊 + 独立 `pose-gen` 服务」分离架构：
   - 画廊继续留在 Cloudflare Pages（零依赖、SEO、CDN 优势不变）；
   - 生成服务单独部署在 GPU 主机（本地 PC + Cloudflare Tunnel，或 RunPod/Replicate/fal）；
   - 前端只通过 `fetch` 调服务，不引入框架或打包器。

3. **可复用的现成能力**：现有的 `fashion-inspo` 已经具备 ComfyUI 接入、Qwen-Image-Edit 图生图、任务队列、生成历史。把画廊的「用它生成」指向这套后端，比从零写推理层省很多时间（需要补一个「直接上传参考图」的入口与跨域鉴权）。

4. **不建议**把该仓库改造成 Next.js/FastAPI 全栈一体化：会破坏零依赖/静态部署的优势，且收益不大。

## 五、主要改造点

### 5.1 前端（`index.html`，改动量小）

- 灯箱右侧 `.download-stack` 增加「用这个姿势生成」按钮；
- 新增生成弹窗：文字描述、负面词、强度/尺寸/seed、模型选择、（可选）用户参考图上传与预览；
- 提交后轮询任务状态，展示进度/失败原因/结果网格/下载/重试；
- 新增极简 API client（`fetch` + `FormData`）与配置（API base URL、鉴权 token/Turnstile）；
- 移动端布局与键盘操作补充；保持零依赖。
- 注意：`index.html` 是单文件内联脚本，功能变大后建议拆成 `assets/app.js`（纯 JS，仍无构建）。

### 5.2 数据与姿势控制预处理

- **离线预生成控制图**：对 1439 张图批量跑 DWPose/OpenPose，或直接生成 lineart/canny/depth 控制图；
- 结果建议存 **R2/服务端**，不要提交进静态仓库（会增加 100–300 MB 与部署文件数）；
- 给 `pose-zh.json` 增加派生字段（如 `control`、`can_generate`），由脚本生成，不改原日文数据；
- 双人姿势（275 条）与俯视/仰视视角需要人工 QA，失败时回退 lineart/canny。

### 5.3 新增服务模块（建议独立目录/仓库）

- **接口层**：创建任务、查询任务、取控制图、模型列表、健康检查；
- **队列与执行**：单 GPU 互斥、超时、取消、重试；ComfyUI workflow 模板（Qwen-Image-Edit 或 SDXL+ControlNet）；
- **存储**：输出图 R2/本地 + TTL 清理；用户上传不持久化或短 TTL；
- **鉴权/限流**：Bearer Token / Cloudflare Turnstile、CORS 白名单、配额；
- **校验与审核**：MIME/尺寸/PIL 解码、防解压炸弹；公开部署时增加 NSFW/人脸审核；
- **可观测性**：日志、任务耗时、GPU 占用、失败率。

### 5.4 依赖

| 层 | 依赖 |
|---|---|
| 后端 | FastAPI、uvicorn、httpx、Pillow、python-multipart、pydantic；可选 Redis/现有任务队列、R2 SDK |
| 推理 | ComfyUI + `comfyui_controlnet_aux`/DWPose、ControlNet 权重、SDXL 或 Qwen-Image-Edit；可选 IP-Adapter/InstantID；CUDA，16 GB 显存级别 |
| 前端 | 无新增（`fetch`/`FormData`）；可选 Turnstile 脚本 |
| 基础设施 | GPU 主机/云 GPU、Cloudflare Tunnel、R2、Pages、监控与日志 |

### 5.5 接口草图（评估用，不是实现）

```text
POST /api/pose-gen/jobs        multipart
  pose_id / 或 pose_image
  reference_image?             # 可选：用户本人/角色参考
  prompt, negative?
  strength?, width?, height?, seed?, model?
→ 202 { job_id, status: "queued" }

GET /api/pose-gen/jobs/{id}
→ { status: "queued|running|done|failed", progress, images: [url], error }

GET /api/pose-gen/poses/{pose_id}/control
→ image/png                   # 预生成的骨架/线稿控制图

GET /api/pose-gen/models
GET /api/health
```

鉴权：`Authorization: Bearer …` 或 Turnstile；CORS 只放行画廊域名。

### 5.6 部署

- Pages 不动；API 部署在 GPU 主机（本地 + Tunnel 或云 GPU）；
- 输出图放 R2（CDN + TTL），控制图也放 R2；
- 不要在纯静态仓库里放模型权重或大量控制图；
- 公开部署需要年龄门禁、内容审核、AIGC 标识、隐私与保留策略。

## 六、主要风险

| # | 风险 | 影响 | 说明/缓解 |
|---|---|---|---|
| 1 | **图片授权（最高）** | 公开/商用可能构成侵权 | MIT 只覆盖代码；图片/数据归原作者，README 明确不构成商业授权。公开生成与再分发前需作者许可，或替换为自有/CC0 姿势资产；至少保留署名与来源 |
| 2 | **成人内容合规（高）** | 平台封禁、支付/法律风险 | 图库本身含成人向分类；公开服务需年龄门禁、内容分级、审核与投诉下架；多数云 GPU/API 禁止 NSFW，若走云 API 很可能不可用 |
| 3 | **AIGC 标识与内容治理（高）** | 合规风险 | 面向国内公开时需显式/隐式 AI 生成标识、内容审核与必要的主体信息；输出加水印/元数据 |
| 4 | **肖像/同意/深伪（高，若开放用户照片）** | 法律与伦理风险 | 第二阶段若做「用户照片换姿势」，需明确同意、禁止未成年人、人脸审核、上传短 TTL、输出水印；优先避免人脸路径 |
| 5 | **GPU 成本与延迟（中）** | 体验与费用 | 单张约 20–60 秒（16 GB 级）；需要队列、限流、冷启动与成本监控 |
| 6 | **姿势提取质量（中）** | 部分姿势生成失败 | 双人、俯仰视角、遮挡与线稿风格可能导致 OpenPose 失败；离线预计算 + lineart/canny 回退 + 人工 QA |
| 7 | **安全（中）** | 被滥用/打穿 | 绝不能直接暴露 ComfyUI 8188；上传做类型/尺寸/解码校验，限流，CORS 白名单，密钥放服务端 |
| 8 | **架构与运维（中）** | 复杂度上升 | 从纯静态变成「静态 + GPU 服务」两套部署；需要监控、日志、存储 TTL、备份 |
| 9 | **模型许可证（中）** | 商用受限 | SDXL、ControlNet、IP-Adapter、InstantID/InsightFace 各有条款；商用前逐个核对，尤其人脸相关模型 |
| 10 | **资产膨胀（低–中）** | 部署变慢/超限 | 控制图不要进静态仓库；Pages 单次部署上限 20,000 文件/25 MiB 单文件 |

## 七、工作量估算

| 范围 | 估算 |
|---|---|
| MVP（本地、方案 A、复用现有 ComfyUI 后端） | 前端 2–3 天 + 后端入口/队列 2–4 天 + 控制图预生成 1–2 天 + QA 2–3 天，约 **1–2 周** |
| 独立新建 pose-gen 服务 | 约 **2–4 周**（含存储、鉴权、部署） |
| 公开产品化（年龄门禁、审核、AIGC 标识、限流、监控） | 再加 **2–4 周**，并需先解决授权 |
| 走托管云 API（Replicate/fal 等） | 集成约 1–2 周，但按张计费、冷启动、内容政策限制 |

## 八、建议路线

1. **先做方案 A**（素体线稿 → 成图），不接用户照片；优先复用现有 ComfyUI + Qwen-Image-Edit（直接参考图比 ControlNet 链路更短）。
2. **画廊保持静态**，新增独立 `pose-gen` 服务；前端只加按钮、上传/参数弹窗与轮询。
3. **离线预生成控制图**并存 R2，给 `pose-zh.json` 加派生字段；双人/特殊视角先人工筛一遍。
4. **只在本地/内网先跑通**；公开前先解决图片授权（联系原作者或替换资产），再加年龄门禁、审核与 AIGC 标识。
5. 若之后要做「用户照片换姿势」，单独评估 IP-Adapter/InstantID 的模型许可与肖像合规，并加同意、审核与保留策略。

## 九、最终结论

- **技术可行性：高**（需要配套推理服务）；**在当前纯静态仓库内独立接入：不可行**。
- **个人/本地使用：推荐**，复用现有 ComfyUI 栈即可，成本与风险可控。
- **公开/商用：条件性可行**。图片授权与成人内容合规是前置门槛，未解决前不建议直接上线。
- 这项工作的核心不是「加一个上传按钮」，而是新增 **GPU 推理 + 姿势控制预处理 + 存储/鉴权/审核** 一整条链路；技术难度中等，主要风险在合规与资产授权。

> 补充：如果真实目标不是「给画廊加生成功能」，而是「把这个图库作为现有 `fashion-inspo` 的姿势参考源」，那会是完全不同的低风险方案：只需导入图片与元数据、在参考图选择器里增加「姿势库」入口，复用现有 i2i 链路即可；授权问题仍然存在，但不需要改这个静态仓库。
