# 数据备份与恢复指南

> **状态**：现行（2026-10-31 校对）。如与代码不一致，以代码为准。


> 对应规划：本地私有文档 `docs/wayfinder/backup-disaster-recovery/MAP.md`（未随仓库发布）
> 恢复级别 **L2**（备份含 DB + 原始素材 + 缩略图/向量 + 运行时配置，恢复即用）；**RPO ≤ 1 天**。

本项目素材库的核心数据——SQLite 数据库、`storage/` 素材文件、LanceDB 向量、`.env` 等运行时配置——均不进 git。本文档说明如何自动/手动备份，以及在误删、磁盘损坏、误触发 `DELETE /api/ai/reset` 后如何恢复。

## 1. 备份了什么

每次备份在目标目录下生成 `YYYY-MM-DD_HHMMSS/`：

| 内容 | 说明 |
| ---- | ---- |
| `fashion_inspo.db` | SQLite 一致性快照（Python `sqlite3.backup`，后端运行中可安全备份） |
| `fashion_inspo.sql` | SQL 明文导出（`iterdump`），DB 文件损坏时的抢救双保险 |
| `storage/` | `images/`、`person_photos/`、`trash/`、`videos/`、`thumbnails/`、`person_thumbnails/`、`lancedb/` |
| `backend/.env`、`backend/prompt_configs.json`、`backend/model_configs.json`、`backend/prompt_versions.json`、`backend/prompt.txt`、`web/.env.local` | 不进 git 的运行时配置（按原相对路径保存） |
| `git_head.txt` | 备份对应的代码提交号 |
| `manifest.json` | 校验清单：关键表行数、各目录文件数/字节数、git HEAD、告警 |
| `SUCCESS` / `FAILED` | 备份结果标记；`SUCCESS` 内含时间戳与 git HEAD |

**明确不备份：** `storage/_crop_backup`（裁剪前原图唯一副本，约 880MB，用户拍板排除以省空间；代价是恢复后无法撤销已做过的裁剪，裁剪后成品图仍在）、`logs/`、`tmp/`、`_crop_dups/`、`cookies/`、`debug/`、`faces/`、Ollama 模型文件、Python 虚拟环境、Chrome profile/cookies、代码与 git 历史（已在 Gitee + GitHub 双远程）。

> 口径补充：`storage/generated/`（出图候选区）与 `storage/keyframes/`（视频关键帧）**会随 `storage/` 镜像一并备份**，但它们不在 `REQUIRED` 里参与「文件数/字节数」校验——这两类都是可再生物（候选重生成、关键帧从 `videos/` 重提取），缺了不该判备份失败。

> ⚠️ **安全提示：** 备份含 `.env`（密钥）。请勿放入未加密的网盘/公共位置；可把备份目标指向已加密/受控的网盘挂载目录，由网盘客户端自行同步（脚本本身不做云上传）。

## 2. 手动备份

```bash
# 推荐：备份到独立物理盘（E 盘）
bash scripts/ops/backup_data.sh E:/fashion-inspo-backups

# 临时同盘备份（会被强警告，需加 --allow-same-disk）
bash scripts/ops/backup_data.sh backups --allow-same-disk

# 额外对所有素材做全量 SHA-256（默认关，较慢：3.2 万素材/几十 GB 读一遍）
bash scripts/ops/backup_data.sh E:/fashion-inspo-backups --verify-hash

# 抽样哈希（默认已开 200 个）：只抓「大小相同但内容不同」的静默损坏
bash scripts/ops/backup_data.sh E:/fashion-inspo-backups --verify-sample 500
bash scripts/ops/backup_data.sh E:/fashion-inspo-backups --verify-sample 0   # 关掉抽样
```

**三层校验分别抓什么**（默认就跑前两层，第三层按需）：

| 层 | 手段 | 抓得住 | 成本 |
| --- | --- | --- | --- |
| 1 | `PRAGMA integrity_check` + 关键表行数 + SQL 内存试导 | DB 损坏 / 备份不可导入 | 秒级 |
| 2 | 与「冻结源端清单」比对文件数 + 字节数 + 必备目录 | 漏复制 / 目录缺失 / 数量对不上 | 秒级（只 stat） |
| 3 | **抽样哈希（默认 200 个，`--verify-sample N`）** | **大小一模一样、内容却坏**（坏道、复制中断、被改写） | 约 N×单文件，200 张图≈数十 MB |
| 3' | 全量 SHA-256（`--verify-hash`） | 同上，覆盖面 100% | 几十 GB 全读 |

抽样实现见 `backend/scripts/verify_backup_sample.py`（有单测）。两个刻意的设计：

- **抽样是确定性的**（`--seed 0` 固定）：同一批备份重跑得到同一组样本，便于复查；
- **区分「内容不一致」与「备份后源端又写」**：备份是时点快照，复制完成后后台任务继续
  往源端写入是正常的；只有「大小完全相同、哈希却不同」才判为静默损坏（写进 manifest 的
  `errors` 并让退出码为 2），大小已变的样本只记为 `changed` 告警。

结果落在 `manifest.json` 的 `hash_sample` 字段：`{total, sample, checked, missing, corrupt, changed, ok}`。

**增量评估结论（2026-10-21）**：素材存储**已经是增量的** —— `robocopy /E` 只复制新增/变更
文件，收敛阶段用 `/MIR` 只重同步不一致目录，所以「全量备份」实际只搬运增量；真正的全量成本
在 **DB 快照与 SQL 明文导出**（实测 464.8 MB → `fashion_inspo.db` 465 MB + `fashion_inspo.sql`
369 MB，每次全量写）。因此**不引入单独的文件级增量方案**（收益低、恢复复杂度高）；若将来库再
翻倍，优先考虑「DB 快照保留 3 份 + 更早的只留 SQL」这类策略，而不是自研增量格式。

备份完成后看 `SUCCESS` 标记与退出码：`0` 成功，`2` 备份/校验失败（失败目录写 `FAILED`，保留排障，不自动删除）。日志同时写入备份目录的 `backup.log` 与 `backend/storage/logs/backup.log`。

**热写入收敛：** 备份期间后台任务（标签分析/向量回填）持续写入 `storage/lancedb/` 等目录属正常场景。脚本在复制后做「比对 → 增量修复」循环（`robocopy /MIR` 只重同步不一致目录，最多 5 次），随后把该时刻的源端统计冻结为 `.source_stats.json`，最终校验以冻结清单为基准——收敛通过后源端继续写入不会误判失败。连续修复仍不一致（写入密度极高）才会判 FAILED，此时暂停相关任务或等其结束后补备即可。

**保留策略（自动 rotation）：** 每日成功备份保留最近 7 份；更早的、落在周日的备份额外保留 4 份（周备）；失败备份独立保留最近 3 份；被中断的半截备份（无任何标记）立即清理。只删除匹配 `YYYY-MM-DD_HHMMSS` 的目录，手动放入的文件不受影响。

## 3. 自动每日备份（注册 Windows 计划任务）

项目约定**不自动注册计划任务**，请在确认目标盘存在后手动执行一次：

```bat
schtasks /Create /SC DAILY /TN "FashionInspo-Backup" ^
  /TR "\"C:\Users\Administrator\Desktop\Claude Code\MMK\fashion-inspo\scripts\backup_task.bat\"" ^
  /ST 03:00 /F
```

- 每日 **03:00** 运行 `scripts/ops/backup_task.bat`，它会调用 Git Bash 执行备份到 `E:\fashion-inspo-backups`。
- 目标盘在 `backup_task.bat` 顶部的 `BACKUP_TARGET` 变量修改；Git Bash 路径脚本会自动探测常见安装位置。

管理命令：

```bat
schtasks /Query  /TN "FashionInspo-Backup"            REM 查看状态/上次结果
schtasks /Run    /TN "FashionInspo-Backup"            REM 立即手动触发一次
schtasks /Delete /TN "FashionInspo-Backup" /F         REM 删除计划任务
```

**双通道补充：** 除每日定时外，后端启动并稳定运行约 10 分钟后会自动补备一次（若距上次成功备份 ≤20 小时则跳过），之后每 6 小时复查。该通道由以下 `.env` 配置控制（均有默认值）：

```ini
BACKUP_ON_STARTUP=true                # 设为 false 关闭启动补备
BACKUP_TARGET_PATH=E:/fashion-inspo-backups
BACKUP_STARTUP_DELAY_MINUTES=10       # 启动后延迟多久再检查
BACKUP_MIN_INTERVAL_HOURS=20          # 距上次成功备份小于此时长则跳过
BACKUP_TICK_HOURS=6                   # 复查周期
```

两个通道（schtasks 凌晨定时 + 后端启动补备）通过 `backup.lock` 目录锁互斥，不会并发；启动补备的日志同样写入 `backend/storage/logs/backup.log`。

## 4. 恢复

### 4.1 同机恢复（误删 / 误触发 reset 后）

```bash
# 先确认后端与 worker 已停止（脚本检测到 18888 端口在监听会拒绝恢复）
# 列出可用备份（选带 SUCCESS 的最新一份）
ls E:/fashion-inspo-backups/

# 执行恢复（目标已有数据时，脚本会先快照当前状态再覆盖）
bash scripts/ops/restore_data.sh E:/fashion-inspo-backups/2026-08-26_102630 --allow-overwrite

# 或用 bat 包装（无参数时自动选最新 SUCCESS 备份）
scripts\restore_task.bat
```

恢复脚本步骤：

1. **前置检查**：备份有 `SUCCESS`（无则拒绝，`--force` 可强跳）；磁盘空间充足；18888 端口空闲（要求你先停服务，脚本不自行 kill）；目标已有数据需 `--allow-overwrite`。
2. **恢复前快照**：把当前 `fashion_inspo.db`（含 WAL/SHM）和 storage 必备目录移到 `backend/storage/_pre_restore_snapshot/<时间戳>/`，保留 7 天——选错备份也能回退。
3. **还原 DB**：默认用 `.db` 快照（先删现有 WAL 三件套）；`--from-sql` 时用 `fashion_inspo.sql` 在全新库 `executescript` 重建（`.db` 损坏时用）。
4. **还原 storage**：robocopy 逐目录镜像回必备目录；`_crop_backup/logs/tmp` 恢复后不存在属预期，不告警。
5. **还原配置**：`.env` 与 prompt/model 配置、`web/.env.local` 拷回原位。
6. **恢复后校验**：`PRAGMA integrity_check` + 关键表 count 与 `manifest.json` 比对 + 随机抽查 20 个素材文件在磁盘存在。不一致非零退出，但**不自动回滚**（数据已落盘，由你按步骤 2 的快照决定）。

恢复完成后脚本会打印后续步骤提示，但不自动启动服务。

### 4.2 新机器从零恢复（磁盘损坏/换机）

按顺序执行（均为手动，脚本不自动安装系统软件）：

1. **基础环境**：安装 Python 3.12、Node.js 20+、Git、Git Bash（Windows）、ffmpeg。
2. **取代码并对齐版本**：
   ```bash
   git clone <仓库地址> fashion-inspo
   cd fashion-inspo
   # 用备份记录的提交号对齐代码版本（见备份目录的 git_head.txt 或 manifest.json）
   git checkout <git_head>
   ```
3. **Python 依赖**：
   ```bash
   cd backend
   python -m venv .venv
   source .venv/Scripts/activate   # Git Bash 下
   pip install -r requirements.txt
   cd ..
   ```
4. **放置备份并恢复**：把 E 盘（或异地）备份拷到本机，运行：
   ```bash
   bash scripts/ops/restore_data.sh <备份目录>
   ```
5. **数据库迁移（必需，不是保险）**：备份库可能落后于当前代码（实测 10-27 的备份就落后一个迁移，
   不迁移则新代码查新列直接报错）。换代码版本或恢复较旧备份后必须跑一次：
   ```bash
   cd backend && alembic upgrade head && cd ..
   ```
6. **Ollama 与模型**：安装 Ollama 后拉取模型（模型文件不入备份）：
   ```bash
   ollama pull qwen3-vl:8b-instruct   # 视觉分析模型（以实际配置为准）
   ollama pull all-minilm             # 文本嵌入模型
   ```
7. **face-service（可选，需要人脸识别时）**：按 README 在独立 Python 3.10 环境部署 insightface 子服务。
8. **前端构建**：
   ```bash
   cd web && npm install && npm run build   # 或开发模式 npm run dev
   ```
9. **核对 `.env`**：在新机器上检查 API Key、Ollama 地址、存储路径等是否需要调整。
10. **启动并验证**：手动启动后端/前端/worker，然后：
    - 访问 `GET http://127.0.0.1:18888/api/health` 确认健康；
    - 后台查看素材总数、抽查图片可显示、标签搜索正常；
    - 确认 `audit_logs`、收藏、审核状态等历史数据在。
11. **重新注册自动备份**：计划任务不会跨机器迁移，按第 3 节重新执行 `schtasks /Create`。
12. **定期演练**：建议每季度取一份备份在临时目录跑一次 `restore_data.sh` + 校验，确认备份真的可用。

## 5. 恢复演练记录（2026-10-27 首次实跑）

「没验过恢复不算备份」——这一节是**真跑过一次**的记录，不是设计推演。

### 5.1 怎么跑才不碰真数据

真实备份 2 GB 级（DB 522 MB + storage 17 GB / 3.6 万个文件），反复演练不现实；
换成假数据又测不出真问题。做法：**把真实库裁剪到 60 条素材**（外键级联清理到 0 违规、
`integrity_check` ok、`VACUUM` 后 87 MB），storage 只放这 60 条对应的文件，
manifest 按裁剪后的库重算——数据是假的，**结构与真备份完全一致**，
脚本每一步（快照 / robocopy / count 比对 / 抽查）都走真实路径。

沙箱：`%TEMP%\fi-drill\project`（只有 `scripts/ops/restore_data.sh` + 空 `backend/`），
备份在 `%TEMP%\fi-drill\backup`。

> 演练时真实后端正在跑（18888）。为了不停服务，沙箱里用 PATH 桩把 `netstat` 屏蔽掉，
> 绕过「服务在跑就拒绝恢复」的前置检查——**真机恢复必须先停后端与 worker**，
> 这个检查本身也单独验证过（见下表的 negative 用例）。

### 5.2 用例矩阵与结果

| # | 用例 | 预期 | 实测 |
| - | ---- | ---- | ---- |
| 1 | 空目标恢复（`.db` 快照路径） | 成功 | ✅ exit 0，8 张表行数与 manifest 一致，抽查 20/20 文件存在 |
| 2 | 目标已有数据、未加 `--allow-overwrite` | 拒绝 | ✅ exit 1，提示「恢复会覆盖现有数据」 |
| 3 | 备份缺 `SUCCESS`、未加 `--force` | 拒绝 | ✅ exit 1，提示可能是不完整备份 |
| 4 | 目标已有数据 + `--allow-overwrite` | 先快照再恢复 | ✅ 快照出 DB + 4 个 storage 目录，随后恢复成功 |
| 5 | `--from-sql`（DB 损坏时的重建路径） | 成功 | ✅ exit 0，33 张表行数与备份**逐表一致** |
| 6 | 真实服务检测（不屏蔽 netstat） | 拒绝 | ✅ exit 1，提示先停后端/worker |
| 7 | 恢复**旧备份**（落后一个迁移） | 成功但需迁移 | ✅ 恢复 exit 0；`alembic check` 报「库结构落后于迁移链」 |

### 5.3 深度校验（脚本自带的校验之外）

脚本的恢复后校验只查「行数 + 文件是否存在」，两点不够，另做了三项：

| 校验 | 结果 |
| ---- | ---- |
| 恢复出的 `.db` 与备份 `.db` 的 SHA-256 | ✅ 一致（`.db` 路径是整文件复制） |
| 备份 storage 里**全部 120 个文件**逐个 SHA-256 比对 | ✅ 120/120 一致 |
| 恢复库可读性 | ✅ `integrity_check`=ok、`foreign_key_check` 违规 0、真实标签关联查询有结果 |
| 恢复库与**当前代码**的结构一致性 | ✅ `alembic_version`=现行 head、`check_alembic_drift.py` 报「ORM 与数据库结构一致」 |

即：**恢复当天备份后，不需要跑迁移就能直接被当前代码使用**。

### 5.4 旧备份的关键一步（最容易漏）

`2026-10-27_084508` 那份备份的库在 `c92d4f8329ac`，比当前 head 落后一个迁移：

```
恢复后 alembic_version: c92d4f8329ac
ALEMBIC_DB_URL=... python scripts/check_alembic_drift.py
  → [fail] 库结构落后于迁移链：先 `alembic upgrade head`
ALEMBIC_DB_URL=... python -m alembic upgrade head
  → c92d4f8329ac -> n7o8p9q0r1s2「博主资料卡：新增粉丝/作品/获赞等平台统计快照字段」
再 check → [ok] ORM 与数据库结构一致
迁移后数据：inspirations 60 / tags 22952 / inspiration_tags 1516 / bloggers 488（未丢）
新列到位：follower_count、aweme_count、total_favorited
```

结论：**恢复不是恢复完就结束**。跨版本恢复（或恢复几天前的备份）后必须跑
`alembic upgrade head`，否则新代码查新列会直接报错。文档 4.2 的第 5 步不是「保险」，
是**必需步骤**。

### 5.5 演练中发现并修掉的两个问题

| 问题 | 现象 | 修法 |
| ---- | ---- | ---- |
| 前置检查卡两分钟以上 | `du -sk` 在真实备份（3.6 万文件 / 17 GB）上实测 **>120 s** 未返回，用户会以为脚本挂了 | 体积优先读 `manifest.json`（`db_size`+`sql_size`+`dir_stats` 字节数，毫秒级），缺 manifest 才退回 `du` 并提示 |
| 恢复后校验只查「文件存在」 | 复制中断导致的**半截文件**能通过检查，用户到打开图时才发现 | 新增 6.4：按固定种子抽 200 个文件比对「备份/恢复后」体积；新增 6.5：`.db` 路径比对恢复库与备份库的 SHA-256（`--from-sql` 自动跳过） |

修完后同一套用例重跑：空目标恢复 **1 秒**完成，输出多两行
`抽查文件体积：120/120 与备份一致`、`数据库字节一致性：一致`。

### 5.6 这套校验测不到什么（边界）

- **同尺寸的内容损坏**：磁盘静默位翻转后大小不变，体积比对与 DB 行数都看不出来。
  这类只能靠备份时的 `--verify-hash`（全量 SHA-256）或定期抽检；
- **备份本身有问题**：恢复校验是「恢复出来的 == 备份里的」，备份里本来就坏的话照样通过。
  所以备份侧要开 `backend/scripts/verify_backup_sample.py` 抽样哈希（默认已开，
  与源端对比，能区分「真损坏」与「备份后源端又写」）；
- **恢复的可用性**：脚本只保证文件与库完整，不保证应用能跑起来。人工还要做第 4.2 节
  第 10 步的验证（健康检查 / 抽查图片 / 标签搜索 / 收藏与审核状态）。

### 5.7 下次演练清单

```bash
# 1) 挑一份带 SUCCESS 的最新备份
ls -d /e/fashion-inspo-backups/*/ | tail -3
```

## 6. 常见场景

| 场景 | 做法 |
| ---- | ---- |
| 误删了一批素材（已进垃圾桶） | 优先用界面「垃圾桶 → 恢复」；若已清空垃圾桶，用最近备份整库恢复（会回滚到备份时点）。 |
| 误触发 `DELETE /api/ai/reset` | reset 执行前会自动快照 DB 与素材目录到 `storage/_pre_reset_snapshot/`（保留 7 天）；若需整库回退，用最近备份按 4.1 恢复。 |
| 怀疑 DB 文件损坏 | 先用 `.db` 快照恢复；若 `integrity_check` 不过，改用 `--from-sql` 从 `fashion_inspo.sql` 重建。 |
| 备份失败 | 看 `backend/storage/logs/backup.log` 与失败目录下的 `backup.log`/`FAILED`；失败目录保留最近 3 份。 |
| 备份盘空间不够 | rotation 自动保留约 11 份（~17GB）；可手动删除更早的时间戳目录，或调小脚本里的 daily/weekly 保留数。 |
| 备份进行中又触发了一次 | 第二次会因 `backup.lock` 直接跳过并退出 0，不会并发。 |
