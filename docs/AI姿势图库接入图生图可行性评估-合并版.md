## 0. 结论先行

### 0.1 统一结论表（v1 + v2 汇总）

| 问题 | 判断 |
| --- | --- |
| 技术上能否接入图生图？ | **能**——项目没有阻碍 i2i 的技术债，现有 900×1200 多角度原图、筛选 UI 与结构化数据是优质输入侧；**但不能在该仓库内部独立完成**：它是纯静态站点，没有后端、账号、存储与推理，i2i 必须新增一套「推理 + 任务 + 存储 + 鉴权 + 审核」服务层（v2 补充：Pages/Workers 只能做静态托管与轻量代理，不能跑 GPU） |
| 个人/本地使用是否可行？ | **可行且推荐**。可复用现有 ComfyUI + Qwen-Image-Edit 后端；先做提示词/参考图导出（P0），需要站内生成时再做受控服务（P1） |
| 值得在公开站点做在线生成吗？ | **当前不建议**。图片/数据授权（MIT 只覆盖代码）与成人内容合规是 go/no-go，不是技术问题；公开/商用需先取得原作者许可并完成内容分级、AIGC 标识与法务确认 |
| 推荐路线 | **P0（先做）**：提示词模板 + 参考图导出/复制，生成交给用户自己的工具，约 0.5~1 人日、0 算力、0 输出合规风险。<br>**P1（确需站内生成）**：受控服务 + 全年龄子集（765 条）+ 访问口令 + 每日硬限额，定位内部/自用，约 5~7 人日【v1 估算 5~6.5 人日，v2 复评 5~7 人日】。<br>**P2（公开在线生成）**：不建议，除非先解决授权与内容分级 |

### 0.2 一句话结论

**工程可行性高，合规可行性低；能做，但应换个做法做，或者不在这个项目里做。**（v1/v2 表述一致，合并保留）

v1 原话：当前项目适合继续做"参考图库"，不适合直接变"生成站"；生成能力应当放在别处（用户自己的工具，或一个受控的独立服务）。若要在这个仓库做，只能做"受控的小范围工具"，不能做"公开的在线生成"。

### 0.3 v2 复评相对 v1 的变化（v2 原文保留）

- 新增：仓库热度与社区先例（3,153★ / 812 fork / 3 个开放 PR）、数据分布与图片像素统计、Cloudflare Pages/Workers 限制实测核对、Workers AI 模型目录核对、线稿 vs 骨架的技术分歧分析、P0/P1/P2 分级路线。
- 调整：推荐顺序从「先建本地生成服务」改为「先做 P0 提示词/参考图导出，再做受控 P1」。理由：公开生成的内容/授权风险高，而社区已有「把姿势图作为生图参考导出」的方向（PR #2/#4）。

> 合并说明：v1 的判断路径是"先判断可不可行、再给方案对比"；v2 在同一结论基础上补充了更细的实测数据（像素/颜色/视角覆盖）、Workers AI 核对、三种图生图形体与 Go/No-Go 门槛。下文按"先事实、后判断"的合并结构编排，两版细节都在。

### 1.3 现有「图像处理」实现

全仓库**没有任何模型推理、图像编解码或像素级处理**，只有两处字节级校验【v1/v2 一致】：

1. `scripts/verify.py`：读文件前 8 字节判断 JPEG/PNG 魔数 + 大小阈值，校验 2878 个文件完整性（v2：JPEG/PNG 魔数 + 大小阈值）；
2. `scripts/download.py`：按实际字节数校验下载结果、原子替换落盘（v2：`urllib` + 48 线程 + 断点续传；v1：并发 48 线程/断点续传/自动重试）。

即：**无 PIL / OpenCV / numpy / ffmpeg 等图像库依赖，仅有 Python 标准库**；没有后端、Serverless、数据库、鉴权、任务队列。v2 补充：**缩略图是预生成后入库的，仓库里没有缩略图生成逻辑**；接入 i2i 等于第一次给这个项目引入真正的图像 I/O 与推理链路。

### 1.5 结论：这是「参考图库」，不是「生成应用」

## 2. 接入 i2i 的能力缺口

| 环节 | 现状 | 缺口 |
| --- | --- | --- |
| 参考图输入 | ✅ 900×1200 PNG、每姿势 5 视角、可按分类/视角筛选 | 基本无需改造；最多加裁剪/缩放/白底处理 |
| 提示词 | ⚠️ 只有体系/分类/姿势名/角度（中文），可程序化拼模板 | 缺服装/场景/风格描述，需要用户输入或 LLM 补全 |
| 模型推理 | ❌ 完全没有 | **核心缺口**：云端 API / 自建 GPU / 浏览器 WebGPU 三选一 |
| 结果存储 | ❌ 无 | 生成图 1~2 MB/张，不能塞进 `dist/`（Pages 文件数上限），需 R2/外部存储 |
| 任务状态 | ❌ 无 | i2i 通常 5~45 s【v2；v1 记 5~30 s，以实测为准】，需要异步任务 + 轮询/SSE + 取消 |
| 鉴权/配额 | ❌ 无（纯静态公开站） | 必须新增，否则密钥与成本裸奔 |
| 内容审核 | ❌ 无 | 18+ 条目占 46.8%，必须分级与过滤 |
| 观测/日志 | ❌ 仅第三方统计 | 失败率、耗时、成本、滥用需要记录 |

## 3. 「图生图」在本项目的形态与技术分歧

### 3.1 三种形态（v2 表）

| 方案 | 输入 | 技术路线 | 姿势保真 | 主要风险 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. 素体线稿 → 成图** | 选中姿势线稿 + 文字描述 | Qwen-Image-Edit / FLUX.2 multi-reference（直接参考图编辑）；或 SDXL + ControlNet lineart/canny | 中~高（取决于模型与提示词） | 低（不涉及真人肖像） | **先做**；最能体现图库价值 |
| **B. 姿势迁移** | 用户照片/角色图 + 姿势线稿 | ControlNet OpenPose/DWPose + IP-Adapter/InstantID；或双参考图编辑 | 高（若骨架可靠） | 高（肖像/同意/深伪、模型许可） | 第二阶段；先做小样本验证 |
| **C. 普通 img2img 重绘** | 线稿 + 去噪强度 | SDXL img2img / 云 API | 低（易改姿势） | 低 | 不建议作为主功能；对素体线稿价值有限 |

### 3.2 关键技术分歧：普通 i2i vs 骨架控制（v1 + v2 扩展）

v1 版本（两条路线）：

- **普通 i2i / 图像编辑**（参考图直接进模型，如 Qwen-Image-Edit、Flux Kontext、gpt-image edits）：风格自然，但**姿势不保证完全一致**，模型容易"改着改着把姿势也改了"；
- **ControlNet + OpenPose/DWPose（姿势骨架约束）**：先对参考图做人姿估计得到骨架图，再用骨架约束生成——姿势一致性好，但**必须跑姿态估计模型**（要么 GPU，要么浏览器端 WASM），且骨架对 3D 视角（俯视/仰视）的适配需调参。

v2 扩展（三条路线的细节）：

- **直接参考图编辑（Qwen-Image-Edit / FLUX.2 multi-reference）**：把 900×1200 线稿直接作为参考，用指令描述「变成穿白色连衣裙的真人照片」。链路最短、与现有 `fashion-inspo` 后端最匹配；缺点是**姿势不保证逐关节一致**，模型可能顺手改姿势。
- **ControlNet + OpenPose/DWPose**：先对线稿做人姿估计得到骨架，再用骨架约束生成；姿势一致性好，但：
  - DWPose/OpenPose 主要在**真人照片**上训练，对「灰色素体线稿」属于跨域输入，置信度与稳定性需实测；
  - 双人姿势（275 条）与俯视/仰视视角（3D 透视）更容易失败；
  - 需要额外模型、显存与预处理时间。
- **lineart/canny/depth 控制**：比 OpenPose 更贴合本图库（线稿本身就是线稿），能较好保留构图/轮廓，但对「换体型/换服装」的约束更强，可能限制创作自由度。

**v2 建议（原文）**：先做 10~20 个样本的对比实验（覆盖 4 体系 × 5 视角 × 单人/双人），比较 Qwen-Image-Edit、FLUX.2 multi-reference、SDXL+ControlNet(lineart/openpose) 的姿势保真、解剖错误、手部/脚部、耗时与显存；用结果决定 P1 的默认模式，而不是先押注某一条链路。

## 4. 架构方案对比

### 4.1 五种方案总表（v1 与 v2 合并，保留两版措辞与结论差异）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A 浏览器直连** 第三方 i2i API | 前端直接 `fetch` 服务商接口 | 改造最小、无服务器（v2：改造最小） | API Key 必然暴露给所有访客；多数服务商不允许浏览器跨域调用；无法限流 → 被刷爆（v2：Key 必泄露；跨域/限流不可控） | ❌ **不可行**（v1/v2 一致） |
| **B Pages Functions 代理 + 云端 i2i** | 项目已在 Cloudflare Pages，新增 `functions/api/i2i/*` 做代理、鉴权、配额、审核；生成图存 R2（v2：做鉴权、配额、审核，结果存 R2） | 架构最贴合现状；免费额度够内部用（Workers 免费 10 万请求/天、HTTP 请求无 wall time 上限、等待外部 API 不计 CPU）；密钥只存服务端 | 成本转移给上游 API；需内容审核；需新增 R2/KV/Secrets；从"纯静态"变"静态 + Serverless"（v2：成本转给上游；仍需审核） | ✅ **推荐（P1，限受控/内部）**：v1 "推荐（限自用/内部）"、v2 "P1 推荐（限受控/内部）" |
| **C 自建 GPU + ComfyUI / SD-WebUI** | 独立机器跑 ComfyUI / SD-WebUI（可上 ControlNet OpenPose 做姿势迁移）+ 反代（v2：反代 + 队列） | 姿势控制最准、可选模型最多、单图边际成本最低（v2：模型最自由；可复用 `fashion-inspo` 现有栈） | 需常驻 GPU + 运维 + 公网鉴权 + 带宽；对 3.1k star 的公开项目作者不可承受 | ⚠️ **仅本地/内网**（v1：仅作者自用/内网；v2：本项目最现实的复用路径） |
| **D 纯浏览器本地推理** | WebGPU + onnxruntime-web / Web stable diffusion（SD-Turbo、SDXS 等） | 保持零后端、零密钥、运营零成本 | 首次要下载数百 MB~GB 权重；移动端/集显体验差；画质与可控性弱；无上游审核兜底 | ⚠️ 实验性，不作为主路径 |
| **E 不做生成，只做提示词/参考图辅助** | 按姿势/分类/角度生成 i2i prompt 模板，一键复制 + 参考图下载/导出，用户在 ComfyUI/SD/即梦等外部工具完成生成（v2 同） | 0 算力、0 成本、0 版权输出风险；最贴合"参考图库"定位；与社区 PR 方向一致 | 不是"在线生成"体验 | ✅ **P0 首选** |

### 4.2 关于 Cloudflare Workers AI（v2，方案 B 的上游候选）

复评时核对 Cloudflare Workers AI 模型目录：有 SDXL base/lightning、SD1.5 inpainting、FLUX.1 schnell、FLUX.2 dev/klein（目录标注 FLUX.2 支持 multi-reference）；**未检索到 ControlNet/OpenPose/姿态条件类模型**。

- 因此 Workers AI 可以用于方案 A（线稿直接编辑）的**原型**，尤其 FLUX.2 multi-reference，但姿势保真需要实测；
- 不能替代 ControlNet 做精确姿势迁移；
- 内容政策仍是硬门槛：图库近半为 18+，公共托管 API 很可能拒绝参考图或输出。

### 4.3 与本机 `fashion-inspo` 的关系（v2）

`fashion-inspo` 已有可复用的 i2i 链路（Qwen-Image-Edit，参考图 1~10 张，最大 1024² 像素，任务队列 + 生成历史）。因此：

- **本地/内网**做姿势生成，方案 C 最省事：把姿势图作为参考输入，复用现有 ComfyUI 与队列；
- **公开站**不能直接依赖本机 GPU（稳定性、带宽、安全、成本都不合适），应使用方案 B 的上游 API 或独立 GPU 服务。

### 5.5 接口草案（契约层，非实现；两版草案均保留）

**5.5.1 v1 草案（简版）**

```text
POST /api/i2i                   提交生成任务
  body: { pose_id: "full_std_P001_front" | upload_token,
          prompt: "……",          # 可由姿势数据预填模板
          strength: 0.45,         # 参考图影响强度
          width: 900, height: 1200,
          seed: 12345,
          mode: "pose" | "style"  # 骨架约束 / 风格参考
        }
  → 202 { job_id, eta_s, quota: { used, daily_limit } }
  → 400/413/422 参数错误、图片过大
  → 429 超配额 / 人机校验失败

GET  /api/i2i/{job_id}          轮询任务
  → { status: "queued|running|succeeded|failed",
      image_url: "https://…/r2/…",   # 仅 succeeded
      error: "上游超时，请重试",       # 仅 failed
      cost_estimate: 0.04 }

POST /api/i2i/upload            可选：自定义参考图（≤10 MB，PNG/JPG，尺寸校验）
DELETE /api/i2i/{job_id}        删除生成图（R2 对象）与记录

GET  /api/i2i/limits            能力与限额（含"仅全年龄子集可用"的开关状态）
```

**5.5.2 v2 草案（更细，含控制图与健康检查）**

```text
POST /api/i2i/jobs
  multipart 或 JSON:
    pose_id: "full_sexy_P001_front" | upload_token
    mode: "edit" | "pose" | "style"
    prompt: "白色连衣裙，室内自然光，全身照"
    negative?: "..."
    strength?: 0.45
    width?: 768, height?: 1024
    seed?: 0
    model?: "qwen_image_edit" | "sdxl_controlnet" | "flux2"
  → 202 { job_id, status: "queued", quota: { used, daily_limit } }
  → 400/413/415/422/429 参数/大小/类型/超额

GET /api/i2i/jobs/{job_id}
  → { status: "queued|running|succeeded|failed", progress, images: [url], error, cost_estimate? }

POST /api/i2i/uploads         可选：用户参考图（≤10 MB，PNG/JPG，服务端校验）
DELETE /api/i2i/jobs/{job_id} 删除任务与输出
GET /api/i2i/controls/{pose_id}?type=lineart|openpose
GET /api/i2i/limits           当前开放范围（是否仅全年龄）、模型与配额
GET /api/health
```

**共同约定**（两版合并）：`Idempotency-Key` 幂等；轮询 2 s、最长 90 s；失败必须给中文可执行原因；生成图带「AI 生成」标识与来源；输出保留 7 天自动清理；上传图不持久化【v2】；同一 `idempotency-key` 请求幂等、失败必带可执行的中文原因、生成记录保留 7 天后自动清理【v1】。

### 6.2 Go/No-Go 门槛（v2）

- 未取得原作者对「生成/公开传播」的许可 → **不做公开服务**；
- 上游平台政策禁止 18+ 或参考图被拒 → **不用该上游**（或只做全年龄子集）；
- 10~20 样本的姿势保真/解剖质量不达标 → **不推进 ControlNet 路径**，退回直接编辑或 P0；
- 无法实现年龄门禁、审核与硬限额 → **不做公开发布**；
- 单张成本超过可接受阈值 → **只做内部/本地，或 BYOK**。

## 9. 最终结论（两版完整保留）

**v1 结论（原文）**

1. **能力可行性：高。** 项目没有阻碍 i2i 的技术债；原图、多角度、筛选 UI 可直接复用，真正的缺口是"推理 + 存储 + 任务 + 鉴权 + 审核"这一整套服务层，属于新增基础设施而非改造既有功能。
2. **路径建议（按优先级）：**
   - **P0（建议先做，0.5~1 人日）**：提供"提示词模板 + 一键复制 + 参考图导出"，生成由用户在外部工具完成 → 零算力、零成本、零版权输出风险，且与社区已有方向一致（社区 PR #2 正是把姿势图作为 Agent 生图参考）。
   - **P1（确需站内生成，5~6.5 人日）**：Cloudflare Pages Functions 代理云端 i2i；仅全年龄子集、访问口令（Cloudflare Access/Turnstile）、每日硬限额、R2 自动清理、强审核；定位"内部/自用工具"，**不设公开生成入口**。
   - **P2（公开在线生成）**：**不建议**。内容属性（18+ 近半）与生成类服务合规要求正面冲突，公开站的滥用与成本不可控；若未来仍要做，应先完成内容分级、法律意见与平台政策确认，再重新评估。
3. **一句话**：当前项目适合继续做"参考图库"，不适合直接变"生成站"；生成能力应当放在**别处**（用户自己的工具，或一个受控的独立服务）。若要在这个仓库做，只能做"受控的小范围工具"，不能做"公开的在线生成"。

**v2 结论（原文）**

1. **技术可行性：高。** 项目没有阻碍 i2i 的技术债；900×1200 多角度白底线稿、筛选 UI 与结构化数据是优质输入侧。真正的缺口是「推理 + 任务 + 存储 + 鉴权 + 审核」服务层，属于新增基础设施。
2. **纯静态仓库内独立接入：不可行。** Pages/Workers 只能做静态托管与轻量代理，不能跑 GPU；Workers AI 有生成/多参考模型但没有 ControlNet/OpenPose 姿态条件，且内容政策不适合本站素材。
3. **个人/本地：推荐。** 复用现有 ComfyUI + Qwen-Image-Edit，先做 P0，再做受控 P1；成本与风险可控。
4. **公开/商用：条件性可行，当前不建议。** 图片授权（MIT 不覆盖图片/数据）与成人内容合规是前置门槛；3.1k★ 的公开项目还会放大滥用与成本风险。
5. **一句话**：这个项目适合继续做「参考图库」，不适合直接变「公开生成站」；生成能力应放在用户自己的工具或一个受控的独立服务里。

### 1.2 现有"图像处理"相关实现（关键判断依据）

全仓库**没有任何模型推理、图像编解码或像素级处理**，只有两处字节级校验：

1. `scripts/verify.py`：读取文件前 8 字节判断 JPEG/PNG 魔数 + 大小阈值，校验 2878 个文件完整性；
2. `scripts/download.py`：按 Content-Length/实际字节数校验下载结果，原子替换落盘。

即：**无 PIL / OpenCV / numpy / ffmpeg 等图像库依赖，仅有 Python 标准库**；没有后端、Serverless、数据库、鉴权、任务队列。网站是纯静态资源分发，生图所需的"算力 + 状态 + 存储 + 密钥"全部不存在。

## 2. 接入图生图的能力缺口

图生图（参考图 + 提示词 → 新图）至少需要以下链路，逐项对照现状：

| 环节 | 现状 | 缺口 |
| --- | --- | --- |
| 参考图输入 | ✅ 现成：900×1200 PNG、每姿势 5 个角度、可按分类/视角筛选 | 基本无需改造，最多加裁剪/缩放预处理 |
| 提示词 | ⚠️ 只有体系/分类/姿势名/角度（中文，可程序化拼模板） | 缺"服装/场景/风格"等画面描述，需要用户输入或 LLM 补全 |
| 模型推理 | ❌ 完全没有 | **核心缺口**：云端 API / 自建 GPU / 浏览器 WebGPU 三选一 |
| 结果存储 | ❌ 无 | 生成图约 1~2 MB/张，不能塞进 `dist/`（Pages 每次部署上限 2 万文件），需 R2 或外部存储 |
| 任务状态 | ❌ 无 | i2i 需 5~30 s，需异步任务 + 轮询/SSE |
| 鉴权与配额 | ❌ 无（公开静态站） | 必须新增，否则密钥与成本裸奔 |
| 内容审核 | ❌ 无 | 18+ 内容近半，必须分级与过滤 |
| 观测/日志 | ❌ 无（仅第三方统计） | 失败率、成本、滥用需要记录 |

结论：**"接入 i2i"= 在静态站旁边新增一套"服务端 + 生成服务"**。前端和数据不仅不是障碍，反而是现成的优质输入侧资产。

## 3. 四种接入方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A 浏览器直连** 第三方 i2i API | 前端直接 `fetch` 服务商接口 | 改造最小、无服务器 | API Key 必然暴露给所有访客；多数服务商不允许浏览器跨域调用；无法限流 → 被刷爆 | ❌ 不可行 |
| **B Pages Functions 代理 + 云端 i2i** | 项目已在 Cloudflare Pages，新增 `functions/api/i2i/*` 做代理、鉴权、配额、审核；生成图存 R2 | 架构最贴合现状；免费额度够内部用（Workers 免费 10 万请求/天、HTTP 请求无 wall time 上限、等待外部 API 不计 CPU）；密钥只存服务端 | 成本转移给上游 API；需内容审核；需新增 R2/KV/Secrets；从"纯静态"变"静态+Serverless" | ✅ 推荐（限自用/内部） |
| **C 自建 GPU 服务** | 独立机器跑 ComfyUI / SD-WebUI（可上 ControlNet OpenPose 做姿势迁移）+ 反代 | 姿势控制最准、可选模型最多、单图边际成本最低 | 需常驻 GPU + 运维 + 公网鉴权 + 带宽；对 3.1k star 的公开项目作者不可承受 | ⚠️ 仅作者自用/内网 |
| **D 纯浏览器本地推理** | WebGPU + onnxruntime-web / Web stable diffusion（SD-Turbo、SDXS 等） | 保持零后端、零密钥、运营零成本 | 首次要下载数百 MB~GB 权重；移动端/集显体验差；画质与可控性弱；无上游审核兜底 | ⚠️ 实验性，不作为卖点 |
| **E 不做生成，只做提示词/参考图辅助** | 按姿势/分类/角度生成 i2i prompt 模板，一键复制 + 参考图下载/导出，用户在 ComfyUI/SD/即梦等外部工具完成生成 | 0 算力、0 成本、0 版权输出风险；最贴合"参考图库"定位 | 不是"在线生成"体验 | ✅ **P0 推荐** |

### 3.1 关于"该用哪种生成方式"的一个技术分歧（重要）

本项目图库的核心价值是**姿势准确**。若目标是"把参考图的姿势迁移到新图"，两条技术路线效果差异很大：

- **普通 i2i / 图像编辑**（参考图直接进模型，如 Qwen-Image-Edit、Flux Kontext、gpt-image edits）：风格自然，但**姿势不保证完全一致**，模型容易"改着改着把姿势也改了"；
- **ControlNet + OpenPose/DWPose（姿势骨架约束）**：先对参考图做人姿估计得到骨架图，再用骨架约束生成——姿势一致性好，但**必须跑姿态估计模型**（要么 GPU，要么浏览器端 WASM），且骨架对 3D 视角（俯视/仰视）的适配需调参。

若采用方案 B/C，建议生成入口区分「姿势一致（ControlNet）」与「风格参考（i2i）」两种模式，并在数据里标注该姿势是否适合骨架提取。

### 4.2 接口草案（契约层面，非实现）

```text
POST /api/i2i                   提交生成任务
  body: { pose_id: "full_std_P001_front" | upload_token,
          prompt: "……",          # 可由姿势数据预填模板
          strength: 0.45,         # 参考图影响强度
          width: 900, height: 1200,
          seed: 12345,
          mode: "pose" | "style"  # 骨架约束 / 风格参考
        }
  → 202 { job_id, eta_s, quota: { used, daily_limit } }
  → 400/413/422 参数错误、图片过大
  → 429 超配额 / 人机校验失败

GET  /api/i2i/{job_id}          轮询任务
  → { status: "queued|running|succeeded|failed",
      image_url: "https://…/r2/…",   # 仅 succeeded
      error: "上游超时，请重试",       # 仅 failed
      cost_estimate: 0.04 }

POST /api/i2i/upload            可选：自定义参考图（≤10 MB，PNG/JPG，尺寸校验）
DELETE /api/i2i/{job_id}        删除生成图（R2 对象）与记录

GET  /api/i2i/limits            能力与限额（含"仅全年龄子集可用"的开关状态）
```

语义约定：轮询 2 s、最长 90 s；同一 `idempotency-key` 请求幂等；失败必带可执行的中文原因；所有生成图带来源与"AI 生成"标识；生成记录保留 7 天后自动清理。

## 5. 主要风险

| 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- |
| **内容合规** | 高 | 图库 46.8% 为 18+ 体系；主流云端 i2i 服务政策普遍禁止露骨色情/性暗示内容，参考图本身可能直接触发拒绝；若生成成人内容并在公开站传播，境内涉嫌违反治安管理处罚法与刑法相关条款（制作、传播淫秽物品），托管平台也有权停用服务 | 生成入口仅对"全年龄子集（365+400=765 条）"开放；18+ 条目不提供生成入口；上游审核 + 关键词/图像过滤双保险；免责声明与年龄分级 |
| **版权** | 高 | 图片与原始数据版权属原作者ギア，代码 MIT **不覆盖**图片/数据；i2i 输出属于对原图的演绎，公开传播/商用有侵权风险，原作者可要求下架 | 仅内部/个人自用；生成结果不默认公开、不对外分发；页面与导出文件标注来源与"不得商用"；保留删除通道 |
| **密钥与滥用** | 高 | 公开静态站没有鉴权，若直连 API 或代理不限流，Key 会泄露、额度会被刷爆 | 只走服务端代理；Cloudflare Turnstile + 每 IP/每日硬配额；必要时 Cloudflare Access 加访问口令 |
| **成本不可控** | 中高 | 3.1k star 的公开项目一旦开放生成，流量远超个人预算；上游按张/按分辨率计费 | 硬上限（每日总张数 + 单 IP 张数）、BYOK（用户自带 Key 但仅经代理转发、不落库）、或干脆只做内部工具 |
| **体验与超时** | 中 | 云端 i2i 通常 5~30 s；上游抖动/限流会失败 | 异步任务 + 轮询 + 可取消 + 明确失败原因；前端先出缩略图占位 |
| **架构漂移** | 中 | 从"零依赖静态站"变成"静态站 + Functions + R2 + KV + 外部 API + 计费"；fork 者需自建密钥与绑定；README/部署文档维护成本上升 | 做成**可选模块**（配置了才启用，默认关闭）；把生成能力放独立 `functions/` 与独立分支，主干保持纯静态 |
| **存储与隐私** | 低中 | 用户上传图/提示词、生成图留存；第三方 API 的数据处理与保留政策 | 上传图不落地、生成图 R2 生命周期清理、隐私说明 |
| **供应链** | 低 | 上游 API 价格/政策/稳定性变动 | 抽象一层"生成供应商适配器"，便于切换 |
| **浏览器兼容（方案 D）** | 高 | WebGPU 支持面、iOS 限制、磁盘配额、首次数百 MB~GB 下载 | 只作为实验入口，不作为主路径 |

## 6. 最终结论

1. **能力可行性：高。** 项目没有阻碍 i2i 的技术债；原图、多角度、筛选 UI 可直接复用，真正的缺口是"推理 + 存储 + 任务 + 鉴权 + 审核"这一整套服务层，属于新增基础设施而非改造既有功能。
2. **路径建议（按优先级）：**
   - **P0（建议先做，0.5~1 人日）**：提供"提示词模板 + 一键复制 + 参考图导出"，生成由用户在外部工具完成 → 零算力、零成本、零版权输出风险，且与社区已有方向一致（社区 PR #2 正是把姿势图作为 Agent 生图参考）。
   - **P1（确需站内生成，5~6.5 人日）**：Cloudflare Pages Functions 代理云端 i2i；仅全年龄子集、访问口令（Cloudflare Access/Turnstile）、每日硬限额、R2 自动清理、强审核；定位"内部/自用工具"，**不设公开生成入口**。
   - **P2（公开在线生成）**：**不建议**。内容属性（18+ 近半）与生成类服务合规要求正面冲突，公开站的滥用与成本不可控；若未来仍要做，应先完成内容分级、法律意见与平台政策确认，再重新评估。
3. **一句话**：当前项目适合继续做"参考图库"，不适合直接变"生成站"；生成能力应当放在**别处**（用户自己的工具，或一个受控的独立服务）。若要在这个仓库做，只能做"受控的小范围工具"，不能做"公开的在线生成"。

## 7. 延伸：接入我们项目（fashion-inspo）的建议

我们项目（`fashion-inspo`）**已经具备 i2i 链路**，因此该图库对我们更有价值的用法是"姿势参考图源"，而不是在本仓库里重造生成：

- 我方现状：本地出图页已支持图生图（Qwen-Image 2.1，参考图 1~10 张；候选两段式入库；入库标记 AI 生成）；素材库有 `source_type` 来源枚举与筛选。
- 建议接入方式：
  1. 新增来源类型 `pose_gallery`（前后端 `sourceLabel` 各改一处）；
  2. 写一次性导入脚本：只导**全年龄子集（标准系 365 + 上半身 400 = 765 张，约 340 MB）**，生成缩略图/内容哈希入库，带来源与版权字段；18+ 体系默认不导；
  3. 素材卡片/详情加"用这张图改款"入口（已有入口），把姿势图作为 i2i 参考图；
  4. 生成链路复用现有质量审核与 AI 生成标记，不需要新算力。
- 工作量估算：导入脚本 + 后端来源枚举/筛选 2~3 人日；前端来源筛选与标签 1~2 人日。
- 注意：图片版权非 MIT，**仅本地自用、不随仓库分发原图**；不导入 18+ 子集；README 记录来源与使用限制。

一句话：**工程可行性高，合规可行性低；能做，但应换个做法做，或者不在这个项目里做。**

### 1.3 现有「图像处理」实现

全仓库**没有任何模型推理、图像编解码或像素级处理**，只有两处字节级校验：

1. `scripts/verify.py`：读文件前 8 字节判断 JPEG/PNG 魔数 + 大小阈值；
2. `scripts/download.py`：按实际字节数校验下载结果、原子替换落盘。

即：无 PIL / OpenCV / numpy / ffmpeg 依赖（脚本只用 Python 标准库）；缩略图是**预生成后入库**的，仓库里没有缩略图生成逻辑。接入 i2i 等于第一次给这个项目引入真正的图像 I/O 与推理链路。

## 3. 「图生图」在本项目的三种形态

| 方案 | 输入 | 技术路线 | 姿势保真 | 主要风险 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. 素体线稿 → 成图** | 选中姿势线稿 + 文字描述 | Qwen-Image-Edit / FLUX.2 multi-reference（直接参考图编辑）；或 SDXL + ControlNet lineart/canny | 中~高（取决于模型与提示词） | 低（不涉及真人肖像） | **先做**；最能体现图库价值 |
| **B. 姿势迁移** | 用户照片/角色图 + 姿势线稿 | ControlNet OpenPose/DWPose + IP-Adapter/InstantID；或双参考图编辑 | 高（若骨架可靠） | 高（肖像/同意/深伪、模型许可） | 第二阶段；先做小样本验证 |
| **C. 普通 img2img 重绘** | 线稿 + 去噪强度 | SDXL img2img / 云 API | 低（易改姿势） | 低 | 不建议作为主功能；对素体线稿价值有限 |

### 3.1 关键技术分歧：线稿直接编辑 vs 骨架控制

- **直接参考图编辑（Qwen-Image-Edit / FLUX.2 multi-reference）**：把 900×1200 线稿直接作为参考，用指令描述「变成穿白色连衣裙的真人照片」。链路最短、与现有 `fashion-inspo` 后端最匹配；缺点是**姿势不保证逐关节一致**，模型可能顺手改姿势。
- **ControlNet + OpenPose/DWPose**：先对线稿做人姿估计得到骨架，再用骨架约束生成；姿势一致性好，但：
  - DWPose/OpenPose 主要在**真人照片**上训练，对「灰色素体线稿」属于跨域输入，置信度与稳定性需实测；
  - 双人姿势（275 条）与俯视/仰视视角（3D 透视）更容易失败；
  - 需要额外模型、显存与预处理时间。
- **lineart/canny/depth 控制**：比 OpenPose 更贴合本图库（线稿本身就是线稿），能较好保留构图/轮廓，但对「换体型/换服装」的约束更强，可能限制创作自由度。

**建议**：先做 10~20 个样本的对比实验（覆盖 4 体系 × 5 视角 × 单人/双人），比较 Qwen-Image-Edit、FLUX.2 multi-reference、SDXL+ControlNet(lineart/openpose) 的姿势保真、解剖错误、手部/脚部、耗时与显存；用结果决定 P1 的默认模式，而不是先押注某一条链路。

## 4. 架构方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 浏览器直连第三方 API** | 前端直接 `fetch` 服务商接口 | 改造最小 | API Key 必然暴露；跨域/限流不可控；被刷爆 | ❌ 不可行 |
| **B. Pages Functions 代理 + 云端 i2i** | 新增 `functions/api/i2i/*` 做鉴权、配额、审核；结果存 R2 | 贴合现有 Cloudflare 部署；密钥在服务端；免费额度可做内部工具 | 从「纯静态」变「静态 + Serverless」；成本转给上游；仍需审核 | ✅ **P1 推荐（限受控/内部）** |
| **C. 自建 GPU + ComfyUI** | 独立 GPU 机器跑 ComfyUI（Qwen-Image-Edit / SDXL+ControlNet），反代 + 队列 | 姿势控制最准、模型最自由、单图边际成本低；可复用 `fashion-inspo` 现有栈 | 常驻 GPU、运维、公网鉴权、带宽；对公开项目作者不可承受 | ⚠️ **仅本地/内网**；本项目最现实的复用路径 |
| **D. 纯浏览器 WebGPU** | onnxruntime-web / Web stable diffusion | 零后端、零密钥、零运营成本 | 首次下载数百 MB~GB；移动端/集显差；画质与可控性弱 | ⚠️ 实验性，不作为主路径 |
| **E. 不做生成，只做提示词/参考图辅助** | 按姿势/分类/角度生成 i2i prompt 模板，一键复制 + 参考图下载/导出 | 0 算力、0 成本、0 输出合规风险；最贴合「参考图库」定位；与社区 PR 方向一致 | 不是站内生成体验 | ✅ **P0 首选** |

### 4.1 关于 Cloudflare Workers AI（方案 B 的上游候选）

复评时核对 Cloudflare Workers AI 模型目录：有 SDXL base/lightning、SD1.5 inpainting、FLUX.1 schnell、FLUX.2 dev/klein（目录标注 FLUX.2 支持 multi-reference）；**未检索到 ControlNet/OpenPose/姿态条件类模型**。

- 因此 Workers AI 可以用于方案 A（线稿直接编辑）的**原型**，尤其 FLUX.2 multi-reference，但姿势保真需要实测；
- 不能替代 ControlNet 做精确姿势迁移；
- 内容政策仍是硬门槛：图库近半为 18+，公共托管 API 很可能拒绝参考图或输出。

### 4.2 与本机 `fashion-inspo` 的关系

`fashion-inspo` 已有可复用的 i2i 链路（Qwen-Image-Edit，参考图 1~10 张，最大 1024² 像素，任务队列 + 生成历史）。因此：

- **本地/内网**做姿势生成，方案 C 最省事：把姿势图作为参考输入，复用现有 ComfyUI 与队列；
- **公开站**不能直接依赖本机 GPU（稳定性、带宽、安全、成本都不合适），应使用方案 B 的上游 API 或独立 GPU 服务。

### 5.7 若改为「接入我们自己的 fashion-inspo」

如果目标是把该图库作为 `fashion-inspo` 的**姿势参考源**（而不是给画廊加生成），工作量会低很多：

- 现有 i2i：`reference_ids` 1~10 张、Qwen-Image-Edit、最大 1024²；生成图走候选区/入库；
- 方案一：把姿势图导入素材库（新增 `source_type=pose_gallery`，`web/mobile` 的 `sourceLabel` 各改一处），再作为参考图使用；缺点：会污染素材库，且 1439 张体积大；
- 方案二（更干净）：给生成服务加「直传参考图」接口，把选中的姿势图作为临时参考，不入素材库；
- 建议只导**全年龄子集 765 张**（标准系 365 + 上半身 400，约 340 MB），18+ 不导；
- 仍需注意：图片版权非 MIT，仅本地自用、不随仓库分发原图。

## 6. 主要风险

| # | 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- | --- |
| 1 | **图片授权** | **极高（公开/商用）** | 代码 MIT 不覆盖图片/数据；镜像本身就不构成商业授权；i2i 输出属于对原图的演绎，公开传播/商用有侵权风险 | 仅本地自用；公开前取得原作者许可或替换为自有/CC0 姿势资产；保留署名与删除通道；不默认公开生成结果 |
| 2 | **成人内容合规** | **高** | 18+ 条目 46.8%；主流云端 i2i/托管 API 普遍禁止露骨色情或性暗示；公开传播在境内可能触及治安管理处罚法/刑法相关条款；平台可停用 | 生成入口只开放全年龄子集（765 条）；18+ 不提供生成；关键词+图像审核；年龄分级与免责声明；优先本地/内网 |
| 3 | **AIGC 标识与生成式服务合规** | **高（公开）** | 国内对 AI 生成内容有显式/隐式标识要求；公开生成服务还可能涉及安全评估/备案等义务（需法务确认） | 输出加水印/元数据标识；服务条款与隐私政策；公开前完成合规评估 |
| 4 | **肖像/同意/深伪（若开放用户照片）** | **高** | 用户上传真人照片做姿势迁移涉及敏感个人信息、深度合成与同意问题；未成年人风险 | 默认不做用户照片；若做，需明示同意、年龄门禁、人脸/NSFW 审核、短 TTL、输出标识、禁止未成年人 |
| 5 | **密钥与滥用** | **高（公开）** | 静态站无鉴权；直连 API Key 必泄露；3.1k star 项目一旦开放生成，流量与恶意刷量不可控 | 只走服务端代理；Turnstile/Access；每 IP/每日硬限额；预算告警；必要时关闭公开入口 |

| 9 | **架构漂移** | 中 | 从零依赖静态站变成「静态 + Functions + R2 + 上游 API + 计费」；fork 者需自建密钥与绑定 | 做成可选模块（配置了才启用，默认关闭）；生成逻辑放独立 `functions/`/独立服务；主干保持纯静态 |
| 10 | **模型许可证** | 中 | SDXL（OpenRAIL++）、Qwen-Image-Edit、ControlNet、IP-Adapter、InstantID/InsightFace 条款不同；人脸相关模型常限非商用 | 商用前逐个核对权重许可证；优先 Apache/可商用模型；避免 InsightFace 非商用依赖 |
| 11 | **供应链/上游稳定性** | 低中 | 上游 API 价格、政策、模型下线、限流 | 抽象供应商适配层；模型/工作流版本化；失败降级 |
| 12 | **隐私与数据保留** | 低中 | 用户上传图、提示词、生成图留存；第三方处理政策 | 上传不落盘/短 TTL；输出 7 天清理；隐私说明 |

### 6.1 Go/No-Go 门槛

- 未取得原作者对「生成/公开传播」的许可 → **不做公开服务**；
- 上游平台政策禁止 18+ 或参考图被拒 → **不用该上游**（或只做全年龄子集）；
- 10~20 样本的姿势保真/解剖质量不达标 → **不推进 ControlNet 路径**，退回直接编辑或 P0；
- 无法实现年龄门禁、审核与硬限额 → **不做公开发布**；
- 单张成本超过可接受阈值 → **只做内部/本地，或 BYOK**。

## 7. 工作量与成本估算

| 范围 | 估算 | 说明 |
| --- | --- | --- |
| **P0 提示词/参考图导出** | **0.5~1 人日** | 模板生成、复制、导出；0 算力、0 输出合规风险 |
| **P1 受控站内生成（方案 B）** | **5~7 人日** | 前端 2~3 天 + Functions/鉴权/配额 1.5~2 天 + 数据/控制图 0.5~1 天 + 存储/部署/文档 1 天；不含法律意见与审核细则 |
| **C 自建 GPU/ComfyUI** | **5~10 人日 + 长期运维** | 复用现有 ComfyUI 可压缩到 3~5 人日；需要常驻 GPU、反代、队列、监控 |
| **D 浏览器 WebGPU** | **5~8 人日** | 模型转换/量化、兼容性、移动端体验；不建议作为主路径 |
| **公开产品化** | **再 +2~4 周** | 年龄门禁、审核、AIGC 标识、隐私、限流、预算告警、法务/平台确认 |
| **样本对比实验（Phase 0）** | **1~2 天** | 10~20 个姿势 × 3 条技术路线；产出选型结论 |

成本假设（仅供量级参考，实际随供应商/地区变化）：

- 云端 GPU：约 $0.3~1/小时级别；按 10~30 s/张，单张约 $0.01~0.05（不含失败重试）；
- 上游按张计费 API：价格差异大，需以当前报价为准；
- 存储：生成图 1~2 MB/张，R2 成本低；按 7 天 TTL 控制；
- 控制图预生成：lineart/canny 用 CPU 分钟级；DWPose/OpenPose 用 GPU 约 10~40 分钟（1439 张，需实测）。

## 8. 推荐路线（阶段化）

1. **Phase 0（1~2 天，先做）**：样本实验。选 10~20 个覆盖 4 体系 × 5 视角 × 单人/双人的姿势，比较：
   - Qwen-Image-Edit 直接编辑；
   - FLUX.2 multi-reference / 云端 API；
   - SDXL + ControlNet（lineart / OpenPose）；
   记录姿势保真、解剖/手部、耗时、显存、失败率。
2. **Phase 1（0.5~1 天，P0）**：上线「提示词模板 + 一键复制 + 参考图导出」。这是零算力、零输出合规风险、与社区方向一致的增强；先验证用户需求。
3. **Phase 2（5~7 天，P1，仅内部/受控）**：确需站内生成时，做方案 B：
   - 只开放全年龄子集（765 条）；
   - Cloudflare Access/Turnstile + 每日硬限额；
   - R2 存结果 + 7 天清理；
   - 强审核与「AI 生成」标识；
   - 不放公开入口。
4. **Phase 3（公开在线生成）**：**暂不做**。除非同时满足：原作者许可/资产替换、内容分级与审核、AIGC 标识、平台政策允许、成本可控、法务确认。
5. **若目标是服务自己的 `fashion-inspo`**：走 5.7 的低风险方案——只导入全年龄子集、新增 `pose_gallery` 来源、复用现有 i2i，不需要改动这个静态仓库。

**Kill criteria**：原作者拒绝授权、上游政策不允许、样本身份/姿势质量不达标、无法控制成本或审核 → 立即停在 P0，不做站内生成。

---

## 9. 最终结论

1. **技术可行性：高。** 项目没有阻碍 i2i 的技术债；900×1200 多角度白底线稿、筛选 UI 与结构化数据是优质输入侧。真正的缺口是「推理 + 任务 + 存储 + 鉴权 + 审核」服务层，属于新增基础设施。
2. **纯静态仓库内独立接入：不可行。** Pages/Workers 只能做静态托管与轻量代理，不能跑 GPU；Workers AI 有生成/多参考模型但没有 ControlNet/OpenPose 姿态条件，且内容政策不适合本站素材。
3. **个人/本地：推荐。** 复用现有 ComfyUI + Qwen-Image-Edit，先做 P0，再做受控 P1；成本与风险可控。
4. **公开/商用：条件性可行，当前不建议。** 图片授权（MIT 不覆盖图片/数据）与成人内容合规是前置门槛；3.1k★ 的公开项目还会放大滥用与成本风险。
5. **一句话**：这个项目适合继续做「参考图库」，不适合直接变「公开生成站」；生成能力应放在用户自己的工具或一个受控的独立服务里。
