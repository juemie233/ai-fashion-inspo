拆分方法（每一步都不能省）：

1. 函数体**原样搬移**（含注释与文档字符串，只改归属模块）；
2. 原文件以**同名再导出**（`# noqa: E402, F401` 并注明理由），既有调用方与测试无需改动；
3. 跑全量 `pytest` + `ruff check app` + 漂移门禁；
4. 独立提交（一个切片一条历史，便于 bisect）。

只选**自包含**切片：若新模块与原模块互相 import 会成环，必须**先**抽共享助手（路径解析、VLM 调用、
`_current_status` 这类跨切片助手）再抽主体。`crop_common.py` → `crop_scan.py` 就是按这个顺序拆的。

#### 拆分的三条硬经验（下次拆文件先看这里）

1. **monkeypatch 点会随符号一起搬家，且失效是静默的**：测试 patch 的是「读取该名字的模块」。
   函数搬到新模块后，patch 旧模块不会报错——真实现照样跑（限制/取消/伪造全不生效），
   只会表现为「用例莫名断言失败」或「测试变慢」。本次已同步的 patch 目标见
   `tests/test_f2_import_execute.py` / `tests/test_f2_import_status.py` / `tests/test_crop_scan.py`
   的 import 处注释。搬走后旧模块**没有**该属性时（如 `_run_subprocess`），patch 会直接
   AttributeError —— 这是好事，遇到报错不要急着把名字补回旧模块。
2. **跨切片助手只能「转发」，不能复制**：`_current_status` 留在 `f2_import`（切片 E/F 也要用），
   `f2_fetch_stages.py` / `f2_plan_apply.py` 里的同名函数是**延迟导入的转发壳**（见其 docstring）。
   若照抄实现，测试的取消/暂停 patch 会静默失效，且两模块在模块级互相 import 会成环。
3. **搬走后要顺手收尾导入**：原文件顶部那些只被搬走代码使用的 import 会立刻变成 `ruff F401`
   （本次遇到 `Path`、`time`、`_PROGRESS_AFTER_DOWNLOAD`、`_run_subprocess` 等）；
   仍在别处（或测试）使用的名字则改成带注释的再导出，**不要**删掉公开面
   （例：`crop_service.py` 里的 `detect_screenshot_features` / `screenshot_confidence`）。

验收标准：每次拆分后两个原文件的行数单调下降，且 `pytest`、`ruff`、漂移门禁三者全绿。

**这是一个「本地优先、单进程、数据量千级」的应用架构**，不是高并发服务。评估一切组件的标尺应该是：*引入它能解决当前哪个真实痛点？引入后它的守护/备份/运维成本谁来承担？*

---

### 1. 结论先行

**当前阶段不建议引入 Redis、PostgreSQL、Celery、MinIO 等重型组件**——复杂度与收益不成正比，且会引入新的常驻进程、备份对象和排障面。

真正值得投入的反而是**不引入新组件也能做的健壮性工程**（备份、守护、日志轮转、健康探针）——这些正是 TODO 高优先级里尚未完成的两项（①数据备份 ④服务守护与监控），优先级远高于引入 Redis。

---

### 2. 候选组件逐项评估

#### 2.1 不推荐引入（当前阶段）

| 组件 | 现状替代 | 不引入的理由 |
|---|---|---|
| **Redis** | 缓存=进程内/磁盘；队列=自研 `task_queue` + worker | ① 读多写少的场景（标签分组、模型列表、配置、素材列表）用进程内缓存即可，缓存一致性还更好控制；② 自研队列在个人规模（批量分析/审核/去重任务）完全够用；③ 引入=多一个**需要守护、备份、占内存的常驻进程**，Windows 上反而新增故障点 |
| **PostgreSQL / MySQL** | SQLite + SQLAlchemy async | 21.5MB/千级数据，SQLite 单文件=备份即拷贝（极大优势）；并发写锁（`database is locked`）在**单用户本地**场景概率极低，且 WAL + 重试已缓解。换 PG 的并发/在线备份收益在单机无感，代价是运维复杂度与备份方案重做 |
| **Celery / RQ** | 自研 `task_queue` + `app/worker.py` 分发表 | Celery 的分布式 worker 优势在单机无意义；RQ 依赖 Redis。现有队列已支撑批量分析、质量审核、去重、向量回填四类任务，且有重试/暂停/进度机制 |
| **MinIO / 对象存储** | 本地文件系统 + `storage/` | 素材是本地文件，对象存储解决的是多机共享，当前无此需求 |
| **Prometheus + Grafana** | `/api/health` + 日志 | 监控全家桶对单机应用过重；轻量探针 + 前端健康卡片足够 |

#### 2.2 值得引入（轻量工具/做法，非重型组件）

| 项 | 方案 | 解决的真实痛点 |
|---|---|---|
| **进程守护与自动拉起** | NSSM / WinSW 把 `uvicorn`、`worker` 注册为 Windows 服务（或计划任务 + 看门狗脚本） | TODO 高优先级④的核心：**worker 是单点、崩溃后任务永久卡死**（`--reload` 崩溃事件已暴露过此问题） |
| **日志轮转** | Python `RotatingFileHandler`（后端/worker 各一份，按大小/日期切分） | 日志无限增长、排查困难；零新依赖 |
| **自动备份** | 备份脚本（DB 快照 + `storage/` 增量）+ Windows 计划任务，保留多份历史 | TODO 高优先级①：3000+ 素材全部依赖本地磁盘，无任何备份；`ai/reset` 可一键清空 |
| **Alembic 迁移** | ✅ **已引入**（baseline `1aef95ac59` 已生成） | 替代手写 `db_migrations`，后续新增字段走 revision |
| **进程内缓存**（可选） | 标签分组、模型列表、配置等读多写少接口加 TTL 缓存 | 目前每次请求重查 DB；个人规模收益小，属锦上添花 |

#### 2.3 现有架构的一个真实边界（供决策参考）

`ai_shared.py` 的 `_active_analyses` / `_pending_queue` 是**进程内内存状态**——API 进程与 worker 进程不共享。当前单 worker 架构没问题，但若未来：① 想加第二个 worker 实例，② API 进程重启会丢队列内存视图。**这是将来唯一可能让 Redis（共享队列/发布订阅）变得合理的动机点**——但触发条件是"多 worker / 进程重启频繁"，个人场景可接受现状。

---

### 3. 优先级建议路线

```
阶段 A（强烈建议，零/极少新依赖，对应 TODO 高优先级①④）
  ├─ 备份脚本 + 计划任务（数据可逆性，最紧急）
  ├─ 进程守护：NSSM/WinSW 注册 uvicorn + worker 为服务
  ├─ 日志轮转：RotatingFileHandler
  └─ 健康探针/前端健康卡片（/api/health 已有，加展示层）

阶段 B（可选，收益明确且轻量）
  ├─ ruff 静态检查 + black 格式化（代码质量，CI 可用）
  ├─ uv 统一包管理（可选）
  └─ 进程内 TTL 缓存（读多接口）

阶段 C（仅在出现以下信号时才重新评估 Redis/PostgreSQL/Celery）
  ├─ 多用户 / 多实例 / 部署到服务器
  ├─ 素材量级到数十万、向量检索成为瓶颈
  ├─ 采集/AI 并发大幅提升、需要跨进程共享任务状态
```

---

### 4. 一句话总结

**当前架构的"短板"不在缺 Redis/消息队列，而在缺守护与备份**——前者是给规模化的系统用的，后者才是 3000+ 素材单机应用真正的风险点。把 TODO 里的「数据备份」和「服务守护与监控」落地（都是轻量脚本/工具），健壮性提升会远大于引入 Redis。

### 附：决策信号清单（何时重新评估重型组件）

| 信号 | 触发条件 | 应引入 |
|---|---|---|
| 多实例部署 | 部署到服务器 / 多用户访问 | PostgreSQL + 迁移方案重做 |
| 跨进程共享任务状态 | 多 worker / API 频繁重启导致队列视图丢失 | Redis（队列 + 发布订阅） |
| 高并发采集/AI | 并发任务量显著上升 | RQ/ARQ（Redis 队列）或 Celery |
| 素材规模数十万级 | 向量检索/列表查询成为瓶颈 | 独立向量库 + 缓存层 |
