## 2. 已修复项摘要

审查发现的全部问题已修复并合入（提交 `3e6ba05`，34 文件 +884/-256；另 `1ae5f41` 修复审查发现的攒批清理回归）。分类摘要：

### 2.1 严重问题（数据丢失 / 一致性风险）

| 项 | 修复 |
| ------ | ------ |
| `delete_inspiration` 物理删除无垃圾桶守卫、无审计 | 增加 `deleted_at` 守卫（active 素材必须先软删）+ `record_audit_log` 留痕 |

| LanceDB 单条 upsert 在跨进程写锁外打开表句柄 | `_table(kind)` 移入 `_vector_write_lock()` 内，与批量写入路径对齐 |
| `purge_small_backfill_tasks` 误删攒批新机制任务（worker 重启兜底时） | 仅清理已终态（success/failed/cancelled）小任务；pending 保留、running 交由心跳租约 |

### 2.2 事务边界 / 一致性

- `enqueue_vector_backfills` / `flush_pending_vector_backfills` 不再内部 commit，事务边界交还调用方（5 处调用点逐一适配）
- 恢复素材时解除来源 URL 墓碑（与移入时 `seal_urls` 对称）；恢复平台 ID 并发冲突捕获转 409
- `batch_delete` 崩溃窗口自愈：待清理文件清单预存 task.result，worker 崩溃重试可从 result 恢复清理
- 质量审核 CAS 写回校验 rowcount：判定未生效（素材已被人工翻案）不再记入审核日志与任务统计
- 429 限流错误分类与分析链路对齐（可恢复重试，不再整批永久失败）
- URL 下载：异常路径统一清理半写文件、SSRF 防护（拒绝回环/私网/链路本地）、内部异常不再泄露给客户端
- 统计口径统一：分析失败过的素材纳入「未分析」，可被「分析全部未分析」批量重跑
- 批量打标改走向量攒批登记（不再串行 N 次 Ollama 阻塞请求）；`update_tag` 单条改名补向量重建登记

### 2.3 健壮性 / 性能

- `_read_image_base64` 线程池化（读盘 + PIL + base64 不再阻塞事件循环 / worker 心跳）
- `batch_rename_tags` 预检批内改名冲突、空名、别名冲突；`create_tag` 别名冲突与空名拒绝
- `merge_tags` / `import_tags` / `get_or_create_tag` 竞态 SAVEPOINT 保护；`delete_unused_tags` 补向量登记
- 分类器单类测试集指标计算保护（不再 ravel 解包崩溃）；近似重复扫描文件缺失容错
- 采集链路：启动失败 / 续采次数耗尽时任务置 failed（不再永久 pending）；取消/删除/清空/重试补审计；`_check_cdp`、`get_task_log` 去线程池；`chrome_manager` 监控线程复用事件循环（消除跨 loop 风险）并对 `_proc` 加锁
- 人物：xhs_id 唯一冲突转 409、CSV 表头首尾空白容错修复、创建空名校验
- 其余：model_config / model_prompt 按 mtime 缓存（消除高频读盘）、`seal_urls` 批量插入、GPU 字段容错、avg_tags 统计口径、prompt 注入输入截断、`_scraper_handles` 死状态清理等

**测试**：新增 / 更新 16 处用例，全量 312 项通过（临时数据库，不触碰真实数据）。

## 3. 评估后未修复项（本文件重点）

以下问题经评估后**暂不修复**，记录现象、原因与后续建议，避免重复评估。

### 3.1 并发上传同文件可重复入库（content_hash 无唯一约束）

- **现象**：内容去重为「先查后插」（`inspiration_dedupe.find_duplicate_by_hash` 查无结果即放行），`inspirations.content_hash` 仅为普通索引而非唯一约束。两个并发上传同一文件的请求可同时通过查重，产生两条重复记录。
- **评估**：加「部分唯一索引（`deleted_at IS NULL`）」可在 DB 层兜底，但历史库可能已存在重复哈希数据，直接建唯一索引会使迁移失败；先清理历史重复又涉及「删除哪一条」的数据决策，风险大于收益。单用户本地部署下，同一文件几乎同时并发上传的概率极低，且已有应用层查重 + 上传 409 清理文件的保护。
- **后续建议**：若多用户/多进程并发上传成为常态，先做一次历史重复数据核查（按 content_hash 分组计数，人工确认保留策略），再迁移建部分唯一索引，并在 `create_inspiration` / `create_inspiration_from_url` 的 flush 处捕获 IntegrityError 转 409（应用层代码已预留此处理）。

### 3.2 人物照片组内去重无唯一约束（add_photo_to_set TOCTOU）

- **现象**：`person_service.add_photo_to_set` 先查重（`set_id + content_hash`）后插入，两步之间无唯一约束兜底，并发上传同一照片到同一组时可产生重复照片记录。
- **评估**：与 3.1 同构的问题（需迁移 + 历史数据核查），且照片上传是单人操作、并发同图概率极低；已有应用层查重 + 409 清理文件。
- **后续建议**：需要时对 `(set_id, content_hash)` 建唯一索引（历史核查后），插入侧捕获 IntegrityError 转 409 并清理已落盘文件。

### 3.3 取消采集任务不级联终止 Playwright 浏览器进程

- **现象**：`cancel_scraper_task` 仅向采集子进程（run_scraper.py）发送 SIGTERM；抖音路径由该子进程 spawn 独立浏览器，Windows 上 SIGTERM 不级联杀子进程，可能残留浏览器进程。
- **评估**：浏览器的创建与清理归属采集子进程（`backend/scripts/run_scraper.py`，scripts 目录按项目约定不纳入自动审查/修改范围）；服务层无法安全地拿到浏览器 pid，需在脚本层注册信号处理或记录浏览器 pid 一并终止，超出本次服务层审查边界。
- **后续建议**：在 `run_scraper.py` 内注册 SIGTERM 处理（收到信号时先关闭 Playwright 浏览器再退出）；或让子进程退出前统一 `browser.close()`（现有实现若已在 `finally` 中关闭则仅剩「强杀」窗口）。

### 3.4 tag.category / platform 无强枚举约束

- **现象**：`Tag.category`、`Person.platform` 等字段无 CHECK 约束，服务层任意字符串可入库；前端分组/平台展示依赖固定枚举，非法值会落入「未知」分组。
- **评估**：加 DB 级 CHECK 或 schema 级 Literal 校验涉及 API 契约面改动（前后端 schema 版本握手、已有脏数据兼容），且当前由前端映射兜底（未知值正常显示），影响面可控。
- **后续建议**：在 Pydantic schema 层对创建/更新入口加 `Literal` 校验（服务层不必重复校验），如需清理存量脏数据另做一次性脚本。

## 4. 遗留风险与后续建议

1. **删除类任务的崩溃窗口**（batch_delete / deduplicate / purge_trash「先 DB 后文件」顺序）：已对 batch_delete 预存清理清单自愈；purge_trash 与 deduplicate 的「DB 已删、文件未删」窗口仍存在，孤儿文件可由存储完整性检查（仅扫 images/thumbnails/videos，不含 trash/）外的手动清理兜底。若要求绝对收敛，可扩展孤儿文件清理任务覆盖 trash/ 目录。
2. **`run_scraper.py`（scripts）链路契约问题**：批量回滚只清理当前失败文件（同批孤儿 + items_added 虚增）、硬编码 DB 路径绕过 `settings.database_url`、跨次内容哈希查重缺失、下载无图片格式校验——已核实的脚本层缺陷，按项目约定不在自动审查修改范围，建议单独安排脚本层修复。
3. **向量能力降级面**：CLIP / Ollama / LanceDB 任一不可用时向量静默降级，语义搜索与相似推荐回退标签匹配——属设计取舍，若希望运维可见，可考虑在管理页对「向量缺失素材数」增加告警。
