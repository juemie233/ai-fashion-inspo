## 1. R2（SDXL + ControlNet lineart）PoC 的成本与代价评估

> 原文件：`pose/换姿势R2方案成本与代价评估.md`｜原题：R2（SDXL + ControlNet lineart）PoC 的成本与代价评估

> **状态**：已归档（2026-10-31）。本方向已结项；成本预估与 PoC 过程数据保留在本文件，
> 最终结论与后续路线见 [换姿势方向结项报告](换姿势方向结项报告-2026-10-31.md)。

> 目的：在正式投入开发前，评估「用 SDXL + ControlNet lineart 提升换姿势保真度」这一方案的**代价**（时间、磁盘、显存、下载、工程与维护）与**风险**，并给出是否值得做 PoC、PoC 怎么做、做到什么程度停。
> 范围：**只做评估与 PoC 方案，不写业务代码**。
> 背景：当前「换姿势」走 R1 = Qwen-Image 2.1 多参考图编辑（参考图 1~10 张，姿势图作为最后一张）。实测问题是**姿势跟得不够准**——见 [`姿势图库换姿势（路径一）实现说明.md`](姿势图库换姿势（路径一）实现说明.md) 与本文第 2 节。
> 评估时间：2026-10-30。

### 0. 结论摘要

| 项 | 最小方案（R2-A：SDXL + lineart ControlNet） | 带身份保持（R2-B：+IP-Adapter） | 产品化（若 PoC 通过） |
| --- | --- | --- | --- |
| 新增下载 | **约 9.4 GB**（SDXL 基座 ~6.9 GB + lineart ControlNet ~2.5 GB） | 再 +3.2 GB（IP-Adapter ~0.7 GB + CLIP-ViT-H ~2.5 GB） | 无新增（沿用） |
| GPU 时间 | PoC 约 **1~2 小时**（含参数扫描与 60 样本对比） | 再 +1~2 小时 | 每张比 R1 略慢/持平（实测为准） |
| 工程时间 | **2.5~4 人日**（环境 0.5~1 + 工作流 1~1.5 + 样本与评估 1~1.5） | 再 +1~2 人日（装插件/调 IP-Adapter） | **再 +3~5 人日**（新档位/参数/前端/测试/文档） |
| 磁盘 | 见 §3：D 剩 78.6 GB / G 剩 74.4 GB 都够；建议统一放 G 并配 `extra_model_paths.yaml` | 同左 | 同左 |
| 收益 | 姿势**逐线可控**，理论上比 R1 更贴姿势线稿 | 姿势 + 有希望保住脸/服装 | 换姿势质量上限提高 |
| 主要代价 | 画面质量/身份保持可能**不如 Qwen 2.1**；姿势线稿是「素体技术图」，ControlNet 域不匹配风险高 | 多一套模型/插件与许可问题（FaceID/InsightFace 非商用） | 同时维护两套生成栈 + 一键出图的档位策略变复杂 |

**建议**（2026-10-30 更新：零成本验证已完成，见 §10——结论有反转）：
1. **零成本验证已完成**：R1 的瓶颈不是提示词/参考顺序，而是**姿势线稿本身被当内容融合**（出现关节圆/素体雕塑/直接抄线稿）；只用文字描述姿势（不传线稿）反而姿势大致能改、身份保住、速度快 3 倍。下一步应先评估「换姿势改成文字描述」的小改造，再决定要不要花 9.4 GB 做 R2。
2. **先评估「文字姿势描述」小改造**（零下载、预计 1~2 人日）：换姿势不再传线稿，只用姿势名/角度/分类拼提示词——单素材实测姿势 3/5、25 张批量实测 **姿势均分 4.0/5、84% ≥4 分、身份 5.0/5、31 s/张**；若「大致姿态」已够用，就不必下 SDXL（失败模式：坐/跪类姿势与相机角度不跟随、源图手机/UI 会传染）。
3. 若仍需**逐关节精确姿势**，再做 **R2-A 最小 PoC**（2.5~4 人日 + 9.4 GB 下载 + 1~2 小时 GPU），用 60 个样本对照「文字方案」，**不写产品代码**（只在 ComfyUI 里搭工作流 + `scripts/oneoff/` 临时脚本）；注意 ControlNet 只是把线稿当控制信号，关节圆圈仍可能变成结构线，PoC 必须验「无关节痕」。
4. PoC 也可能得出「姿势更准但画面/身份更差」——若如此，**不产品化**，把预算转向「升级编辑模型/两段式」，或接受 R1 的姿势限度。

### 2. 方案拆解：R2 有三种递进形态

#### 2.1 R2-A 最小方案（只验证「姿势可控性」）

```text
主体照片（1 张）──copy──┐
                         ├─→ SDXL 基座 → ControlNet(lineart, 姿势线稿) → KSampler → VAE → 成图
姿势图（900×1200 PNG）──┬─┘
       （可选：黑白阈值化）
```

- 优点：模型最小、无自定义节点、工程最简单；
- 缺点：SDXL + ControlNet **不保脸/不保服装**（只有姿势约束）；成图质量大概率不如 Qwen 2.1；
- 用途：**只回答一个问题**——lineart ControlNet 能不能把「素体线稿」的姿势带进成图。

#### 2.2 R2-B 带身份保持（+IP-Adapter）

在 R2-A 基础上加 IP-Adapter（image prompt adapter）把主体照片的「长相/风格」注入，或用两段式：先生成姿势 → 再用 Qwen 编辑回填脸/服装。

- 需装 `ComfyUI_IPAdapter_plus` 自定义节点 + 模型；
- 质量与复杂度上升一档；**许可与插件兼容风险**也随之上升（见 §6）；
- 用途：如果 R2-A 姿势对了但脸不对，才值得做。

#### 2.3 R2-C 两段式（R2 出构图 + Qwen 回填）

R2-A 出「姿势对但人物不像」的图 → 作为中间图，交给现有 Qwen-Image-Edit（以主体照片为参考）二次编辑，把脸/服装/质感找回来。

- 优点：姿势与身份各用最擅长的模型；
- 缺点：两步延迟（约 20~45 s + 20~45 s）、两步失败率叠加、要新编排一条链路；
- 用途：若 R2-A 的姿势优势明显，这是最可能「能用」的形态。

  1. 在 `ComfyUI/extra_model_paths.yaml` 里把 `checkpoints/controlnet/clip_vision` 指向 `G:\AI\comfy-models\...`（G 剩 74.4 GB），**D 盘零增长**；

### 5. 质量与效果代价（决定成败的部分）

#### 5.1 姿势保真 vs 身份/画质：本质是取舍

| 维度 | R1（Qwen 2.1 多参考编辑，现状） | R2-A（SDXL + lineart ControlNet） | R2-B（+IP-Adapter） | R2-C（两段式） |
| --- | --- | --- | --- | --- |
| 姿势跟随 | 中（实测不够准） | **高（理论上逐线可控）** | 高 | 高 |
| 长相/身份 | **较好**（多参考编辑保主体） | **差**（不保脸） | 中（IP-Adapter 找回一部分） | 中~好（第二段回填） |
| 服装一致 | 较好 | 差 | 中 | 中~好 |
| 画面/解剖质量 | 较好（新模型） | 中（SDXL 较旧，手/细节弱） | 中 | 中~好 |
| 单张耗时 | 20~45 s | 15~40 s（预估） | +10~20% | **40~90 s** |
| 链路复杂度 | 低（已上线） | 中 | 中高 | 高 |

#### 5.2 最关键的域不匹配风险：我们的姿势图是「素体技术图」

姿势图库的线稿不是「人体轮廓线稿」，而是**灰阶素体 + 关节圆圈**的技术图。lineart ControlNet 的强约束会把**关节圆圈、结构线**一起当成画面线稿：

- 可能结果：人物身上出现「关节圆/机械感」、被理解为服装装饰或纹身；
- 灰度阴影（不是纯黑白）也可能让线稿判定不稳定；
- 缓解手段都有额外代价：阈值化/去圆处理（图像处理 + QA，不确定能去干净）、降低 control weight（姿势跟随又变弱）、改走 OpenPose 骨架（需姿态估计，且**素体线稿是跨域输入**，DWPose 未必能稳定识别人体关键点——之前评估里已列为高不确定项）。

**这是 R2 PoC 的头号风险**：可能投入了下载与 2~4 人日，结论是「我们的线稿不适合 ControlNet」。

#### 5.3 双人/俯视/仰视等困难样本

- 双人（275 条）：ControlNet lineart 对多人重叠/遮挡的线条归属易混淆；
- 俯视/仰视（每体系约 1/5）：透视夸张的线稿，ControlNet 可能直接画成「俯视看板」或畸变人；
- 这些样本在 R1 里也差，但 R2 未必更好——PoC 必须按体系/角度分层统计，不能只看总平均。

### 6. 风险与合规

| 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- |
| **线稿域不匹配**（§5.2） | **高** | 素体技术图 ≠ 人体线稿；可能产生关节圆/机械感 | PoC 先验证；不行就停 |
| **身份/服装丢失** | **高** | R2-A 不保主体；R2-B 才缓解 | 先 R2-A 看姿势收益，值得再上 R2-B |
| 下载/磁盘/网络 | 中 | 9.4 GB；D/G 各剩 78.6/74.4 GB；HF 可能需代理 | 模型统一放 G 盘 + `extra_model_paths.yaml`；用镜像/代理并校验 |
| 模型/权重许可 | 中 | SDXL 是 OpenRAIL++-M；ControlNet 权重许可因发布者而异；IP-Adapter/FaceID 部分依赖非商用模型（InsightFace） | 个人自用问题不大；产品化前逐项核对许可证 |
| ComfyUI/插件兼容 | 中 | R2-A 原生支持；R2-B 需第三方插件，升级可能不兼容 | 优先 R2-A；插件版本锁定并记录 |
| 显存/并发 | 中 | 与 Ollama、打标/审核任务共存，需沿用互斥与显存守门 | 档位 `vram_gib` 保守配置；出图前释放 Ollama |
| 维护成本 | 中 | 两套生成栈、两套参数语义（参考图 vs 控制图）、一键出图策略分叉 | 只在 PoC 通过且确有收益时产品化 |
| 机会成本 | 中 | 2.5~4 人日 + 产品化 3~5 人日，可用于升级编辑模型/两段式等替代方案 | 先零成本验证，再决定预算 |

### 7. 替代方案对比（先想清楚「不下载 SDXL」能不能解决）

| 方案 | 新增下载 | 工程代价 | 姿势收益 | 建议顺序 |

**Kill criteria（任一命中即不产品化）**：
1. 姿势保真人工评分中位数 **不高于** R1（或提升 <0.5 分）；

### 9. 建议（按先后顺序）

1. **先做零成本验证**（0.5~1 人日，不下载模型）：用现有 R1 的 20 个样本，只改「参考顺序 / 提示词 / 参考数量」，看姿势是否有可感知改善。若改善明显，R2 的收益预期下降。

#### 10.2 关键结论（推翻了 §9 原来的假设）

1. **R1 的瓶颈不是提示词或参考顺序，是姿势线稿本身被当「内容」融合**：
   模型把灰色素体当成「要画进画面的身体/雕塑」——出现关节圆圈烙在人物腿上（v0/v1）、
   旁边多一个素体雕塑（v2）、重复线稿直接变雕塑（v4）、顺序调换直接抄线稿（v3）。
   这与用户此前截图反馈「最后一张图有问题，不是姿态图」完全对应：**线稿进了模型，但被当成内容而不是控制信号**。
2. **提示词越解释越糟**：v2 明确说「线稿只作姿势参考」，模型反而更认真地渲染了素体。
3. **不传姿势图、只用文字描述姿势，反而效果最好**：姿势大体跟上了（v5 两组：侧身站姿 / 手扶墙顶胯），
   身份/服装保持好、无伪影，且**耗时从 85~137 s 降到 32~34 s（快 2.6~4 倍）**。
4. 提示词带姿势名/角度（v1）相比基线（v0）**没有可感知改善**——文字只有在「不传线稿」时才有发挥空间。

#### 10.3 对产品与 R2 决策的影响

- **零成本可立刻采用**：把「换姿势」的生成方式从「传姿势图」改为「传姿势文字描述」（姿势仍从 399 库里选，
  但只取名称/角度/分类拼进提示词；`pose_id` 仍记录用于溯源）——预计 1~2 人日、无新模型、还快 3 倍；
  代价：姿势只到大体姿态（3/5），不能逐关节复刻线稿，且依赖姿势名称的准确度。
- **R2-A 的价值依然成立，但目标更明确**：既然 R1 的图像路线不可用，lineart ControlNet 是唯一能把
  线稿当「控制信号」而非「内容」的路线；但关节圆圈在 ControlNet 下仍可能变成结构线/衣物缝线，
  PoC 必须验证「无关节痕」。
- **R2 PoC 的 kill criteria 增加一条**：若 R2-A 姿势明显优于 v5 文字方案（例如 ≥4/5 且逐关节一致）
  且无关节痕，才值得产品化；否则直接用文字方案，9.4 GB 可以省掉。

## 2. 「模特素材 → 详情页按钮 → 图生图工作台换姿势」链路评估

> 原文件：`pose/模特素材换姿势图生图链路评估.md`｜原题：「模特素材 → 详情页按钮 → 图生图工作台换姿势」链路评估

> **状态**：已归档（2026-10-31）。路径一已按本评估落地（见 [实现说明](姿势图库换姿势（路径一）实现说明.md)）；
> 实际效果与最终结论见 [换姿势方向结项报告](换姿势方向结项报告-2026-10-31.md)。


> 评估对象：把姿势图库 **ai-pose-gallery-zh** 接入一条「选中模特素材 → 跳到图生图网页 → 选姿势图 → 改姿态 → 出图」的链路
> 评估时间：2026-10-30　评估范围：**仅方案与可行性，不写代码**
> 前置结论来自同目录两份评估：合并版（本文第 3 节）（技术栈、生成能力缺口、合规风险）
> 本机环境事实：`fashion-inspo` 已有 i2i 链路（ComfyUI + Qwen-Image 2.1，参考图 1~10 张，最大 1024²；16 GB 显卡实测 1024² 文生图约 6.8 s、i2i 单图约 21 s；已有任务队列/生成历史/候选两段式入库）

### 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 这个效果能不能做？ | **能，但不是"在当前项目里加一个按钮"就能闭环**。它实际是 **A（有模特素材的素材前端）→ B（图生图工作台）→ C（姿势图库 ai-pose-gallery-zh）** 三个角色的协同；ai-pose-gallery-zh 只能承担 **C**（姿势资产 + 选图 + 可选深链），**B 的生成能力与 A 的素材详情页都不在它内部**。 |
| 当前项目（ai-pose-gallery-zh）能否直接实现？ | **不能闭环**：它是纯静态站，没有模特素材、没有生成、没有存储/鉴权（详见先前评估）。在它内部能落地的是：姿势数据 CORS 化、按 id 的图片直链、可选的 `?pose=<id>` 深链、"在 i2i 中使用此姿势"按钮——**改动很小（1~2 人日级）**。 |
| 推荐路径 | **路径一（最省事）**：B 直接复用我们现有的 `fashion-inspo` 出图页（已有 i2i + 队列 + 候选入库），A 用素材库详情页加「换个姿势」按钮，C 以"构建期同步全年龄子集数据 + 缩略图"或"CORS 化只读接口"的方式接入。**PoC 3~5 天 → MVP 6~8 人日**，主要风险是"换姿势后身份/服装是否保得住"，而不是工程打通。 |
| 一句话 | **链路的"接线"很简单，难的是"换姿势后还像不像原来这个模特"**；建议先做 PoC 用样张验证质量，再决定是否投入产品化。 |

### 1. 需求拆解与角色澄清

用户描述的四个步骤，对应三个系统角色：

| 步骤 | 角色 | 现状归属 |
| --- | --- | --- |
| 1. 前端网页中已有模特的某个素材 | **A：素材前端**（素材库/详情页，持有模特照片、穿搭素材） | 不在 ai-pose-gallery-zh（该站只有 1439 张素体/姿势参考图，没有"模特照片素材"） |
| 2. 详情页按钮 → 跳转图生图网页 | **A → B 的衔接** | 按钮加在 A；ai-pose-gallery-zh 不承担 |
| 3. 在图生图网页中选择姿态图、改变模特姿态 | **B：图生图工作台 + C：姿势图库** | B 需要新建/复用；C = ai-pose-gallery-zh（姿势数据与图片） |
| 4. 最终生成图片 | **B + 生成后端** | B 及其后端；ai-pose-gallery-zh 无生成能力 |

> **需求角色说明（两种可能读法，结论一致）**
> - 读法一（推荐）：A = 我们自己的素材库（`fashion-inspo` 素材/模特详情页），B = 现有出图页升级为"带姿势库的工作台"，C = ai-pose-gallery-zh。此时 A/B 是现成或近现成的，C 作为姿势数据源接进来。
> - 读法二：A = ai-pose-gallery-zh 的前端灯箱（把"素体模特"当作"模特素材"）。那么按钮可直接加在灯箱里，但 B 依然必须是外部的生成服务；点进去后"选姿势"这一步会显得重复（因为起点本身就是姿势图），体验上不自然，不如让 C 直接提供 `?pose=<id>` 深链到 B。

### 2. 当前项目（ai-pose-gallery-zh）能做到什么，缺什么

#### 2.1 现成可用的能力（已实测）

| 能力 | 事实 | 对本链路的价值 |
| --- | --- | --- |
| 姿势元数据 | `data/pose-zh.json` 1439 条，字段 `id / 体系 / 分类 / 姿势名称 / 角度 / 缩略图 / 原图 / 检索`；4 体系、26 分类、5 角度 | 可直接作为"姿势选择器"的数据源 |
| 图片直链 | 实测 URL 规律稳定：`https://ai-pose-gallery.anhao.app/thumbs/<id>.jpg`（约 12 KB，300×400）与 `/img/<id>.png`（900×1200，白底线稿）均 200 可访问、长缓存 | B 用 `<img>` 直接展示姿势缩略图/原图，**无需 CORS**；生成后端按 URL 服务端拉取也可行 |
| 静态托管与缓存 | Cloudflare Pages，`_headers` 对 `img/`、`thumbs/` 一年强缓存 | 姿势图分发成本低、延迟低 |
| 数据可复制 | 仓库可 clone，数据与图片可一次性同步 | B 也可离线镜像全年龄子集，不依赖在线站点 |

#### 2.2 关键缺口（实测确认）

| 缺口 | 实测 | 影响 |
| --- | --- | --- |
| **无 CORS 头** | `curl -I https://ai-pose-gallery.anhao.app/data/pose-zh.json`：无 `access-control-allow-origin`；图片同样无 | B 的前端**不能跨域 `fetch` 姿势 JSON**（`<img>` 展示不受影响）；需给 C 加 CORS 或在 B 侧镜像数据 |
| 无生成/后端/存储/鉴权 | 全部不存在（见合并版评估 §1.3、§2） | B 的生成能力必须由外部提供（现有 `fashion-inspo` 或独立服务） |
| 无"模特素材"概念 | 数据里只有素体姿势图，无真人模特照片/穿搭素材 | "已有模特的某个素材"必须来自 A，而不是 C |
| 无深链参数 | 站点无路由参数处理 | 想"从 C 一键带姿势 id 跳到 B"需加一小段 JS 支持；从 A 跳到 B 则与 C 无关 |
| 内容属性 | 18+ 体系 674/1439（46.8%），全年龄子集 765 张 | 姿势选择器必须按 `age_rating` 过滤，只开放全年龄子集 |

#### 2.3 C 侧最小改造清单（若让 gallery 作为在线姿势源）

1. `_headers` 增加 CORS（只放行 B 的正式域名与本地开发），或单独输出一个 `data/pose-api.json`（轻量：id/名称/角度/缩略图/原图/分级）；
2. 可选：灯箱加「在 i2i 中换这个姿势」按钮，生成 `https://<B>/i2i?pose=<id>` 深链；
3. 可选：构建期筛选出全年龄子集（765 条）单独输出 `pose-allages.json`；
4. **不新增生成能力**（延续合并版评估的结论：公开站在线生成不建议）。
5. 控制图（lineart/canny/openpose）**不建议塞进静态仓库**（100~300 MB），由 B 侧按需生成/缓存或放 R2。

### 3. 衔接方式：素材详情页按钮 ↔ 图生图网页

#### 3.1 五种衔接方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **① URL 深链（推荐）** | 详情页按钮 `window.open(B + "?src=<素材引用>&from=<来源>")`；B 启动时解析参数并加载素材 | 无状态、可分享、可回退、实现最简；对新标签页/移动端友好 | 素材必须是 B 能访问的地址（公开 URL 或短时签名 URL）；大图/私有素材需签名 | A、B 不同产品/不同域时首选 |
| **② 同域路由跳转** | 若 A 与 B 在同一前端（如都在 `fashion-inspo`），直接 `router.push({name:'generate', query:{ref:<素材id>}})` + 前端状态 | 最省事：无跨域、无签名、可用前端 store 传大对象 | 仅限同域/同产品 | **路径一推荐**（B 复用现有出图页） |
| ③ iframe + postMessage | A 里嵌 B，或 B 里嵌 C；`postMessage` 传素材/姿势 | A 不离开页面、体验连贯 | 跨域 CSP/X-Frame、移动端 iframe 体验差、状态与鉴权复杂 | 仅做"姿势选择器"嵌入时可用 |
| ④ 剪贴板交接 | 按钮把图片 + JSON 复制到剪贴板，用户到 B 粘贴 | 零后端、零跨域 | 用户要多一步操作；浏览器剪贴板权限不稳定；大图/移动端差 | 兜底/低频 |
| ⑤ 服务端交接 token | A 后端把素材转存到临时存储，生成一次性 token URL，B 用 token 拉取 | 支持私有素材、可审计、可限时 | A/B 都需要后端与共享存储；成本最高 | 素材私有、合规要求高的生产环境 |

#### 3.2 推荐衔接设计（路径一：B 复用现有出图页）

```text
[素材详情页] --点击「换个姿势」--> [出图页 /generate?ref=<素材id>&pose_lib=1]
                                      │
                                      ├─ 左侧：素材预览（已选为 i2i 参考图，恢复为现有 reference_ids）
                                      └─ 右侧：姿势选择器
                                             ├─ v1：弹窗内嵌「姿势库」（读镜像的全年龄子集数据）
                                             └─ v2：打开 C 的页面（?pose= 深链）或 iframe 选图

[选姿势] --> [参数面板：强度/尺寸/seed/模式] --> [生成任务] --> [候选区对比/下载/入库]
```

- **素材交接**：同一产品内用路由 + 素材 id（A 与 B 共享后端/素材库）即可；若 B 是独立产品，用 URL `?src=<签名URL>` 或 `?material_id=` + B 后端回调 A 的素材接口换取图片（需要 A 提供凭据/公开接口）。
- **姿势交接**：选姿势本质是"选中一条姿势记录"（`pose_id`），交接给 B 的生成参数（不是把姿势图当用户上传图）。`pose_id` 也可直接用于深链/日志/复现。
- **返回路径**：`?return=<A的地址>`（可选），生成成功后"回传"成 B 的素材（或 A 直接接收生成结果），避免用户手动搬运。
- **安全**：签名 URL 有有效期、只读、绑定 B 域名；CORS 白名单只放 B；C 侧不做鉴权（静态），敏感能力全部在 B 后端。

#### 3.3 从 C 到 B 的另一条入口（可选，反向）

C 的姿势灯箱加「用这个姿势生成」→ `https://<B>/i2i?pose=<id>`。这样用户也可以"先在姿势库挑姿势、再去配模特"；与需求主链方向相反，但成本极低（一行深链），可作为补充入口。

### 4. 选姿态图 → 改变模特姿态 → 出图：链路可行性

把这条链路拆成 5 个环节，逐个判断：

| 环节 | 方案 | 可行性 | 主要风险/备注 |
| --- | --- | --- | --- |
| **① 姿势资产获取** | C 的 `pose_id` → `/img/<id>.png`（900×1200 白底线稿）；B 用 `<img>` 展示、后端按 URL 拉取 | **高** | 需要 CORS 仅在前端 fetch JSON 时需要；图片直链无需 CORS；18+ 需过滤 |
| **② 控制信号生成** | 路线 A：**lineart/canny**（线稿本身就是线稿，可直接当控制图，无需姿态估计）；路线 B：OpenPose/DWPose 骨架（需对素体线稿做姿态估计，跨域输入，双人/俯视/仰视不稳） | **A 高 / B 中** | 建议先做 A；B 只在对"关节级一致"有硬要求时再评估 |
| **③ 主体保持（像原模特）** | 路线 1：SDXL + ControlNet(lineart) + IP-Adapter/FaceID/InstantID 保身份与服装；路线 2：Qwen-Image-Edit / FLUX.2 multi-reference 双参考图指令编辑（源照片 + 姿势线稿） | **中~高** | 身份漂移、服装/肤色/发型变化是主要失败点；双人姿势、遮挡、手脚细节更差；不同路线需样张对比 |
| **④ 生成执行** | 本地 ComfyUI（已有：16 GB 卡，Qwen-Image 2.1 i2i 单图约 21 s、1024²；SDXL+ControlNet 预计 5~15 s/张）或云端 API | **高** | 显存 16 GB 下分辨率/步数受限（现有出图页已有尺寸与显存守门）；排队/超时/失败重试需沿用现有任务队列 |
| **⑤ 结果交付与迭代** | 候选区对比（原图/生成图）、多张候选、重跑、下载、入库（现有两段式）；带 `pose_id` 记入生成历史便于复现 | **高** | 生成历史/候选入库/失败文案都是现成能力，几乎零改造 |

#### 4.1 三条推荐技术路线的对比（PoC 需要实测）

| 路线 | 输入 | 优势 | 劣势 | 建议 |
| --- | --- | --- | --- | --- |
| R1：Qwen-Image-Edit 双参考图 | 模特素材 + 姿势线稿 + 指令 | 复用现有 ComfyUI/模型；自然、链路最短 | 姿势保真不保证；双图关系靠提示词，可能"各画各的" | **PoC 首选**（成本最低） |
| R2：SDXL + ControlNet(lineart/canny) + IP-Adapter | 模特素材（身份/服装）+ 姿势线稿控制图 | 姿势/构图可控、可批量 | 需新增 SDXL+ControlNet+IP-Adapter 模型与工作流；显存/速度需实测；融合质量需调参 | **质量优先时的主路线** |
| R3：SDXL + ControlNet(OpenPose) + FaceID | 模特素材 + 骨架图 | 关节级姿势最准 | 骨架提取对素体线稿是跨域，双人/俯仰易失败；人脸模型许可与肖像合规风险 | 二期，仅在 R1/R2 不达标时评估 |

#### 4.2 质量验收（PoC 建议）

- 样本：20~30 张，覆盖 4 体系 × 5 视角 × 单人/双人 × 全年龄子集，模特素材覆盖正/侧/半身；
- 指标：姿势保真（人工 1~5 分或骨架距离）、身份相似（人工/人脸相似度）、服装一致性、解剖错误（手/脚/多指）、背景与构图、耗时与显存、失败率；
- 通过线：姿势保真 ≥4 分占比 ≥70%、身份"能认出是同一人"≥80%、单张 ≤30 s（本地）、失败率 ≤10%；不达标则回退 R1 或只做"风格参考"不承诺姿势一致。

#### 4.3 链路级风险（除质量外）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **内容合规** | C 的 18+ 占 46.8%；成人姿势用于换装生成在多数平台/法规下不可行 | 姿势选择器只开放全年龄子集（765 张）；B 侧审核与限额；不公开生成结果 |
| **版权** | C 的姿势图版权归原作者、MIT 不覆盖；生成图基于该姿势可能构成演绎 | 仅内部/自用；公开前取得许可或替换自有姿势资产；保留来源与删除通道 |
| **肖像/同意/深伪** | 若模特素材是真人（尤其他人照片），换姿势属于深度合成 | 默认只对自有/授权素材开放；明示同意、AIGC 标识、不留存原始/生成图可选 |
| **素材比例/构图** | 姿势图 900×1200（3:4），素材可能是任意比例/多人/特写 | 进入 B 时做裁剪对齐提示；单人全身优先；多人素材先裁剪 |
| **身份漂移** | 换姿势后脸/发型/身材变化 | PoC 选路线；必要时加 FaceID/IP-Adapter；结果给"身份保真度"提示与重试 |
| **性能与成本** | 本地 GPU 排队/显存；云端按张计费 | 沿用现有互斥/队列与显存守门；限额与预算告警 |
| **可复现性** | 同姿势/同素材结果不可控 | 生成历史记录 `pose_id + seed + 模型/工作流版本`（现有历史已能存参数） |

### 5. 推荐落地形态与工作量的分级

#### 5.1 路径一（推荐）：A/B 复用 `fashion-inspo`，C 做姿势数据源

| 改动 | 说明 | 量级 |
| --- | --- | --- |
| A 素材详情页 | 加「换个姿势」按钮 → 跳转出图页并带素材 id（同域路由，最简） | 0.5 人日 |
| B 出图页 | 加"姿势选择器"（弹窗/侧栏）：列表 + 预览 + 搜索/体系/角度筛选（复用现有出图页样式）；选中写入生成参数 `pose_id`；调用现有生成接口 | 2~3 人日 |
| 姿势数据接入 | 构建期同步 C 的全年龄子集数据（765 条）+ 缩略图到本机/仓库静态目录（约 10 MB 数据 + 10 MB 缩略图）；或前端直连 C（需 C 加 CORS） | 1~2 人日 |
| 生成后端 | 新增 ComfyUI workflow：R1（Qwen-Image-Edit 双参考）或 R2（SDXL+ControlNet lineart）；接入现有任务队列/候选/历史；`pose_id` 与参考图一起落库 | 2~3 人日（复用现有链路） |
| 联调/验收 | 20~30 样本质量评估、失败文案、限额 | 1~2 人日 |
| **合计（MVP，内部可用）** | | **6~8 人日**（不含合规评审与生产化） |

#### 5.2 路径二（独立 i2i 工作台）

若"图生图网页"要求是独立产品（不能复用 `fashion-inspo`）：B 需要新前端 + 新后端/存储 + 鉴权 + 计费，参考合并版评估的 P1 方案，约 **5~7 人日**起（仅受控内部用），公开化再 +2~4 周（合规/审核/限额）。

#### 5.3 阶段建议

1. **Phase 0（3~5 天）PoC**：20~30 样本，对比 R1/R2（必要时 R3），只验证"选姿势 → 出图 → 像不像/姿势对不对"，不改产品；
2. **Phase 1（MVP，6~8 人日）**：路径一，内部可用；姿势选择器 + 现有出图页 + R1/R2 工作流；只开放全年龄子集；加 AIGC 标识与来源记录；
3. **Phase 2（产品化）**：若质量达标且确有需求，再讨论公开入口、审核、限额、授权与法务；C 侧仅做 CORS/深链/CORS 化数据等轻改造，**不在画廊内加生成**。

---

### 6. 最终结论

1. **可实现性**：目标效果整体**可实现**，但必须按 A（素材前端）→ B（图生图工作台）→ C（姿势库）三段式落地；**在当前项目 ai-pose-gallery-zh 内无法闭环**（它没有模特素材、没有生成/存储/鉴权），它只能做 C：提供姿势数据、图片直链、可选深链与 CORS 化——这部分改动很小（1~2 人日级）。
2. **衔接方式**：优先 **URL 深链**（跨产品）或**同域路由**（复用现有出图页）；素材用"公开 URL / 短时签名 URL / material_id + 后端换取"三种交接之一；姿势用 `pose_id` 交接而不是传图；可选 iframe 仅用于嵌入姿势选择器；剪贴板只作兜底。
3. **生成链路**：选姿态图 → 控制图（lineart/canny 优先，OpenPose 谨慎）→ 主体保持（Qwen-Image-Edit 双参考或 SDXL+ControlNet+IP-Adapter）→ 生成 → 候选/入库。**工程上每一环都可行**，最大不确定性是"换姿势后身份/服装是否保得住"——必须先用 20~30 个样本做 PoC，达标再产品化。
4. **推荐落地**：复用现有 `fashion-inspo` 出图页作为 B（它已有 i2i、任务队列、生成历史、候选入库），素材库详情页加按钮作为 A，ai-pose-gallery-zh 作为全年龄姿势数据源（构建期同步 765 条或 CORS 化只读接口）；MVP 约 6~8 人日，PoC 3~5 天。
5. **一句话**：**接线简单、质量是门槛；先 PoC 验证"像不像"，再投入产品化。**

### 0. 结论先行

| 问题 | 判断 |
| --- | --- |

### 3. 技术路线与我们的实验验证

原评估（v1/v2）比较了三条路线；后续本机实验补上了关键结论，**这是评估与最终选型之间最重要的修正**：

| 路线 | 原判断 | 本机实测（见结项报告） |
| --- | --- | --- |
| **A. 线稿 → 直接参考图编辑**（Qwen-Image-Edit / FLUX.2 multi-reference） | 链路最短、与现有后端最匹配；姿势不保证一致 | **姿势不跟随**：线稿作参考图时，模型把线稿当「内容」而非控制信号（R1-A/P0）；英文约束 prompt 能保身份/服装（5/5）但姿势 0/5 |
| **B. ControlNet lineart / canny** | 更贴合图库（本身就是线稿），保留构图/轮廓 | **姿势 5/5，但关节圆被画成护具/服装装饰**（R2-A）；加 Qwen 清洗仍丢身份 |
| **C. ControlNet depth** | 原评估未展开 | **消掉关节圆伪影（10/10）**，姿势 3.7/5；但保不住服装/发型（E3） |
| **D. 骨架 OpenPose/DWPose** | 姿势一致性最好，但线稿跨域、双人/俯仰视角风险 | **不可行**：社区记录 DWPose/OpenPose 识别不了素体线稿；我们的尝试也未成立 |
| **E. 普通 img2img 重绘** | 易改姿势，价值有限 | 不推荐；身份与姿势跷跷板 |

**结论**：图库线稿适合做 **lineart / depth 控制图**，不适合直接当「编辑参考图」；「图库 + 生成」的 1+1<2 根因在此（社区证据见 社区姿势图库与出图结合项目调研（本文第 4 节））。

### 4. 架构方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A 浏览器直连**第三方 API | 前端直接 `fetch` 服务商接口 | 改造最小 | API Key 必然暴露；跨域/限流不可控 | ❌ 不可行 |
| **B Pages Functions 代理 + 云端 i2i** | 新增 `functions/api/i2i/*` 做代理、鉴权、配额、审核；结果存 R2 | 最贴合现状；密钥只在服务端；免费额度够内部用 | 成本转给上游；需内容审核；需新增 R2/KV/Secrets | ✅ **P1 推荐（限受控/内部）** |
| **C 自建 GPU + ComfyUI** | 独立机器跑 ComfyUI + 反代 + 队列 | 姿势控制最准、模型最自由、可复用现有栈 | 需常驻 GPU、运维、公网鉴权、带宽 | ⚠️ **仅本地/内网** |
| **D 纯浏览器本地推理** | WebGPU + onnxruntime-web / WebSD | 零后端、零密钥、零运营成本 | 首次下载数百 MB~GB；移动端/集显差；画质与可控性弱 | ⚠️ 实验性，不作主路径 |
| **E 不做生成，只做提示词/参考图辅助** | 按体系/分类/角度生成 prompt 模板，一键复制 + 导出 | 0 算力、0 成本、0 输出风险；最贴合定位；与社区方向一致 | 不是「在线生成」体验 | ✅ **P0 首选** |

**Cloudflare Workers AI 核对**：模型目录有 SDXL、FLUX.1 schnell、FLUX.2 dev/klein（标注支持 multi-reference），**未检索到 ControlNet/OpenPose 姿态条件模型**——可用于方案 A 的原型，不能替代 ControlNet 做精确姿势迁移；内容政策也不适合本站素材。

**与本机 `fashion-inspo` 的关系**：已有 Qwen-Image-Edit i2i 链路（参考图 1~10 张、最大 1024²、任务队列 + 生成历史）。本地/内网做姿势生成，方案 C 最省事；公开站不能依赖本机 GPU。

### 8. 推荐路线

1. **Phase 0（1~2 天）**：样本实验——选 10~20 个覆盖 4 体系 × 5 视角 × 单人/双人的姿势，比较直接编辑 / ControlNet lineart / depth，记录姿势保真、解剖、耗时、显存、失败率。
2. **Phase 1（0.5~1 天，P0）**：上线「提示词模板 + 一键复制 + 参考图导出」；零算力、零输出合规风险，先验证需求。
3. **Phase 2（5~7 天，P1，仅内部/受控）**：确需站内生成时做方案 B——只开全年龄子集、Access/Turnstile + 每日硬限额、R2 存结果 + 7 天清理、强审核与 AI 标识、不放公开入口。
4. **Phase 3（公开在线生成）**：**暂不做**，除非同时满足原作者许可/资产替换、内容分级与审核、AIGC 标识、平台政策允许、成本可控、法务确认。
5. **若目标是服务自己的 `fashion-inspo`**：只导入全年龄子集、新增 `pose_gallery` 来源、复用现有 i2i，不需要改动这个静态仓库（本项目后来正是这么做的，但生成效果问题见结项报告）。

**Kill criteria**：原作者拒绝授权、上游政策不允许、样本质量不达标、无法控制成本或审核 → 立即停在 P0。

---

### 9. 最终结论

1. **技术可行性：高。** 没有阻碍 i2i 的技术债；900×1200 多角度白底线稿、筛选 UI 与结构化数据是优质输入侧；真正缺口是「推理 + 任务 + 存储 + 鉴权 + 审核」服务层。
2. **纯静态仓库内独立接入：不可行。** Pages/Workers 不能跑 GPU；Workers AI 无 ControlNet/OpenPose 姿态条件，内容政策也不适合本站素材。
3. **个人/本地：推荐。** 复用现有 ComfyUI + Qwen-Image-Edit；但后续实测表明「线稿直接作编辑参考」姿势不跟随，必须用 lineart/depth 控制，且仍解决不了身份/服装一致性（见结项报告）。
4. **公开/商用：条件性可行，当前不建议**——图片授权与成人内容合规是前置门槛，3.1k★ 会放大滥用与成本风险。
5. **一句话**：这个项目适合继续做「参考图库」，不适合直接变「公开生成站」；生成能力应放在用户自己的工具或一个受控的独立服务里。

### 2. 1+1 到底等于几：有实测证据的四种组合

#### 2.1 只做「浏览/装载」节点：1+1 ≈ 1

Stone、PoseAtlas、icefox、以及 lnyuqian 的 Gallery 部分，都只是把图库搬进 ComfyUI：
省去手动找图/下载，但**不改变任何生成质量**。这是目前多数项目的真实价值。

#### 2.2 线稿直接控制（Anima LLLite / 我们的 R2-A）：1+1 < 2（有第三方实锤）

- wangweihong 的 Anima LLLite v2 实测 8 组（同一提示词、同种子，9.4 s/张）原文记录：
  - 「单膝跪、俯卧：**肩部关节圆圈被转成服装开口或圆形装饰**」
  - 「**蹲姿：头部上仰**，与参考头部角度存在偏移」
  - 「服装款式、配饰和脸部可随姿势变化；**手指需要人工检查**」
  - 「每组仅测试一个固定种子，未验证多人、所有视角及完整图库的成功率」
- 这与我们 R2-A 的结果**完全一致**（关节圆 → 护具/圆片；俯仰角不跟随；手部需检查）。
- 结论：**线稿直接当控制信号 = 社区和我们都复现的 1+1<2**。不是我们实现错了，是这条路的固有缺陷。

#### 2.3 深度控制（MOSS / Krea2）：1+1 ≈ 1.5

- MOSS 工作流：姿势线稿 → `Depth Anything V2 Large` → `MOSS-Image Color/Depth Control`（LoRA）→ MOSS SFT 50 步，46.4 s；
  作者明确写到「**提前结束深度控制用于减少素体外观**」（深度强度 0.75，结束 0.5），
  且「手指和脸部仍由模型生成」。
- Krea2 深度：8 步、9.4 s/张，深度约束轮廓；但作者实测总结「**手脚细节和精确关节角度仍可能偏离参考**」。
- 结论：深度路线比线稿干净（不会把关节圆画成服装装饰），但仍然只到「轮廓对、细节偏」；
  且 MOSS 要新增一整套模型（MOSS 主模型 + 文本编码器 + flux2 VAE + 控制 LoRA），ComfyUI 需 0.43+。

#### 2.4 Qwen-Image 2.1 + **Pose Studio v2 LoRA**：目前唯一「可能 1+1 > 2」

wangweihong 的 Qwen 工作流（ComfyUI 0.43.0，25 步、CFG 1、Euler/simple、876×1184、17 s/张，LoRA 强度 1）：

- 输入：**图库线稿 → image_1**，**人物参考 → image_2**（明确要求不要交换顺序）；
- 提示词（英文，原文）：
  > Replace the pose of the person in image2 with the pose shown in image1. Use image1 only as a reference for
  > body pose, limb placement, body orientation and camera viewpoint. Preserve the identity, facial features,
  > hairstyle, clothing, accessories, colors, visual style, background and lighting of image2. … do not copy the
  > line drawing, mannequin appearance or annotations from image1.
- 关键配料：**VNCCS Pose Studio QI2.1 v2 LoRA**（HF `MIUProject/VNCCS_PoseStudio_QI2.1`，**152 MB**），
  对应仓库 `loras/qwen2.1/...safetensors`；
- 实测（`pose_gallery_qwen21_validation.json`）：`full_sexy_P002_front`（站）与 `full_sexy_P031_front`（跪）两例，
  17.05 s / 16.82 s，visual_review =「arms behind head and corresponding standing/kneeling pose followed;
  **reference clothing and hairstyle retained**」；limitations =「只测了这两个单人正面姿势，不保证全部姿势」。

> **这是和我们最接近、也最有价值的参照**：它证明「线稿只作姿势、人物身份和服装由 image_2 保留」在 Qwen 2.1 上
> **可以做到**——前提是 **pose LoRA + 明确的英文提示词 + 图1=姿势/图2=人物**。
> 我们之前失败，是因为缺了 pose LoRA，且提示词要求「换成黑裙」；不是路线本身不行。

#### 2.5 普通 Qwen 线稿参考（lnyuqian 的 2 个 Qwen 工作流）：1+1 < 2（作者自述）

README 原文要点（对我们非常有用的坑）：

- 「线稿只有人体结构，没有五官、服装、场景等。**模型容易按训练分布自由发挥**——例如把「站立单手摸头」画成
  「举手摸头/叉腰」……实际对弱姿态提升明显。」→ 需要额外加**中文姿势描述**；
- 「**`cfg = 1.0` 时负面提示词不生效**」（Qwen 2.1 蒸馏 LoRA 的推荐设置；我们之前也一直 cfg=1，等于负向白写）；
- 「**姿势图是线稿人体模型，DWPose / OpenPose 等骨架检测节点识别不上**」→ 我们尝试 openpose 的想法被第三方证实希望渺茫；
- 「`TextEncodeQwenImage21` 只取 batch 的第一张参考图；多张参考图尺寸不一致时 latent 尺寸取第一张」——
  解释了为什么「重复线稿/批量参考」会失效。

### 3. 结论：X + 图库 的「1+1」真相

| 组合方式 | 1+1 效果 | 依据 |
| --- | --- | --- |
| 图库接入为「浏览/选图」节点 | ≈1 | 多个节点项目，只省操作 |
| 图库线稿 → 线稿/边缘 ControlNet 直控 | **<2** | 社区 Anima 8 组实测 + 我们 R2-A |
| 图库线稿 → 深度先验（MOSS/Krea2） | ≈1.5 | 作者实测：轮廓对、手脚/关节偏；需新模型栈 |
| 图库线稿 + 普通 Qwen 参考 | **<2** | lnyuqian 自述模型自由发挥；我们 R1 同款 |
| 图库线稿 + Qwen2.1 + **Pose Studio v2 LoRA** + 明确英文 prompt | **>2（2 例）** | wangweihong 实测：姿势跟随 + 服装/发型保留；样本极少，需自测扩展 |

**一句话**：你的直觉成立——大多数「X + ai-pose-gallery」没有 1+1>2，甚至 <2；
但社区里确实出现了一个「做了额外动作（+pose LoRA、+英文约束 prompt、明确图序）」后可能 >2 的组合，
而且它正好补上了我们缺的那块。

### 4. 对我们项目的直接启示与下一步

1. 我们之前踩的坑**社区都踩过并记录**：关节圆变服装装饰、俯仰角不跟随、DWPose 不认线稿、cfg=1 负向无效、
   Qwen 只认第一张参考/取第一张尺寸——这些不是我们实现错误，而是路线固有边界。
2. **最值得补的一课**：Qwen 2.1 + **Pose Studio QI2.1 v2 LoRA（152 MB）** + 英文「image1 只作姿势、
   image2 保留身份/服装/发型/背景」prompt + 图1=姿势/图2=人物。这是唯一被第三方实测证明「保留服装发型 +
   换姿势」的组合，且 LoRA 很小（152 MB）。
3. 下一步实验（暂停后待你拍板，按成本排序）：
