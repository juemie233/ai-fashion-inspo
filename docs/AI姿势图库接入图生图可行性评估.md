# AI 姿势图库接入图生图（image-to-image）能力可行性评估

> 评估对象：<https://github.com/anhao/ai-pose-gallery-zh>（中文版 AI 姿势参考图库）
> 评估时间：2026-10-30　评估范围：**仅可行性，不含业务代码实现**
> 方法：GitHub 元数据 + 源码稀疏检出实测（index.html / scripts / data 实际读取统计）+ Cloudflare 官方文档核对平台限制

---

## 0. 结论先行

| 问题 | 判断 |
| --- | --- |
| 技术上能否接入图生图？ | **能**。项目本身没有阻碍性技术债，现有原图（900×1200 PNG）、多角度数据与选图 UI 可直接当 i2i 的输入侧；缺的是**模型推理这一整套算力/服务层**，属于"新增一套基础设施"，不是"改造一个功能"。 |
| 值得在**公开站点**做在线生成吗？ | **不建议**。图库 46.8% 的条目属于 18+ 体系，而主流云端 i2i 服务政策普遍禁止色情/性暗示内容（参考图本身就可能被拒）；公开站还叠加密钥滥用、成本失控、平台停用三重风险。 |
| 推荐做法 | **P0（建议先做）**：只做"提示词模板 + 参考图导出/复制"，生成交给用户自己的工具（0 算力、0 合规风险，约 0.5~1 人日）。<br>**P1（确需站内生成）**：Cloudflare Pages Functions 代理云端 i2i，但**限定全年龄子集 + 访问口令 + 每日硬限额**，定位为内部/自用工具（约 5~6.5 人日）。<br>**P2（公开在线生成）**：不建议，除非先解决内容分级与合规。 |

一句话：**工程可行性高，合规可行性低；能做，但应换个做法做——或者别在这个项目里做。**

## 1. 项目现状盘点（实测数据）

### 1.1 技术栈

| 层面 | 实现 | 实测证据 |
| --- | --- | --- |
| 前端 | 单文件 `index.html`，原生 HTML/CSS/JS，**零框架、零构建、零 npm 依赖** | 922 行 / 58.6 KB；内联 CSS 285 行；内联 JS 440 行（2 个 `<script>` 块） |
| 交互 | 筛选、搜索、分组/逐张浏览、灯箱、键盘/触屏导航、原图下载 | 仅 `fetch('data/pose-zh.json')` 一个数据请求；下载用 `<a download>`，无 canvas/WebGL/Worker |

| 部署 | Cloudflare Pages（Git 集成，构建命令 `bash scripts/build.sh`，产物 `dist/`） | `_headers` 为 `img/`、`thumbs/` 配一年强缓存；`.assetsignore` 兜底排除 `.git` 等非站点文件 |
| 外部依赖 | 仅一个第三方统计脚本 | `https://u.authbox.cn/script.js`（前台埋点，与生成能力无关） |
| 内容属性 | 4 体系 / 26 分类 / 5 角度 / 288 个姿势名 | 体系：全身标准系 365、上半身 400、全身性感系 399、双人缠绵 275；**18+ 体系合计 674 条（46.8%）**；README 自述部分分类名称涉及性行为术语 |
| 许可 | 代码 MIT；**图片与原始数据不在 MIT 范围**（版权属原作者） | `LICENSE` 中"Scope"明确排除 `img/`、`thumbs/`、`data/` |

### 1.2 现有"图像处理"相关实现（关键判断依据）

全仓库**没有任何模型推理、图像编解码或像素级处理**，只有两处字节级校验：

1. `scripts/verify.py`：读取文件前 8 字节判断 JPEG/PNG 魔数 + 大小阈值，校验 2878 个文件完整性；
2. `scripts/download.py`：按 Content-Length/实际字节数校验下载结果，原子替换落盘。

即：**无 PIL / OpenCV / numpy / ffmpeg 等图像库依赖，仅有 Python 标准库**；没有后端、Serverless、数据库、鉴权、任务队列。网站是纯静态资源分发，生图所需的"算力 + 状态 + 存储 + 密钥"全部不存在。

## 2. 接入图生图的能力缺口

图生图（参考图 + 提示词 → 新图）至少需要以下链路，逐项对照现状：

| 环节 | 现状 | 缺口 |
| --- | --- | --- |
| 参考图输入 | ✅ 现成：900×1200 PNG、每姿势 5 个角度、可按分类/视角筛选 | 基本无需改造，最多加裁剪/缩放预处理 |
| 提示词 | ⚠️ 只有体系/分类/姿势名/角度（中文，可程序化拼模板） | 缺"服装/场景/风格"等画面描述，需要用户输入或 LLM 补全 |
| 模型推理 | ❌ 完全没有 | **核心缺口**：云端 API / 自建 GPU / 浏览器 WebGPU 三选一 |
| 结果存储 | ❌ 无 | 生成图约 1~2 MB/张，不能塞进 `dist/`（Pages 每次部署上限 2 万文件），需 R2 或外部存储 |
| 任务状态 | ❌ 无 | i2i 需 5~30 s，需异步任务 + 轮询/SSE |
| 鉴权与配额 | ❌ 无（公开静态站） | 必须新增，否则密钥与成本裸奔 |
| 内容审核 | ❌ 无 | 18+ 内容近半，必须分级与过滤 |
| 观测/日志 | ❌ 无（仅第三方统计） | 失败率、成本、滥用需要记录 |

结论：**"接入 i2i"= 在静态站旁边新增一套"服务端 + 生成服务"**。前端和数据不仅不是障碍，反而是现成的优质输入侧资产。

## 3. 四种接入方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **A 浏览器直连** 第三方 i2i API | 前端直接 `fetch` 服务商接口 | 改造最小、无服务器 | API Key 必然暴露给所有访客；多数服务商不允许浏览器跨域调用；无法限流 → 被刷爆 | ❌ 不可行 |
| **B Pages Functions 代理 + 云端 i2i** | 项目已在 Cloudflare Pages，新增 `functions/api/i2i/*` 做代理、鉴权、配额、审核；生成图存 R2 | 架构最贴合现状；免费额度够内部用（Workers 免费 10 万请求/天、HTTP 请求无 wall time 上限、等待外部 API 不计 CPU）；密钥只存服务端 | 成本转移给上游 API；需内容审核；需新增 R2/KV/Secrets；从"纯静态"变"静态+Serverless" | ✅ 推荐（限自用/内部） |
| **C 自建 GPU 服务** | 独立机器跑 ComfyUI / SD-WebUI（可上 ControlNet OpenPose 做姿势迁移）+ 反代 | 姿势控制最准、可选模型最多、单图边际成本最低 | 需常驻 GPU + 运维 + 公网鉴权 + 带宽；对 3.1k star 的公开项目作者不可承受 | ⚠️ 仅作者自用/内网 |
| **D 纯浏览器本地推理** | WebGPU + onnxruntime-web / Web stable diffusion（SD-Turbo、SDXS 等） | 保持零后端、零密钥、运营零成本 | 首次要下载数百 MB~GB 权重；移动端/集显体验差；画质与可控性弱；无上游审核兜底 | ⚠️ 实验性，不作为卖点 |
| **E 不做生成，只做提示词/参考图辅助** | 按姿势/分类/角度生成 i2i prompt 模板，一键复制 + 参考图下载/导出，用户在 ComfyUI/SD/即梦等外部工具完成生成 | 0 算力、0 成本、0 版权输出风险；最贴合"参考图库"定位 | 不是"在线生成"体验 | ✅ **P0 推荐** |

### 3.1 关于"该用哪种生成方式"的一个技术分歧（重要）

本项目图库的核心价值是**姿势准确**。若目标是"把参考图的姿势迁移到新图"，两条技术路线效果差异很大：

- **普通 i2i / 图像编辑**（参考图直接进模型，如 Qwen-Image-Edit、Flux Kontext、gpt-image edits）：风格自然，但**姿势不保证完全一致**，模型容易"改着改着把姿势也改了"；
- **ControlNet + OpenPose/DWPose（姿势骨架约束）**：先对参考图做人姿估计得到骨架图，再用骨架约束生成——姿势一致性好，但**必须跑姿态估计模型**（要么 GPU，要么浏览器端 WASM），且骨架对 3D 视角（俯视/仰视）的适配需调参。

若采用方案 B/C，建议生成入口区分「姿势一致（ControlNet）」与「风格参考（i2i）」两种模式，并在数据里标注该姿势是否适合骨架提取。

### 4.2 接口草案（契约层面，非实现）

```text
POST /api/i2i                   提交生成任务
  body: { pose_id: "full_std_P001_front" | upload_token,
          prompt: "……",          # 可由姿势数据预填模板
          strength: 0.45,         # 参考图影响强度
          width: 900, height: 1200,
          seed: 12345,
          mode: "pose" | "style"  # 骨架约束 / 风格参考
        }
  → 202 { job_id, eta_s, quota: { used, daily_limit } }
  → 400/413/422 参数错误、图片过大
  → 429 超配额 / 人机校验失败

GET  /api/i2i/{job_id}          轮询任务
  → { status: "queued|running|succeeded|failed",
      image_url: "https://…/r2/…",   # 仅 succeeded
      error: "上游超时，请重试",       # 仅 failed
      cost_estimate: 0.04 }

POST /api/i2i/upload            可选：自定义参考图（≤10 MB，PNG/JPG，尺寸校验）
DELETE /api/i2i/{job_id}        删除生成图（R2 对象）与记录

GET  /api/i2i/limits            能力与限额（含"仅全年龄子集可用"的开关状态）
```

语义约定：轮询 2 s、最长 90 s；同一 `idempotency-key` 请求幂等；失败必带可执行的中文原因；所有生成图带来源与"AI 生成"标识；生成记录保留 7 天后自动清理。

### 4.3 平台限制核对（Cloudflare，已查官方文档）

| 项 | 免费版 | 付费版 | 对本方案的含义 |
| --- | --- | --- | --- |
| Pages 站点文件数 | 20,000 个 | 100,000 | 生成图不能进 `dist/`（现有 2878 个 + 生成图会挤占上限）→ R2 |
| 单文件大小 | 25 MiB | 25 MiB | 现有最大 917 KB，无压力 |
| Workers 请求数 | 100,000/天 | 无限制 | 内部/小流量够用 |
| Workers CPU 时间 | 10 ms/请求 | 5 分钟（默认 30 s） | 免费版不适合在边缘做图像解码/审核；预处理放浏览器或升级付费 |
| 子请求 | 50/请求 | 10,000/请求 | 一次生成 1 次上游调用足够 |
| HTTP 请求 wall time | 无硬上限（等外部 API 不计 CPU） | 同左 | **可以在 Functions 里等待 10~30 s 的上游生成**，但更稳的做法是异步 + 轮询（避免客户端断开导致任务丢失） |

## 5. 主要风险

| 风险 | 等级 | 说明 | 缓解 |
| --- | --- | --- | --- |
| **内容合规** | 高 | 图库 46.8% 为 18+ 体系；主流云端 i2i 服务政策普遍禁止露骨色情/性暗示内容，参考图本身可能直接触发拒绝；若生成成人内容并在公开站传播，境内涉嫌违反治安管理处罚法与刑法相关条款（制作、传播淫秽物品），托管平台也有权停用服务 | 生成入口仅对"全年龄子集（365+400=765 条）"开放；18+ 条目不提供生成入口；上游审核 + 关键词/图像过滤双保险；免责声明与年龄分级 |
| **版权** | 高 | 图片与原始数据版权属原作者ギア，代码 MIT **不覆盖**图片/数据；i2i 输出属于对原图的演绎，公开传播/商用有侵权风险，原作者可要求下架 | 仅内部/个人自用；生成结果不默认公开、不对外分发；页面与导出文件标注来源与"不得商用"；保留删除通道 |
| **密钥与滥用** | 高 | 公开静态站没有鉴权，若直连 API 或代理不限流，Key 会泄露、额度会被刷爆 | 只走服务端代理；Cloudflare Turnstile + 每 IP/每日硬配额；必要时 Cloudflare Access 加访问口令 |
| **成本不可控** | 中高 | 3.1k star 的公开项目一旦开放生成，流量远超个人预算；上游按张/按分辨率计费 | 硬上限（每日总张数 + 单 IP 张数）、BYOK（用户自带 Key 但仅经代理转发、不落库）、或干脆只做内部工具 |
| **体验与超时** | 中 | 云端 i2i 通常 5~30 s；上游抖动/限流会失败 | 异步任务 + 轮询 + 可取消 + 明确失败原因；前端先出缩略图占位 |
| **架构漂移** | 中 | 从"零依赖静态站"变成"静态站 + Functions + R2 + KV + 外部 API + 计费"；fork 者需自建密钥与绑定；README/部署文档维护成本上升 | 做成**可选模块**（配置了才启用，默认关闭）；把生成能力放独立 `functions/` 与独立分支，主干保持纯静态 |
| **存储与隐私** | 低中 | 用户上传图/提示词、生成图留存；第三方 API 的数据处理与保留政策 | 上传图不落地、生成图 R2 生命周期清理、隐私说明 |
| **供应链** | 低 | 上游 API 价格/政策/稳定性变动 | 抽象一层"生成供应商适配器"，便于切换 |
| **浏览器兼容（方案 D）** | 高 | WebGPU 支持面、iOS 限制、磁盘配额、首次数百 MB~GB 下载 | 只作为实验入口，不作为主路径 |

## 6. 最终结论

1. **能力可行性：高。** 项目没有阻碍 i2i 的技术债；原图、多角度、筛选 UI 可直接复用，真正的缺口是"推理 + 存储 + 任务 + 鉴权 + 审核"这一整套服务层，属于新增基础设施而非改造既有功能。
2. **路径建议（按优先级）：**
   - **P0（建议先做，0.5~1 人日）**：提供"提示词模板 + 一键复制 + 参考图导出"，生成由用户在外部工具完成 → 零算力、零成本、零版权输出风险，且与社区已有方向一致（社区 PR #2 正是把姿势图作为 Agent 生图参考）。
   - **P1（确需站内生成，5~6.5 人日）**：Cloudflare Pages Functions 代理云端 i2i；仅全年龄子集、访问口令（Cloudflare Access/Turnstile）、每日硬限额、R2 自动清理、强审核；定位"内部/自用工具"，**不设公开生成入口**。
   - **P2（公开在线生成）**：**不建议**。内容属性（18+ 近半）与生成类服务合规要求正面冲突，公开站的滥用与成本不可控；若未来仍要做，应先完成内容分级、法律意见与平台政策确认，再重新评估。
3. **一句话**：当前项目适合继续做"参考图库"，不适合直接变"生成站"；生成能力应当放在**别处**（用户自己的工具，或一个受控的独立服务）。若要在这个仓库做，只能做"受控的小范围工具"，不能做"公开的在线生成"。

## 7. 延伸：接入我们项目（fashion-inspo）的建议

我们项目（`fashion-inspo`）**已经具备 i2i 链路**，因此该图库对我们更有价值的用法是"姿势参考图源"，而不是在本仓库里重造生成：

- 我方现状：本地出图页已支持图生图（Qwen-Image 2.1，参考图 1~10 张；候选两段式入库；入库标记 AI 生成）；素材库有 `source_type` 来源枚举与筛选。
- 建议接入方式：
  1. 新增来源类型 `pose_gallery`（前后端 `sourceLabel` 各改一处）；
  2. 写一次性导入脚本：只导**全年龄子集（标准系 365 + 上半身 400 = 765 张，约 340 MB）**，生成缩略图/内容哈希入库，带来源与版权字段；18+ 体系默认不导；
  3. 素材卡片/详情加"用这张图改款"入口（已有入口），把姿势图作为 i2i 参考图；
  4. 生成链路复用现有质量审核与 AI 生成标记，不需要新算力。
- 工作量估算：导入脚本 + 后端来源枚举/筛选 2~3 人日；前端来源筛选与标签 1~2 人日。
- 注意：图片版权非 MIT，**仅本地自用、不随仓库分发原图**；不导入 18+ 子集；README 记录来源与使用限制。
