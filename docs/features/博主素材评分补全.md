# 博主素材评分补全（人物页「补全评分」）

> **状态**：现行（2026-11-18 实施）
> **一句话**：人物页手动选一个统一星级，后台按博主把「未评分」素材批量补分；**只填空缺、绝不覆盖已评分**。

## 1. 目的与范围

- **背景**：人物页不少博主名下素材未评分，逐张打星成本高；补一个默认分后，「按评分排序」「按均分排序」「随机评分页」等能力才有足够样本。
- **只写** `inspirations.rating`，不动标签 / 质量状态 / 向量 / 收藏 / 合集。
- **目标博主（全量模式）**：所有有未评分素材的穿搭博主。排序分两层：先处理关联的**未删除**素材总数 > `MIN_RATING_SAMPLE`（=5，见 `backend/app/services/person/base.py`）的博主（按素材数升序，让刚够统计门槛的先有均分），再处理其余素材较少的博主（同样按素材数升序），同数按博主 id 升序。
- **显式 `blogger_ids` 模式**：按给定博主补（用户已明确选择），排序规则不变。
- **只补未评分素材**：`rating IS NULL OR rating = 0` 且 `deleted_at IS NULL`；已评分素材一律原样保留。

## 2. 接口

`POST /api/bloggers/rating-backfill`（`201 Created`）

请求体：

```json
{"rating": 5, "blogger_ids": [1, 2]}
```

| 字段 | 必填 | 说明 |
| --- | :-: | --- |
| `rating` | ✓ | 统一星级，整数 1~5 |
| `blogger_ids` | ✗ | 限定博主范围；不传 / 空 = 全部有未评分素材的博主 |

响应：

```json
{
  "task_id": 42,
  "total": 37,
  "message": "本次将为 3 位博主的 37 条未评分素材补全为 5 星评分"
}
```

- `total` 是**创建任务时**的未评分素材总数；执行期间若有人并发评分，实际更新数可能更少（以任务 `result` 为准）。
- `rating` 缺省/越界、`blogger_ids` 非整数数组 → **422**（Pydantic 校验）。
- 没有任何可补素材（含显式范围都无未评分素材）→ **400**，detail「没有可补评分的素材…」。
- 进度与逐博主明细：`GET /api/tasks/{task_id}`；运行中可 `POST /api/tasks/{task_id}/cancel`。

## 3. 任务类型 `blogger_rating_backfill`

| 项 | 说明 |
| --- | --- |
| 执行器 | `backend/app/services/task_runners/blogger_rating_backfill.py` |
| 注册 | `backend/app/services/task_runner.py` 的 `TASK_HANDLERS` |
| 可取消 | ✓（`backend/app/routers/tasks.py` 的 `_CANCELABLE_RUNNING_TYPES`；取消在博主之间检查，已补保留） |
| 可暂停 | ✗（单博主更新是毫秒级，暂停无收益） |
| GPU 互斥 | ✗（纯数据库写，不进 `GPU_EXCLUSIVE_TASK_TYPES`） |
| 分批 | **每个博主一次 commit**：进度可见，取消/崩溃时已补的数据不丢 |
| 结果字段 | 创建时 `rating/total/blogger_ids/blogger_targets`；完成后追加 `updated_materials/updated_bloggers/skipped/failed/cancelled/bloggers`（逐博主明细：状态、更新条数、跳过原因） |

执行口径：

- 逐博主执行
  `UPDATE inspirations SET rating=? WHERE id IN (该博主的素材) AND deleted_at IS NULL AND (rating IS NULL OR rating=0)`；
- `task.total` = 创建时未评分素材总数；`task.done` 按**实际更新条数**推进，结束时 `progress=100`；
- 创建后素材可能被手动评分/删除：该博主已无可补素材时记 `skipped`（原因「执行时已无可补的未评分素材」）；单个博主更新异常记 `failed` 并继续后面的博主，不拖垮整批；
- **失败重跑幂等**：已补素材 `rating > 0`，不会被再次选中。

```bash
cd backend
pytest tests/test_unit_blogger_rating_backfill.py -q   # 本功能
pytest tests/test_tasks.py -q                          # 取消白名单（任务类型已加入）
```

覆盖点：目标排序（`>5` 优先、其余随后，均按素材数升序、同数 id 升序）、显式范围、只补未评分、已评分不覆盖、垃圾桶素材不更新、无目标 400、参数 422、运行中取消、`TASK_HANDLERS` 注册、按博主进度与 result 明细。

## 5. 边界与已知取舍

- 「素材数」按**未删除素材总数**计，不是未评分数；`> 5` 只决定**优先级**（这些博主才有资格进入均分排行/筛选），不排除素材较少的博主，它们排在后面继续补。
- 不与其它任务互斥：只写 `rating` 列，且每次 commit 只覆盖一个博主，SQLite 写锁竞争可控；后续若出现明显争用，可再考虑进互斥组。
- 同一范围重复提交会创建多个任务：后执行的那个发现已无可补素材，按 0 更新收尾（不报错）。当前没有「同类任务进行中则拒绝」的需求，故未加。
- 未来若给评分加「来源」字段（人工/批量补全区分），本任务的 `updated_bloggers/bloggers` 明细可直接复用；当前 `inspirations` 只有 `rating` 一个列，无法区分评分来源。
- Web 人物页的入口、星级选择组件由前端并行任务实现，本文只描述后端契约。
