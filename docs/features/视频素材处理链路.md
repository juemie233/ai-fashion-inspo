# 视频素材处理链路

> **状态**：现行（2026-11-22 按代码核对）。真源：`backend/app/services/video_service.py`、
> `services/file_service.py`（缩略图）、`services/task_runners/batch_analyze.py`（多帧分析）、
> `routers/files.py`（关键帧接口）、`web/src/views/DetailView.vue`（横向缩略图）。
> 上传入口与去重见 [上传素材与入库前处理](上传素材与入库前处理.md)；打标链路见
> [AI分析与标签治理](AI分析与标签治理.md)。

## 1. 一句话

视频不落第二种数据形态：**原视频进 `storage/`，关键帧按「素材 ID 命名的目录」懒提取**，
四个下游（向量、人脸、AI 分析、详情页）各自从这里取帧；ffmpeg 不可用时整条链路**静默降级**而不是报错。

## 2. 关键帧从哪来

| 维度 | 实现 |
|---|---|
| 存放位置 | `storage/keyframes/{inspiration_id}/`，**不建表不加字段**，目录即索引 |
| 提取时机 | **懒提取**：第一次有人要帧时才跑 ffmpeg（详情页、向量回填、分析任务） |
| 幂等 | 目录已存在且帧数 > 0 → 直接返回，不重复抽 |
| 抽帧策略 | 默认固定间隔 `fps=1/{keyframe_interval_seconds}`；场景检测阈值 > 0 时改 `select=gt(scene,t)` + `-vsync vfr`（画面突变才抽） |
| 上限 | 单视频最多 `keyframe_max_frames` 帧（默认 60，防长视频刷爆磁盘） |
| 超时 | 单次 ffmpeg 120 秒（长视频全量解码需放宽，超时强杀防挂死调用方） |
| 失败处理 | 文件缺失 / ffmpeg 报错 / 超时 → 记日志 + 返回空列表，**不抛异常**，不阻断上传/向量/人脸/分析 |

> 场景检测表达式里的逗号必须转义（`select=gt(scene\,0.3)`）：没有 shell 包一层，逗号会被 ffmpeg
> 当成过滤器分隔符，这也是这行代码看起来有点怪的原因。

## 3. 配置项

| 配置 | 默认 | 含义 |
|---|---|---|
| `keyframe_interval_seconds` | 3.0 | 固定间隔模式的抽帧间隔（秒） |
| `keyframe_scene_threshold` | 0.0 | 场景检测阈值，0 = 关闭（如 0.3 表示画面变化 >30% 才抽帧） |
| `keyframe_max_frames` | 60 | 单视频关键帧数量上限 |
| `video_analysis_max_frames` | 3 | 参与 AI 分析的帧数（从关键帧里**均匀采样**） |
| `face_scan_video_max_frames` | 3 | 人脸扫描取前 N 帧 |
| `max_video_upload_mb` | 500 | 视频上传大小上限（按内容类型分档，与图片分开） |

支持扩展名：`.mp4 .mov .avi .mkv .webm`（`file_service._VIDEO_EXTS`）。

## 4. 四个下游消费方

```
                    ┌─→ 向量：首帧 → CLIP 图像向量（512 维）
原视频 → 关键帧目录 ├─→ 人脸：前 N 帧 → 人脸检测/注册
                    ├─→ AI 分析：均匀采样 N 帧 → 逐帧分析 → 标签按最高置信度融合
                    └─→ 详情页：GET /api/files/keyframes/{id} → 横向滚动缩略图
```

### 4.1 AI 分析用几帧、怎么采样

`batch_analyze` 执行器调 `video_service.resolve_analysis_frames(insp)`：

- 图片素材 → `[原图相对路径]`（单帧，与原有 `analyze_image` 链路一致）；
- 视频素材 → 先懒提取关键帧，再按 `video_analysis_max_frames` 均匀采样；
- 其他类型 → `[]`（调用方按「无帧」降级）。

均匀采样的实现（`sample_frames`）：要 N 帧就取第 `round(i * (总帧-1) / (N-1))` 帧，
用 `dict.fromkeys` 去重并保持时间序（帧数不足 N 时全给）。**N=1 特判取首帧**——
这就是「视频也有封面图」的来源。

### 4.2 关键帧接口

`GET /api/files/keyframes/{inspiration_id}`：

| 情况 | 返回 |
|---|---|
| 非视频素材 | `{"inspiration_id": …, "media_type": "image", "frames": []}` —— 不报错，前端不用特判 |
| 视频、帧已存在 | `{"frames": ["/api/files/keyframes/{id}/001.jpg", …]}` |
| 视频、首次访问 | 先懒提取再返回（可能等几百毫秒） |
| 视频、抽取失败 | `frames: []`，页面照常渲染（只是没有缩略图条） |

## 5. 缩略图与清理

- **封面缩略图**：`file_service._generate_video_thumbnail` 取一帧做视频卡片的封面；
- **清理**：`cleanup_keyframes_batch(ids)` 在**批量物理删除 / 清空垃圾桶**时删掉对应关键帧目录
  （幂等）；进垃圾桶（软删）不删帧，恢复后还能看到。
- 后台预热任务用模块级 `_prewarm_tasks` 集合持有引用，防止 asyncio 任务被 GC 掉。

## 6. 常见坑

1. **详情页视频没有缩略图条**：先确认 `ffmpeg` 在 PATH 里（`ffmpeg -version`）；缺依赖时整条链路静默降级，
   日志里能看到「关键帧提取失败」，但接口不报错。
2. **长视频只出 60 帧、且分布不均**：撞了 `keyframe_max_frames` 上限，且固定间隔模式下帧是等距的；
   想按镜头抽就打开 `keyframe_scene_threshold`。
3. **分析结果比图片"糊"**：视频只采 3 帧（默认），镜头变化大的视频会漏掉部分穿搭；调高
   `video_analysis_max_frames` 要同步考虑 Ollama 调用成本（N 帧 = N 次视觉调用）。
4. **磁盘涨得快**：`keyframes/` 是纯派生产物，不进备份（见 [数据备份与恢复](../ops/数据备份与恢复.md) 的
   可重建项），误删无损失，但要重跑抽帧。
5. **换了抽帧参数历史帧不更新**：幂等只看「有没有帧」，不看参数；改间隔/阈值后想重抽要先删
   `storage/keyframes/{id}/` 目录。
