# 人脸注册与候选审核方案

> **状态**：实施中（阶段 0 已完成；阶段 1/2 代码已落地，待执行注册与人工审核）｜编写日期 2026-11-01
> **依据**：`backend/app/services/face_match.py`、`routers/face_scan.py`、`services/person/face_candidates.py`、`web/src/views/FaceScanView.vue`，以及当前库（30,282 条素材）的只读统计
> **一句话**：**先修正 `pending` 语义，再批量注册 484 位博主，重跑匹配，最后审核候选与未匹配聚类**；顺序不能反。

---

## 0. 结论

| 阶段 | 做什么 | 为什么必须按这个顺序 |
| --- | --- | --- |
| **0** | 修正 `pending` 语义 + 回填 16,823 条无匹配记录 | 否则“批量驳回”会永久排除这些脸，注册完也再匹配不到 |
| **1** | 批量注册 484 位有素材但未注册的博主 | 未匹配的 21,479 张脸里，很大一部分就是他们 |
| **1.5** | 重跑全库匹配（scope=bloggers） | 把新注册的脸转成候选，是收益最大的一步 |
| **2** | 审核真实候选（当前 871 条，重跑后会增加） | 数据量小，可逐人核对 |
| **3** | 未匹配人脸聚类审核（21,479 条） | 放在最后，避免审一堆“其实是未注册博主”的脸 |

**不要直接开始审核 1.7 万条 pending**：其中 16,823 条不是候选，是语义错误产生的噪声。

## 2. 根因：`pending` 被当成“匹配过”而不是“有候选”

`services/face_match.py:285-313`：

```python
if (
    det.matched_blogger_id != new_blogger
    or det.matched_model_id != new_model
    or det.confidence != new_conf
    or det.match_status != "pending"
):
    changes.append({..., "matched_blogger_id": new_blogger, ...})
...
await db.execute(update(InspirationFaceDetection),
    [{**c, "match_status": "pending"} for c in changes])
```

当 `result is None`（没有任何人物超过阈值）时，`new_blogger` / `new_model` 都是 `None`，但这行**仍然被写入 `pending`**。于是：

1. **统计失真**：pending 从 871 被放大到 17,694；
2. **审核页分组混乱**：`pending` 结果按人物聚合，16,823 条没有人物，无法审核；
3. **最危险**：`POST /api/face-scan/confirm` 的 `reject` 会把 `match_excluded` 置为 `True`——该人脸**永久退出后续匹配**。一旦对这批无匹配记录批量驳回，等博主注册完再跑匹配，这些脸永远不会被捞起。

## 3. 目标与非目标

### 3.1 目标

1. `pending` 只表示“有具体人物的 AI 候选”；
2. 把有素材博主的注册覆盖率从 4.3% 提到尽可能高（取决于有稳定人脸的博主数）；
3. 审核完真实候选，误确认率可抽检；
4. 通过注册 + 重匹配，让未匹配人脸数量显著下降；
5. 剩余未匹配人脸按“疑似同一人”聚类，支持整组指派 / 新建人物 / 忽略。

### 3.2 非目标

- **不自动注册**：注册错人会让全库持续误判，代价高于“没注册”；
- **不追求 484 位全部注册**：全身街拍、合影、路人、无正脸素材注定无法注册；
- **不做人脸特征导出/外部比对**：生物特征只在本机库内使用；
- **不借机做 LoRA / 跨平台去重**：与本方案无关。

## 4. 阶段 0：修正 `pending` 语义

### 4.1 代码修改

`services/face_match.py`：

- 只有 `result is not None` 才在更新载荷里写 `match_status = "pending"`；
- `result is None` 时写 `match_status = None`（未匹配是“普通检测”，不是候选）；
- 只更新真正变化的行（现有 diff 逻辑保留）；
- 已确认（`confirmed`）与人工排除（`match_excluded`）记录继续跳过。

### 4.2 数据回填

先备份数据库（放 `backend/storage/_db_backups/`），再执行：

```sql
UPDATE inspiration_face_detections
SET match_status = NULL
WHERE match_status = 'pending'
  AND matched_blogger_id IS NULL
  AND matched_model_id IS NULL;
```

> 回填只改状态，不动 `matched_*`、`confidence`、`match_excluded`。
> 执行后 `pending` 应为 **871** 左右；`match_excluded` 数量应保持 **1,499** 不变。

### 4.3 测试

- 单测：批量匹配中，未超过阈值的人脸结果 `match_status IS NULL`；
- 单测：有匹配的人脸仍为 `pending`；
- 单测：`confirmed` 记录不被重跑覆盖；
- 回归：审核页 pending 总数与“按人物聚合”的总和一致。

### 4.4 UI 文案

- pending 区标题改为「AI 候选（已匹配到人物）」；
- 未匹配区说明「未超过阈值，可指派或参与聚类」；
- 驳回按钮提示文案写明「永久排除，后续匹配不再出现」。

**验收**：`pending` ≈ 871；`match_excluded` 不增加；回填前后有备份与审计记录。

## 5. 阶段 1：批量注册

### 5.1 候选来源（复用现有能力）

`services/person/face_candidates.py` 已经提供了核心判断：

| 来源 | 逻辑 | 现状 |
| --- | --- | --- |
| 已确认/历史匹配 | 该博主素材里已匹配到 TA 的检测，按 `det_score` 排序，最多 12 张 | 只覆盖已注册的 22~30 位 |
| 未匹配人脸簇 | 该博主素材里**单脸素材**中反复出现 ≥3 次的未匹配人脸，聚成簇，每簇给封面、成员数、平均置信度、前 3 张素材 | 文档实测 **141 位博主**满足；这是放量的主路径 |

**候选规则**（沿用现有常量）：

- 只用单脸素材（多脸无法判断哪张是本人）；
- 单簇成员 ≥3、≤50；
- `det_score ≥ 0.5`；
- 每位最多取 `det_score` 最高的 3 张注册。

### 5.2 批量注册工作台

位置：`FaceScanView` 新增「批量注册」Tab（或 `PersonView` 的批量操作入口）。

列表按「簇成员数 × 平均 det_score」排序，每行展示：

```text
[头像] 博主名（素材 342 张）
       候选：簇 A 出现 18 次 · 平均置信度 0.71
       [封面1][封面2][封面3]   [采用] [换一组] [跳过]
```

操作：

- **采用**：调 `POST /api/bloggers/{id}/face`（现有接口，传 `inspiration_ids`）；
- **换一组**：切到下一个候选簇；
- **跳过**：本轮隐藏，不写库；
- **无候选**：显示「素材里没有稳定人脸」，不强行注册。

批量操作：

- 「采用当前页（20 位）」：只对已有建议素材的博主执行；
- 执行后逐行显示结果（成功 / 无脸 / 子服务不可用）；
- 失败项保留，可重试。

### 5.3 接口设计

#### `POST /api/face-scan/register-plan`（只读）

请求：

```json
{ "limit": 200, "min_cluster_size": 3, "min_det_score": 0.5, "only_with_candidates": true }
```

响应：

```json
{
  "items": [
    {
      "person_type": "blogger",
      "person_id": 192,
      "name": "示例博主",
      "inspiration_count": 342,
      "registered": false,
      "clusters": [
        { "size": 18, "avg_det_score": 0.71,
          "suggested_inspiration_ids": ["…","…","…"],
          "cover_detection_ids": [1,2,3] }
      ],
      "skip_reason": null
    }
  ],
  "summary": { "total": 484, "with_candidates": 141, "no_candidates": 343 }
}
```

- 不写库，供用户先看规模与质量；
- 排序、分页在服务端完成，避免前端拉 484 位的全量候选。

#### `POST /api/face-scan/register-batch`

请求：

```json
{
  "items": [
    { "person_type": "blogger", "person_id": 192,
      "inspiration_ids": ["…","…","…"] }
  ]
}
```

响应：逐条 `{person_id, ok, face_count, error}`。

- 服务端串行调用现有 `register_blogger_face`（每位 1–5 张，内部已做平均池化）；
- 一次最多 20 位，由前端分批循环——**不新增任务类型**，避免改动 `TASK_HANDLERS`、暂停/取消白名单、前端文案三处；
- 子服务不可用时整批快速失败，返回可读原因，不逐位超时。

### 5.4 执行流程

1. 启动 face-service（18889），审核页状态条应显示可用；
2. 先拉 register-plan，确认 `with_candidates` 规模；
3. 按页采用；每批 20 位；
4. 记录本轮结果：成功 N 位、无脸 M 位、失败 K 位；
5. 失败项单独重试。

### 5.5 注册后重跑匹配

`POST /api/face-match/run`，`scope=bloggers`。

- 这一步把新注册博主的特征加入矩阵，未匹配人脸转成候选；
- 跑完后重新统计 `pending` 与未匹配数；
- **不要**在重跑前审核低置信度候选，否则会基于旧特征库做判断。

### 5.6 验收

- 注册覆盖：22 → 尽量接近 `with_candidates + 已注册`（预期 140~160，具体取决于候选质量）；
- 每位注册后 `GET /api/bloggers/{id}/face` 返回已注册且特征维度 512；
- 重跑匹配后，未匹配人脸数量较 21,479 明显下降（记录前后值）；
- 抽检 20 位注册结果：注册素材确实属于本人。

## 6. 阶段 2：真实候选审核

当前 871 条候选集中在 4 位人物（一位 821 条），重跑匹配后会增加。

### 6.1 页面调整

- pending 区只列“有具体人物”的候选（阶段 0 之后自然满足）；
- 按人物聚合排序：数量降序，展示「N 条 · 平均置信度 · 最高置信度」；
- 点开某人后展示人脸裁剪 + 来源素材大图并排；
- 支持按人物批量确认 / 批量驳回；单条可切换。

### 6.2 阈值

- 快捷确认阈值从写死 0.75 改为**可配置**，默认 0.65（当前 0.65–0.75 有 30 条）；
- 阈值只影响“是否显示快捷按钮”，不自动确认；
- 重跑匹配后重新看分布再定值。

### 6.3 驳回

- 保留现有语义（`match_excluded=true`，永久退出匹配）；
- 弹窗必须写明影响范围与数量；
- 不提供“全选驳回低置信度”——低置信度不等于错误，需看脸。

### 6.4 验收

- 871 条（及重跑后的新增）全部过审；
- 随机抽 20 条已确认记录，素材归属正确率 ≥95%；
- `match_excluded` 的增加量有记录、可解释。

## 7. 阶段 3：未匹配人脸聚类审核

前置：阶段 1.5 已重跑匹配。

### 7.1 流程

1. 启动 `face_cluster` 任务（hnswlib 主路径，建边 0.6、平均链接）；
2. 按簇大小排序，先审 ≥10 次的组（大概率是真博主）；
3. 每组展示代表脸、成员数、来源素材抽样；
4. 动作：
   - **指派已有博主/模特**（现有 `confirm` 接口支持整组未匹配人脸）；
   - **新建人物并注册**（先建博主，再用组内最高质量 3 张注册）；
   - **整组忽略**（`match_excluded`，提示永久）；
5. 审完的组不再参与后续聚类。

### 7.2 验收

- 未匹配人脸中，属于已有人物的被尽量指派；
- 新建人物数量与来源可追溯；
- 簇内明显混入不同人的组被拆开或忽略。

## 10. 风险与回滚

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 注册错人 | 全库匹配持续误判，代价高于不注册 | 人工确认 + 展示来源素材；不自动注册 |
| 批量驳回无匹配记录 | 人脸永久退出匹配 | **阶段 0 必须先做**；驳回弹窗写明 |
| 子服务离线 | 注册/扫描全部失败 | 先看 `/api/face-scan/service-status`；离线时禁用动作 |
| 重匹配耗时/抢占资源 | 与 Ollama 任务争 GPU | `face_match` 已在重负载互斥组；安排空闲时段 |
| 候选质量差 | 注册后仍匹配不到 | 以“重跑后未匹配下降”为验收，而不是注册数 |
| 生物特征合规 | 隐私风险 | 只存本机库、不导出、不进分享/备份以外位置 |

**回滚**：

- 阶段 0 回填前备份 DB（`_db_backups`），可用备份恢复；
- 注册是覆盖式（重新注册即覆盖），错误注册可用 `DELETE /api/bloggers/{id}/face` 注销；
- 驳回是永久操作，不提供批量回滚；执行前先小批量验证。
