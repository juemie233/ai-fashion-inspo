## 1. 通用评分契约（素材库 / 详情 / 搜索 / 合集 + 后端）

> 原文件：`features/评分功能开发方案-2026-11-12.md`｜原题：评分功能开发方案（2026-11-12）

> 状态：已实施（2026-11-12）
> 范围：Web 素材库 / 素材详情 / 搜索 / 人物详情 / 智能合集 + 后端评分契约；**手机端本期不做评分入口**
> 结论：评分按「单用户、0–5 整数星、0 表示未评分」设计，只参与排序、筛选与智能合集，不进入 AI 质量审核、相似推荐或质量学习。现有 Web 已有一套可用的五星评分，但存在 3 个必须先修的缺口：**批量评分接口丢字段、详情页评分不同步列表、评分排序无稳定分页**。
> 说明：本文只做方案，未改代码。文中「现状」均按当前仓库代码核对。

---

### 1. 一句话定义

**评分是用户对一条素材的个人偏好标记，不是 AI 质量分，也不是推荐信号。**

- 0 = 未评分（默认）；
- 1–5 = 用户手动打星；
- 只影响：列表排序、`rating_min` 筛选、智能合集的 `min_rating`；
- 不影响：`quality_status` / 质量初筛 / 负样本 / 相似推荐权重 / 自动删除（去重里的「人工投入」保护除外，见 §4.5）。

### 4. 关键设计决策

#### 4.1 P0：批量评分接口现在实际上不生效

这是现状里最硬的一个 bug：

- `BatchUpdateRequest` 有 `rating`（`backend/app/schemas/inspiration.py:151`）；
- `batch_update_inspirations()` 有 `rating` 参数（`backend/app/services/inspiration_update.py:77-85`）；
- 但 router 调用时只传了 `source_type / is_favorite / quality_status / is_ai_generated`，**没有传 `rating`**（`backend/app/routers/inspirations.py:493-506`）。

结果：`POST /api/inspirations/batch-update` 带 `rating` 会返回 `updated: N`，但评分根本没变。Web 的 `BatchUpdateFields` 也没有 `rating` 字段，所以界面上暂时没暴露——一旦加批量评分 UI，就会踩到这个坑。

**决策：本期必须修**，否则「批量评分」是假的。

#### 4.2 0 的语义：未评分，不是 0 星

保持 `0 = 未评分`，不新增 `NULL`：

- 迁移成本最低（现有字段 NOT NULL DEFAULT 0）；
- `a-rate allow-clear` 天然返回 0；
- UI 文案统一说「清除评分」，不说「0 分」；
- `rating_min` 的 `ge=1` 也与此一致：筛 0 分没有意义。

**代价**：无法区分「明确打 0 星（很差）」与「还没评」。如果未来确实需要 0 星，建议改成 `rating` 可空（NULL=未评分，0=0 星），而不是把 0 同时当两种含义。本期不做。

#### 4.3 「评分最低」是否包含未评分？

现状 `sort=rating_asc` 是 `ORDER BY rating ASC`，0 分（未评分）会排最前。测试也锁了这个行为（`test_search.py` 断言 `a(0) → c(2) → b(5)`）。

这有两种产品解释：

| 方案 | 行为 | 适合 |
| --- | --- | --- |
| A. 保持现状 | 未评分排最前，等于「先处理没评过的」 | 把评分当待办队列 |
| B. 只排已评分 | `WHERE rating > 0 ORDER BY rating ASC`，未评分不出现 | 「评分最低」字面语义 |
| C. 拆成两个排序 | 「评分最低（仅已评分）」+「未评分优先」 | 两种需求都满足，但 UI 多一个选项 |

**建议 C**：默认「评分最低」只排已评分；如果确实需要「先清未评分」，单独给「未评分优先」。这样不会出现「点评分最低，结果全是 0 分」的困惑。

**影响**：需要改 `inspiration_query.py` / `search.py` 的 `rating_asc` 分支、更新 `test_search.py` 的断言，并在筛选栏/排序菜单加「未评分优先」选项。

#### 4.4 评分排序必须有稳定次序

现状 `ORDER BY rating DESC` 没有第二排序键。素材库有大量 0 分/同分，翻页时 SQLite 对同分行的顺序不稳定，可能出现「第 2 页重复第 1 页的图」或漏图。

**决策**：所有评分排序统一加 `created_at DESC, id DESC` 作为 tie-breaker，并加复合索引：

```sql
CREATE INDEX ix_inspirations_active_rating_created
ON inspirations (deleted_at, rating, created_at);
```

- `deleted_at` 等值 + `rating` + `created_at`，同时服务筛选和排序；
- 降序扫描可复用同一索引；
- 与 2026-11-06 数据库审查里补的 `(deleted_at, created_at)` 系列索引同一思路。

#### 4.5 去重评分里的 +20：保留，但明确它不是推荐

`deduplicate.py` 把 `rating > 0` 视为「用户手工投入」，在重复组保留评分里 +20（`_collect_manual_investment` / `_score_groups`）。这不是推荐算法，而是**防止自动去重删掉用户打过分的副本**。

**决策：保留**。它和「评分不参与 AI/推荐」不冲突：前者是数据保护，后者是排序信号。若未来要改成纯排序筛选，需要同时接受「已评分副本可能被自动删除」的风险，建议不要动。

#### 4.6 卡片上的五星：保留直接操作，但要防误触

现状卡片悬浮层里直接放 `a-rate`，点击星不会打开详情（`@click.stop`），但星与收藏/删除按钮并排，触摸设备上常显。

**建议**：

- 桌面：保持 hover 才显示操作层（现状 CSS 已是 hover；触摸设备 `@media (hover: none)` 常显）；
- 触摸/平板：评分收成「★ 4」紧凑 chip，点开 1–5 星弹层，避免在卡片上直接点错；
- 已评分卡片显示紧凑星级，未评分不占位；
- 无论哪种，`aria-label` 要含「当前 N 星，点击修改」。

这条是体验优化，不阻塞后端修复；如果本期只做正确性，可以保留现状。

#### 4.7 详情页评分要同步列表 store

`DetailView.vue` 的 `handleRate` 直接调 `updateRating` 并只改 `detail.value.rating`；而 `useInspirationsStore.setRating` 会同时更新 `items` 与 `currentDetail`（`stores/inspirations.ts:168-176`）。

从素材库点进详情改评分，再返回列表，卡片仍显示旧分数，直到重新加载。

**决策**：详情页统一走 `store.setRating(id, value)`，不要自己调 API；如果详情页不是从 store 进入，也至少更新 store 中同 ID 的项。评分失败要回滚 UI 并提示。

#### 4.8 手机端：不做入口，但别留死排序

按你的决定，手机端本期不加评分控件。当前手机排序菜单里已有「评分」，但没有打分入口；如果库里绝大多数是 0 分，这个排序基本没意义。

**建议**：本期顺手隐藏手机端「评分」排序（或标注「Web 端可用」），等手机评分入口排期时再恢复。若你希望保留只读排序，也可以不改，但要在文档里注明「手机只能看不能打分」。

### 5. 接口设计

#### 5.1 单条评分（保持不变）

```http
PATCH /api/inspirations/{id}
Content-Type: application/json

{"rating": 4}
```

- `rating` 取值 0–5；0 = 清除；
- 非整数/越界返回 422；
- 返回更新后的 `InspirationOut`（含 `rating`）。

#### 5.2 批量评分（修复）

```http
POST /api/inspirations/batch-update
Content-Type: application/json

{"ids": ["..."], "rating": 4}
```

修复点：

1. router 把 `rating=data.rating` 传给 `batch_update_inspirations`；
2. Web `BatchUpdateFields` 增加 `rating?: number`；
3. 批量评分与批量收藏/审核状态可以同请求组合，但建议 UI 一次只改一类，避免误操作；
4. 只更新未删除素材（service 已用 `NOT_DELETED`），返回实际更新行数。

#### 5.3 列表/搜索/人物筛选

沿用 `rating_min=1..5`。是否新增「未评分」参数：

- 方案 A：不新增，用 `sort=rating_asc` 间接看未评分；
- 方案 B：新增 `unrated=true` 或 `rating_state=unrated`，语义明确。

**建议 B（可选）**：如果确实要做「待评分队列」，加 `rating_state=unrated`，不要用 `rating_max=0` 这种反直觉参数。本期可以先不做，等有明确需求再加。

#### 5.4 排序

- `sort=rating`：`rating DESC, created_at DESC, id DESC`；
- `sort=rating_asc`：按 §4.3 决策改为「仅已评分，rating ASC」；
- 新增（可选）`sort=unrated_first`：`rating = 0` 优先，再按 `created_at DESC`。

排序值需要同步到：

- `backend/app/services/inspiration_query.py` 的 `sort_map`；
- `backend/app/routers/search.py` 的 `sort_mapping`；
- `web/src/composables/useInspirationFilters.ts` 的 `sortOptions`；
- `web/src/components/home/HomeFilterBar.vue` 的展示；
- 如有 `rating_asc` 测试，更新断言。

#### 5.5 智能合集

`query_json.min_rating` 已支持；本期只保证：

- 0 表示不限；
- 与列表 `rating_min` 同口径（都排除垃圾桶）；
- 修改评分后，智能合集内容动态变化（已有 `test_collections.py` 覆盖）。

#### 6.3 批量评分

在批量操作条增加「评分」按钮：

- 点开小弹层选 1–5 星 / 清除；
- 对选中素材执行 `batch-update`；
- 成功后退出批量模式并刷新当前页（与批量编辑一致）；
- 评分是可逆操作，不需要二次确认；但要显示「已更新 N 个素材」。

#### 6.4 筛选与排序文案

- 筛选下拉：`全部评分 / ≥1 星 / ≥2 星 / ≥3 星 / ≥4 星 / 5 星`（已有）；
- 排序：`评分最高` / `评分最低（仅已评分）`；
- 如做待评分队列：`未评分优先`；
- 所有文案中文，与现有 UI 一致。

- `rating_min` 与 `sort=rating` 组合走同一索引；
- 现有数据分布先跑一次：

```sql
SELECT rating, COUNT(*) FROM inspirations GROUP BY rating ORDER BY rating;
```

用于判断「评分最低」是否真的会被 0 分淹没（若 0 分占绝大多数，§4.3 的方案 C 更有必要）。

### 9. 边界与风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 语义混淆 | 0 同时被理解为「未评分」和「0 星」 | UI 只说「清除评分」；文档固定 0=未评分 |
| 分页不稳定 | 同分素材多，翻页重复/漏图 | tie-breaker + 复合索引 |
| 批量误操作 | 批量评分一次改很多素材 | 只改显式选中项；可逆；显示更新数量 |
| 个人偏好污染 AI | 评分如果进质量学习，会把审美当质量 | 明确禁止；去重 +20 仅作为人工投入保护 |
| 多用户 | 未来多人使用时 `inspirations.rating` 只能存一个值 | 本期单用户；未来新建 `inspiration_ratings` 关联表 |
| 手机端死选项 | 有「评分」排序但没有打分入口 | 本期隐藏或标注；等手机评分排期再恢复 |

## 2. 博主详情作品评分应用（复用 inspirations.rating）

> 原文件：`features/博主详情作品评分方案-2026-11-12.md`｜原题：博主详情作品评分方案（2026-11-12）

> 状态：已实施（2026-11-12）
> 范围：Web 博主详情页的「全部（按张）」素材网格 + Web 博主列表的评分排序/筛选
> 结论：**复用现有 `inspirations.rating`，不新增 `bloggers.rating`**。用户在博主详情给每张作品打 0–5 星；博主列表按「已评分作品的平均分」排序/筛选，且**至少 5 张已评分作品**才参与排名。作品分组视图与手机端本期不加评分。
> 关联文档：评分功能开发方案（本文第 1 节）（通用评分契约、批量评分与排序语义）。

---

### 1. 需求定义

#### 1.1 这次要做什么

在某个穿搭博主的详情页里，用户可以直接给**她的作品（单张素材）**打 1–5 星，表达「这张穿搭我喜欢/想参考」；素材库与博主列表复用同一份评分数据，博主列表显示「作品均分」，并支持按均分排序、按最低均分筛选。

#### 1.2 不做什么

| 不做 | 原因 |
| --- | --- |
| 给「博主本人」打总分 | 本次明确评价对象是作品；博主本人评分需要新增 `bloggers.rating`，是另一套数据 |
| 给「作品组」打整组评分 | 评分存在单张素材上；整组评分需要新存储或复杂的组级聚合 |
| 手机端评分入口 | 按你的决定，手机端本期不做 |
| 评分进入 AI 质量/相似推荐 | 沿用上次决策：评分只做排序、筛选、智能合集，不参与推荐算法 |
| 半星/十分制 | 沿用 0–5 整数，和现有素材评分一致 |
| 博主列表默认排序改为评分 | 默认仍是「素材数最多」；评分是可选排序 |

### 2. 现状与缺口

#### 2.1 已有能力

| 单条评分 API | `PATCH /api/inspirations/{id}`，`rating` 校验 0–5 |
| 博主详情素材 API | `GET /api/bloggers/{id}/inspirations` 已返回每条素材的 `rating`（`backend/app/services/person/base.py` 的素材查询列里有 `Inspiration.rating`） |

#### 2.2 缺口

1. **详情页能看不能打**：`PersonItemsSection.toInspirationOut()` 把 `rating` 丢掉了；同时 `MasonryGrid` 传了 `show-actions=false`，卡片悬浮层（含五星）整体不渲染。
2. **博主列表没有评分聚合**：`list_items` 的统计子查询只算素材数和最近素材时间，没有均分/已评分数。
3. **博主列表没有评分排序/筛选**：`/api/bloggers` 的 `sort` 只允许 `newest|name|count`；前端 `sortOptions` 也只有这三项。
4. **没有样本门槛**：按平均分排序时，1 张 5 星会排在 10 张 4.8 前面；本方案用「至少 5 张已评分」控制。

### 3. 数据与口径

#### 3.1 评分对象

- 一条 `inspirations` = 一张作品（图片或视频）；
- 评分写入 `inspirations.rating`，与素材库、素材详情、智能合集共用；
- 0 = 未评分，不参与平均分分母；
- 1–5 整数，UI 不出现半星。

#### 3.2 博主「作品均分」

```text
avg = 该博主所有未删除、rating > 0 的作品评分之和 / 已评分作品数
rated_count = 该博主所有未删除、rating > 0 的作品数
样本门槛 = 5
```

- **分母只算已评分作品**，不是全部作品；「10 张里 5 张 5 星」和「5 张全 5 星」都是 5.0；
- **至少 5 张才参与排名/筛选**；不足 5 张显示「样本不足 N/5」，不参与评分排序与评分筛选；
- 平均分保留 2 位小数；
- 已删除（垃圾桶）作品不计入；恢复后自动重新计入；
- 视频与图片一视同仁。

#### 3.3 人物组合并时怎么算

博主列表默认按人物组折叠（同一人的多个平台账号只显示主账号）。**建议按组内所有账号的作品合并计算**：

- `组均分 = 组内所有账号的 rating>0 作品评分之和 / 组内已评分作品总数`；
- `组已评分数 = 组内所有账号已评分作品数之和`；
- 组内单个账号的 `group_members` 仍显示各自均分与样本数；
- 平台筛选时后端自动平铺，此时每个账号各自算。

理由：列表折叠后用户看到的是「一个人」，不是「一个账号」；如果只取主账号，会漏掉同组另一个账号的高分作品。

**代价**：需要把 `rating_sum` 和 `rated_count` 一起聚合，不能只传 `avg`。这也是后端实现要注意的点。

#### 3.4 数据预检（实施前必须做）

「至少 5 张」是较强的门槛。当前库有多少博主满足，需要先统计；如果满足的博主很少，列表排序/筛选会几乎为空，需要把门槛降到 3 或在 UI 明确显示「样本不足」。

```sql
SELECT COUNT(*) FROM (
  SELECT ib.blogger_id
  FROM inspiration_bloggers ib
  JOIN inspirations i ON i.id = ib.inspiration_id
  WHERE i.deleted_at IS NULL AND i.rating > 0
  GROUP BY ib.blogger_id
  HAVING COUNT(*) >= 5
);
```

以及分布：

```sql
SELECT cnt, COUNT(*) AS bloggers
FROM (
  SELECT ib.blogger_id, COUNT(*) AS cnt
  FROM inspiration_bloggers ib
  JOIN inspirations i ON i.id = ib.inspiration_id
  WHERE i.deleted_at IS NULL AND i.rating > 0
  GROUP BY ib.blogger_id
)
GROUP BY cnt ORDER BY cnt;
```

若 `>=5` 的博主为 0 或个位数，建议本期先把门槛做成后端常量 3 或 5 可切换，而不是硬编码 5。

### 4. 后端方案

#### 4.1 统计子查询增加评分聚合

`backend/app/services/person/base.py` 的 `list_items()` 里，`count_subq` 目前是：

```python
select(
    link_id.label("pid"),
    func.count(link_model.inspiration_id).label("cnt"),
    func.max(Inspiration.created_at).label("last_at"),
)
```

增加：

```python
func.sum(
    case((Inspiration.rating > 0, Inspiration.rating), else_=0)
).label("rating_sum"),
func.sum(
    case((Inspiration.rating > 0, 1), else_=0)
).label("rated_count"),
```

- 只统计 `deleted_at IS NULL`（现有 where 已有）；
- 只统计 `rating > 0`；
- 用 `sum` 而不是直接 `avg`，因为人物组折叠时要把多个账号加总；
- 在 `_to_dict()` 里计算 `rating_average = round(rating_sum / rated_count, 2) if rated_count else None`，并返回 `rated_count`。

#### 4.2 返回字段

`backend/app/schemas/person.py` 的 `BloggerOut` 增加：

```python
rating_average: float | None = None
rated_count: int = 0
```

`shared/types/person.ts` 的 `Person` 增加可选字段：

```ts
rating_average?: number | null
rated_count?: number
```

模特接口不需要评分聚合；字段可选，模特返回默认空即可。

#### 4.3 列表排序

`GET /api/bloggers` 的 `sort` 允许值扩展为：

```text
newest | name | count | rating | rating_asc
```

口径：

- `rating`：有样本（rated_count >= 5）的博主在前，按 `rating_average DESC`；样本不足的排最后；同分按 `rated_count DESC, id DESC`；
- `rating_asc`：有样本的博主在前，按 `rating_average ASC`；样本不足的排最后；同分按 `rated_count DESC, id ASC`；
- `newest/name/count` 行为不变；
- 分页必须稳定：所有评分排序都带 `id` 兜底。

#### 4.4 列表筛选

`GET /api/bloggers` 增加：

```text
rating_min: int | None = Query(None, ge=1, le=5)
```

语义：

- 仅返回 `rated_count >= 5 AND rating_average >= rating_min` 的博主；
- `rating_min` 为空时不过滤；
- 与平台/来源/搜索/分组叠加；
- 模特接口不提供该参数。

#### 4.5 分组折叠路径

`_list_grouped()` 目前在内存里折叠、排序、分页。评分要特殊处理：

1. 每个账号的 `rating_sum / rated_count` 从子查询带进来；
2. 折叠时把组内所有账号的 `rating_sum` 与 `rated_count` 相加，得到组均分；
3. **评分筛选必须在折叠后做**，不能先过滤账号——否则组均分会被低分账号被剔除而失真；
4. 评分排序也在折叠后做；
5. 独立账号（无组）各自一行。

#### 4.6 性能

当前规模：583 位博主、23,918 条博主-素材关联、33,762 条素材。聚合子查询按 `blogger_id` 分组，数据量很小；现有 `inspiration_bloggers(blogger_id)` 索引可用。

可选的索引优化（P2）：

- `inspiration_bloggers (blogger_id, inspiration_id)` 覆盖索引，避免回表取 inspiration_id；
- `inspirations (deleted_at, rating)` 对评分筛选有帮助，但当前 33k 行、按主键回表，收益要先测。

**不建议**为了这个功能加 `bloggers.rating` 字段或缓存列：当前单用户、数据量小，实时聚合足够；缓存会带来「评了分但列表没更新」的一致性问题。

### 9. 风险与边界

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 评分样本太少 | 至少 5 张的门槛可能让榜单几乎为空 | 上线前 SQL 预检；必要时把门槛做成常量 3/5 可切换，或先只显示「样本不足」 |
| 组均分口径 | 同人多账号合并还是只取主账号 | 推荐按组内全部账号合并；平台筛选时平铺各自算 |
| 评分与列表不同步 | 详情打分后返回列表仍是旧均分 | 列表 `onMounted` 强制 reload（现状已如此）；详情内更新本地 items；不要做跨页缓存 |
| 卡片点击冲突 | 点星误开灯箱 | `@click.stop` + 单独 `showRating` 层；补测试 |
| 作品组歧义 | 一组多图无法用一个星表达 | 本期只在「全部」视图按张评；作品组不加星 |
| 个人偏好污染算法 | 评分进入推荐/质量会变形 | 只做排序/筛选/智能合集；去重 +20 是人工投入保护，不是推荐 |
| 未来多用户 | 单用户 rating 字段无法存多人评分 | 本期单用户；未来新建 `inspiration_ratings(user_id, inspiration_id)` |
| 手机端死排序 | 手机有 `sort=rating` 但没有入口 | 本期不改手机；等手机评分排期时一起处理，或先隐藏该排序 |

### 11. 结论

- 数据模型不新增字段，复用 `inspirations.rating`；
- 详情页只在「全部」视图的每张缩略图上加五星；
- 博主列表新增「作品均分」列 + 评分排序 + 评分筛选，至少 5 张已评分才参与排名；

- 默认排序、素材评分、手机端、AI/推荐都不受影响。
