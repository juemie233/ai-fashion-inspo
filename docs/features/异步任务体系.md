# 异步任务体系（task_queue / worker）说明

> **状态**：现行｜编写日期 2026-11-01｜依据 `backend/app/worker.py`、`routers/tasks.py`、`services/task_runner.py`
> **一句话**：API 只往 `task_queue` 表写任务，独立 worker 进程原子认领并执行；前端通过 WebSocket 收进度、断线退回轮询。
> **适用场景**：批量分析、质量审核、向量回填、人脸扫描、采集入库、出图等分钟级到小时级的工作。

---

## 1. 组件与职责

| 组件 | 职责 | 位置 |
| --- | --- | --- |
| API（FastAPI） | 创建任务、查询列表/详情、暂停/恢复/取消/删除、广播事件 | `routers/tasks.py` 及各业务路由 |
| worker（独立进程） | 轮询认领、执行、写进度、心跳、崩溃恢复 | `app/worker.py` |
| 执行器 | 每种任务类型的 `execute_xxx(db, task)` | `app/services/task_runners/` |
| 任务表 | 状态、进度、重试、心跳、暂停快照 | `models/task.py` |
| 事件通道 | `type=task_event` 的 WS 广播 + 前端轮询兜底 | `services/task_events.py`、`routers/ws.py` |

启动 worker（在 `backend/` 下）：

```bash
python -m app.worker
```

> worker **不执行 Alembic 迁移**，由 API 进程统一负责；两边同时 `upgrade` 会竞争 SQLite 写锁。worker 启动只做 `create_all` + `ensure_schema` 兜底。

## 2. 状态机

```text
                 ┌────────── 用户取消（pending 直接删记录）
                 ▼
  [pending] ──认领──► [running] ──成功──► [success]
      ▲                  │  │
      │                  │  └──永久错误/重试耗尽──► [failed]
      │                  │
      │                  └──用户暂停（白名单类型）──► [paused] ──恢复──► pending 或 running
      │                                                    │
      └──────── worker 心跳超时（≤90s）重置回 pending ◄────┘
                                                           └──用户取消──► [cancelled]
```

- `pending`：排队中，可被 worker 认领；**取消会物理删除记录**。
- `running`：已被认领，带 `claimed_by` 与 `heartbeat_at`。
- `paused`：仅可暂停类型；不会被 worker 认领，可恢复或取消。
- `success` / `failed` / `cancelled`：终态；可删除记录（`failed` 保留 `error`）。

关键字段（`TaskQueue`）：

| 字段 | 用途 |
| --- | --- |
| `priority` | 认领排序：`priority DESC, id ASC`；默认 0，清理类（批量删除）为 -5 |
| `progress` / `total` / `done` | 0~100 与计数；总数为 0 的任务会直接置 100 |
| `result` | 初始为输入载荷，完成后写统计（如 `deleted_count`、`freed_bytes`） |
| `retry_count` / `max_retries` / `next_retry_at` | 重试计数、上限（默认 2）、指数退避时间 |
| `claimed_by` / `heartbeat_at` | 心跳租约，判定 worker 是否存活 |
| `paused_at` / `last_stage` / `stage_state` | 暂停快照；标签网络分析恢复时从中续算 |

> 三份白名单的**真源**：后端 `worker.py` 的 `GPU_EXCLUSIVE_TASK_TYPES`、`routers/tasks.py` 的
> `_CANCELABLE_RUNNING_TYPES` / `_PAUSABLE_RUNNING_TYPES`；前端必须同步

**GPU 互斥**：组内任务全局串行（同一时刻只允许一个 running），其余任务照常执行。
原因是一次实测：向量回填与质量审核并发时，同一检查点从 **5.4 秒退化到 12.7 分钟**（130 倍）。
取舍：一个 handler 卡死时，任务看门狗会在 `TASK_STALL_TIMEOUT_SECONDS`（默认 30 分钟）无进度后
取消它并标 failed、释放槽位；若整个事件循环卡死（连心跳都不写），supervisor 会按心跳超时
强制重启 worker。两者见 [worker 假死与任务队列加固](../ops/worker假死与任务队列加固-2026-11-02.md)。

## 4. 认领与并发

- 轮询间隔 1 秒；只认领 `status=pending` 且 `next_retry_at` 已到期的任务；
- 排序：**可认领任务优先**（互斥组忙时先挑不吃 GPU 的）→ `priority DESC` → `id ASC`（同优先级 FIFO）；
- 认领与互斥判定写在**同一条条件 UPDATE** 里，多 worker / 多进程也不会重复执行或突破互斥；
- 同时执行数由 `settings.worker_concurrency` 控制（`.env` 的 `WORKER_CONCURRENCY`，默认 1）；
  调大前先考虑 Ollama 显存与 SQLite 写锁，建议 1~2；
- SQLite 报 `database is locked` 时本轮静默跳过，下一轮再试（不视为任务失败）。

## 5. 心跳与崩溃恢复

| 参数 | 值 | 含义 |
| --- | --- | --- |
| 心跳间隔 | 10s | worker 刷新 `service_heartbeats` 与本实例 running 任务的 `heartbeat_at` |
| 失联阈值 | 90s | 超过视为认领它的 worker 已死（任务重置 + supervisor 判不健康） |
| 清扫间隔 | 30s | 运行期周期性把失联的 running 任务重置 |
| 任务看门狗 | 1800s | `updated_at` 超过该秒数没更新 → worker 取消任务、标 failed、释放槽位（`TASK_STALL_TIMEOUT_SECONDS`，0=关闭） |

重置规则（`_reset_stale_tasks`）：

- `retry_count + 1`；
- 未耗尽 `max_retries` → 回 `pending` 重新排队；
- 已耗尽 → 直接 `failed`，错误写「进程异常终止…」，避免「必崩任务」无限重启；
- 同时清理已死 worker 的服务心跳行。

> 为什么运行期也要清扫：只靠启动时清扫有漏洞——重启在 90 秒内完成时，旧任务心跳仍「新鲜」，会被跳过并永久卡在 running。
>
> **进程假死（进程活着、心跳停了）**：supervisor 读 `service_heartbeats` 的心跳年龄，超过
> `WORKER_HEARTBEAT_STALE_SECONDS`（默认 90s）判为不健康，连续 3 次后强制重启 worker（详见
> [加固说明](../ops/worker假死与任务队列加固-2026-11-02.md)）。worker 启动时还会把超过 2 小时
> 仍 `running` 的 `task_run_logs` 标记 failed，避免「运行记录」长期显示进行中。

## 6. 暂停 / 恢复 / 取消

### 6.1 取消

| 当前状态 | 行为 |
| --- | --- |
| `pending` | **物理删除**记录（`deleted=true`）；与认领竞态时用带状态条件的 DELETE 防误删 |
| `running` 且在可取消白名单 | 置 `cancelled`，执行器在下一个批次/文件/检查点自行停止；已产出结果保留 |
| `paused` 且在可暂停白名单 | 直接置 `cancelled`（暂停任务不占资源，无需先恢复） |
| 其它 | 400，记录不变 |

### 6.2 暂停与恢复

- 仅 `running` + 可暂停类型可暂停；执行器在下一个批次边界看到 `paused` 后保存进度返回；
- 恢复：
  - `tag_network_analyze` → 回到 `running`，保留 `last_stage` / `stage_state` 断点续算；
  - 其余可暂停类型 → 回到 `pending`，由 worker 重新认领，靠**幂等**跳过已完成部分：
    - 批量/组合分析：已有成功分析日志的素材跳过；
    - 质量审核：只处理 `quality_status == 'pending'`；
    - f2 导入：已下载文件 / 已入库素材按内容与平台 ID 判重跳过；
    - 向量回填：从 `done` 断点续算，已写入 LanceDB 的向量不重算。

### 6.3 删除记录

- `pending`：拒绝（要走取消，取消即删）；
- `running`：仅心跳超时（僵尸任务）可删，正常执行中拒绝；
- `paused` / 终态：可删。

## 7. 重试策略

执行器抛出不同错误，决定是否重试：

| 错误类型 | 判定 | 行为 |
| --- | --- | --- |
| `RecoverableTaskError` / 可恢复关键字 | 超时、无法连接 Ollama、Ollama 不可用/返回异常、请求过于频繁、`database is locked` | `retry_count+1`，回 `pending`，指数退避：第 1 次约 30s，第 2 次约 120s（上限 120s） |
| `PermanentTaskError` / 其它异常 | 图片损坏、文件不存在、参数错误 | 直接 `failed`，不重试 |

- 默认 `max_retries=2`；重试前会把 `progress` / `done` 归零，避免「100% 却排队中」；
- 用尽后写 `failed` + `error`，前端任务中心可看原因。

## 8. 进度与实时推送

- 执行器在每个检查点更新 `progress`（0~100）与 `done/total`；看不到细粒度进度时用「第 N/M 个」阶段文案；
- 事件契约（`services/task_events.py`）：

```json
{
  "type": "task_event",
  "event": "running | progress | success | failed | cancelled",
  "task_id": 123,
  "task_type": "batch_analyze",
  "status": "running",
  "progress": 42,
  "done": 420,
  "total": 1000,
  "error": null
}
```

- 广播**永不抛错**：worker 进程没有 WS、无连接、序列化失败都只记日志，不影响任务；
- 前端 `useTaskEvents` 断线自动重连，失败降级为轮询；任务列表把 `paused` 排最前。

## 8.1 运行台账与按天日志（2026-11-02）

**目的**：复盘批处理耗时/算力成本时不再依赖会被轮转覆盖的 `backend.log`。

### 8.1.1 运行台账表 `task_run_logs`

每次任务执行尝试一行（重试是独立行），由 worker 自动写入：

| 字段 | 内容 |
| --- | --- |
| `task_id` / `task_type` | 任务 id 与类型 |
| `attempt` | worker 认领时的 `retry_count` 快照（0=首次，1=第一次重试） |
| `started_at` / `finished_at` | 开始/结束（UTC naively 存，按项目时间约定） |
| `item_count` / `total_count` | 实际完成张数 / 任务计划张数 |
| `status` | running / success / failed / retry / cancelled / paused |
| `gpu_model` | `nvidia-smi` 探测一次并缓存；探测不到为 NULL（不猜） |
| `error` | 失败/重试原因（截断 2000 字） |

- 写入点：`app/worker.py` 的 `_start_run_log` / `_finish_run_log`，包裹 `_run_task` 全流程；
- 开始行独立提交：即使 handler 随后失败/回滚或进程崩溃，也能看出「这次执行开始过但没结束」；
- 不回溯历史任务：表从本功能上线后开始记录。
- 读取：`GET /api/tasks/{id}/runs`（任务管理页「运行记录」弹窗）；worker 启动时把超过 2 小时
  仍 `running` 的孤儿行标记 failed 并补 `finished_at`（进程崩溃/看门狗未收尾的兜底）。

### 8.1.3 `/api/tasks` 列表性能（2026-11-02 加固）

`task_queue.result` 是 JSON 大字段（单条最大 2.9 MB，历史数据合计 78.8 MB）。列表接口
`GET /api/tasks` **不再返回完整 result**：只回传 `substr(result, 1, 8192)` 能解析出的前缀
（小结果原样保留，供前端摘要），超长结果在列表里为 `null`，完整内容走
`GET /api/tasks/{id}`。实测 200 行响应从 **30.6 MB 降到约 0.16 MB**，前端 5 秒轮询不再拖慢页面。

### 8.1.2 按天日志 `logs/analyze-YYYY-MM-DD.log`

- worker 启动时在 root logger 上挂 `app/utils/daily_log.py::DailyFileHandler`；
- 按**本地日期**写 `logs/analyze-2026-08-22.log` 这类文件，跨天自动切换；
- 内容带 `%(asctime)s [%(levelname)s] %(name)s: ...`，任务开始/结束各一行（含 GPU/张数/耗时）；
- supervisor 的 `backend.log` 仍保留为服务 stdout 汇总，但**批处理审计以按天文件 + DB 台账为准**。

> 生效需要重启 backend/worker（本会话不自动执行启停脚本）。

## 9. 新增任务类型 checklist

按顺序改，漏一步就会出现「能创建但跑不起来」「前端没按钮」「互斥失效」：

1. **执行器**：新增 `backend/app/services/task_runners/<name>.py`
   - `create_<name>_task(db, ...) -> TaskQueue`：写 `type`、`status="pending"`、`total`、输入载荷到 `result`；
   - `async def execute_<name>(db: AsyncSession, task: TaskQueue) -> None`：循环里检查取消/暂停，写进度与结果，异常按可恢复/永久分类。
2. **注册**：在 `services/task_runner.py` re-export，并把 `execute_<name>` 加进 `TASK_HANDLERS`。
3. **资源互斥**：会大量占 GPU（CLIP/VLM/人脸/出图）或整批打满 CPU 的，加进 `worker.py` 的 `GPU_EXCLUSIVE_TASK_TYPES`。
4. **可暂停 / 可取消**：需要的话同时改
   - `routers/tasks.py` 的 `_PAUSABLE_RUNNING_TYPES` / `_CANCELABLE_RUNNING_TYPES`；
   - `web/src/utils/taskPresentation.ts` 的同名常量（两侧有用例锁定，只改一边会红）。
5. **前端文案**：`web/src/utils/taskPresentation.ts` 的类型中文/颜色/图标；移动端 `mobile/constants/labels.ts`。
6. **创建入口**：在对应业务路由里调用 `create_xxx_task`；破坏性操作记得挂 `Depends(require_api_key)`。
7. **测试**：至少覆盖创建、执行成功、可恢复重试、暂停/恢复或取消（若支持）、前端按钮显隐。

## 10. 排障

| 现象 | 排查顺序 |
| --- | --- |
| 任务一直 `pending` | worker 是否启动（`python -m app.worker`）；`worker_concurrency` 是否被长任务占满；是否在重试退避期内（看 `next_retry_at`） |
| 任务卡在 `running` | 先看 `/api/health/services` 的 worker 状态：心跳超时 = worker 假死，等 supervisor 自动重启（`supervisor.log` 有「worker 心跳 Ns 未更新，强制重启」）；心跳正常但 handler 卡死 → 任务看门狗会在 `TASK_STALL_TIMEOUT_SECONDS`（默认 30 分钟）后取消并标 failed |
| worker「进程在但什么都不动」 | 看 `logs/service_status.json` 里 worker 的 `heartbeat_age_seconds`；心跳年龄持续增大 = 事件循环卡死，supervisor 应在 ~105s 内重启；若超过 2 分钟没重启，检查 supervisor 是否在跑、任务库路径是否可读 |
| 页面上的任务列表很卡 | `GET /api/tasks?size=200` 的响应大小；列表已只回传 result 前缀（>8KB 结果置 null），若仍慢看是否有新增的大字段任务类型 |
| 别的任务都停了 | 是否有 GPU 互斥任务在跑（组内串行）；取消卡住的那个 |
| 暂停了但还在跑 | 执行器只在批次边界检查 `paused`，等当前批次结束；确认该类型在可暂停白名单 |
| 恢复后从头跑 | 该执行器没有幂等跳过逻辑；检查是否只处理剩余项 |
| 反复失败后 `failed` | 看 `error` 与 `retry_count`；可恢复错误会重试 2 次（30s/120s） |
| 无法删除任务 | `pending` 要走取消；`running` 只有心跳超时的僵尸任务可删 |
| 迁移后列不存在 | worker 不跑 Alembic；先启动 API 让它 `upgrade head` |
