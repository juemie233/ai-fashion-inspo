# 搜索与向量检索

> **状态**：现行（2026-11-15 按代码校对）。真源：`backend/app/routers/search.py`（检索接口）、
> `services/vector/`（向量库、嵌入、相似度）、`services/near_duplicate_service.py`（近似重复）。
> 概念铺垫见 [CLIP编码说明](CLIP编码说明.md)；本文只讲**接口怎么用、结果怎么排、什么时候会降级**。

## 1. 三条独立路径，别混着理解

| 路径 | 靠什么匹配 | 入口 |
| --- | --- | --- |
| 结构化筛选 | 标签 / 来源 / 评分 / 时间 / 状态 | `GET /api/search` |
| 语义与以图搜图 | 向量近邻（文本向量 / 图像向量） | `POST /api/search/vector` |
| 相似素材 | 图像向量 + 标签重合度加权 | `GET /api/search/similar/{id}` |

另有两条辅助：`GET /api/search/suggestions`（输入联想）、`GET /api/search/tag-cooccurrence`（标签共现）。

**所有检索一律排除垃圾桶素材**（`deleted_at IS NULL`），垃圾桶只能在 `GET /api/inspirations/trash` 里看到。

## 2. 结构化搜索（`GET /api/search`）

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `keyword` | 文本 | 关键词（标题/描述/作者等，走库内匹配） |
| `include_tags` / `exclude_tags` | 标签 id 列表 | 必须含 / 必须不含 |
| `combine` | `AND`（默认）/ `OR` | 只作用于 `include_tags` 之间 |
| `dominant_color` | 颜色值 | 主色调筛选 |
| `source_type` | 见来源映射 | `manual_upload` / `scraper` / `xiaohongshu` / … |
| `media_type` | `image` / `video` | |
| `is_favorite` | bool | 仅收藏 / 全部 |
| `analysis_status` | `done` / `pending` / `error` | AI 分析状态 |
| `tag_status` | `tagged` / `untagged` | 有无标签 |
| `date_from` / `date_to` | ISO 日期 | 按入库时间 |
| `rating_min` | 1~5 | 评分下限（0 = 未评分不计入） |
| `page` / `size` | 1 / 默认 50，上限 200 | 与全站分页约定一致 |

**`sort` 的七个取值**（语义差别容易踩坑）：

| 值 | 排序 | 备注 |
| --- | --- | --- |
| `newest`（默认） | 入库时间倒序 | |
| `oldest` | 入库时间正序 | |
| `tag_count` | 标签数倒序 | 标签多的靠前 |
| `match_score` | 匹配度倒序 | 向量模式下的相似度 |
| `rating` | 评分倒序 | 未评分当作 0，会排在最后 |
| `rating_asc` | 评分正序 | **仅已评分素材**参与 |
| `unrated_first` | 未评分优先 | 用于「补评分」场景 |

> `rating_asc` 与 `unrated_first` 是 2026-11-12 评分功能加的，分页稳定性由后端保证
> （同分时按 id 兜底），不要在 SQL 之外另排。

## 3. 向量检索（`POST /api/search/vector`）

**两个向量空间，物理隔离**：

| 空间 | 表 | 维度 | 生成方式 |
| --- | --- | --- | --- |
| 文本 | LanceDB `text` | 384 | Ollama 文本嵌入（`all-minilm`） |
| 图像 | LanceDB `image` | 512 | 本地 CLIP `clip-ViT-B-32`（首次使用自动下载约 600MB） |

请求约束：

- **`text` 与 `file` 二选一**，都给或都不给都返回 400。
- 文本检索：`text` → 文本向量 → 在 `text` 表做近邻。
- 以图搜图：上传临时图片 → 图像向量 → 在 `image` 表做近邻 → 按 `inspiration_id` 回查在用素材
  （已进垃圾桶的命中会被过滤掉）。
- `top_k` 由请求控制；结果带相似度，前端展示为「92% 相似」这类角标。

**依赖与降级**：`vector_store.is_lancedb_available()` 为假时接口直接报错（不会静默返回空），
提示 `pip install lancedb`。向量表未回填时命中会很少——用向量回填任务补齐，不要临时在请求里算。

`GET /api/search/vector/status` 返回两表的覆盖情况，用于判断「搜不到」是没数据还是没匹配。

## 4. 相似素材（`GET /api/search/similar/{id}`）

不是纯向量近邻，而是**混合打分**：

```
score = vector_similarity_weight × 视觉相似度      (默认 0.6)
      + vector_tag_weight        × 标签重合度      (默认 0.4)

标签重合度 = 共同标签数 / 源素材标签数
```

- 先取 `top_k × 2` 条视觉近邻再重排（留出标签加权翻盘的空间）。
- 视觉结果不足 `top_k` 时，**用纯标签匹配补足**；返回里 `match_source` 标注
  `visual` / `hybrid` / `tag`，前端据此提示「仅标签相似」。
- 源素材已在垃圾桶时无法作为查询源（先恢复）。

## 5. 视觉近似重复（`POST /api/admin/near-duplicates`）

与「精确重复」（SHA-256 相同）互补：识别**字节不同但视觉相似**的图（不同压缩/缩放/水印）。

| 项 | 值 |
| --- | --- |
| 哈希 | 感知哈希（pHash，768 位），缓存在 `inspirations.phash` |
| 判定 | 汉明距离 ≤ `threshold`，默认 **32** |
| 分组 | 分带倒排索引（鸽巢原理切带，阈值越大桶越宽），实测 2.2 万张全库 ≈ 1.7 秒 |
| 抽样 | 默认 `limit=1000`，每次随机抽样覆盖不同素材 |
| 副作用 | **只读**，只返回候选分组，删除由人工在前端并排预览后确认 |

**为什么不在请求里补算哈希**：补 300 张实测要 34 秒，超过前端 30 秒上限，用户会看到「扫描失败」
而后端其实跑完了。返回里的 `missing` / `cache_complete` 说明缓存缺口；缺口用
`POST /api/admin/phash-backfill` 起后台任务补齐（`force=true` 整库重算，哈希来源变更后才需要）。
素材被替换（如手机图剪裁）时 `phash` 会被置空，下次扫描懒重算。

## 6. 缓存与性能

| 场景 | 表现 | 说明 |
| --- | --- | --- |
| 结构化搜索 | 毫秒级 | 有索引（来源/时间/评分/标签关联表） |
| 向量检索 | 数十毫秒 | LanceDB 近邻；首次加载 CLIP 模型有一次性开销 |
| 相似素材 | 数十毫秒 | 向量 + 标签重排 |
| 近似重复扫描 | ≈1.7 秒 / 2.2 万张 | 只读缓存；冷缓存时结果不完整但不报错 |
| 详情页首屏 | 可能卡顿 | CLIP 在首次编码图片时占 CPU，见 [CLIP编码说明](CLIP编码说明.md) §5 |

## 7. 常见坑

1. **以为「搜索」能搜到垃圾桶**：不能。垃圾桶素材不进任何检索结果（含相似推荐）。
2. **用 `rating` 排序找「未评分」**：未评分按 0 排最后；要补评分用 `unrated_first`。
3. **以图搜图拿垃圾桶素材当查询图**：先把素材恢复，或直接上传原图。
4. **近似重复扫描报「不完整」就以为坏了**：那是缓存未就绪，跑一次 phash 回填任务再扫。
5. **改了 CLIP 模型或文本嵌入模型**：两个向量表必须整表重建（维度/空间都变了），只回填增量会得到乱序结果。
