## 1. 人脸能力与人物关联（机制说明）

> 原文件：`features/人脸识别与人物关联.md`｜原题：人脸识别与人物关联说明

> **状态**：现行｜编写日期 2026-11-01｜依据 `face-service/`、`backend/app/services/face_*.py`、`blogger_face.py`、`model_face.py`、`models/face.py`
> **一句话**：主后端通过 HTTP 调用独立的人脸子服务提取 512 维特征，为博主 / 模特建立特征库；素材人脸与特征库做余弦匹配，批量结果先进入「待审核候选」，人工确认后才写人物关联。
> **隐私边界**：人脸特征属生物特征数据，只存在本机数据库，不随素材导出、不上传外部服务。

---

### 1. 架构

```text
主后端（Python 3.12，FastAPI，18888）
   │  HTTP（FACE_SERVICE_URL，默认 http://127.0.0.1:18889）
   ▼
人脸识别子服务（Python 3.10 + onnxruntime，18889）
   │  buffalo_l：RetinaFace 检测 + ArcFace 识别（512 维）
   ▼
主库：blogger_face_embeddings / model_face_embeddings / inspiration_face_detections
子服务单独维护 face_service.db（注册库，与主库隔离）
```

**为什么拆子服务**：insightface 不支持 Python 3.12，而主后端是 3.12；子服务用独立 3.10 环境，主后端保持不动。子服务**不依赖 insightface 包**，直接用 onnxruntime 加载 buffalo_l 的 onnx 模型，推理结果与 insightface 原生一致。

启动方式与模型准备见 `face-service/README.md`；主后端启动不会自动拉起子服务，`scripts/ops/restart.sh` 会单独处理。

### 2. 数据模型

| 表 | 内容 |
| --- | --- |
| `bloggers` / `models` | 人物拆成两张独立表；各自带 `face_match_threshold`（可空，空则用全局兜底） |
| `blogger_face_embeddings` | 一位博主一条平均池化 512 维特征（float32 BLOB） |
| `model_face_embeddings` | 一位模特一条平均池化特征，来源为写真照片组 |
| `inspiration_face_detections` | 素材图内每张人脸一条：`embedding`、`bbox`、`det_score`、`matched_blogger_id` / `matched_model_id`、`confidence`、`match_status`、`match_excluded` |

#### 2.1 match_status 语义（关键）

| 值 | 含义 | 素材详情页 |
| --- | --- | --- |
| `NULL` | 单素材「检测并匹配」或手动指派的历史结果 | **展示** |
| `pending` | **仅**批量匹配产出的「已匹配到具体人物」的 AI 候选，未经人工审核 | **不展示**（避免「没确认却显示已关联」） |
| `confirmed` | 人工确认，已写入人物关联表 | 展示 |

`match_excluded=true`：用户驳回「不是这个人」，该人脸不再参与后续全库匹配、也不再出现在候选区。

> 一张人脸至多命中一个博主或一个模特（两者特征在同一空间，合并取最高分）。
>
> **未命中（相似度不足）= `match_status=NULL`，不是 `pending`**。2026-11-01 修正前批量匹配把 16,823 条未命中记录也写成 pending，导致「待审候选」被放大 20 倍、按人物聚合出现大量空组，且一旦批量驳回会被 `match_excluded` 永久排除；该语义已修并回填（方案见 人脸注册与候选审核方案（本文第 2 节） §14）。

### 3. 特征注册

#### 3.1 博主

- 两种来源可**合计 1~5 张**：上传正脸照片，或从该博主已关联的素材中选图；
- 多张照片分别提取特征后**平均池化**成一条 512 维特征；
- 支持重新注册（覆盖）与注销；
- 视频素材用导入时生成的首帧缩略图送检；webp 等格式统一重编码为 JPEG（子服务只吃 JPG/PNG）；
- 注册时按人脸质量过滤：`det_score` 与「人脸宽度占画面比例」都要达标。

接口：`POST /api/bloggers/{id}/face`、`GET .../face`、`DELETE .../face`。

#### 3.2 模特

- 数据源是模特写真照片组（`model_photo_sets` / `model_photos`），不是素材关联；
- 写真组可能几十上百张，**按 `det_score` 取 Top-K 最高质量人脸**再平均池化（侧脸 / 远景 / 闭眼会稀释特征）；
- 重复注册即覆盖。

接口：`POST /api/models/{id}/face`、`GET .../face`。

#### 3.3 按人阈值

- 全局兜底 `FACE_MATCH_THRESHOLD`（默认 0.5，建议 0.45~0.55 按样本调）；
- 人物表可单独设 `face_match_threshold`；
- 匹配报告会区分「兜底阈值」与「另 N 人按各自阈值判定」，不再把兜底值误读成唯一阈值。

### 4. 匹配流程

#### 4.1 单素材（同步语义）

素材详情页「检测并匹配」：检测图内人脸 → 逐张与合并特征库比对 → 高于阈值即关联。结果 `match_status=NULL`，直接展示，可手动改绑 / 解除。

#### 4.2 批量扫描（待审核语义）

`POST /api/face-scan/start` 创建 `face_scan` 任务（可取消）：

1. 遍历素材（视频取前 `FACE_SCAN_VIDEO_MAX_FRAMES` 帧，默认 3）；
2. 批量送子服务 `embed-batch`（32 张/批）；
3. 用 numpy **矩阵乘**一次性完成「所有人脸 × 全部人物特征」比对（`face_match.py`），不再逐条 Python 循环；
4. **只有高于阈值、匹配到具体人物的结果**写 `match_status=pending`，进入扫描审核页；未命中的保持 `NULL`；
5. 人工确认 → `POST /api/face-scan/confirm` 写人物关联并置 `confirmed`；驳回 → `match_excluded=true`。

> 为什么批量结果不直接生效：人脸相似度有误判，自动写关联会造成「素材详情显示错人」。确认动作是人审关口。

#### 4.3 未匹配人脸聚类

`POST /api/face-scan/cluster/run` 创建 `face_cluster` 任务：

- 对 `matched_blogger_id` / `matched_model_id` 为空、且未被驳回的人脸做聚类，产出「疑似同一人」的组；
- **主路径 hnswlib**：ANN 查 Top-K 近邻，只在近邻间建边，O(n log n)；
- 未装 hnswlib 时回退 numpy 分块矩阵（O(n²)，超过上限直接报错提示安装）；
- **平均链接合并**（组间平均相似度达标才合并），不是并查集传递闭包；
- 实测教训：0.5 阈值 + 传递闭包会把 4068 张脸链成一个 2446 张的巨型组（组内中位相似度仅 0.227）；现建边阈值 `0.6`、合并门槛 `0.40`，并把阈值提高到 0.65 后巨型组碎成 1170 块；
- 过滤非 512 维脏向量（真实库曾出现 388 条异常维度）。

查看：`GET /api/face-scan/cluster/groups`、`.../groups/{id}/detections`；博主侧候选：`GET /api/bloggers/{id}/face-candidates`。
审核动作：整组指派（现有 confirm）、`POST .../cluster/groups/{id}/ignore`（整组永久忽略）、`POST .../cluster/groups/{id}/create-person`（新建人物并注册后整组确认）。

#### 4.4 批量注册（未注册博主补特征库）

`POST /api/face-scan/register-plan`（只读）→ 对「有素材但未注册人脸」的博主，按「单脸素材里未匹配人脸 ≥3 次」聚类，返回候选簇（最多 5 组/人）、建议注册素材与封面；`POST /api/face-scan/register-batch` 串行注册（≤20 位/批），素材必须属于该博主；子服务不可用时整批快速失败。
前端在扫描页「批量注册」Tab 操作：采用 / 换一组 / 跳过 / 采用当前页 20 位。**不自动注册**：候选簇可能混入插画/遮挡脸，需人工看封面确认。

> 完整方案、阶段与验收指标见 人脸注册与候选审核方案（本文第 2 节）。

---

### 5. 子服务离线与降级

- 子服务未部署或不可达时，人脸相关按钮**禁用并给出可操作提示**（不是静默失败）；
- 前端提示条带「重新检测」，离线期间每 15 秒自动复检；启动子服务后不必刷新页面；
- 主后端调用抛 `FaceServiceUnavailableError`，调用方按「功能不可用」处理，不影响素材浏览。

### 6. 关键配置

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `FACE_SERVICE_URL` | `http://127.0.0.1:18889` | 子服务地址；留空视为未部署 |
| `FACE_SERVICE_TIMEOUT` | 30 秒 | 单次调用超时 |
| `FACE_MATCH_THRESHOLD` | 0.5 | 全局匹配余弦阈值 |
| `FACE_SCAN_VIDEO_MAX_FRAMES` | 3 | 每个视频取前 N 帧送检 |

### 8. 排障

| 现象 | 原因 / 处理 |
| --- | --- |
| 人脸按钮全灰 | 子服务未启动 / 模型缺失 / CUDA 运行时未加载；`curl 127.0.0.1:18889/health`，看 `logs/face-service.log` |
| 注册报「无法解析图片」 | 送了视频或 webp；已由 `face_image.normalize_image` 处理，检查是否绕过了该函数 |
| 注册成功但匹配不到 | 阈值偏高 / 照片侧脸多 / 人脸占比太小；看匹配报告里的阈值与 `det_score` |
| 批量扫描结果在详情页看不到 | 候选是 `pending`，需在扫描审核页确认；这是有意设计 |
| 驳回后仍反复出现 | 检查 `match_excluded` 是否写入；全库匹配会排除被驳回记录 |
| 聚类出现巨型组 | 阈值过低或走了并查集直连；确认使用平均链接与 `EDGE_THRESHOLD=0.6` |
| 聚类报维度错误 | 库内有非 512 维脏向量；聚类入口已过滤，若仍报错查 `inspiration_face_detections.embedding` 长度 |
| 扫描很慢 | 两侧并发未对齐；子服务 `FACE_EMBED_WORKERS` 与主后端 `EMBED_CONCURRENCY` 同时调到 8 左右 |

## 2. 人脸注册与候选审核（方案与实施）

> 原文件：`features/人脸注册与候选审核方案.md`｜原题：人脸注册与候选审核方案

> **状态**：实施中（阶段 0 已完成；阶段 1/2 代码已落地，待执行注册与人工审核）｜编写日期 2026-11-01
> **依据**：`backend/app/services/face_match.py`、`routers/face_scan.py`、`services/person/face_candidates.py`、`web/src/views/FaceScanView.vue`，以及当前库（30,282 条素材）的只读统计
> **一句话**：**先修正 `pending` 语义，再批量注册 484 位博主，重跑匹配，最后审核候选与未匹配聚类**；顺序不能反。

---

### 0. 结论

| 阶段 | 做什么 | 为什么必须按这个顺序 |
| --- | --- | --- |
| **0** | 修正 `pending` 语义 + 回填 16,823 条无匹配记录 | 否则“批量驳回”会永久排除这些脸，注册完也再匹配不到 |
| **1** | 批量注册 484 位有素材但未注册的博主 | 未匹配的 21,479 张脸里，很大一部分就是他们 |
| **1.5** | 重跑全库匹配（scope=bloggers） | 把新注册的脸转成候选，是收益最大的一步 |
| **2** | 审核真实候选（当前 871 条，重跑后会增加） | 数据量小，可逐人核对 |
| **3** | 未匹配人脸聚类审核（21,479 条） | 放在最后，避免审一堆“其实是未注册博主”的脸 |

**不要直接开始审核 1.7 万条 pending**：其中 16,823 条不是候选，是语义错误产生的噪声。

### 2. 根因：`pending` 被当成“匹配过”而不是“有候选”

`services/face_match.py:285-313`：

```python
if (
    det.matched_blogger_id != new_blogger
    or det.matched_model_id != new_model
    or det.confidence != new_conf
    or det.match_status != "pending"
):
    changes.append({..., "matched_blogger_id": new_blogger, ...})
...
await db.execute(update(InspirationFaceDetection),
    [{**c, "match_status": "pending"} for c in changes])
```

当 `result is None`（没有任何人物超过阈值）时，`new_blogger` / `new_model` 都是 `None`，但这行**仍然被写入 `pending`**。于是：

1. **统计失真**：pending 从 871 被放大到 17,694；
2. **审核页分组混乱**：`pending` 结果按人物聚合，16,823 条没有人物，无法审核；
3. **最危险**：`POST /api/face-scan/confirm` 的 `reject` 会把 `match_excluded` 置为 `True`——该人脸**永久退出后续匹配**。一旦对这批无匹配记录批量驳回，等博主注册完再跑匹配，这些脸永远不会被捞起。

---

### 3. 目标与非目标

#### 3.1 目标

1. `pending` 只表示“有具体人物的 AI 候选”；
2. 把有素材博主的注册覆盖率从 4.3% 提到尽可能高（取决于有稳定人脸的博主数）；
3. 审核完真实候选，误确认率可抽检；
4. 通过注册 + 重匹配，让未匹配人脸数量显著下降；
5. 剩余未匹配人脸按“疑似同一人”聚类，支持整组指派 / 新建人物 / 忽略。

#### 3.2 非目标

- **不自动注册**：注册错人会让全库持续误判，代价高于“没注册”；
- **不追求 484 位全部注册**：全身街拍、合影、路人、无正脸素材注定无法注册；
- **不做人脸特征导出/外部比对**：生物特征只在本机库内使用；
- **不借机做 LoRA / 跨平台去重**：与本方案无关。

### 4. 阶段 0：修正 `pending` 语义

#### 4.1 代码修改

`services/face_match.py`：

- 只有 `result is not None` 才在更新载荷里写 `match_status = "pending"`；
- `result is None` 时写 `match_status = None`（未匹配是“普通检测”，不是候选）；
- 只更新真正变化的行（现有 diff 逻辑保留）；
- 已确认（`confirmed`）与人工排除（`match_excluded`）记录继续跳过。

#### 4.2 数据回填

先备份数据库（放 `backend/storage/_db_backups/`），再执行：

```sql
UPDATE inspiration_face_detections
SET match_status = NULL
WHERE match_status = 'pending'
  AND matched_blogger_id IS NULL
  AND matched_model_id IS NULL;
```

> 回填只改状态，不动 `matched_*`、`confidence`、`match_excluded`。
> 执行后 `pending` 应为 **871** 左右；`match_excluded` 数量应保持 **1,499** 不变。

#### 4.3 测试

- 单测：批量匹配中，未超过阈值的人脸结果 `match_status IS NULL`；
- 单测：有匹配的人脸仍为 `pending`；
- 单测：`confirmed` 记录不被重跑覆盖；
- 回归：审核页 pending 总数与“按人物聚合”的总和一致。

#### 4.4 UI 文案

- pending 区标题改为「AI 候选（已匹配到人物）」；
- 未匹配区说明「未超过阈值，可指派或参与聚类」；
- 驳回按钮提示文案写明「永久排除，后续匹配不再出现」。

**验收**：`pending` ≈ 871；`match_excluded` 不增加；回填前后有备份与审计记录。

### 5. 阶段 1：批量注册

#### 5.1 候选来源（复用现有能力）

`services/person/face_candidates.py` 已经提供了核心判断：

| 来源 | 逻辑 | 现状 |
| --- | --- | --- |
| 已确认/历史匹配 | 该博主素材里已匹配到 TA 的检测，按 `det_score` 排序，最多 12 张 | 只覆盖已注册的 22~30 位 |
| 未匹配人脸簇 | 该博主素材里**单脸素材**中反复出现 ≥3 次的未匹配人脸，聚成簇，每簇给封面、成员数、平均置信度、前 3 张素材 | 文档实测 **141 位博主**满足；这是放量的主路径 |

**候选规则**（沿用现有常量）：

- 只用单脸素材（多脸无法判断哪张是本人）；
- 单簇成员 ≥3、≤50；
- `det_score ≥ 0.5`；
- 每位最多取 `det_score` 最高的 3 张注册。

#### 5.2 批量注册工作台

位置：`FaceScanView` 新增「批量注册」Tab（或 `PersonView` 的批量操作入口）。

列表按「簇成员数 × 平均 det_score」排序，每行展示：

```text
[头像] 博主名（素材 342 张）
       候选：簇 A 出现 18 次 · 平均置信度 0.71
       [封面1][封面2][封面3]   [采用] [换一组] [跳过]
```

操作：

- **采用**：调 `POST /api/bloggers/{id}/face`（现有接口，传 `inspiration_ids`）；
- **换一组**：切到下一个候选簇；
- **跳过**：本轮隐藏，不写库；
- **无候选**：显示「素材里没有稳定人脸」，不强行注册。

批量操作：

- 「采用当前页（20 位）」：只对已有建议素材的博主执行；
- 执行后逐行显示结果（成功 / 无脸 / 子服务不可用）；
- 失败项保留，可重试。

#### 5.3 接口设计

##### `POST /api/face-scan/register-plan`（只读）

请求：

```json
{ "limit": 200, "min_cluster_size": 3, "min_det_score": 0.5, "only_with_candidates": true }
```

响应：

```json
{
  "items": [
    {
      "person_type": "blogger",
      "person_id": 192,
      "name": "示例博主",
      "inspiration_count": 342,
      "registered": false,
      "clusters": [
        { "size": 18, "avg_det_score": 0.71,
          "suggested_inspiration_ids": ["…","…","…"],
          "cover_detection_ids": [1,2,3] }
      ],
      "skip_reason": null
    }
  ],
  "summary": { "total": 484, "with_candidates": 141, "no_candidates": 343 }
}
```

- 不写库，供用户先看规模与质量；
- 排序、分页在服务端完成，避免前端拉 484 位的全量候选。

##### `POST /api/face-scan/register-batch`

请求：

```json
{
  "items": [
    { "person_type": "blogger", "person_id": 192,
      "inspiration_ids": ["…","…","…"] }
  ]
}
```

响应：逐条 `{person_id, ok, face_count, error}`。

- 服务端串行调用现有 `register_blogger_face`（每位 1–5 张，内部已做平均池化）；
- 一次最多 20 位，由前端分批循环——**不新增任务类型**，避免改动 `TASK_HANDLERS`、暂停/取消白名单、前端文案三处；
- 子服务不可用时整批快速失败，返回可读原因，不逐位超时。

#### 5.4 执行流程

1. 启动 face-service（18889），审核页状态条应显示可用；
2. 先拉 register-plan，确认 `with_candidates` 规模；
3. 按页采用；每批 20 位；
4. 记录本轮结果：成功 N 位、无脸 M 位、失败 K 位；
5. 失败项单独重试。

#### 5.5 注册后重跑匹配

`POST /api/face-match/run`，`scope=bloggers`。

- 这一步把新注册博主的特征加入矩阵，未匹配人脸转成候选；
- 跑完后重新统计 `pending` 与未匹配数；
- **不要**在重跑前审核低置信度候选，否则会基于旧特征库做判断。

#### 5.6 验收

- 注册覆盖：22 → 尽量接近 `with_candidates + 已注册`（预期 140~160，具体取决于候选质量）；
- 每位注册后 `GET /api/bloggers/{id}/face` 返回已注册且特征维度 512；
- 重跑匹配后，未匹配人脸数量较 21,479 明显下降（记录前后值）；
- 抽检 20 位注册结果：注册素材确实属于本人。

### 7. 阶段 3：未匹配人脸聚类审核

前置：阶段 1.5 已重跑匹配。

#### 7.1 流程

1. 启动 `face_cluster` 任务（hnswlib 主路径，建边 0.6、平均链接）；
2. 按簇大小排序，先审 ≥10 次的组（大概率是真博主）；
3. 每组展示代表脸、成员数、来源素材抽样；
4. 动作：
   - **指派已有博主/模特**（现有 `confirm` 接口支持整组未匹配人脸）；
   - **新建人物并注册**（先建博主，再用组内最高质量 3 张注册）；
   - **整组忽略**（`match_excluded`，提示永久）；
5. 审完的组不再参与后续聚类。

#### 7.2 验收

- 未匹配人脸中，属于已有人物的被尽量指派；
- 新建人物数量与来源可追溯；
- 簇内明显混入不同人的组被拆开或忽略。

### 10. 风险与回滚

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 注册错人 | 全库匹配持续误判，代价高于不注册 | 人工确认 + 展示来源素材；不自动注册 |
| 批量驳回无匹配记录 | 人脸永久退出匹配 | **阶段 0 必须先做**；驳回弹窗写明 |
| 子服务离线 | 注册/扫描全部失败 | 先看 `/api/face-scan/service-status`；离线时禁用动作 |
| 重匹配耗时/抢占资源 | 与 Ollama 任务争 GPU | `face_match` 已在重负载互斥组；安排空闲时段 |
| 候选质量差 | 注册后仍匹配不到 | 以“重跑后未匹配下降”为验收，而不是注册数 |
| 生物特征合规 | 隐私风险 | 只存本机库、不导出、不进分享/备份以外位置 |

**回滚**：

- 阶段 0 回填前备份 DB（`_db_backups`），可用备份恢复；
- 注册是覆盖式（重新注册即覆盖），错误注册可用 `DELETE /api/bloggers/{id}/face` 注销；
- 驳回是永久操作，不提供批量回滚；执行前先小批量验证。
