# 素材生命周期与垃圾桶（软删除）

> **状态**：现行（2026-11-15 按代码校对）。真源：`backend/app/services/inspiration_state.py`（状态机）、
> `inspiration_trash.py`（移入/恢复/清空）、`schemas/inspiration.py`（原因枚举）。
> 这是**核心链路**：改它必须跑 `backend/tests/` 里与垃圾桶相关的用例，并按 CLAUDE.md
> 「链路走查约定」从 router → service → worker → 前端走一遍。

## 1. 一句话

素材只有两个状态：**在用**（`deleted_at IS NULL`）与**垃圾桶**（软删除）。进垃圾桶不删文件、不删向量，
只把「三字段」一起写上；只有「清空垃圾桶」才是物理删除。

## 2. 状态与三字段

| 字段 | 类型 | 在用 | 垃圾桶 | 语义 |
| --- | --- | --- | --- | --- |
| `deleted_at` | datetime | `NULL` | 移入时间（naive UTC） | 状态本身，**唯一判定依据** |
| `trash_reason` | str(32) | `NULL` | 见 §3 枚举 | **为什么删** |
| `trash_source` | str(16) | `NULL` | `manual` / `auto` | **谁移进来的** |

> 三字段**同真同假**。任何一条路径只写其中两个，都会留下「已删除但没有原因」这类半状态，
> 后续按原因统计负样本、恢复、清空全部失真。

## 3. 删除原因（`TRASH_REASONS`）

| 值 | 谁触发 | 说明 |
| --- | --- | --- |
| `质量差` | 用户主动 / 质量审核自动 | 自动路径固定配 `trash_source=auto` |
| `重复` | 用户主动 | 与去重链路无关（去重是**入库时**拦截，不入库） |
| `不喜欢` | 用户主动 | 默认原因（未显式传且非 rejected 时） |
| `隐私` | 用户主动 | **不进负样本**（见 §6） |
| `其他` | 用户主动 | |
| `AI生成` | 系统自动（疑似 AI） | 语义是「系统判定的原因」，与 `trash_source=auto` 通常同时出现 |

原因推断规则（`_resolve_trash_reason`）：显式传入的合法值优先；否则 `quality_status == "rejected"` → `质量差`，
其余 → `不喜欢`。

## 4. 状态转移与校验

`_assert_trash_transition` 是内部防御——非法组合**直接抛 `ValueError`**，而不是静默写半状态：

| 转移 | 前置条件 | 不满足时 |
| --- | --- | --- |
| 在用 → 垃圾桶 | 必须不在垃圾桶；`reason ∈ TRASH_REASONS`；`source ∈ {manual, auto}` | 抛错：重复移入 / 原因缺失 / 来源非法 |
| 垃圾桶 → 在用 | 必须已在垃圾桶（`deleted_at` 非空） | 抛错：不在垃圾桶却要恢复 |

所有移入路径都要经 `_mark_trashed()`、所有恢复路径都要经 `_mark_restored()`——这两处是**三字段的唯一写入口**。
新增「自动清理」「审核后处理」等逻辑时不要自己赋值 `deleted_at`。

## 5. 各入口的实际行为

| 入口 | 端点 / 服务 | 文件 | 向量 | 备注 |
| --- | --- | --- | --- | --- |
| 单条移入 | `POST /api/inspirations/{id}/trash` | 移到 `storage/trash/` | 保留 | 可带 `reason`，默认推断 |
| 批量移入 | `POST /api/inspirations/batch-trash` | 同上（逐条） | 保留 | |
| 恢复 | `POST /api/inspirations/{id}/restore` | `restore_from_trash` 移回媒体目录；移不动则保留 `trash/` 路径 | 保留 | 先提交恢复标记、再移文件；移动失败只记日志不阻断；同时**解除来源 URL 墓碑** |
| 垃圾桶列表 | `GET /api/inspirations/trash` | — | — | 可按原因筛选 |
| 清空垃圾桶 | `DELETE /api/inspirations/trash`（`only_expired`） | **物理删除** + 清向量 | **删除** | 破坏性，写审计 |
| 批量删质量拒绝 | `DELETE /api/inspirations/quality-rejected` | 移入 `storage/trash/`（分批 100） | 保留 | `质量差` + `auto`，**不物理删** |
| 质量审核自动 | `services/ai_service/quality.py` | 同单条 | 保留 | 三字段同时写，`auto` |
| 单条硬删 | `DELETE /api/inspirations/{id}` | 物理删除 | 删除 | 破坏性、不可恢复，写审计 |

关键设计：**移入垃圾桶会写来源 URL 墓碑**（`seal_urls`），所以采集路径不会再次导入同一链接；
恢复时**解除墓碑**（与移入对称），否则恢复后的素材会永久被采集器拦截。
清空（`purge`）的顺序是「写墓碑 → 删库提交 → 写审计 → 删向量/文件」——**先保证库落库成功再动磁盘**。

## 6. 与负样本学习的关系（最容易搞错的一节）

垃圾桶素材是质量初筛器（`quality_learner`）的负样本来源，但有**两条排除**，分属不同维度：

| 排除项 | 判定字段 | 理由 |
| --- | --- | --- |
| `隐私` | `trash_reason`（`NEGATIVE_EXCLUDED_TRASH_REASONS`） | 隐私图不是「穿得不好」，学进去会让分类器把露肤/私密场景判成垃圾 |
| AI 生成图 | `is_ai_generated = True`（**不是** `trash_reason='AI生成'`） | 本地出图废片多是「构图不满意」，混进负样本会让初筛器误杀风格接近 AI 的优质素材 |

> 注意两者的关系：`trash_reason='AI生成'` 是「系统按原因归的类」，而是否排除看的是 `is_ai_generated` 标志。
> 改这一段之前先读 `services/quality_learner.py` 的注释，那里写了推翻结论的条件。

**清空垃圾桶 = 永久失去负样本**：负样本靠 `deleted_at IS NOT NULL` 现查现用，没有单独归档表。
所以「清空」是不可逆的训练数据损失，执行前要确认。

## 7. 唯一约束：删除后能否重新入库

| 场景 | 行为 |
| --- | --- |
| 平台 ID 已存在于**在用**素材 | 由部分唯一索引 `ix_inspirations_source_platform_id`（`WHERE deleted_at IS NULL`）拦截 |
| 平台 ID 只存在于**垃圾桶** | 允许重新入库（索引不覆盖垃圾桶行）——上传/导入路径可用 |
| 采集路径（同一条 URL） | 被 URL 墓碑拦截：进垃圾桶时 `seal_urls`，恢复时解除；所以「删了再采集」不会重复入库 |

因此软删除表上的唯一约束**必须**是部分唯一索引；改成普通 `UNIQUE` 会让「删除后重新上传」永久失败。

## 8. 保留期与清空策略

- `trash_retention_days` 默认 **0 = 不自动回收**（垃圾桶不会自己变少）。
- `purge_trash(only_expired=True)`：仅清理超过保留期的素材；保留期为 0 时该模式**不做任何事**，
  这是刻意的（避免「以为配了保留期其实全删」）。
- `purge_trash(only_expired=False)`：清空全部，物理删文件 + 删向量 + 写审计。

## 9. 不变量校验（巡检与测试用）

`verify_trash_invariants(db)` 扫全库返回违规清单（空列表 = 健康）：

| 规则 | 判定 | 典型成因 |
| --- | --- | --- |
| R1 | 在垃圾桶 ⇒ `trash_reason` 必须非空 | 新路径只写了 `deleted_at` |
| R2 | 在垃圾桶 ⇒ `trash_source` 必须非空 | 同上 |
| R3 | 在用 ⇒ 两个 trash 字段必须为空 | 恢复路径漏清字段 |

用法：测试里断言 `assert not await verify_trash_invariants(db)`；管理端完整性检查也调它。

## 10. 常见坑

1. **绕过状态机直接赋值**：最隐蔽。测试里 `verify_trash_invariants` 能兜住，但要跑。
2. **恢复后路径不复位**：文件还在 `storage/trash/` 但 `file_path` 指向原目录 → 缩略图 404。恢复逻辑会尝试移回，
   移不动时保留新路径；不要手改 `file_path`。
3. **把「清空垃圾桶」当「删除」用**：清空会连负样本一起删，且不可恢复；日常删除走 trash。
4. **按 `trash_reason='AI生成'` 统计 AI 占比**：应统计 `is_ai_generated`，两者会不一致。
5. **新增删除原因不判断负样本适配性**：不适配的要加进 `NEGATIVE_EXCLUDED_TRASH_REASONS`。
