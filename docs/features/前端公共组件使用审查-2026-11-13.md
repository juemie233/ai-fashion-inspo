# 前端公共组件使用审查（2026-11-13）

> 状态：审查报告（未改代码）
> 范围：Web 前端 `web/src/components` 的 161 个 Vue SFC、`components/common` 公共层、组件测试与引用关系；同时观察视图/组件边界、重复实现、组件体积、无障碍与死代码门禁。移动端组件不在本文范围（其设计令牌/裸字符串检查单独成立）。
> 方法：静态 import 关系扫描 + 组件行数统计 + API/Message/router/DOM/颜色用法检索 + 测试清单核对 + 重点组件人工阅读。
> 结论：**公共组件层「有，但偏薄」**。8 个 common 组件全部有生产引用，质量总体不错；但 161 个组件里只有 8 个 common，且 **108 个组件直接 import `@/api`（62 个真正调用 fetch/create/update/delete/apiClient）**、**80 个组件各自写 loading/empty/error**、**两个 hover preview 重复实现**、**8 个 common 里 7 个没有测试**。整体不是「组件坏了」，而是**组件边界与复用层没有收口**。

## 2. 主要问题

### P1-1 组件直接访问 API，组件边界被侵蚀

统计：

- **108 / 161 个组件** import 了 `@/api/`（其中一部分只是 `getFileUrl` 等 URL 工具，不一定是数据请求）；
- **62 个组件**直接使用 `apiClient` 或 `fetch*/create*/update*/delete*`，共 **251 处**；
- 典型：`SettingsPanel.vue` 18 处、`AdminNearDuplicates.vue` 15 处、`ModelListPanel.vue` 15 处、`ReviewPanel.vue` 10 处、`F2ImportCard.vue` 4 处；
- 53 个组件直接使用 `Message.success/error/warning`（303 处），把「业务结果提示」也放在组件里。

这与项目约定「视图只做编排，子组件按域放，props + emit 通信」有冲突。组件同时承担：

1. 取数（API）；
2. 业务校验/重试；
3. 成功失败提示；
4. 渲染。

**影响**：

- 组件无法在不 mock axios 的情况下单测；
- 同一业务逻辑在多个组件重复（如加载失败提示、重试、分页）；
- 修改接口/错误口径要改多个组件；
- 组件复用范围被 API 和路由绑定死。

**建议**：

- 区分三类组件，并把边界写进规范：
  - **presentational**（common/UI）：只接收 props、emit 事件，不 import API/router；
  - **domain container**：可以编排，但数据请求放 `composables/useXxx.ts`；
  - **page-level panel**：如 `GenerateParamForm`、`SettingsPanel` 这种接近页面的组件，单独标注为例外，并按视图标准拆分。
- 优先把 Top 10「API 调用最多」的组件抽 composable，不必一次性全改。

### P1-2 没有统一的异步三态组件

统计：**80 个组件**直接使用 `a-empty` / `a-spin` / `a-result`，共 **205 处**；`components/common` 里没有 `AsyncState` / `EmptyState` / `ErrorState`。

现状是每个页面自己拼：

```vue
<a-spin v-if="loading" />
<a-empty v-else-if="!items.length" />
<a-result v-else-if="error" status="error" />
```

**影响**：

- 空态/错误态/加载态样式和文案不一致；
- 错误经常被伪装成空态（与移动端此前的审查问题同源）；
- 每个页面重复写重试按钮和分页尾部。

**建议**：新增一个轻量 `AsyncState`（或 `DataState`）组件：

```vue
<AsyncState :loading="loading" :error="error" :empty="!items.length" @retry="load">
  <template #empty>...</template>
  <template #default>...</template>
</AsyncState>
```

不强制所有 80 个文件立刻迁移；先在新页面和 common 组件中使用，再逐步替换高重复页面。

### P1-3 两个 hover preview 重复实现

`HoverImagePreview.vue` 与 `ImageHoverPreview.vue` 都是「悬停显示大图」：

| 组件 | 实现 | API | 使用 |
| --- | --- | --- | --- |
| `HoverImagePreview` | 自写 Teleport + fixed 浮层 + 定时器 | `largeSrc` + 包裹内容 | 素材卡、ThumbCard、人脸 Tab |
| `ImageHoverPreview` | Arco `a-popover` | `src` + `previewSrc` + `imgClass` | 出图历史、入库弹窗 |

两者行为、延迟、定位、URL 处理都不同，名字也极易混淆。长期会出现「改了一个，另一个没改」的分叉。

**建议**：保留一个（优先 `HoverImagePreview` 的 Teleport 方案，行为可控），给 `ImageHoverPreview` 的两个使用方做适配；如果 Arco Popover 的定位更合适，则反过来合并，但**不要保留两套**。合并前补 fake timer 测试，避免定时器泄漏。

### P1-4 common 组件测试严重不足

8 个 common 里只有 `DensityImageGrid` 有测试；`StatusTag`、`StatCardGrid`、`HoverImagePreview`、`ImageHoverPreview`、`ThumbCard`、`LoadMoreBar`、`ErrorBoundary` 都没有。

其中风险最高的是：

- `ErrorBoundary`：根级白屏兜底，出错时如果自身再挂，用户只看到白屏；
- `StatusTag`：状态文案/颜色映射是任务中心的核心语义；
- `HoverImagePreview` / `ImageHoverPreview`：定时器 + Teleport/Popover，容易泄漏或残留；
- `ThumbCard`：上传/采集/垃圾桶多处在用，状态遮罩错了会误导「已上传/失败」。

**建议**：common 组件至少补：

- `StatusTag`：pending/running/success/completed/failed/cancelled/未知状态；
- `ErrorBoundary`：子组件抛错时渲染兜底 + 重试；
- `HoverImagePreview`：延迟显示、移出清除、卸载清理；
- `ThumbCard`：各状态/选中/hoverSrc；
- `StatCardGrid`：数字/字符串/空值/高亮；
- `LoadMoreBar`：加载/无更多。

## 3. 其他情况

### P2-1 状态语义分散

`StatusTag` 只处理「任务状态」，依赖 `utils/taskLabel`；但项目里还有：

- 质量状态（approved/pending/rejected）；
- 疑似 AI / AI 生成；
- 垃圾桶原因；
- 来源类型；
- 人脸匹配状态。

这些状态在 `InspirationCard`、`DetailInfoPanel`、`AdminTrash`、`PersonItemsSection`、`ReviewPanel` 等组件里各自用 `a-tag` + 颜色映射，容易出现「同一个状态在不同页面文案/颜色不一致」。建议：

- 要么扩展 `StatusTag` 支持 `kind`（task/quality/ai/trash/source）；
- 要么明确「任务状态用 StatusTag，其余用域内 `XxxStatusTag`」，并禁止在页面里手写颜色映射。

### P2-2 网格/卡片抽象有三套

- `MasonryGrid`：JS 断点列数 + `InspirationCard`，用于素材库/搜索/合集；
- `DensityImageGrid`：CSS `minmax` + 插槽单元 + 密度按钮，用于剪裁/采集/人物头像；
- `ThumbCard`：通用缩略图卡，配合 `DensityImageGrid` 或采集网格。

三者各有用途，但「密度」定义有两套（JS breakpoints 与 CSS minmax），列数/间距可能不一致。`InspirationCard`（491 行）还承担标签、质量徽标、评分、收藏、删除、相似度角标、打开方式等多种职责。

**建议**：

- 统一密度常量/断点（`DENSITY` 单一来源）；
- 在文档中写清「素材卡（InspirationCard）/ 缩略图卡（ThumbCard）/ 采集网格（DensityImageGrid）」的边界；
- 不要为了合并而合并，避免把 `ThumbCard` 变成第二个 500 行大组件。

### P2-3 无障碍覆盖不足

- 全仓组件里只有 **3 个组件**出现显式 `aria-label` / `role`（4 处）；
- `InspirationCard` 的卡片根是 `<div @click>`，没有 `role="button"` / `tabindex` / 键盘 Enter；
- 卡片上的收藏、删除、审核等 icon-only 按钮大多没有 `aria-label` 或可见文本；
- `MasonryGrid` 的键盘浏览没有专门处理。

Arco 组件自带语义，但自绘卡片/图标按钮不会自动获得。建议先做一轮「键盘 + 读屏」抽查，重点：素材卡、灯箱、批量操作栏、任务行。

### P2-4 颜色与视觉常量分散

`web/src/components` 中约有 **115 个文件、740 处**十六进制颜色（包含图表色板、状态色、遮罩色）。Web 没有移动端那种「禁止裸颜色」的令牌门禁。

这不是错误——ECharts 色板和临时状态色用 hex 很常见——但会导致：

- 深色/主题切换不彻底；
- 同一状态色在不同组件不一致；
- 改品牌色需要全局 grep。

建议先收敛 **状态色/遮罩色/图表主色** 三类到 CSS 变量或 `utils/colors.ts`，不要把 740 处一次性重写。

### P2-5 死代码门禁不覆盖 Vue 组件

`scripts/ci/check-web-dead-code.mjs` 用 `ts-prune` 查「未使用导出」；ts-prune 不解析 `.vue` SFC 的模板使用，因此**未使用的 Vue 组件不会被门禁拦住**。

本次静态扫描没有发现零引用组件（所有 `.vue` 至少被一个文件 import），但这是一次性结论，不是持续保障。建议增加一个轻量脚本：

- 扫描 `web/src/components/**/*.vue` 的 import 关系；
- 排除 `App.vue` / 动态 `<component :is>` 白名单；
- 对零引用组件报错或进基线。

### P2-6 router / window / Message 的耦合

- 13 个组件使用 `useRouter/useRoute`（34 处），组件内部直接跳详情/搜索/合集；
- 22 个组件直接使用 `window` / `document` / `localStorage`（75 处），其中 `ImageLightbox` 14 处、`TagGroupList` 8 处；
- 53 个组件直接 `Message.*`（303 处）。

这些不全是坏事（文件选择、滚动、灯箱键盘事件天然需要 DOM），但组件越接近「页面」，复用和测试成本越高。建议把「路由跳转/提示/本地存储」视为副作用，优先放在 composable 或父级编排层。

### 正面项

- 组件目录按域划分清晰，命名统一 PascalCase；
- 视图行数都在 800 以下，视图拆分约定执行得不错；
- `any` 使用很少（6 个文件、10 处）；
- `common` 组件全部被使用，没有死目录；
- `ThumbCard` 通过插槽把「卡片框架」和「业务覆盖层」分开，方向正确；
- `StatCardGrid`、`StatusTag` 已经在多个域复用，说明公共层有实际价值；
- 组件测试虽然覆盖不全，但出图域（Generate*）测试相对密集，说明复杂组件可以测。

## 5. 需要讨论/拍板的点

1. **`GenerateParamForm` / `SettingsPanel` 这类「页面级组件」是否允许继续直接调 API？** 如果允许，需要在规范里明确例外；如果不允许，按 composable 拆分。
2. **`HoverImagePreview` 与 `ImageHoverPreview` 保留哪一套？** 推荐 Teleport 版（行为可控、URL 由父级决定），但需要适配出图页的 `?w=1024` 预览。
3. **状态标签做成通用 `StatusTag(kind)`，还是拆成 `TaskStatusTag` / `QualityStatusTag` / `AiStatusTag`？** 推荐「通用容器 + 域内映射函数」，避免一个组件塞进所有枚举。
4. **Web 是否需要像移动端一样建立颜色令牌门禁？** 不建议一次性扫 740 处；先收敛状态色/遮罩色/图表主色。
5. **是否接受 34/161 的组件测试覆盖率作为现状基线？** 建议先把 common 与 P1 组件的测试补齐，再谈全局比例。
