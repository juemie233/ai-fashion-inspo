# 人脸识别与人物关联说明

> **状态**：现行｜编写日期 2026-11-01｜依据 `face-service/`、`backend/app/services/face_*.py`、`blogger_face.py`、`model_face.py`、`models/face.py`
> **一句话**：主后端通过 HTTP 调用独立的人脸子服务提取 512 维特征，为博主 / 模特建立特征库；素材人脸与特征库做余弦匹配，批量结果先进入「待审核候选」，人工确认后才写人物关联。
> **隐私边界**：人脸特征属生物特征数据，只存在本机数据库，不随素材导出、不上传外部服务。

---

## 1. 架构

```text
主后端（Python 3.12，FastAPI，18888）
   │  HTTP（FACE_SERVICE_URL，默认 http://127.0.0.1:18889）
   ▼
人脸识别子服务（Python 3.10 + onnxruntime，18889）
   │  buffalo_l：RetinaFace 检测 + ArcFace 识别（512 维）
   ▼
主库：blogger_face_embeddings / model_face_embeddings / inspiration_face_detections
子服务单独维护 face_service.db（注册库，与主库隔离）
```

**为什么拆子服务**：insightface 不支持 Python 3.12，而主后端是 3.12；子服务用独立 3.10 环境，主后端保持不动。子服务**不依赖 insightface 包**，直接用 onnxruntime 加载 buffalo_l 的 onnx 模型，推理结果与 insightface 原生一致。

启动方式与模型准备见 `face-service/README.md`；主后端启动不会自动拉起子服务，`scripts/ops/restart.sh` 会单独处理。

## 2. 数据模型

| 表 | 内容 |
| --- | --- |
| `bloggers` / `models` | 人物拆成两张独立表；各自带 `face_match_threshold`（可空，空则用全局兜底） |
| `blogger_face_embeddings` | 一位博主一条平均池化 512 维特征（float32 BLOB） |
| `model_face_embeddings` | 一位模特一条平均池化特征，来源为写真照片组 |
| `inspiration_face_detections` | 素材图内每张人脸一条：`embedding`、`bbox`、`det_score`、`matched_blogger_id` / `matched_model_id`、`confidence`、`match_status`、`match_excluded` |

### 2.1 match_status 语义（关键）

| 值 | 含义 | 素材详情页 |
| --- | --- | --- |
| `NULL` | 单素材「检测并匹配」或手动指派的历史结果 | **展示** |
| `pending` | **仅**批量匹配产出的「已匹配到具体人物」的 AI 候选，未经人工审核 | **不展示**（避免「没确认却显示已关联」） |
| `confirmed` | 人工确认，已写入人物关联表 | 展示 |

`match_excluded=true`：用户驳回「不是这个人」，该人脸不再参与后续全库匹配、也不再出现在候选区。

> 一张人脸至多命中一个博主或一个模特（两者特征在同一空间，合并取最高分）。
>
> **未命中（相似度不足）= `match_status=NULL`，不是 `pending`**。2026-11-01 修正前批量匹配把 16,823 条未命中记录也写成 pending，导致「待审候选」被放大 20 倍、按人物聚合出现大量空组，且一旦批量驳回会被 `match_excluded` 永久排除；该语义已修并回填（方案见 [人脸注册与候选审核方案](人脸注册与候选审核方案.md) §14）。

## 3. 特征注册

### 3.1 博主

- 两种来源可**合计 1~5 张**：上传正脸照片，或从该博主已关联的素材中选图；
- 多张照片分别提取特征后**平均池化**成一条 512 维特征；
- 支持重新注册（覆盖）与注销；
- 视频素材用导入时生成的首帧缩略图送检；webp 等格式统一重编码为 JPEG（子服务只吃 JPG/PNG）；
- 注册时按人脸质量过滤：`det_score` 与「人脸宽度占画面比例」都要达标。

接口：`POST /api/bloggers/{id}/face`、`GET .../face`、`DELETE .../face`。

### 3.2 模特

- 数据源是模特写真照片组（`model_photo_sets` / `model_photos`），不是素材关联；
- 写真组可能几十上百张，**按 `det_score` 取 Top-K 最高质量人脸**再平均池化（侧脸 / 远景 / 闭眼会稀释特征）；
- 重复注册即覆盖。

接口：`POST /api/models/{id}/face`、`GET .../face`。

### 3.3 按人阈值

- 全局兜底 `FACE_MATCH_THRESHOLD`（默认 0.5，建议 0.45~0.55 按样本调）；
- 人物表可单独设 `face_match_threshold`；
- 匹配报告会区分「兜底阈值」与「另 N 人按各自阈值判定」，不再把兜底值误读成唯一阈值。

## 4. 匹配流程

### 4.1 单素材（同步语义）

素材详情页「检测并匹配」：检测图内人脸 → 逐张与合并特征库比对 → 高于阈值即关联。结果 `match_status=NULL`，直接展示，可手动改绑 / 解除。

### 4.2 批量扫描（待审核语义）

`POST /api/face-scan/start` 创建 `face_scan` 任务（可取消）：

1. 遍历素材（视频取前 `FACE_SCAN_VIDEO_MAX_FRAMES` 帧，默认 3）；
2. 批量送子服务 `embed-batch`（32 张/批）；
3. 用 numpy **矩阵乘**一次性完成「所有人脸 × 全部人物特征」比对（`face_match.py`），不再逐条 Python 循环；
4. **只有高于阈值、匹配到具体人物的结果**写 `match_status=pending`，进入扫描审核页；未命中的保持 `NULL`；
5. 人工确认 → `POST /api/face-scan/confirm` 写人物关联并置 `confirmed`；驳回 → `match_excluded=true`。

> 为什么批量结果不直接生效：人脸相似度有误判，自动写关联会造成「素材详情显示错人」。确认动作是人审关口。

### 4.3 未匹配人脸聚类

`POST /api/face-scan/cluster/run` 创建 `face_cluster` 任务：

- 对 `matched_blogger_id` / `matched_model_id` 为空、且未被驳回的人脸做聚类，产出「疑似同一人」的组；
- **主路径 hnswlib**：ANN 查 Top-K 近邻，只在近邻间建边，O(n log n)；
- 未装 hnswlib 时回退 numpy 分块矩阵（O(n²)，超过上限直接报错提示安装）；
- **平均链接合并**（组间平均相似度达标才合并），不是并查集传递闭包；
- 实测教训：0.5 阈值 + 传递闭包会把 4068 张脸链成一个 2446 张的巨型组（组内中位相似度仅 0.227）；现建边阈值 `0.6`、合并门槛 `0.40`，并把阈值提高到 0.65 后巨型组碎成 1170 块；
- 过滤非 512 维脏向量（真实库曾出现 388 条异常维度）。

查看：`GET /api/face-scan/cluster/groups`、`.../groups/{id}/detections`；博主侧候选：`GET /api/bloggers/{id}/face-candidates`。
审核动作：整组指派（现有 confirm）、`POST .../cluster/groups/{id}/ignore`（整组永久忽略）、`POST .../cluster/groups/{id}/create-person`（新建人物并注册后整组确认）。

### 4.4 批量注册（未注册博主补特征库）

`POST /api/face-scan/register-plan`（只读）→ 对「有素材但未注册人脸」的博主，按「单脸素材里未匹配人脸 ≥3 次」聚类，返回候选簇（最多 5 组/人）、建议注册素材与封面；`POST /api/face-scan/register-batch` 串行注册（≤20 位/批），素材必须属于该博主；子服务不可用时整批快速失败。
前端在扫描页「批量注册」Tab 操作：采用 / 换一组 / 跳过 / 采用当前页 20 位。**不自动注册**：候选簇可能混入插画/遮挡脸，需人工看封面确认。

> 完整方案、阶段与验收指标见 [人脸注册与候选审核方案](人脸注册与候选审核方案.md)。

## 5. 子服务离线与降级

- 子服务未部署或不可达时，人脸相关按钮**禁用并给出可操作提示**（不是静默失败）；
- 前端提示条带「重新检测」，离线期间每 15 秒自动复检；启动子服务后不必刷新页面；
- 主后端调用抛 `FaceServiceUnavailableError`，调用方按「功能不可用」处理，不影响素材浏览。

## 6. 关键配置

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `FACE_SERVICE_URL` | `http://127.0.0.1:18889` | 子服务地址；留空视为未部署 |
| `FACE_SERVICE_TIMEOUT` | 30 秒 | 单次调用超时 |
| `FACE_MATCH_THRESHOLD` | 0.5 | 全局匹配余弦阈值 |
| `FACE_SCAN_VIDEO_MAX_FRAMES` | 3 | 每个视频取前 N 帧送检 |
| 子服务 `FACE_EMBED_WORKERS` | 8 | 子服务推理线程池；需与主后端 `EMBED_CONCURRENCY` 对齐才能喂满 |

性能实测（RTX 5060 Ti / 300 张）：串行 16.8 张/秒 → 4 线程 2.87× → **8 线程 3.6×（约 60 张/秒）**；只提高主后端并发无效，必须两侧同时调。

## 8. 排障

| 现象 | 原因 / 处理 |
| --- | --- |
| 人脸按钮全灰 | 子服务未启动 / 模型缺失 / CUDA 运行时未加载；`curl 127.0.0.1:18889/health`，看 `logs/face-service.log` |
| 注册报「无法解析图片」 | 送了视频或 webp；已由 `face_image.normalize_image` 处理，检查是否绕过了该函数 |
| 注册成功但匹配不到 | 阈值偏高 / 照片侧脸多 / 人脸占比太小；看匹配报告里的阈值与 `det_score` |
| 批量扫描结果在详情页看不到 | 候选是 `pending`，需在扫描审核页确认；这是有意设计 |
| 驳回后仍反复出现 | 检查 `match_excluded` 是否写入；全库匹配会排除被驳回记录 |
| 聚类出现巨型组 | 阈值过低或走了并查集直连；确认使用平均链接与 `EDGE_THRESHOLD=0.6` |
| 聚类报维度错误 | 库内有非 512 维脏向量；聚类入口已过滤，若仍报错查 `inspiration_face_detections.embedding` 长度 |
| 扫描很慢 | 两侧并发未对齐；子服务 `FACE_EMBED_WORKERS` 与主后端 `EMBED_CONCURRENCY` 同时调到 8 左右 |
